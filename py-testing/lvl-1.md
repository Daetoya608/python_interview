# Тестирование Python — уровень 1

Основы unit-тестов, pytest и unittest: утверждения, запуск, организация проекта и выбор сценариев. Материал рассчитан на Python 3.11+; запускаемые примеры находятся в `practice/`.

## 1. Что проверяет тест

Тест задаёт входные данные, вызывает код и сравнивает наблюдаемое поведение с ожидаемым: результат, исключение, изменение состояния или важное взаимодействие.

**Unit-тест** проверяет небольшую единицу поведения, например расчёт скидки или деление. Такая единица может включать несколько функций: границу выбирают по смыслу, а не обязательно «один тест — один метод».

Тест нужен для обнаружения ошибок и регрессий после изменений. Зелёные тесты подтверждают проверенные сценарии, но не доказывают отсутствие всех ошибок. Качество определяется полезностью проверок, а не количеством файлов.

Типичная структура — **Arrange → Act → Assert**:

1. Arrange: подготовить вход и зависимости.
2. Act: выполнить проверяемую операцию.
3. Assert: проверить ожидаемый результат.

```python
from study_app.calculator import add

def test_add_positive_numbers():
    first, second = 2, 3       # Arrange
    result = add(first, second) # Act
    assert result == 5         # Assert
```

Ожидаемое значение берут из требований: не стоит в тесте повторять ту же формулу тем же способом, что и в реализации. В примере 5 — заранее известный результат конкретного случая.

## 2. pytest и unittest

| | pytest | unittest |
|---|---|---|
| Установка | Сторонний пакет | Стандартная библиотека Python |
| Организация | Функции `test_*`, необязательные классы | Класс-наследник TestCase, методы `test_*` |
| Проверки | Обычный assert с подробным отчётом | Методы assertEqual/assertTrue/assertRaises и другие |
| Подготовка | Fixtures | setUp/tearDown, addCleanup и другие hooks |
| Много входов | parametrize | subTest или отдельные методы |
| Совместимость | Может запускать unittest.TestCase | Не запускает обычные pytest-функции и фикстуры |

Оба инструмента поддерживают полезные проверки. Pytest удобен для кратких тестов и переиспользуемой подготовки; unittest подходит без установки стороннего раннера и часто встречается в существующих проектах.

Документация: [pytest: начало работы](https://docs.pytest.org/en/stable/getting-started.html), [unittest](https://docs.python.org/3/library/unittest.html).

## 3. Небольшое приложение

В `practice/study_app/calculator.py` находятся add, subtract, multiply, divide и is_positive. Для деления контракт такой: нормальный знаменатель даёт частное; нулевой вызывает ValueError с понятным сообщением.

```python
def divide(a, b):
    if b == 0:
        raise ValueError("denominator must not be zero")
    return a / b
```

Чистая функция не зависит от сети, времени и БД — её легко тестировать изолированно.

## 4. Простой pytest-тест

```python
from study_app.calculator import divide, is_positive

def test_divide_positive_numbers():
    assert divide(10, 2) == 5

def test_zero_is_not_positive():
    assert is_positive(0) is False
```

Pytest находит тесты по соглашениям имён и выполняет их. При ложном assert тест падает с AssertionError, а раннер показывает значения и место ошибки. Если необработанное исключение возникло раньше проверки, тест тоже считается неуспешным.

Тесты проверяют наблюдаемое поведение. Сам по себе вызов функции без assert может проверить лишь отсутствие неожиданного исключения — он не проверяет правильность результата.

## 5. Проверки значений

| unittest | pytest / Python | Что проверяет |
|---|---|---|
| `assertEqual(a, b)` | `assert a == b` | Равенство значений |
| `assertTrue(value)` | `assert value` | Истинность, не обязательно точный bool True |
| `assertFalse(value)` | `assert not value` | Ложность |
| `assertIsNone(value)` | `assert value is None` | Именно None |
| `assertIs(a, b)` | `assert a is b` | Тождество объектов |
| `assertIn(item, items)` | `assert item in items` | Наличие элемента |
| `assertAlmostEqual(a, b)` | `assert a == pytest.approx(b)` | Приближённое равенство чисел |

`==` сравнивает значения, `is` — идентичность. `assert result` не заменяет `assert result == expected`: любое непустое значение может пройти слабую проверку.

Для float учитывают погрешность представления:

```python
import pytest

def test_float_sum():
    assert 0.1 + 0.2 == pytest.approx(0.3)
```

Не выбирайте слишком широкий допуск, который скрывает ошибку. Для денег часто нужна точная десятичная арифметика Decimal; выбор типа — часть требований приложения.

Assert в тестах — средство проверки. В рабочем коде он не должен заменять обязательную валидацию входа: при оптимизации Python такие проверки могут отключаться. Тесты запускайте обычным интерпретатором без `-O`.

## 6. Тот же сценарий через unittest

```python
import unittest
from study_app.calculator import add, is_positive

class TestCalculator(unittest.TestCase):
    def setUp(self):
        self.values = [2, 3]

    def test_add(self):
        self.assertEqual(add(*self.values), 5)

    def test_positive(self):
        self.assertTrue(is_positive(1))
        self.assertFalse(is_positive(0))

if __name__ == "__main__":
    unittest.main()
```

setUp выполняется перед каждым тестовым методом, tearDown — после успешно выполненного setUp, даже если сам тест упал. Для каждого метода TestCase создаётся отдельный экземпляр класса, однако глобальные переменные и внешние ресурсы всё ещё могут быть общими.

Если setUp частично создал ресурс и затем упал, обычный tearDown не спасёт. После получения ресурса можно сразу зарегистрировать освобождение через addCleanup. Подробнее о подготовке и очистке — в уровне 2.

## 7. Структура файлов и discovery

Учебный проект:

```text
practice/
├── requirements.txt
├── pytest.ini
├── study_app/
│   ├── __init__.py
│   ├── calculator.py
│   ├── pricing.py
│   ├── storage.py
│   └── api.py
├── tests/
│   ├── conftest.py
│   ├── test_calculator.py
│   └── ...
└── unittest_examples/
    ├── test_calculator_unittest.py
    └── test_async_unittest.py
```

Основные соглашения pytest:

- Файлы `test_*.py` или `*_test.py`; в практике используется первый вариант.
- Функции и методы `test_*`.
- Обычный тестовый класс `TestSomething` без собственного __init__; наследование TestCase для pytest-функций не нужно.
- `conftest.py` содержит общие fixtures/hooks для каталога и его потомков; импортировать его в тесты вручную не нужно.
- `pytest.ini` или pyproject.toml задаёт настройки обнаружения, markers и плагины.

Для unittest стандартный шаблон discovery — `test*.py`; тестовые методы находятся в наследниках TestCase. Используйте явный каталог запуска, чтобы не искать тесты во всём репозитории с разными учебными проектами.

Тесты можно делить по модулям и/или уровням: unit, integration, e2e. Название каталога само по себе не делает тест модульным: важны реальные зависимости и границы.

## 8. Установка и запуск практики

PowerShell из корня репозитория:

```powershell
cd py-testing/practice
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pytest
```

Unix/macOS: `python3 -m venv .venv`, затем `.venv/bin/python -m pip ...` и `.venv/bin/python -m pytest`.

Далее `python` означает интерпретатор этого окружения. Команды выполняют из practice:

```console
python -m pytest
python -m pytest -q
python -m pytest tests/test_calculator.py -v
python -m pytest tests/test_calculator.py::test_divide_by_zero
python -m pytest -k "divide"
python -m pytest -x
python -m pytest --collect-only -q
```

- `-q` — короткий отчёт, `-v` — подробные имена.
- `-k` — отбор по выражению имён, `::` — конкретный тест/класс.
- `-x` — остановиться после первой ошибки.
- `--collect-only` — показать обнаруженные тесты без выполнения.

`python -m ...` привязывает запуск к выбранному интерпретатору. Убедитесь, что устанавливаете зависимости и запускаете тесты одним Python.

Unittest-примеры отдельно:

```console
python -m unittest discover -s unittest_examples -p "test_*.py" -v
```

Им достаточно стандартной библиотеки и локального study_app. Полный pytest-запуск также обнаруживает эти TestCase. Успешный запуск возвращает код 0; отсутствие найденных тестов не является подтверждением работоспособности.

## 9. Какие сценарии выбирать

Для каждого правила ищите:

- Обычный успешный случай.
- Границы: ноль, пустое значение, минимальное/максимальное допустимое.
- Недопустимый ввод и ожидаемую ошибку.
- Особые случаи предметной области: отрицательные числа, повторы, отсутствующий объект.

Для divide это обычное деление, отрицательный результат, нулевой числитель, дробный результат и запрещённый нулевой знаменатель.

Хорошее имя объясняет ситуацию и ожидание: `test_divide_by_zero_raises_value_error`. Тесты не должны зависеть от порядка, реального интернета, чужих данных или оставленного предыдущим тестом состояния.

Не объединяйте десятки несвязанных сценариев в один тест. Несколько assert допустимы, когда вместе описывают один результат операции, например статус и тело HTTP-ответа.
