# Тестирование Python: конспект для аттестации

Краткое повторение уровней 1–2. Объяснения и упражнения — в `lvl-1.md`, `lvl-2.md`; запускаемый проект — в `practice/`.

## 1. Что делает хороший тест

**Arrange → Act → Assert**: подготовить данные, вызвать реальную проверяемую логику, проверить наблюдаемый результат. Ожидание берут из контракта, а не копируют формулу реализации.

Проверяют обычные случаи, границы и ошибки. Тест должен быть понятным, повторяемым и независимым от порядка других тестов. Несколько проверок допустимы для одного результата; множество несвязанных сценариев лучше разделить.

| Проверка | pytest | unittest |
|---|---|---|
| Равенство | `assert actual == expected` | `self.assertEqual(actual, expected)` |
| Истинность | `assert value` | `self.assertTrue(value)` |
| Ложность | `assert not value` | `self.assertFalse(value)` |
| Именно None | `assert value is None` | `self.assertIsNone(value)` |
| Приближённое число | `assert actual == pytest.approx(expected)` | `self.assertAlmostEqual(actual, expected)` |
| Исключение | `with pytest.raises(ValueError):` | `with self.assertRaises(ValueError):` |

`==` — равенство значений; `is` — идентичность. `assert result` слишком слаб, если контракт требует конкретного значения. Float сравнивают с осмысленным допуском. Обязательную валидацию рабочего кода не строят на assert, который может отключаться при оптимизации.

## 2. Обнаружение и запуск

Pytest: файлы `test_*.py`/`*_test.py`, функции `test_*`, классы TestSomething без собственного __init__. Unittest: TestCase с методами test_*, стандартный discovery ищет test*.py.

```console
python -m pytest
python -m pytest -q
python -m pytest tests/test_calculator.py -v
python -m pytest tests/test_calculator.py::test_divide_by_zero
python -m pytest -k "divide"
python -m pytest -m integration
python -m pytest -x
python -m pytest --collect-only -q
python -m unittest discover -s unittest_examples -p "test_*.py" -v
```

Команды выполняют из `py-testing/practice`; python — интерпретатор с установленными requirements.txt. `-k` отбирает по имени, `-m` — по маркеру, `-x` останавливает после первой ошибки. Pytest может запускать TestCase; unittest не запускает pytest-функции.

## 3. Fixtures и очистка

Pytest передаёт fixture по имени аргумента. Общие fixtures размещают в conftest.py нужного каталога; вручную его не импортируют. Fixture может зависеть от другой fixture.

```python
import pytest
from study_app.storage import Notes

@pytest.fixture
def notes(tmp_path):
    resource = Notes(tmp_path / "notes.db")
    try:
        yield resource
    finally:
        resource.close()
```

Scopes: **function** по умолчанию, затем class, module, package, session. Широкий scope ускоряет подготовку, но может разделить состояние. Широкая fixture не может зависеть от более узкой. Порядок задают зависимости и scope, а не порядок функций в файле.

Если setup упал **до yield**, обычный код после yield не выполняется. Для уже созданных ресурсов нужен try/finally, охватывающий последующую подготовку, или своевременно зарегистрированный finalizer. Очистка других успешно подготовленных fixtures при этом всё равно выполняется.

`tmp_path` даёт временный каталог; `monkeypatch` временно меняет атрибуты/окружение; `capsys` перехватывает вывод; `caplog` — логи. Autouse-fixture срабатывает без явного аргумента, поэтому может скрыть зависимости теста.

Unittest: setUp/tearDown на тест, setUpClass/tearDownClass на класс. Если setUp упал, обычный tearDown не вызывается; addCleanup регистрируют сразу после получения ресурса. Обычные fixture-аргументы и parametrize не добавляют прямо к методам TestCase.

## 4. Исключения и параметризация

```python
import pytest
from study_app.calculator import divide

@pytest.mark.parametrize("a,b,expected", [(10, 2, 5), (-6, 2, -3), (0, 2, 0)])
def test_divide(a, b, expected):
    assert divide(a, b) == expected

def test_zero_denominator():
    with pytest.raises(ValueError, match="denominator must not be zero"):
        divide(10, 0)
```

Каждый набор parametrize — отдельный тестовый случай. Изменяемые параметры автоматически не копируются. В unittest несколько входов можно проверить через subTest; setUp на каждую его итерацию не повторяется.

Внутри raises оставляют только ожидаемо падающую операцию, а проверки error.value делают после блока. Match — регулярное выражение. Чрезмерно общий тип Exception может пропустить не ту ошибку.

## 5. Mocking

Тестовый двойник заменяет зависимость, а проверяемая логика продолжает выполняться. Stub задаёт ответы, mock записывает взаимодействия, fake даёт упрощённую рабочую реализацию.

```python
from decimal import Decimal
from unittest.mock import patch
from study_app.pricing import price_in_rubles

def test_price():
    with patch("study_app.pricing.getenv", autospec=True, return_value="100") as getenv:
        assert price_in_rubles(Decimal("2")) == Decimal("200")
    getenv.assert_called_once_with("USD_RATE", "90")
```

**Patch делают там, где код ищет имя.** Если модуль сделал from os import getenv, меняют его локальное имя, а не только os.getenv.

- `return_value` задаёт результат.
- `side_effect` задаёт ошибку, последовательность результатов или функцию поведения.
- `spec` ограничивает доступный интерфейс; spec_set также запрещает новые атрибуты при присваивании.
- `autospec` помогает проверить сигнатуру, но не всю семантику внешнего API.
- `assert_called_once_with` проверяет вызов и аргументы; `assert_not_called` — отсутствие вызова.

Моки не проверяют реальную БД/сеть и могут устареть относительно настоящего интерфейса. Не подменяйте саму проверяемую функцию и не проверяйте лишь её настроенное значение. Не фиксируйте внутренние детали, если контракт допускает другую реализацию.

## 6. Async-тесты

```python
from decimal import Decimal
from unittest.mock import AsyncMock
import pytest
from study_app.pricing import quote

@pytest.mark.asyncio
async def test_quote():
    provider = AsyncMock(return_value=Decimal("100"))
    assert await quote(Decimal("2"), provider) == Decimal("200")
    provider.assert_awaited_once_with("USD")
```

Нужен плагин pytest-asyncio. В strict-режиме async-тесты помечают asyncio, async-fixtures — pytest_asyncio.fixture. В unittest используют IsolatedAsyncioTestCase с asyncSetUp/asyncTearDown и addAsyncCleanup.

Вызов async-функции ещё не выполняет корутину: нужен await. Called не означает awaited. В AsyncMock return_value — результат await. Внутри async-теста не вызывают asyncio.run. Фоновые задачи дожидаются, при остановке отменяют и дожидаются cleanup. Для согласования используют Event, а не угадываемый sleep.

Следят за временем жизни ресурсов и их event loop; широкий scope клиента не должен случайно пересечь разные циклы. Async-маркер сам по себе не запускает тесты параллельно.

## 7. Уровни тестирования

| Уровень | Проверяет | Компромисс |
|---|---|---|
| Unit | Небольшое поведение с контролируемыми зависимостями | Быстро и понятно, но не проверяет реальную интеграцию |
| Integration | Связку компонентов/настоящую границу | Лучше проверяет совместимость, дороже подготовка |
| E2E | Сквозной путь через развёрнутую систему | Выше уверенность в целом, сложнее диагностика и больше нестабильности |

Пирамида — много быстрых тестов, меньше интеграционных и небольшой набор критичных E2E; обязательных процентов нет. Вызов ASGI-приложения внутри процесса — полезный API-тест, но он не проверяет реальный сетевой сервер и развёртывание.

У HTTPX ASGITransport нет автоматического lifespan. Если startup создаёт ресурсы, тест должен отдельно запустить их жизненный цикл. В API-тесте проверяют статус, тело и важные последствия; ошибки валидации и бизнес-ошибки — разные сценарии.

## 8. Самопроверка

1. **Зелёные тесты доказывают отсутствие ошибок?** Только подтверждают проверенные сценарии.
2. **100% coverage достаточно?** Нет: исполненная строка не гарантирует полезный assert.
3. **Почему suite падает только целиком?** Часто из-за общего состояния, порядка тестов или неосвобождённых ресурсов.
4. **Fixture — просто фабрика данных?** Она также управляет зависимостями, scope и очисткой.
5. **Где patch?** В пространстве имён, используемом тестируемым кодом.
6. **Mock вместо интеграционного теста?** Он проверяет реакцию на двойника, а не настоящий контракт внешней системы.
7. **Как проверить async-вызов?** Await реальную функцию и assert_awaited для подменённой async-зависимости.
8. **Чем плох sleep в тесте конкурентности?** Он угадывает время вместо проверки события и делает результат зависимым от нагрузки.
9. **Зачем raises с конкретным типом?** Чтобы посторонняя ошибка не выдала себя за правильное поведение.

Для подробностей: [unittest](https://docs.python.org/3/library/unittest.html), [pytest fixtures](https://docs.pytest.org/en/stable/how-to/fixtures.html), [unittest.mock](https://docs.python.org/3/library/unittest.mock.html), [pytest-asyncio](https://pytest-asyncio.readthedocs.io/en/stable/concepts.html). В конспекте собраны правила; практика показывает их на работающем коде.
