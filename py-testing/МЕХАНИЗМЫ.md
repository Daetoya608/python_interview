# Тестирование: наблюдаемое поведение и управляемая среда

Хороший тест делает конкретную ошибку заметной. Синтаксис pytest/unittest — в [КОНСПЕКТ.md](КОНСПЕКТ.md), исполняемый учебный проект — в [practice](practice/).

## 1. Из чего состоит доказательство теста

У теста есть входные условия, действие, наблюдение и **оракул** — правило, определяющее правильный результат. Arrange–Act–Assert помогает отделить эти части, но наличие трёх блоков ещё не делает проверку полезной.

Если тест копирует формулу реализации для расчёта expected, обе стороны могут содержать одну ошибку. Ожидания лучше получать из требований, вручную разобранных примеров, независимых свойств или эталонного результата.

```python
def discounted(price_cents, percent):
    if not 0 <= percent <= 100:
        raise ValueError("percent")
    return price_cents * (100 - percent) // 100

def test_full_discount():
    assert discounted(1500, 100) == 0

def test_no_discount():
    assert discounted(1500, 0) == 1500
```

Эти проверки фиксируют граничные свойства, а не способ разложения арифметики. Для полной спецификации ещё нужно определить округление, отрицательную цену и допустимые типы. Зелёный тест подтверждает проверенный случай, не все возможные входы.

## 2. Уровень теста определяется границей

Unit проверяет небольшой контракт с управляемыми зависимостями. Integration проверяет настоящую границу: ORM с реальной СУБД, сериализацию клиента и сервера, работу файлового хранилища. E2E проходит пользовательский путь через развёрнутую систему.

Чем больше настоящих компонентов, тем больше потенциальных причин отказа и дороже диагностика. Чем больше подмен, тем меньше уверенность в совместимости с реальной средой. Нужен набор разных границ, а не универсальный процент unit-тестов.

API-вызов внутри процесса хорошо проверяет маршрутизацию, валидацию и обработчик. Он не проверяет TLS, балансировщик, сетевой сервер и настройки deployment. Название «интеграционный» само по себе не говорит, какие именно риски покрыты.

## 3. Как runner превращает функции в тестовый прогон

Runner обнаруживает тесты по соглашениям, строит набор случаев, подготавливает зависимости, выполняет тело, собирает ошибки и очищает ресурсы. В pytest параметризация создаёт отдельный случай на каждый набор параметров, поэтому каждый получает собственный результат.

Отбор по имени/маркеру влияет на набор запуска, но не делает тест независимым. Если тест проходит только после другого, в нём неявно отсутствует часть подготовки. Порядок файлов не должен быть необходимым условием корректности suite.

## 4. Fixture — граф зависимостей и область владения

Fixture может зависеть от другой fixture, поэтому подготовка образует граф. Pytest разрешает зависимости и переиспользует результат в рамках scope. Один и тот же mutable-объект широкого scope может быть виден многим тестам.

Function-scope обычно даёт изоляцию; session-scope сокращает дорогой setup. Это обмен времени на управление общим состоянием. Широкая fixture не может зависеть от более короткоживущей: её ресурс должен оставаться действительным весь период использования.

Код до yield получает ресурс, значение yield передаётся тесту, выход освобождает его. Успешно подготовленные зависимости очищаются в обратном порядке. Если fixture упала до yield, её обычный код после yield не был достигнут — уже полученные ресурсы требуют охватывающего try/finally или своевременного finalizer.

```python
import pytest

@pytest.fixture
def output_file(tmp_path):
    file = (tmp_path / "result.txt").open("w+")
    try:
        yield file
    finally:
        file.close()
```

Autouse скрывает явный аргумент, но не убирает зависимость. Его удобно применять для общей политики очистки, однако он может затруднить понимание того, почему тест ведёт себя иначе вне suite.

## 5. Изоляция данных и эффектов

Тесты могут делить БД, файлы, env, часы, глобальные словари, случайный генератор и фоновые задачи. Изоляция означает, что каждый случай сам задаёт необходимое состояние и не оставляет помех следующему.

Транзакция с rollback полезна для БД, если приложение действительно использует соединения/транзакции, которые тест контролирует. Если код самостоятельно сделал commit в другом соединении, внешний rollback теста не отменит его изменения. Очистка схемы или отдельная БД могут быть честнее сложной иллюзии изоляции.

Внешнее время и случайность контролируют там, где они влияют на контракт. Важнее проверить «после заданного срока доступ закрыт», чем надеяться, что тест успеет попасть в нужную миллисекунду.

## 6. Двойник заменяет зависимость, сохраняя проверяемую логику

Stub задаёт ответы, fake реализует упрощённое рабочее поведение, mock наблюдает взаимодействия. Названия помогают понять роль, но один инструмент может совмещать их.

Если подменить саму проверяемую функцию и сравнить её return_value, тест доказывает лишь настройку двойника. Полезная подмена оставляет реальный код решения и контролирует только границу.

```text
checkout → реальное вычисление заказа → двойник платёжного клиента
        ↘ реальная обработка отказа/успеха
```

Проверка взаимодействия нужна, когда вызов является частью контракта: например, один платёж на один заказ. Количество вызовов внутреннего вспомогательного метода обычно менее устойчивый критерий, чем итоговое состояние.

Spec/autospec помогают выявить неверные атрибуты и сигнатуры. Они не доказывают, что настоящий сервер принимает те же данные или возвращает те же ошибки. Для этого нужны интеграционные/контрактные проверки.

## 7. Почему patch делают в месте поиска имени

При `from gateway import charge` модуль checkout получает собственную привязку charge. Поздняя замена gateway.charge не меняет автоматически уже сохранённую привязку checkout.charge.

Patch временно заменяет имя, которое код действительно читает в момент вызова. При `import gateway` это обычно атрибут gateway, при прямом импорте — имя импортирующего модуля. После выхода подмена должна быть восстановлена, иначе тесты начнут влиять друг на друга.

Это следствие модели имён и объектов Python, а не специальное заклинание библиотеки mock. Аналогично нужно учитывать зависимости, сохранённые раньше в аргументе по умолчанию или экземпляре объекта.

## 8. Исключения и отрицательные сценарии

Тест на ошибку должен отличать ожидаемый отказ от случайной ошибки. Слишком широкий `raises(Exception)` может принять AttributeError за правильную бизнес-валидацию. Внутри raises оставляют действие, которое обязано упасть; последствия проверяют снаружи.

Важно проверять не только тип отказа, но и отсутствие нежелательного эффекта: после отклонённой оплаты остаток не уменьшен, после неавторизованного запроса данные не раскрыты. Это помогает заметить ошибки, которые статус HTTP сам по себе не показывает.

## 9. Конкурентные и async-тесты

Async-тест должен исполняться в подходящем event loop. Вызов async-функции создаёт корутину, поэтому «вызвана» и «дождались» — разные события; AsyncMock различает called и awaited.

Проверка конкурентного сценария должна управлять важным порядком через Event/Barrier и ожидать наблюдаемые события. Sleep «чтобы worker успел» зависит от нагрузки машины и часто создаёт flaky-тест. Timeout полезен как ограничитель зависания, а не как основной способ синхронизации.

Фоновые задачи нужно дожидаться или отменять с ожиданием cleanup. Ресурс, связанный с event loop, не должен случайно пережить свой цикл и использоваться в другом. ASGITransport HTTPX не запускает lifespan автоматически: если startup создаёт ресурсы, тест обязан организовать жизненный цикл.

## 10. Покрытие и диагностика

Coverage показывает, какой код исполнялся, но не качество оракула. Строка может пройти без полезного assert, а ошибка на границе условия — остаться незамеченной. Branch coverage помогает увидеть непроверенные ветви; mutation testing проверяет, замечают ли тесты небольшие искусственные поломки.

При нестабильном тесте ищут неконтролируемую зависимость: порядок, время, общий ресурс, случайность, сеть, утёкший worker. Повтор запуска без выяснения причины уменьшает доверие к сигналу CI.

## 11. Самопроверка

1. Какую реальную поломку заметит этот assert? Из какого требования взят expected?
2. Какие компоненты настоящий API-тест в процессе вообще не затрагивает?
3. Что переживёт session-fixture и где может остаться изменяемое состояние?
4. Почему patch исходного модуля иногда не влияет на вызов?
5. Как проверить отказ вместе с отсутствием побочного эффекта?
6. Как воспроизвести нужное чередование задач без угадывания sleep?
7. Почему 100% coverage не является доказательством корректности?
