# SQLAlchemy: объекты, единица работы и SQL

ORM управляет соответствием двух моделей: объектов приложения и строк БД. Здесь разбирается, когда между ними происходят переходы. Синтаксис — [КОНСПЕКТ.md](КОНСПЕКТ.md), полная учебная схема — [practice/models.py](practice/models.py). Основной стиль — SQLAlchemy 2.0.

## 1. Какие задачи решают Core и ORM

Core описывает таблицы и SQL-выражения, компилирует их под диалект и исполняет через соединение. ORM добавляет отображение классов на строки, навигацию по отношениям, identity map и отслеживание изменений.

ORM не превращает БД в обычный Python-список. Чтение атрибута иногда вызывает сеть, JOIN размножает строки, ограничения могут отклонить запись, транзакции конкурируют. Для оценки корректности и скорости нужно понимать полученный SQL.

| Сущность | Роль |
|---|---|
| Engine | Конфигурация доступа: диалект, драйвер и обычно пул |
| Connection | Полученное подключение для исполнения SQL |
| MetaData/Table | Описание структуры таблиц в памяти приложения |
| Mapper/ORM-класс | Правила отображения строки на объект и его поля |
| sessionmaker | Фабрика одинаково настроенных Session |
| Session | Контекст объектов и единицы работы с транзакциями |

Engine обычно создают один раз на конфигурацию в процессе. Он не равен постоянно открытому единственному соединению. Session обычно берёт соединение по мере необходимости и возвращает его при завершении соответствующей работы.

## 2. Identity map: одна строка — один объект в контексте

В рамках Session ORM сопоставляет идентичность строки экземпляру Python. Два get по одному PK могут вернуть один и тот же объект. Иначе изменение одной версии объекта было бы трудно согласовать с другой внутри одной операции.

Identity map — не кэш произвольных запросов. SELECT с фильтром обычно всё равно идёт в БД, после чего ORM сопоставляет возвращённые идентичности существующим объектам. Другая Session имеет собственную карту и может вернуть другой экземпляр той же строки.

Загруженные поля не становятся автоматически свежими после чужого commit. Видимость определяется транзакцией БД, а обновление состояния объекта — также правилами expire/refresh и загрузки ORM. «Тот же Python-объект» не означает «последние данные во всём кластере».

## 3. Состояния объекта

```text
transient → add → pending → flush → persistent
                                ↘ удаление/фиксация → detached
persistent → close/expunge → detached
```

Это упрощённая схема: rollback и удаление имеют дополнительные переходы. Transient создан обычным конструктором и не прикреплён. Pending зарегистрирован для INSERT. Persistent соответствует идентичности в Session. Deleted после flush участвует в удалении до завершения транзакции. Detached больше не связан с активной Session.

Присваивание `user.name = ...` меняет объект и отмечает историю атрибута. Unit of work собирает новые, изменённые и удалённые объекты, определяет необходимые SQL-операции и порядок с учётом связей. Само присваивание обычно ещё не выполняет UPDATE.

Detached-объект может читать уже загруженные неистёкшие поля, но не может сам догрузить отсутствующую связь. Del Python-имени не является DELETE строки; удаление БД должно пройти через соответствующую операцию и commit.

## 4. Flush и commit разделены намеренно

Flush переводит накопленные изменения в SQL **внутри текущей транзакции**. БД может выдать PK, проверить ограничения и разрешить последующие запросы, зависящие от новых строк. Внешняя фиксация ещё не произошла.

Commit сначала выполняет необходимый flush, затем фиксирует транзакцию. Rollback отменяет её изменения. Close освобождает ресурсы и не является обещанием сохранения.

```python
from sqlalchemy import String, create_engine
from sqlalchemy.orm import DeclarativeBase, Mapped, Session, mapped_column

class Base(DeclarativeBase):
    pass

class User(Base):
    __tablename__ = "users"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(80))

engine = create_engine("sqlite+pysqlite:///:memory:")
Base.metadata.create_all(engine)

with Session(engine) as session:
    user = User(name="Anna")
    session.add(user)
    session.flush()
    assert user.id is not None  # INSERT уже был, commit ещё нет.
    inserted_id = user.id
    session.rollback()

with Session(engine) as session:
    assert session.get(User, inserted_id) is None
engine.dispose()
```

Autoflush перед некоторыми запросами нужен, чтобы запрос учитывал накопленные изменения. Поэтому IntegrityError может возникнуть на строке с SELECT: перед чтением ORM отправила INSERT. Отключение autoflush не отключает flush при commit.

После неуспешного flush Session требует явного rollback перед продолжением либо закрытия. Ошибка — не повод поймать исключение и продолжить работать в прежнем транзакционном состоянии.

## 5. Кто владеет границей транзакции

Если две внутренние функции каждая делают commit, внешняя операция не может отменить их вместе. Граница атомарности должна соответствовать целому бизнес-сценарию, например оформлению заказа, а не произвольной вспомогательной функции.

`with Session(...)` задаёт закрытие ресурса. `with session.begin()` задаёт commit при успехе и rollback при ошибке. Эти две области решают разные задачи, хотя часто используются совместно.

Одна Session хранит изменяемый контекст, порядок команд и состояние транзакции. Её нельзя конкурентно делить между потоками или asyncio-задачами. Общий Engine/фабрика не требуют общей Session. Отдельные сессии, однако, не защищают общий инвариант сами по себе: нужны механизмы БД из [транзакций](../db-transactions/МЕХАНИЗМЫ.md).

## 6. Связь в БД и навигация ORM

ForeignKey выражает ссылочную целостность на сервере. Relationship задаёт, как загружать и связывать Python-объекты. Back_populates помогает согласовать две стороны объектного отношения в памяти.

Коллекция у родителя и скаляр у ребёнка могут представлять один FK. One-to-one в ORM — ожидание формы доступа; гарантия «не больше одного» требует UNIQUE в БД. Many-to-many использует промежуточную таблицу, а атрибуты самой связи часто требуют association object.

ORM cascade распространяет операции Session по графу объектов. ON DELETE CASCADE действует на уровне БД, в том числе для писателей без этой ORM. Их нужно согласовать, а не считать взаимозаменяемыми. Delete-orphan уместен для принадлежащих родителю детей; удаление связи с общей меткой не должно удалять метку для всех остальных.

## 7. N+1 — результат отложенного I/O

Один запрос загрузил N пользователей. Затем цикл читает tasks каждого, и lazy-loading выполняет ещё N запросов. Python-код выглядит как доступ к атрибуту, но платит сетевыми обменами.

| Стратегия | Как получает данные | Цена |
|---|---|---|
| Lazy select | При первом обращении к незагруженной связи | Риск запросов в цикле |
| Select-in | Дополнительные запросы по ключам родителей, пачками | Обычно удобен для коллекций |
| Joined | JOIN при основной загрузке | Повтор полей родителя и размножение строк |
| Subquery | Отдельная загрузка с подзапросом родителей | Более сложный SQL и требования к порядку при LIMIT |

Join в запросе выбирает сочетания строк и может менять набор родителей. Joinedload задаёт загрузку relationship, стремясь сохранить смысл исходной выборки. Обычный join не означает, что коллекция уже заполнена. Для явного использования JOIN как загрузки есть contains_eager с соответствующим контрактом.

При joinedload коллекции результат в стиле 2.x явно дедуплицируют unique по идентичности родителей. Это не SQL DISTINCT по всем столбцам: разные строки детей остаются нужны для сборки коллекции.

Стратегию выбирают по реальным размерам и нужным полям. «Один запрос» не всегда быстрее двух, если JOIN передаёт огромный декартов объём. Измерять следует на свежей Session: ранее загруженные связи могут скрыть проблему.

## 8. Expire, refresh и async

Expire помечает значения как требующие повторного чтения. Refresh явно выполняет перечитывание. По умолчанию commit истекает состояние persistent-объектов, поэтому следующий доступ может вызвать SELECT в новой транзакции.

В AsyncSession произвольный доступ `obj.children` не содержит await. Если он неожиданно требует I/O, возможен MissingGreenlet. Планируют eager-загрузку либо используют явные async-механизмы refresh/AsyncAttrs. `expire_on_commit=False` оставляет загруженные поля доступными, но не загружает отсутствующие отношения и не гарантирует свежесть.

AsyncSession меняет способ ожидания I/O, а не модель единицы работы. Одну сессию всё равно не используют одновременно в независимых задачах; async def не отменяет ограничений транзакций.

## 9. Миграция — отдельный артефакт

Metadata — описание желаемых таблиц в Python. Create_all создаёт отсутствующее, но не преобразует существующую схему произвольным образом. Alembic хранит последовательность/граф ревизий и записывает применённую версию БД.

Autogenerate сравнивает видимую схему и metadata и предлагает операции. Он не знает, что drop/add на самом деле переименование, как заполнить новый обязательный столбец и какие данные нельзя потерять. Файл ревизии проверяют до применения.

Upgrade выполняет миграцию; создание revision ещё не изменило БД. Downgrade выполняет предусмотренные обратные операции, но не воскрешает удалённые данные. Для работающей системы нужен план совместимости схемы со старой и новой версиями приложения.
