# Docker: образ, изоляция процесса и сохранность данных

Команды — в [КОНСПЕКТ.md](КОНСПЕКТ.md), учебная конфигурация — в [practice/compose.yml](practice/compose.yml). Основная модель ниже относится к Linux-контейнерам.

## 1. Контейнер — процессы с настроенной средой

Контейнер не содержит отдельного гостевого ядра. Его процессы используют ядро Linux-хоста, но получают изолированные представления части ресурсов и свои настройки файловой системы, сети и лимитов.

Namespaces разделяют видимость PID, сети, mount points и других пространств имён. Cgroups учитывают и ограничивают ресурсы. Capabilities и другие механизмы уменьшают доступные привилегии. Это разные составляющие изоляции, а не одна магическая «коробка».

Виртуальная машина имеет собственное гостевое ядро и другой уровень изоляции/накладных расходов. На macOS/Windows Linux-контейнеры Docker Desktop обычно работают внутри Linux VM: они не начинают напрямую использовать ядро macOS как Linux.

## 2. Image, container и registry

| Сущность | Что представляет |
|---|---|
| Image | Неизменяемые слои и конфигурацию будущего запуска |
| Container | Созданный экземпляр со своим writable-слоем, настройками и процессами |
| Registry | Сервис хранения и получения артефактов образов |
| Tag | Удобное изменяемое имя версии/указателя |
| Digest | Идентификатор конкретного содержимого манифеста/артефакта |

Один image можно использовать для многих контейнеров. Их writable-слои независимы. Остановка контейнера не удаляет его слой; удаление контейнера удаляет этот слой. Новый запуск из того же образа не восстанавливает изменения старого экземпляра автоматически.

Tag вроде latest может начать указывать на другой образ. Digest позволяет выбрать определённое содержимое. Для multi-platform образа верхний манифест может выбирать платформенный вариант; архитектура всё равно имеет значение.

## 3. Слои и copy-on-write

Образ собирается из слоёв изменений файловой системы. Контейнер видит объединённое дерево, поверх которого пишет в свой слой. Изменение файла из нижнего слоя может потребовать copy-up; конкретная реализация зависит от storage driver.

Удаление файла в следующем слое скрывает его из итогового дерева, но не стирает байты из предыдущего слоя. Поэтому схема «COPY секрет → использовать → удалить следующей командой» оставляет секрет в истории образа. Секреты сборки передают предназначенным для этого механизмом, а не включают в постоянный слой.

Большие часто изменяемые данные БД лучше не связывать с writable-слоем контейнера. Для них используют отдельное хранилище с понятными backup/restore.

## 4. Build и run имеют разные границы

Dockerfile описывает получение образа. RUN исполняется при сборке, а CMD/ENTRYPOINT задают поведение будущего контейнера. Запуск веб-сервера в RUN не создаёт постоянно работающий сервер в готовом образе.

Build context — файлы, доступные сборке; dockerignore уменьшает его и исключает ненужные входы. COPY переносит выбранные файлы в слой. Конфигурация ENV может остаться в образе, поэтому это не подходящий секретный сейф.

Кэш сборки переиспользует результат шагов при совпадении значимых входов. Изменение раннего слоя обычно требует пересчитать зависимые. Поэтому сначала копируют описание зависимостей и устанавливают их, затем код: частая правка кода не обязана переустанавливать всё окружение.

Multi-stage позволяет получить артефакт в сборочной стадии и перенести только нужное в финальную. Компилятор и временные файлы не обязаны попасть в runtime. Но библиотеки, необходимые нативному модулю при запуске, всё равно должны присутствовать.

## 5. Главный процесс определяет жизнь контейнера

Контейнер работает, пока работает его основной процесс. Если он завершился, наличие файлов или ранее запущенного вспомогательного процесса не делает сервис здоровым. Restart policy определяет реакцию на выход, но не исправляет причину.

PID 1 имеет особую роль в обработке сигналов и завершившихся потомков. Exec-форма запуска помогает передавать сигналы приложению напрямую; shell-обёртка без правильного exec/forwarding может мешать корректной остановке.

Обычная остановка сначала даёт приложению время завершиться, затем может последовать принудительное завершение. Приложение должно прекратить приём новой работы, закончить/отменить активную и закрыть ресурсы. Наличие finally не гарантирует очистку после SIGKILL или аварии хоста.

Healthcheck наблюдает доступность по заданной проверке. «Процесс жив» и «сервис готов принимать запросы» — разные состояния. Неверная проверка может считать здоровым приложение без БД либо перегружать сервис.

## 6. Сеть: localhost зависит от участника

У контейнера обычно отдельное сетевое пространство. Localhost внутри него указывает на него самого, а не на хост или соседнюю БД. В Compose сервисы одной сети обычно находят друг друга по DNS-именам сервисов, например db.

Для доступа извне нужен опубликованный порт. EXPOSE документирует ожидаемый порт образа, но не создаёт host mapping. `127.0.0.1:8000:8000` на стороне хоста ограничивает публикацию loopback-интерфейсом; внутри приложение обычно слушает `0.0.0.0:8000`, чтобы принимать трафик через интерфейс контейнера.

Порт хоста, порт контейнера и адрес назначения — разные части маршрута. Для диагностики прослеживают: слушает ли процесс → куда он привязан → есть ли нужная сеть → опубликован ли порт → доступен ли адрес вызывающей стороне.

## 7. Volume и bind mount

Volume — управляемое Docker хранилище вне writable-слоя. Bind mount — выбранный путь хоста, показанный внутри контейнера. Оба могут пережить удаление контейнера, но подчиняются разным правилам управления и удаления.

Mount поверх каталога скрывает лежащие там файлы образа на время подключения. Это частая причина «в образе файл есть, в контейнере нет». Данные не обязательно исчезли: изменился видимый источник каталога.

Volume не является backup. Ошибка приложения, удаление данных или `down -v` могут уничтожить полезное состояние. Нужны отдельные копии и проверяемое восстановление; backup работающей БД должен учитывать её требования согласованности.

## 8. Ресурсы и наблюдаемость

Без настроенных лимитов контейнер может конкурировать за доступные ресурсы хоста. Memory limit способен привести к OOM-завершению; CPU quota ограничивает доступное время CPU, а не обещает отдельное физическое ядро.

Логи обычно собирают из stdout/stderr главного приложения. Exec запускает дополнительный процесс в работающем контейнере: это инструмент диагностики, а не изменение исходного Dockerfile. Ручные исправления внутри экземпляра исчезнут при пересоздании и плохо воспроизводятся.

При проблеме сравнивают конфигурацию, exit code, логи, лимиты, mount и сеть. Увеличение числа контейнеров не устранит общий bottleneck БД и может увеличить число соединений.

## 9. Что делает Compose

Compose описывает согласованный набор сервисов, сетей, volumes и настроек. Service — шаблон компонента, а не обязательно ровно один вечный контейнер. Пересоздание применяет изменившуюся конфигурацию.

Зависимость запуска не равна гарантии готовности БД. Нужны healthcheck/условия готовности и устойчивое подключение приложения с ограниченными повторами. После старта зависимость тоже может стать недоступной.

Обычный Compose удобен для локальной среды и ряда серверных сценариев, но сам по себе не добавляет распределённый кластер, межхостовый failover и все гарантии оркестратора.
