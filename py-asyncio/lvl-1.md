## Корутины

**Исходный код:** [Lib/asyncio/coroutines.py](https://github.com/python/cpython/tree/main/Lib/asyncio/coroutines.py)

[Корутины](https://docs.python.org/3/glossary.html#term-coroutine), объявленные с помощью синтаксиса async/await, — предпочтительный способ написания приложений на asyncio. Например, следующий фрагмент кода печатает «hello», ждёт 1 секунду, а затем печатает «world»:

```python
>>> import asyncio

>>> async def main():
...     print('hello')
...     await asyncio.sleep(1)
...     print('world')

>>> asyncio.run(main())
hello
world
```

Обратите внимание: простой вызов корутины **не** планирует её выполнение:

```python
>>> main()
<coroutine object main at 0x1053bb7c8>
```

Чтобы действительно запустить корутину, asyncio предоставляет следующие механизмы:

* Функция `asyncio.run()` — для запуска функции верхнего уровня, точки входа `main()` (см. пример выше).

* Ожидание корутины через `await`. Следующий фрагмент кода напечатает «hello» после ожидания в 1 секунду, а затем напечатает «world» после ожидания ещё *2 секунд*:

  ```python
  import asyncio
  import time

  async def say_after(delay, what):
      await asyncio.sleep(delay)
      print(what)

  async def main():
      print(f"started at {time.strftime('%X')}")

      await say_after(1, 'hello')
      await say_after(2, 'world')

      print(f"finished at {time.strftime('%X')}")

  asyncio.run(main())
  ```

  Ожидаемый вывод:

  ```
  started at 17:13:52
  hello
  world
  finished at 17:13:55
  ```

* Функция `asyncio.create_task()` — для *конкурентного* запуска корутин в виде [задач](#объект-task) asyncio.

  Изменим пример выше и запустим две корутины `say_after` *конкурентно*:

  ```python
  async def main():
      task1 = asyncio.create_task(
          say_after(1, 'hello'))

      task2 = asyncio.create_task(
          say_after(2, 'world'))

      print(f"started at {time.strftime('%X')}")

      # Ждём завершения обеих задач (это должно занять
      # около 2 секунд.)
      await task1
      await task2

      print(f"finished at {time.strftime('%X')}")
  ```

  Обратите внимание: ожидаемый вывод показывает, что теперь фрагмент выполняется на 1 секунду быстрее, чем раньше:

  ```
  started at 17:14:32
  hello
  world
  finished at 17:14:34
  ```

* Класс `asyncio.TaskGroup` — более современная альтернатива `create_task()`. С этим API последний пример выглядит так:

  ```python
  async def main():
      async with asyncio.TaskGroup() as tg:
          task1 = tg.create_task(
              say_after(1, 'hello'))

          task2 = tg.create_task(
              say_after(2, 'world'))

          print(f"started at {time.strftime('%X')}")

      # await выполняется неявно при выходе из контекстного менеджера.

      print(f"finished at {time.strftime('%X')}")
  ```

  Время выполнения и вывод должны быть такими же, как в предыдущей версии.

  > *Добавлено в версии 3.11:* `asyncio.TaskGroup`.

## Awaitable-объекты

Мы говорим, что объект является **awaitable** («ожидаемым»), если его можно использовать в выражении `await`. Многие API asyncio рассчитаны на то, чтобы принимать awaitable-объекты.

Существует три основных типа *awaitable*-объектов: **корутины**, **задачи (Tasks)** и **футуры (Futures)**.

### Корутины

Корутины Python являются *awaitable*-объектами, поэтому их можно ожидать из других корутин:

```python
import asyncio

async def nested():
    return 42

async def main():
    # Если просто вызвать "nested()", ничего не произойдёт.
    # Будет создан объект корутины, но его никто не ждёт,
    # поэтому он *вообще не выполнится*.
    nested()  # вызовет "RuntimeWarning".

    # А теперь сделаем иначе и дождёмся её:
    print(await nested())  # напечатает "42".

asyncio.run(main())
```

> **Важно**
>
> В этой документации термин «корутина» может обозначать два тесно связанных понятия:
>
> * *функция-корутина* (coroutine function): функция, объявленная через `async def`;
> * *объект корутины* (coroutine object): объект, возвращаемый при вызове *функции-корутины*.
>
> Корутины на основе генераторов, созданные с помощью `types.coroutine()`, не подпадают ни под одно из этих понятий и не поддерживаются asyncio.

### Задачи (Tasks)

*Задачи* используются для *конкурентного* планирования корутин.

Когда корутина оборачивается в *задачу* функциями вроде `asyncio.create_task()`, она автоматически планируется к скорому запуску:

```python
import asyncio

async def nested():
    return 42

async def main():
    # Планируем скорый запуск nested() конкурентно
    # с "main()".
    task = asyncio.create_task(nested())

    # Теперь "task" можно использовать, чтобы отменить "nested()",
    # или просто дождаться её завершения через await:
    await task

asyncio.run(main())
```

### Футуры (Futures)

`Future` — это специальный **низкоуровневый** awaitable-объект, который представляет **конечный результат** асинхронной операции.

Когда объект Future *ожидают* (await), это означает, что корутина будет ждать, пока Future не будет разрешён где-то в другом месте.

Объекты Future в asyncio нужны для того, чтобы код, основанный на колбэках, можно было использовать вместе с async/await.

Обычно в коде уровня приложения **нет необходимости** создавать объекты Future.

Объекты Future, которые иногда отдают библиотеки и некоторые API asyncio, можно ожидать:

```python
async def main():
    await function_that_returns_a_future_object()

    # так тоже можно:
    await asyncio.gather(
        function_that_returns_a_future_object(),
        some_python_coroutine()
    )
```

Хороший пример низкоуровневой функции, возвращающей объект Future, — `loop.run_in_executor()`.

## Создание задач

**Исходный код:** [Lib/asyncio/tasks.py](https://github.com/python/cpython/tree/main/Lib/asyncio/tasks.py)

### `asyncio.create_task(coro, *, name=None, context=None, eager_start=None, **kwargs)`

Оборачивает [корутину](#корутины) *coro* в объект `Task` и планирует её выполнение. Возвращает объект Task.

Полная сигнатура функции во многом совпадает с сигнатурой конструктора (или фабрики) `Task` — все именованные аргументы этой функции передаются в тот интерфейс.

Необязательный, только именованный аргумент *context* позволяет указать пользовательский `contextvars.Context`, в котором будет выполняться *coro*. Если *context* не передан, создаётся копия текущего контекста.

Необязательный, только именованный аргумент *eager_start* позволяет указать, должна ли задача начать выполняться «жадно» (сразу) во время вызова `create_task`, или её выполнение будет запланировано на потом. Если *eager_start* не передан, используется режим, заданный через `loop.set_task_factory()`.

Задача выполняется в цикле, возвращаемом `get_running_loop()`; если в текущем потоке нет запущенного цикла, возбуждается `RuntimeError`.

> **Примечание**
>
> `asyncio.TaskGroup.create_task()` — новая альтернатива, использующая структурную конкурентность; она позволяет ожидать группу связанных задач с сильными гарантиями безопасности.

> **Важно**
>
> Сохраняйте ссылку на результат этой функции, чтобы задача не исчезла посреди выполнения. Цикл событий хранит только слабые ссылки на задачи. Задача, на которую больше нигде нет ссылок, может быть удалена сборщиком мусора в любой момент, даже до своего завершения. Для надёжных фоновых задач в стиле «запустил и забыл» собирайте их в коллекцию:
>
> ```python
> background_tasks = set()
>
> for i in range(10):
>     task = asyncio.create_task(some_coro(param=i))
>
>     # Добавляем задачу в множество. Это создаёт сильную ссылку.
>     background_tasks.add(task)
>
>     # Чтобы не хранить ссылки на завершённые задачи вечно,
>     # пусть каждая задача после завершения сама удаляет
>     # свою ссылку из множества:
>     task.add_done_callback(background_tasks.discard)
> ```
>
> Обратите внимание: при таком подходе задачи никто не ожидает через await, поэтому если задача упадёт, её исключение так и не будет извлечено, и asyncio запишет в лог сообщение «Task exception was never retrieved», когда задачу удалит сборщик мусора. Чтобы этого избежать, используйте `asyncio.TaskGroup`, который хранит сильную ссылку на каждую задачу, ожидает их и пробрасывает их исключения:
>
> ```python
> async with asyncio.TaskGroup() as tg:
>     for i in range(10):
>         tg.create_task(some_coro(param=i))
> ```

> *Добавлено в версии 3.7.*
>
> *Изменено в версии 3.8:* добавлен параметр *name*.
>
> *Изменено в версии 3.11:* добавлен параметр *context*.
>
> *Изменено в версии 3.14:* добавлен параметр *eager_start* — за счёт передачи всех *kwargs*.

## Отмена задач

Задачи можно легко и безопасно отменять. Когда задача отменяется, в ней при первой же возможности возбуждается `asyncio.CancelledError`.

Рекомендуется, чтобы корутины использовали блоки `try/finally` для надёжного выполнения логики очистки. Если `asyncio.CancelledError` перехватывается явно, то после завершения очистки его, как правило, следует пробросить дальше. `asyncio.CancelledError` напрямую наследуется от `BaseException`, поэтому большей части кода не нужно о нём знать.

Компоненты asyncio, обеспечивающие структурную конкурентность, — такие как `asyncio.TaskGroup` и `asyncio.timeout()`, — внутри реализованы через отмену и могут работать неправильно, если корутина «проглатывает» `asyncio.CancelledError`. Аналогично, пользовательский код в общем случае не должен вызывать [`uncancel`](#uncancel). Однако в тех случаях, когда подавление `asyncio.CancelledError` действительно необходимо, нужно также вызвать `uncancel()`, чтобы полностью убрать состояние отмены.

## Группы задач

Группы задач объединяют API создания задач с удобным и надёжным способом дождаться завершения всех задач группы.

### `class asyncio.TaskGroup()`

[Асинхронный контекстный менеджер](https://docs.python.org/3/reference/datamodel.html#async-context-managers), содержащий группу задач. Задачи можно добавлять в группу с помощью `create_task()`. При выходе из контекстного менеджера ожидаются все задачи.

> *Добавлено в версии 3.11.*

#### `create_task(coro, *, name=None, context=None, eager_start=None, **kwargs)`

Создаёт задачу в этой группе задач. Сигнатура совпадает с `asyncio.create_task()`. Если группа задач неактивна (например, в неё ещё не вошли, она уже завершилась или находится в процессе остановки), переданная `coro` будет закрыта, и будет возбуждено `RuntimeError`.

> *Изменено в версии 3.13:* переданная корутина закрывается, если группа задач неактивна.
>
> *Изменено в версии 3.14:* все *kwargs* передаются в `loop.create_task()`.

#### `cancel()`

Отменяет группу задач. Это штатный (не через исключение) досрочный выход из жизненного цикла группы задач — полезен, когда цель группы достигнута или её услуги больше не нужны.

`Task.cancel()` будет вызван для всех ещё не завершённых задач группы, а также для родителя (тела) группы. Контекстный менеджер группы задач завершится *без* возбуждения `asyncio.CancelledError`.

Если `cancel()` вызван до входа в группу задач, группа будет отменена сразу при входе. Это полезно для паттернов, в которых один фрагмент кода передаёт другому неиспользованный экземпляр `asyncio.TaskGroup`, чтобы иметь возможность отменить всё, что запущено внутри группы.

`cancel()` идемпотентен и может вызываться уже после выхода из группы задач.

Некоторые способы использования `cancel()`:

* вызвать его из тела группы задач при определённом условии или событии;
* передать экземпляр группы задач дочерним задачам через `create_task()`, позволив дочерней задаче при определённом условии отменить всю группу;
* передать экземпляр группы задач или связанный метод `cancel()` какой-либо другой задаче *до* открытия группы, что позволяет отменять её извне.

> *Добавлено в версии 3.15.*

Пример:

```python
async def main():
    async with asyncio.TaskGroup() as tg:
        task1 = tg.create_task(some_coro(...))
        task2 = tg.create_task(another_coro(...))
    print(f"Both tasks have completed now: {task1.result()}, {task2.result()}")
```

Несколько моментов, которые стоит помнить при использовании групп задач:

* Инструкция `async with` дождётся завершения всех задач группы. Пока идёт ожидание, в группу всё ещё можно добавлять новые задачи (например, передав `tg` в одну из корутин и вызвав в ней `tg.create_task()`); как только последняя задача завершилась и произошёл выход из блока `async with`, добавлять новые задачи уже нельзя.

* Завершения всей группы задач можно потребовать через `tg.cancel()` при каком-либо условии.

* Если группа останавливается (например, потому что упала другая задача) до того, как только что созданная задача начала выполняться, эта задача отменяется, а её корутина не выполняется вовсе — даже до первого `await`. Чтобы гарантировать запуск корутины, создавайте задачу «жадно» с `eager_start=True` или используйте `asyncio.eager_task_factory()`. Например:

  ```python
  async def job():
      print("job started")  # никогда не будет напечатано
      try:
          await asyncio.sleep(1)
      finally:
          print("job cleaned up")  # никогда не будет напечатано

  async def main():
      async with asyncio.TaskGroup() as tg:
          tg.create_task(job())
          raise RuntimeError  # останавливает группу до запуска job()
  ```

  С `tg.create_task(job(), eager_start=True)` корутина `job()` выполнится до `await`, будет там отменена, и оба сообщения будут напечатаны.

Когда любая из задач группы завершается с исключением, отличным от `asyncio.CancelledError` (или тело инструкции `async with` завершается с исключением, что обрабатывается так же):

* В первый раз, когда это происходит, оставшиеся задачи группы отменяются, а затем ожидаются, и в группу больше нельзя добавлять задачи. Если тело инструкции `async with` всё ещё активно (то есть `__aexit__()` ещё не был вызван), то отменяется также задача, непосредственно содержащая инструкцию `async with`. Возникший `asyncio.CancelledError` прервёт `await`, но не «всплывёт» наружу из содержащей его инструкции `async with`.

* Когда все задачи завершились, исключения, не связанные с отменой, — включая исключение, с которым завершилось тело (если только это не `asyncio.CancelledError`), — объединяются в `ExceptionGroup` или `BaseExceptionGroup` (в зависимости от ситуации; см. их документацию), которое затем возбуждается.

* Некоторые исключения обрабатываются особым образом: если какая-либо задача падает с `KeyboardInterrupt` или `SystemExit`, группа задач всё равно отменяет оставшиеся задачи и ожидает их, но затем повторно возбуждается исходное `KeyboardInterrupt` или `SystemExit` вместо `ExceptionGroup` или `BaseExceptionGroup`. Кроме того, если тело инструкции `async with` возбуждает `GeneratorExit`, а ни одна из других задач не возбуждает исключений, о которых нужно было бы сообщить, повторно возбуждается `GeneratorExit`.

Группы задач аккуратно разделяют внутреннюю отмену, используемую для «пробуждения» их `__aexit__()`, и запросы на отмену задачи, в которой они выполняются, поступающие от других участников. В частности, когда одна группа задач синтаксически вложена в другую и в дочерних задачах обеих одновременно возникают исключения, внутренняя группа обработает свои исключения, а затем внешняя группа получит ещё одну отмену и обработает свои.

В случае, когда группа задач отменяется извне и при этом должна возбудить `ExceptionGroup`, она вызовет метод `Task.cancel()` родительской задачи. Это гарантирует, что при следующем `await` будет возбуждено `asyncio.CancelledError` и отмена не потеряется. Группы задач также сохраняют счётчик отмен, возвращаемый `Task.cancelling()`.

> *Изменено в версии 3.13:* улучшена обработка одновременных внутренних и внешних отмен, и обеспечено корректное сохранение счётчиков отмен.
>
> *Изменено в версии 3.15:* добавлен особый случай для `GeneratorExit`.

## Сон

### `async asyncio.sleep(delay, result=None)`

Блокирует выполнение на *delay* секунд.

Если передан *result*, он возвращается вызывающему коду, когда корутина завершится.

`sleep()` всегда приостанавливает текущую задачу, позволяя выполняться другим задачам.

Задержка, равная 0, — это оптимизированный способ дать поработать другим задачам. Его могут использовать долго выполняющиеся функции, чтобы не блокировать цикл событий на всё время своего вызова.

Пример корутины, которая выводит текущую дату каждую секунду в течение 5 секунд:

```python
import asyncio
import datetime as dt

async def display_date():
    loop = asyncio.get_running_loop()
    end_time = loop.time() + 5.0
    while True:
        print(dt.datetime.now())
        if (loop.time() + 1.0) >= end_time:
            break
        await asyncio.sleep(1)

asyncio.run(display_date())
```

>
> *Изменено в версии 3.13:* возбуждает `ValueError`, если *delay* равен `nan`.

## Конкурентный запуск задач

### `awaitable asyncio.gather(*aws, return_exceptions=False)`

*Конкурентно* запускает [awaitable-объекты](#awaitable-объекты) из последовательности *aws*.

Если какой-либо awaitable в *aws* является корутиной, она автоматически планируется как задача (Task).

Если все awaitable-объекты завершились успешно, результатом будет общий список возвращённых значений. Порядок значений в результате соответствует порядку awaitable-объектов в *aws*.

Если *return_exceptions* равен `False` (по умолчанию), первое возникшее исключение сразу же пробрасывается в задачу, которая ожидает `gather()`. Остальные awaitable-объекты в последовательности *aws* **не будут отменены** и продолжат выполняться.

Если *return_exceptions* равен `True`, исключения обрабатываются так же, как успешные результаты, и собираются в список результатов.

Если `gather()` *отменяется*, все переданные awaitable-объекты (которые ещё не завершились) также *отменяются*.

Если какая-либо задача или Future из последовательности *aws* *отменена*, это обрабатывается так, как будто она возбудила `CancelledError`, — сам вызов `gather()` в этом случае **не** отменяется. Это сделано для того, чтобы отмена одной переданной задачи/Future не приводила к отмене других задач/Future.

> **Примечание**
>
> Новая альтернатива для конкурентного создания и запуска задач с ожиданием их завершения — `asyncio.TaskGroup`. *TaskGroup* даёт более сильные гарантии безопасности, чем *gather*, при планировании вложенных подзадач: если задача (или подзадача — задача, запланированная другой задачей) возбуждает исключение, *TaskGroup* отменит оставшиеся запланированные задачи, а *gather* — нет.

Пример:

```python
import asyncio

async def factorial(name, number):
    f = 1
    for i in range(2, number + 1):
        print(f"Task {name}: Compute factorial({number}), currently i={i}...")
        await asyncio.sleep(1)
        f *= i
    print(f"Task {name}: factorial({number}) = {f}")
    return f

async def main():
    # Планируем три вызова *конкурентно*:
    L = await asyncio.gather(
        factorial("A", 2),
        factorial("B", 3),
        factorial("C", 4),
    )
    print(L)

asyncio.run(main())

# Ожидаемый вывод:
#
#     Task A: Compute factorial(2), currently i=2...
#     Task B: Compute factorial(3), currently i=2...
#     Task C: Compute factorial(4), currently i=2...
#     Task A: factorial(2) = 2
#     Task B: Compute factorial(3), currently i=3...
#     Task C: Compute factorial(4), currently i=3...
#     Task B: factorial(3) = 6
#     Task C: Compute factorial(4), currently i=4...
#     Task C: factorial(4) = 24
#     [2, 6, 24]
```

> **Примечание**
>
> Если *return_exceptions* ложен, отмена gather() после того, как он помечен как завершённый, не отменит ни один из переданных awaitable-объектов. Например, gather может быть помечен как завершённый после проброса исключения вызывающему коду, поэтому вызов `gather.cancel()` после перехвата исключения (возбуждённого одним из awaitable-объектов) из gather не отменит остальные awaitable-объекты.

> *Изменено в версии 3.7:* если отменяется сам *gather*, отмена пробрасывается независимо от *return_exceptions*.
>
> *Изменено в версии 3.10:* удалён параметр *loop*.
>
> *Устарело с версии 3.10:* выдаётся предупреждение об устаревании, если не передано ни одного позиционного аргумента или не все позиционные аргументы являются Future-подобными объектами, и при этом нет запущенного цикла событий.

## Фабрика «жадных» задач

### `asyncio.eager_task_factory(loop, coro, *, name=None, context=None)`

Фабрика задач для «жадного» (eager) выполнения задач.

При использовании этой фабрики (через `loop.set_task_factory(asyncio.eager_task_factory)`) корутины начинают выполняться синхронно прямо во время создания `Task`. Задачи планируются в цикле событий, только если они блокируются. Это может повысить производительность, поскольку для корутин, которые завершаются синхронно, отсутствуют накладные расходы на планирование в цикле.

Типичный пример, где это полезно, — корутины, использующие кэширование или мемоизацию, чтобы по возможности избегать реального ввода-вывода.

> **Примечание**
>
> Немедленное выполнение корутины — это изменение семантики. Если корутина возвращает значение или возбуждает исключение, задача вообще не планируется в цикле событий. Если выполнение корутины блокируется, задача планируется в цикле событий. Это изменение может повлиять на поведение существующих приложений. Например, скорее всего изменится порядок выполнения задач в приложении.

> *Добавлено в версии 3.12.*

### `asyncio.create_eager_task_factory(custom_task_constructor)`

Создаёт фабрику «жадных» задач, аналогичную `eager_task_factory()`, которая при создании новой задачи использует переданный *custom_task_constructor* вместо стандартного `Task`.

*custom_task_constructor* должен быть *вызываемым объектом* с сигнатурой, совпадающей с сигнатурой `Task.__init__`. Вызываемый объект должен возвращать объект, совместимый с `asyncio.Task`.

Эта функция возвращает *вызываемый объект*, предназначенный для использования в качестве фабрики задач цикла событий через `loop.set_task_factory(factory)`.

> *Добавлено в версии 3.12.*

## Защита от отмены

### `awaitable asyncio.shield(arg)`

Защищает [awaitable-объект](#awaitable-объекты) от [отмены](#cancelmsgnone).

Если *arg* — корутина, она автоматически планируется как задача (Task).

Инструкция:

```python
task = asyncio.create_task(something())
res = await shield(task)
```

эквивалентна:

```python
res = await something()
```

*за исключением* того, что если отменяется содержащая её корутина, задача, выполняющая `something()`, не отменяется. С точки зрения `something()` отмены не произошло. При этом вызывающий код всё равно отменяется, поэтому выражение «await» всё равно возбуждает `CancelledError`.

Если `something()` отменяется другими способами (то есть изнутри себя), это также отменит `shield()`.

Если требуется полностью игнорировать отмену (не рекомендуется), функцию `shield()` следует сочетать с конструкцией try/except, например так:

```python
task = asyncio.create_task(something())
try:
    res = await shield(task)
except CancelledError:
    res = None
```

> **Важно**
>
> Сохраняйте ссылку на задачи, переданные в эту функцию, чтобы задача не исчезла посреди выполнения. Цикл событий хранит только слабые ссылки на задачи. Задача, на которую больше нигде нет ссылок, может быть удалена сборщиком мусора в любой момент, даже до своего завершения.

> *Изменено в версии 3.10:* удалён параметр *loop*.
>
> *Устарело с версии 3.10:* выдаётся предупреждение об устаревании, если *arg* не является Future-подобным объектом и нет запущенного цикла событий.

## Таймауты

### `asyncio.timeout(delay)`

Возвращает [асинхронный контекстный менеджер](https://docs.python.org/3/reference/datamodel.html#async-context-managers), с помощью которого можно ограничить время ожидания чего-либо.

*delay* может быть либо `None`, либо числом секунд ожидания (float/int). Если *delay* равен `None`, ограничение по времени не применяется; это может быть полезно, если задержка неизвестна в момент создания контекстного менеджера.

В любом случае после создания контекстного менеджера срок можно перенести с помощью `Timeout.reschedule()`.

Пример:

```python
async def main():
    async with asyncio.timeout(10):
        await long_running_task()
```

Если `long_running_task` выполняется дольше 10 секунд, контекстный менеджер отменит текущую задачу и сам обработает возникший `asyncio.CancelledError`, превратив его в `TimeoutError`, который можно перехватить и обработать.

> **Примечание**
>
> Именно контекстный менеджер `asyncio.timeout()` превращает `asyncio.CancelledError` в `TimeoutError`, а это значит, что `TimeoutError` можно перехватить только *снаружи* контекстного менеджера.

Пример перехвата `TimeoutError`:

```python
async def main():
    try:
        async with asyncio.timeout(10):
            await long_running_task()
    except TimeoutError:
        print("The long operation timed out, but we've handled it.")

    print("This statement will run regardless.")
```

Контекстный менеджер, созданный `asyncio.timeout()`, можно перенести на другой дедлайн и проверить его состояние.

#### `class asyncio.Timeout(when)`

[Асинхронный контекстный менеджер](https://docs.python.org/3/reference/datamodel.html#async-context-managers) для отмены просроченных корутин.

Предпочтительнее использовать `asyncio.timeout()` или `asyncio.timeout_at()`, а не создавать экземпляр `Timeout` напрямую.

`when` должно быть абсолютным моментом времени, когда контекст должен истечь, измеряемым по часам цикла событий:

- Если `when` равно `None`, таймаут никогда не сработает.
- Если `when < loop.time()`, таймаут сработает на следующей итерации цикла событий.

##### `when() -> float | None`

Возвращает текущий дедлайн или `None`, если текущий дедлайн не задан.

##### `reschedule(when: float | None)`

Переносит таймаут.

##### `expired() -> bool`

Возвращает, превысил ли контекстный менеджер свой дедлайн (истёк ли он).

Пример:

```python
async def main():
    try:
        # На старте мы не знаем таймаут, поэтому передаём ``None``.
        async with asyncio.timeout(None) as cm:
            # Теперь таймаут известен, поэтому переносим его.
            new_deadline = get_running_loop().time() + 10
            cm.reschedule(new_deadline)

            await long_running_task()
    except TimeoutError:
        pass

    if cm.expired():
        print("Looks like we haven't finished on time.")
```

Контекстные менеджеры таймаутов можно безопасно вкладывать друг в друга.

> *Добавлено в версии 3.11.*

### `asyncio.timeout_at(when)`

Аналогично `asyncio.timeout()`, за исключением того, что *when* — это абсолютный момент времени, когда нужно прекратить ожидание, или `None`.

Пример:

```python
async def main():
    loop = get_running_loop()
    deadline = loop.time() + 20
    try:
        async with asyncio.timeout_at(deadline):
            await long_running_task()
    except TimeoutError:
        print("The long operation timed out, but we've handled it.")

    print("This statement will run regardless.")
```

> *Добавлено в версии 3.11.*

### `async asyncio.wait_for(fut, timeout)`

Ожидает завершения [awaitable-объекта](#awaitable-объекты) *fut* с таймаутом.

*timeout* может быть либо `None`, либо числом секунд ожидания (float или int). Если *timeout* равен `None`, выполнение блокируется до завершения future.

Если наступает таймаут, функция отменяет *fut* и возбуждает `TimeoutError`.

Чтобы *fut* не был отменён, оберните его в `shield()`.

Функция дождётся фактической отмены future, поэтому общее время ожидания может превысить *timeout*. Если во время отмены возникает исключение, оно пробрасывается.

Если отменяется само ожидание, future *fut* тоже отменяется.

Пример:

```python
async def eternity():
    # Спим один час
    await asyncio.sleep(3600)
    print('yay!')

async def main():
    # Ждём не более 1 секунды
    try:
        await asyncio.wait_for(eternity(), timeout=1.0)
    except TimeoutError:
        print('timeout!')

asyncio.run(main())

# Ожидаемый вывод:
#
#     timeout!
```

> *Изменено в версии 3.7:* когда *fut* отменяется из-за таймаута, `wait_for` ждёт отмены *fut*. Раньше `TimeoutError` возбуждалось немедленно.
>
> *Изменено в версии 3.10:* удалён параметр *loop*.
>
> *Изменено в версии 3.11:* возбуждает `TimeoutError` вместо `asyncio.TimeoutError`.
>
> *Изменено в версии 3.12:* реализовано через `asyncio.timeout()`; корутина, переданная как *fut*, больше не оборачивается в `Task`, когда *timeout* положителен.

## Примитивы ожидания

### `async asyncio.wait(fs, *, timeout=None, return_when=ALL_COMPLETED)`

Конкурентно запускает экземпляры `Future` и `Task` из итерируемого объекта *fs* и блокируется до выполнения условия, заданного *return_when*.

Итерируемый объект *fs* не должен быть пустым.

Возвращает два множества задач/Future: `(done, pending)`.

Использование:

```python
done, pending = await asyncio.wait(fs)
```

*timeout* (float или int), если указан, позволяет задать максимальное число секунд ожидания перед возвратом.

Обратите внимание, что эта функция не возбуждает `TimeoutError`. Future или задачи, не завершившиеся к моменту таймаута, просто возвращаются во втором множестве.

*return_when* указывает, когда эта функция должна вернуть управление. Это должна быть одна из следующих констант:

| Константа | Описание |
|---|---|
| `asyncio.FIRST_COMPLETED` | Функция вернёт управление, когда любой future завершится или будет отменён. |
| `asyncio.FIRST_EXCEPTION` | Функция вернёт управление, когда любой future завершится, возбудив исключение. Если ни один future не возбудит исключение, это эквивалентно `ALL_COMPLETED`. |
| `asyncio.ALL_COMPLETED` | Функция вернёт управление, когда все future завершатся или будут отменены. |

В отличие от `wait_for()`, `wait()` не отменяет future при наступлении таймаута.

Если отменяется сам `wait()`, future из *fs* не отменяются и продолжают выполняться.

> *Изменено в версии 3.10:* удалён параметр *loop*.
>
> *Изменено в версии 3.11:* передавать объекты корутин в `wait()` напрямую запрещено.
>
> *Изменено в версии 3.12:* добавлена поддержка генераторов, выдающих задачи.

### `asyncio.as_completed(fs, *, timeout=None)`

Конкурентно запускает [awaitable-объекты](#awaitable-объекты) из итерируемого объекта *fs*. По возвращаемому объекту можно итерироваться, получая результаты awaitable-объектов по мере их завершения.

Объект, возвращаемый `as_completed()`, можно итерировать как [асинхронный итератор](https://docs.python.org/3/glossary.html#term-asynchronous-iterator) или как обычный [итератор](https://docs.python.org/3/glossary.html#term-iterator). При асинхронной итерации выдаются исходно переданные awaitable-объекты, если они являются задачами или future. Это позволяет легко сопоставлять заранее запланированные задачи с их результатами. Пример:

```python
ipv4_connect = create_task(open_connection("127.0.0.1", 80))
ipv6_connect = create_task(open_connection("::1", 80))
tasks = [ipv4_connect, ipv6_connect]

async for earliest_connect in as_completed(tasks):
    # earliest_connect завершена. Результат можно получить,
    # дождавшись её через await или вызвав earliest_connect.result()
    reader, writer = await earliest_connect

    if earliest_connect is ipv6_connect:
        print("IPv6 connection established.")
    else:
        print("IPv4 connection established.")
```

При асинхронной итерации для переданных awaitable-объектов, которые не являются задачами или future, будут выдаваться неявно созданные задачи.

При использовании как обычного итератора каждая итерация выдаёт новую корутину, которая возвращает результат или возбуждает исключение следующего завершившегося awaitable-объекта. Этот паттерн совместим с версиями Python старше 3.13:

```python
ipv4_connect = create_task(open_connection("127.0.0.1", 80))
ipv6_connect = create_task(open_connection("::1", 80))
tasks = [ipv4_connect, ipv6_connect]

for next_connect in as_completed(tasks):
    # next_connect — это не один из исходных объектов задач. Её нужно
    # дождаться через await, чтобы получить результат или исключение
    # awaitable-объекта, который завершится следующим.
    reader, writer = await next_connect
```

Если таймаут наступает до завершения всех awaitable-объектов, возбуждается `TimeoutError`. Его возбуждает цикл `async for` при асинхронной итерации или выдаваемые корутины при обычной итерации.

`as_completed()` не отменяет задачи, выполняющие переданные awaitable-объекты: если наступает таймаут или итерация отменяется, оставшиеся задачи продолжают выполняться.

> *Изменено в версии 3.10:* удалён параметр *loop*.
>
> *Устарело с версии 3.10:* выдаётся предупреждение об устаревании, если не все awaitable-объекты в итерируемом объекте *fs* являются Future-подобными и нет запущенного цикла событий.
>
> *Изменено в версии 3.12:* добавлена поддержка генераторов, выдающих задачи.
>
> *Изменено в версии 3.13:* результат теперь можно использовать как [асинхронный итератор](https://docs.python.org/3/glossary.html#term-asynchronous-iterator) или как обычный [итератор](https://docs.python.org/3/glossary.html#term-iterator) (раньше — только как обычный итератор).

## Запуск в потоках

### `async asyncio.to_thread(func, /, *args, **kwargs)`

Асинхронно запускает функцию *func* в отдельном потоке.

Все \*args и \*\*kwargs, переданные этой функции, напрямую передаются в *func*. Кроме того, распространяется текущий `contextvars.Context`, что позволяет обращаться к контекстным переменным из потока цикла событий в отдельном потоке.

Возвращает корутину, которую можно дождаться через await, чтобы получить конечный результат *func*.

Эта функция-корутина в первую очередь предназначена для выполнения функций/методов, ограниченных вводом-выводом (IO-bound), которые иначе блокировали бы цикл событий, если бы выполнялись в главном потоке. Например:

```python
def blocking_io():
    print(f"start blocking_io at {time.strftime('%X')}")
    # Обратите внимание: time.sleep() можно заменить любой блокирующей
    # операцией ввода-вывода, например работой с файлами.
    time.sleep(1)
    print(f"blocking_io complete at {time.strftime('%X')}")

async def main():
    print(f"started main at {time.strftime('%X')}")

    await asyncio.gather(
        asyncio.to_thread(blocking_io),
        asyncio.sleep(1))

    print(f"finished main at {time.strftime('%X')}")


asyncio.run(main())

# Ожидаемый вывод:
#
# started main at 19:50:53
# start blocking_io at 19:50:53
# blocking_io complete at 19:50:54
# finished main at 19:50:54
```

Прямой вызов `blocking_io()` в любой корутине заблокировал бы цикл событий на время своего выполнения, что добавило бы 1 секунду к общему времени работы. Вместо этого с помощью `asyncio.to_thread()` мы можем запустить её в отдельном потоке, не блокируя цикл событий.

> **Примечание**
>
> Из-за [GIL](https://docs.python.org/3/glossary.html#term-global-interpreter-lock) `asyncio.to_thread()` обычно можно использовать только для того, чтобы сделать неблокирующими функции, ограниченные вводом-выводом. Однако для модулей расширения, которые освобождают GIL, или для альтернативных реализаций Python, в которых его нет, `asyncio.to_thread()` можно использовать и для функций, нагружающих процессор (CPU-bound).

> *Добавлено в версии 3.9.*

---

## Планирование из других потоков

### `asyncio.run_coroutine_threadsafe(coro, loop)`

Отправляет корутину в указанный цикл событий. Потокобезопасна.

Возвращает `concurrent.futures.Future`, чтобы ждать результат из другого потока ОС.

Эта функция предназначена для вызова из потока ОС, отличного от того, в котором работает цикл событий. Пример:

```python
def in_thread(loop: asyncio.AbstractEventLoop) -> None:
    # Выполняем какой-нибудь блокирующий ввод-вывод
    pathlib.Path("example.txt").write_text("hello world", encoding="utf8")

    # Создаём корутину
    coro = asyncio.sleep(1, result=3)

    # Отправляем корутину в указанный цикл
    future = asyncio.run_coroutine_threadsafe(coro, loop)

    # Ждём результат с необязательным аргументом timeout
    assert future.result(timeout=2) == 3

async def amain() -> None:
    # Получаем запущенный цикл
    loop = asyncio.get_running_loop()

    # Запускаем что-нибудь в потоке
    await asyncio.to_thread(in_thread, loop)
```

Можно сделать и наоборот. Пример:

```python
@contextlib.contextmanager
def loop_in_thread() -> Generator[asyncio.AbstractEventLoop]:
    loop_fut = concurrent.futures.Future[asyncio.AbstractEventLoop]()
    stop_event = asyncio.Event()

    async def main() -> None:
        loop_fut.set_result(asyncio.get_running_loop())
        await stop_event.wait()

    with concurrent.futures.ThreadPoolExecutor(1) as tpe:
        complete_fut = tpe.submit(asyncio.run, main())
        for fut in concurrent.futures.as_completed((loop_fut, complete_fut)):
            if fut is loop_fut:
                loop = loop_fut.result()
                try:
                    yield loop
                finally:
                    loop.call_soon_threadsafe(stop_event.set)
            else:
                fut.result()

# Создаём цикл в другом потоке
with loop_in_thread() as loop:
    # Создаём корутину
    coro = asyncio.sleep(1, result=3)

    # Отправляем корутину в указанный цикл
    future = asyncio.run_coroutine_threadsafe(coro, loop)

    # Ждём результат с необязательным аргументом timeout
    assert future.result(timeout=2) == 3
```

Если в корутине возникает исключение, возвращённый Future получит об этом уведомление. Его также можно использовать для отмены задачи в цикле событий:

```python
try:
    result = future.result(timeout)
except TimeoutError:
    print('The coroutine took too long, cancelling the task...')
    future.cancel()
except Exception as exc:
    print(f'The coroutine raised an exception: {exc!r}')
else:
    print(f'The coroutine returned: {result!r}')
```

См. раздел документации [Конкурентность и многопоточность](https://docs.python.org/3/library/asyncio-dev.html#asyncio-multithreading).

В отличие от других функций asyncio, этой функции аргумент *loop* нужно передавать явно.

> *Добавлено в версии 3.5.1.*

> *Добавлено в версии 3.7.*

## Объект Task

### `class asyncio.Task(coro, *, loop=None, name=None, context=None, eager_start=False)`

[Future-подобный](https://docs.python.org/3/library/asyncio-future.html#asyncio.Future) объект, который выполняет [корутину](#корутины) Python. Не потокобезопасен.

Задачи используются для запуска корутин в циклах событий. Если корутина ожидает Future, задача приостанавливает выполнение корутины и ждёт завершения Future. Когда Future *завершён*, выполнение обёрнутой корутины возобновляется.

Циклы событий используют кооперативное планирование: цикл событий выполняет одну задачу за раз. Пока задача ожидает завершения Future, цикл событий выполняет другие задачи, колбэки или операции ввода-вывода.

Для создания задач используйте высокоуровневую функцию `asyncio.create_task()` или низкоуровневые `loop.create_task()` и `ensure_future()`. Создавать экземпляры Task вручную не рекомендуется.

Чтобы отменить выполняющуюся задачу, используйте метод `cancel()`. Его вызов приведёт к тому, что задача забросит исключение `CancelledError` в обёрнутую корутину. Если во время отмены корутина ожидает Future-подобный объект, ожидаемый объект будет отменён.

С помощью `cancelled()` можно проверить, была ли задача отменена. Метод возвращает `True`, если обёрнутая корутина не подавила исключение `CancelledError` и действительно была отменена.

`asyncio.Task` наследует от `Future` весь его API, кроме `Future.set_result()` и `Future.set_exception()`.

Необязательный, только именованный аргумент *context* позволяет указать пользовательский `contextvars.Context`, в котором будет выполняться *coro*. Если *context* не передан, задача копирует текущий контекст и затем выполняет свою корутину в скопированном контексте.

Необязательный, только именованный аргумент *eager_start* позволяет «жадно» начать выполнение `asyncio.Task` прямо в момент создания задачи. Если он равен `True` и цикл событий запущен, задача начнёт выполнять корутину немедленно — до первой блокировки корутины. Если корутина возвращает значение или возбуждает исключение, не блокируясь, задача будет завершена «жадно» и пропустит планирование в цикле событий.

Задачи являются [обобщёнными (generic)](https://docs.python.org/3/library/typing.html#generics) по типу возвращаемого значения обёрнутых корутин.

> *Изменено в версии 3.7:* добавлена поддержка модуля `contextvars`.
>
> *Изменено в версии 3.8:* добавлен параметр *name*.
>
> *Устарело с версии 3.10:* выдаётся предупреждение об устаревании, если *loop* не указан и нет запущенного цикла событий.
>
> *Изменено в версии 3.11:* добавлен параметр *context*.
>
> *Изменено в версии 3.12:* добавлен параметр *eager_start*.

#### `done()`

Возвращает `True`, если задача *завершена*.

Задача *завершена*, когда обёрнутая корутина либо вернула значение, либо возбудила исключение, либо задача была отменена.

#### `result()`

Возвращает результат задачи.

Если задача *завершена*, возвращается результат обёрнутой корутины (а если корутина возбудила исключение, это исключение возбуждается повторно).

Если задача была *отменена*, этот метод возбуждает исключение `CancelledError`.

Если результат задачи ещё недоступен, этот метод возбуждает исключение `InvalidStateError`.

#### `exception()`

Возвращает исключение задачи.

Если обёрнутая корутина возбудила исключение, возвращается это исключение. Если обёрнутая корутина завершилась нормально, метод возвращает `None`.

Если задача была *отменена*, этот метод возбуждает исключение `CancelledError`.

Если задача ещё не *завершена*, этот метод возбуждает исключение `InvalidStateError`.

#### `add_done_callback(callback, *, context=None)`

Добавляет колбэк, который будет вызван, когда задача *завершится*.

Этот метод следует использовать только в низкоуровневом коде, основанном на колбэках.

Подробнее см. документацию `Future.add_done_callback()`.

#### `remove_done_callback(callback)`

Удаляет *callback* из списка колбэков.

Этот метод следует использовать только в низкоуровневом коде, основанном на колбэках.

Подробнее см. документацию `Future.remove_done_callback()`.

#### `get_stack(*, limit=None)`

Возвращает список кадров стека для этой задачи.

Если обёрнутая корутина не завершена, возвращается стек в месте, где она приостановлена. Если корутина завершилась успешно или была отменена, возвращается пустой список. Если корутина была прервана исключением, возвращается список кадров трассировки (traceback).

Кадры всегда упорядочены от самых старых к самым новым.

Для приостановленной корутины возвращается только один кадр стека.

Необязательный аргумент *limit* задаёт максимальное число возвращаемых кадров; по умолчанию возвращаются все доступные кадры. Порядок в возвращаемом списке зависит от того, что возвращается — стек или трассировка: для стека возвращаются самые новые кадры, а для трассировки — самые старые. (Это соответствует поведению модуля traceback.)

#### `print_stack(*, limit=None, file=None)`

Печатает стек или трассировку для этой задачи.

Выводит то же, что и модуль traceback, для кадров, полученных через `get_stack()`.

Аргумент *limit* передаётся напрямую в `get_stack()`.

Аргумент *file* — поток ввода-вывода, в который записывается вывод; по умолчанию вывод пишется в `sys.stdout`.

#### `get_coro()`

Возвращает объект корутины, обёрнутый в `Task`.

> **Примечание**
>
> Для задач, которые уже завершились «жадно», вернётся `None`. См. [Фабрика «жадных» задач](#фабрика-жадных-задач).

> *Добавлено в версии 3.8.*
>
> *Изменено в версии 3.12:* из-за нового «жадного» выполнения задач результат может быть `None`.

#### `get_context()`

Возвращает объект `contextvars.Context`, связанный с задачей.

> *Добавлено в версии 3.12.*

#### `get_name()`

Возвращает имя задачи.

Если имя задаче явно не присвоено, стандартная реализация Task в asyncio генерирует имя по умолчанию при создании экземпляра.

> *Добавлено в версии 3.8.*

#### `set_name(value)`

Задаёт имя задачи.

Аргумент *value* может быть любым объектом, который затем преобразуется в строку.

В стандартной реализации Task имя будет видно в выводе `repr()` объекта задачи.

> *Добавлено в версии 3.8.*

#### `cancel(msg=None)`

Запрашивает отмену задачи.

Если задача уже *завершена* или *отменена*, возвращает `False`, иначе возвращает `True`.

Метод организует заброс исключения `CancelledError` в обёрнутую корутину на следующем цикле событий.

После этого у корутины есть возможность выполнить очистку или даже отклонить запрос, подавив исключение с помощью блока `try` … `except CancelledError` … `finally`. Поэтому, в отличие от `Future.cancel()`, `Task.cancel()` не гарантирует, что задача будет отменена, хотя полное подавление отмены — нечастая практика, и её настоятельно не рекомендуется применять. Если корутина всё же решит подавить отмену, ей нужно не только перехватить исключение, но и вызвать `Task.uncancel()`.

Если отменяемая задача в данный момент ожидает Future-подобный объект, этот ожидаемый объект тоже будет отменён. Эта отмена распространяется вниз по всей цепочке ожидаемых объектов.

> *Изменено в версии 3.9:* добавлен параметр *msg*.
>
> *Изменено в версии 3.11:* параметр `msg` передаётся от отменённой задачи к тому, кто её ожидает.

Следующий пример показывает, как корутины могут перехватывать запрос на отмену:

```python
async def cancel_me():
    print('cancel_me(): before sleep')

    try:
        # Ждём 1 час
        await asyncio.sleep(3600)
    except asyncio.CancelledError:
        print('cancel_me(): cancel sleep')
        raise
    finally:
        print('cancel_me(): after sleep')

async def main():
    # Создаём задачу "cancel_me"
    task = asyncio.create_task(cancel_me())

    # Ждём 1 секунду
    await asyncio.sleep(1)

    task.cancel()
    try:
        await task
    except asyncio.CancelledError:
        print("main(): cancel_me is cancelled now")

asyncio.run(main())

# Ожидаемый вывод:
#
#     cancel_me(): before sleep
#     cancel_me(): cancel sleep
#     cancel_me(): after sleep
#     main(): cancel_me is cancelled now
```

#### `cancelled()`

Возвращает `True`, если задача *отменена*.

Задача *отменена*, когда отмена была запрошена через `cancel()`, а обёрнутая корутина пробросила заброшенное в неё исключение `CancelledError`.

#### `uncancel()`

Уменьшает счётчик запросов на отмену этой задачи.

Возвращает оставшееся число запросов на отмену.

Обратите внимание: после того как выполнение отменённой задачи завершилось, дальнейшие вызовы `uncancel()` ни на что не влияют.

> *Добавлено в версии 3.11.*

Этот метод используется внутренними механизмами asyncio и не предназначен для использования в коде конечного пользователя. В частности, если отмена задачи успешно снята, это позволяет элементам структурной конкурентности, таким как [группы задач](#группы-задач) и `asyncio.timeout()`, продолжать работу, изолируя отмену в соответствующем структурном блоке. Например:

```python
async def make_request_with_timeout():
    try:
        async with asyncio.timeout(1):
            # Структурный блок, на который действует таймаут:
            await make_request()
            await make_another_request()
    except TimeoutError:
        log("There was a timeout")
    # Внешний код, на который таймаут не действует:
    await unrelated_code()
```

Хотя блок с `make_request()` и `make_another_request()` может быть отменён из-за таймаута, `unrelated_code()` должен продолжить выполняться даже в случае таймаута. Это реализовано с помощью `uncancel()`. Контекстные менеджеры `TaskGroup` используют `uncancel()` аналогичным образом.

Если код конечного пользователя по какой-то причине подавляет отмену, перехватывая `CancelledError`, ему нужно вызвать этот метод, чтобы убрать состояние отмены.

Когда этот метод уменьшает счётчик отмен до нуля, он проверяет, организовал ли предыдущий вызов `cancel()` заброс `CancelledError` в задачу. Если исключение ещё не было заброшено, это распоряжение будет отозвано (сбросом внутреннего флага `_must_cancel`).

> *Изменено в версии 3.13:* при достижении нуля отложенные запросы на отмену отзываются.

#### `cancelling()`

Возвращает число ожидающих запросов на отмену этой задачи, то есть число вызовов `cancel()` за вычетом числа вызовов `uncancel()`.

Обратите внимание: если это число больше нуля, но задача всё ещё выполняется, `cancelled()` по-прежнему будет возвращать `False`. Это потому, что это число можно уменьшить вызовом `uncancel()`, что может привести к тому, что задача в итоге не будет отменена, если число запросов на отмену опустится до нуля.

Этот метод используется внутренними механизмами asyncio и не предназначен для использования в коде конечного пользователя. Подробнее см. `uncancel()`.

> *Добавлено в версии 3.11.*
