# asyncio: объекты и механизмы работы

Материал для ответа «как это устроено», а не для запоминания методов. Примеры работают на Python 3.11+ без сторонних пакетов. [КОНСПЕКТ.md](КОНСПЕКТ.md) остаётся справочником API.

## 1. Какую проблему решает asyncio

Сетевой запрос большую часть времени может ждать ответ. Если поток заблокирован на этом ожидании, выполнять в нём другую работу нельзя. **Асинхронный I/O позволяет приостановить ожидающую операцию и использовать тот же поток для другой готовой работы.**

Например, сервису нужно получить данные из двух независимых API. При последовательном выполнении ожидания складываются. При конкурентном запросы находятся в работе одновременно, и их ожидания перекрываются. Но если второй запрос зависит от результата первого, простое добавление Task эту зависимость не устранит.

| Понятие | Смысл |
|---|---|
| Конкурентность | Несколько задач продвигаются в течение одного периода времени, возможно по очереди |
| Параллелизм | Несколько фрагментов действительно исполняются одновременно, например на разных ядрах |
| Блокирующее ожидание | Поток не может продолжать другую работу до завершения операции |
| Неблокирующее ожидание в asyncio | Приостанавливается задача; поток может выполнять другие задачи или ждать события ОС |

**Асинхронность не равна параллелизму.** Один event loop в одном потоке не исполняет два участка Python-кода одновременно. Долгий расчёт от добавления `async def` быстрее не станет.

Синхронность интерфейса и блокирование тоже не одно и то же: обычная функция может мгновенно вернуть готовое значение, а внутри async-функции можно выполнить блокирующий вызов. Важно, что реально происходит во время выполнения.

## 2. Корутина: выполнение, которое можно приостановить

**Функция-корутина** — `async def` без `yield`. Её вызов создаёт **объект корутины**, но ещё не выполняет тело. Объект представляет конкретный будущий запуск функции с переданными аргументами.

При выполнении корутина может приостановиться, сохранив локальные данные и позицию продолжения. Позже она продолжает с этого места, а не запускает функцию сначала. Это не отдельный поток ОС: у каждой корутины нет собственного системного потока и его стека.

Полезная модель жизненного цикла: **создана → выполняется → приостановлена → снова выполняется → завершена**. Приостановка возможна много раз. Если корутина нигде реально не приостанавливается, она выполнится до конца одним непрерывным участком относительно других задач того же цикла.

Отличия от соседних понятий:

- Обычная функция при вызове начинает выполнение и возвращает результат.
- Генератор выдаёт значения потребителю через `yield`; потребитель продвигает его через `next`/итерацию.
- Корутина выражает асинхронную последовательность действий через `await` и возвращает итог через `return`.
- `async def` с `yield` создаёт **асинхронный генератор**: поток значений для `async for`, а не одну корутину для `create_task`.

Одну завершённую native-корутину повторно ожидать нельзя: для нового запуска снова вызывают функцию. Завершённую Task, напротив, можно ожидать повторно и получать её сохранённый результат.

## 3. Task, Future и awaitable: кто за что отвечает

| Сущность | За что отвечает | Чего сама не делает |
|---|---|---|
| Coroutine | Описывает конкретное приостанавливаемое выполнение | Создание объекта не планирует его выполнение |
| Task | Управляет выполнением корутины в event loop; хранит итог/ошибку, связывает ожидания и отмену | Не создаёт отдельный поток и не ускоряет CPU-код |
| Future | Хранит состояние «результат ещё не готов / получен / ошибка / отмена» и уведомляет ожидающих | Не выполняет вычисление и не запускает I/O сама по себе |
| Awaitable | Общее понятие объекта, допустимого после `await` | Не обещает отдельную задачу или обязательное переключение |

**Task — исполнитель корутины в рамках цикла, Future — место для будущего результата.** Task предоставляет Future-интерфейс, но завершает её выполнение корутины: вручную записывать результат в Task не нужно.

Пример ролей: библиотека начала чтение сокета и создала Future для результата чтения. Task с нашей корутиной ждёт этот Future. Когда библиотека получает данные, она завершает Future; это позволяет Task продолжить корутину.

У Task полезно различать состояния **готова к выполнению**, **исполняется**, **ждёт** и **завершена**. Это модель работы планировщика, а не четыре значения публичного поля Task. `pending` включает и ещё не начавшуюся задачу, и уже работающую, но приостановленную.

У Future завершение означает результат, исключение или отмену. Один Future могут ждать несколько потребителей. Но общий Future не даёт независимые жизненные циклы: отмена ожидающей Task может передаться ему и затронуть остальных.

В прикладном коде Future обычно создаёт библиотека. Вручную он нужен при соединении callback-интерфейса с `async/await`, а не для оборачивания каждой функции.

## 4. Event loop: кто и когда получает управление

**Event loop — цикл событий и планировщик готовой работы.** Он исполняет callbacks, продолжает задачи, обслуживает таймеры и взаимодействует с механизмами I/O ОС. Task не «бежит сама»: её продолжение выполняется, когда цикл передаёт ему управление.

Упрощённая модель цикла:

1. Получить готовые I/O-события и учесть наступившие таймеры.
2. Выполнить готовые callbacks, в том числе шаги задач.
3. Каждый такой участок выполняется до возврата управления: завершения, ошибки или настоящей приостановки.
4. Повторить цикл; если работы пока нет, ждать события ОС с учётом ближайшего таймера.

Это не точный исходный код: порядок внутренних этапов зависит от реализации. Для понимания важны **готовая работа**, **отложенные таймеры** и **зарегистрированные ожидания I/O**. В стандартном цикле CPython для них используются отдельные структуры.

Цикл не проверяет непрерывно каждую корутину вопросом «ты уже готова?». Ожидание регистрируется, а событие приводит к планированию продолжения. Если все ждут, цикл может эффективно спать в системном ожидании, а не расходовать ядро на пустой Python-цикл.

### Кооперативное планирование

Задачи сотрудничают с планировщиком: отдают ему управление при приостановке. Цикл не отбирает у выполняющейся корутины управление каждые N миллисекунд. Поэтому один бесконечный цикл без приостановок остановит продвижение остальных задач.

ОС может переключить **поток**, но это не позволит event loop в этом же потоке внезапно продолжить другую Task посреди занятого участка. Переключение потоков ОС и переключение asyncio-задач — разные уровни.

`asyncio.run(main())` создаёт и обслуживает цикл для точки входа, а затем завершает его ресурсы. В веб-фреймворке цикл обычно уже обслуживает сервер: внутри обработчика не создают вложенный `asyncio.run`. Фоновые Task не получают независимый от приложения срок жизни; при завершении `asyncio.run` оставшиеся задачи отменяются.

## 5. Что именно происходит на await

`await x` означает: **выполнить протокол ожидания x, получить результат либо исключение и при необходимости приостановить текущую цепочку выполнения**.

Это протокол языка, не проверка имени функции. У пользовательского awaitable его задаёт `__await__()`, возвращающий итератор. Native-корутины и объекты asyncio поддерживают соответствующее ожидание. Конкретный awaitable должен быть совместим со средой выполнения: наличие async-синтаксиса не делает объекты разных async-библиотек автоматически взаимозаменяемыми.

### Случай А: await другой корутины

При `await child()` родитель входит в выполнение child **внутри той же Task**. Новая Task автоматически не появляется. Если child позже действительно приостановится, приостановится вся эта цепочка. Если child сразу вернёт значение, управление циклу может вообще не передаваться.

```python
import asyncio

async def main():
    events = []

    async def child():
        events.append("child")
        return asyncio.current_task()

    async def neighbour():
        events.append("neighbour")

    other = asyncio.create_task(neighbour())
    events.append("before await")
    child_task = await child()
    events.append("after await")
    assert child_task is asyncio.current_task()
    await other
    print(events)

asyncio.run(main())
```

При обычном отложенном запуске Task вывод:

```text
['before await', 'child', 'after await', 'neighbour']
```

Соседняя Task уже создана, но `await child()` не дал ей управления: внутри child не было настоящей приостановки. Ожидание **уже готовой** Task/Future тоже может продолжиться сразу. Поэтому считать каждый `await` обязательным переключением нельзя.

### Случай Б: await незавершённого Future

1. Task доходит до ожидания результата, которого пока нет.
2. Регистрируется продолжение после завершения Future; Task перестаёт быть готовой к выполнению.
3. Поток возвращается в event loop и может выполнять другую работу.
4. Кто-то завершает Future результатом, ошибкой или отменой.
5. Пробуждение ожидающей Task планируется через цикл.
6. Когда Task получает управление, корутина продолжает выполнение после `await` с результатом либо получает исключение в месте ожидания.

Завершение Future и исполнение ожидающей Task — **два разных события**. Между ними может выполниться другая готовая работа.

## 6. Как ожидание соединяется с реальным событием

Рассмотрим `await reader.read(...)` в сетевом приложении:

```text
Task выполняет корутину
  → данных в буфере недостаточно, зарегистрировано ожидание
  → Task приостановлена, event loop обслуживает других
  → ОС сообщает о готовности/завершении I/O
  → callback библиотеки обрабатывает данные и завершает ожидание
  → продолжение Task попадает в готовую работу
  → корутина получает данные и выполняется дальше
```

На Unix обычно используется уведомление о **готовности**: например, сокет можно читать без блокирующего ожидания. Цикл/библиотека затем читает данные. На Windows стандартный ProactorEventLoop использует IOCP с уведомлениями о **завершении** асинхронной операции. Детали различаются; принцип одинаков — ожидающая Task не занимает поток выполнением ожидания.

Часть данных может уже находиться в буфере — тогда чтение иногда завершается без приостановки. «Сетевой вызов» не означает, что каждый его await обязательно передаст управление.

Небольшая модель связи callback → Future → продолжение:

```python
import asyncio

async def main():
    loop = asyncio.get_running_loop()
    future = loop.create_future()
    events = []

    def completed():
        events.append("callback: result ready")
        future.set_result(42)
        events.append("callback: returned")

    loop.call_later(0.01, completed)
    events.append("task: waiting")
    result = await future
    events.append(f"task: resumed with {result}")
    print(events)

asyncio.run(main())
```

```text
['task: waiting', 'callback: result ready', 'callback: returned', 'task: resumed with 42']
```

Таймер не создаёт рабочий поток. Callback сначала заканчивает работу, а уже затем цикл возобновляет ожидающую Task. В реальном I/O результат готовит библиотека по событию ОС; здесь это явно делает callback таймера.

## 7. Откуда берётся конкурентность

**Два await подряд не означают две независимые задачи.** Если написать `await load_a(); await load_b()`, второй вызов начнётся после завершения первого. Нужно заранее организовать отдельные задачи, чтобы их ожидания могли перекрываться.

```python
import asyncio

async def load(name):
    print(name, "start")
    await asyncio.sleep(0.01)  # Модель ожидания внешнего результата.
    print(name, "done")
    return name

async def main():
    print("Sequential:")
    await load("A")
    await load("B")

    print("Concurrent:")
    async with asyncio.TaskGroup() as group:
        first = group.create_task(load("A"))
        second = group.create_task(load("B"))
    print(first.result(), second.result())

asyncio.run(main())
```

В первой части B начнётся после завершения A. Во второй обе начнутся до завершения ожиданий. Выигрыш даёт перекрытие пауз, а не более быстрое выполнение тела load.

Если обе Task уже созданы, `await first; await second` **не делает их последовательными**: это порядок ожидания результатов уже запланированной работы. Корутины и задачи нельзя смешивать в рассуждении как одно и то же.

## 8. Почему async-код блокирует сервер

Выполняющийся код занимает поток event loop. Вызовы `time.sleep`, синхронного HTTP-клиента, драйвера БД или долгий расчёт внутри `async def` не становятся неблокирующими автоматически.

Пока такой участок не вернул управление, другие задачи того же цикла не обслуживаются: задерживаются новые запросы, отправка ответов, таймеры и обработка отмены. Даже «маленькая» блокировка, повторённая во многих запросах, увеличивает задержки.

| Работа | Подход |
|---|---|
| Сетевой I/O с async-библиотекой | Ожидать её неблокирующую операцию |
| Блокирующий I/O со старой библиотекой | Вынести в поток, например через to_thread |
| Долгие чистые Python-вычисления | Отдельный процесс/worker; оценить цену передачи данных |
| Очень длинный цикл небольшой работы | Разбить на части для отзывчивости, при необходимости явно уступать управление |

`asyncio.sleep(0)` уступает управление, но не ускоряет вычисления и не превращает блокирующую библиотеку в async. Отмена ожидания потока/процесса также не означает, что уже начатая внешняя работа прекратилась.

**GIL — отдельный механизм.** Он влияет на параллелизм Python-потоков в обычном CPython, а не является причиной кооперативного планирования asyncio. Даже в free-threaded сборке один event loop в одном потоке продолжает выполнять свои callbacks по очереди.

## 9. Отмена и таймаут: что реально останавливается

`task.cancel()` — запрос на кооперативную отмену. При следующем возобновлении корутины организуется `CancelledError`; выполняющийся синхронный участок этим вызовом посреди инструкции не прерывается. Если Task ждёт Future/другую Task, отмена обычно передаётся этому ожиданию.

Далее возможны два исхода:

- корутина выполняет очистку и пропускает `CancelledError` наружу — Task завершается отменой;
- корутина подавляет отмену и продолжает/возвращает результат — запрос cancel не гарантировал отменённого завершения.

Поэтому после запроса отмены **дожидаются Task**, чтобы знать, что она завершилась и очистила ресурсы. `CancelledError` наследуется от BaseException, а не Exception. Его обычно пропускают дальше после очистки.

```python
import asyncio

async def main():
    started = asyncio.Event()
    never = asyncio.Event()
    events = []

    async def worker():
        try:
            started.set()
            await never.wait()
        finally:
            events.append("cleanup")

    task = asyncio.create_task(worker())
    await started.wait()  # Worker уже вошёл в try.
    task.cancel()
    try:
        await task
    except asyncio.CancelledError:
        events.append("caller observed cancellation")
    print(events)

asyncio.run(main())
```

Вывод: `['cleanup', 'caller observed cancellation']`. Если Task отменили **до первого запуска**, тело могло не войти в try: полагаться на его finally для ранее созданного снаружи ресурса нельзя. Повторная отмена также способна прервать асинхронную очистку; её жизненный цикл нужно проектировать.

**Таймаут обычно реализован через отмену.** `asyncio.timeout` отменяет текущую Task и преобразует свою отмену в TimeoutError на выходе; `wait_for` отменяет ожидаемую операцию и ждёт завершения отмены. Это не жёсткий предел CPU-времени: заблокированный цикл не обработает таймер вовремя, а cleanup может продлить ожидание.

**Отмена не равна откату.** Удалённый сервис мог уже принять платёж до потери ответа. Нужны идемпотентность и проверка результата; отмена локальной корутины не возвращает внешний мир в исходное состояние. `shield` защищает конкретное внутреннее ожидание от отмены ожидающего, но не управляет бизнес-последствиями и не делает задачу неотменяемой.

## 10. Ошибки и время жизни задач

У отдельно созданной Task должен быть владелец: кто хранит ссылку, получает ошибку и дожидается завершения. «Запустили и забыли» может привести к потерянным ошибкам, утечкам ресурсов и работе после исчезновения её исходного запроса.

**Структурная конкурентность** связывает время жизни дочерних задач с областью кода, которая ими владеет. TaskGroup ждёт свои задачи; при ошибке одной отменяет остальные и ждёт их завершения. Несколько ошибок могут попасть в ExceptionGroup. Это управление жизненным циклом, а не транзакция: уже выполненные действия не откатываются.

Обычный gather решает другую задачу — собирает результаты. При первой ошибке он по умолчанию пробрасывает её, но не отменяет соседей автоматически. Если после этого заканчивается main, соседей может отменить **завершение asyncio.run**: не путай это с политикой gather.

Группа владеет задачами, созданными через неё; произвольный create_task внутри ребёнка автоматически не становится её потомком. Хранить сильные ссылки на отдельные фоновые Task и получать их ошибки всё равно необходимо.

## 11. Как в одном потоке возникают гонки и deadlock

Гонка возможна без одновременного исполнения инструкций: достаточно, чтобы другая Task изменила состояние **между чтением и последующей записью**, пока первая приостановлена.

```python
import asyncio

async def main():
    counter = 0

    async def increment():
        nonlocal counter
        old = counter
        await asyncio.sleep(0)  # Явно создаём возможность вмешательства.
        counter = old + 1

    await asyncio.gather(increment(), increment())
    print(counter)  # 1: обе прочитали 0, обе записали 1.

asyncio.run(main())
```

Решения: убрать ненужное разделение операции, передавать сообщения одному владельцу состояния или защищать весь инвариант **одним общим asyncio.Lock**. Блокировка только отдельного чтения и отдельной записи проблему не решает. Все участники должны соблюдать тот же протокол доступа.

Между настоящими приостановками другие Task **того же потока/цикла** не вклиниваются. Это полезное свойство, но наличие await внутри вызываемой функции может измениться; зависимость от случайно готового результата ненадёжна. Потоки и внешние писатели БД требуют отдельной синхронизации.

Async-lock при ожидании освобождения приостанавливает Task. Блокирующий threading.Lock может занять весь поток цикла; threading.RLock привязан к потоку и не разделяет разные Task в нём. Поэтому потоковые блокировки не заменяют asyncio-примитивы.

Deadlock: A держит Lock и ждёт B, а B нужен тот же Lock для завершения. Цикл событий может продолжать обслуживать другие задачи, но эти две не продвинутся. Однопоточность не устраняет циклические зависимости.

## 12. Ограничение нагрузки: почему «создадим миллион Task» плохо

Task дешевле отдельного потока, но всё равно хранит состояние, ссылки и ожидания. Огромное число задач расходует память; одновременные запросы могут исчерпать пул соединений и перегрузить зависимость.

- **Semaphore** ограничивает активные операции. Но если создать миллион Task, ожидающих семафор, память под них уже занята.
- **Bounded queue + фиксированные consumers** ограничивают ожидающую работу. При заполнении producer ждёт, пока consumer освободит место. Это **backpressure**: скорость обработки влияет на скорость поступления.
- **Rate limiter** ограничивает частоту запросов за время. Это не то же, что лимит одновременных операций: десять быстрых операций могут породить тысячи запросов в секунду.

Ограничивают и очередь, и активность, и время ожидания; при перегрузке иногда нужно отклонить новую работу. Неограниченное накопление не решает нехватку мощности, а откладывает отказ до исчерпания памяти.

## 13. Контекст, async with и async for

**ContextVar** хранит значение в контексте выполнения, например request ID. thread-local недостаточен для разделения запросов, когда их Task работают в одном потоке. Новая Task по умолчанию получает копию текущего контекста; это не глубокое копирование объектов-значений и не защита общих изменяемых данных.

**async with** вызывает асинхронные вход/выход контекстного менеджера (`__aenter__`/`__aexit__`). Это позволяет ждать получение и освобождение ресурса. Он сам по себе не запускает отдельную Task; освобождение при исключениях следует правилам контекстного менеджера, но не даёт иммунитета к любым сбоям процесса/повторной отмене.

**async for** ждёт следующий элемент асинхронного итератора через `__anext__` и завершает цикл по StopAsyncIteration. Он обрабатывает элементы последовательно в текущей Task; параллельная обработка тела автоматически не появляется. `async def` с yield — удобный способ создать такой источник значений.

## 14. Ответ на собеседовании за минуту

«asyncio даёт кооперативную конкурентность. Вызов async-функции создаёт корутину — конкретное выполнение, которое можно приостанавливать. Task организует её исполнение в цикле событий. Future представляет ожидаемый результат и связывает завершение операции с продолжением задачи.

Пока задача выполняет Python-код, другие задачи этого цикла не исполняются. Если await доходит до незавершённого ожидания, задача приостанавливается, и цикл обслуживает другую готовую работу. Когда результат получен, продолжение задачи планируется снова. Await готового результата или корутины без приостановок может не передать управление вообще.

Выигрыш получается от перекрытия ожиданий I/O. Блокирующий вызов или долгий расчёт занимают поток цикла. Отмена кооперативная, гонки возможны на разделённых ожиданием операциях, а временем жизни задач и нагрузкой нужно управлять явно».

## 15. Проверка понимания без заучивания API

1. **Почему созданная корутина ничего не напечатала?** Её тело ещё никто не начал выполнять; вызов async-функции только создал объект.
2. **Сколько Task при main → await a() → await b()?** Если отдельные задачи не создавались, одна; вложенные корутины — цепочка выполнения внутри неё.
3. **Кто возобновит задачу после сетевого ожидания?** Завершение ожидания запланирует её пробуждение; затем event loop выполнит продолжение.
4. **Может ли await не отдать управление?** Да: результат уже готов или вложенная корутина не приостановилась.
5. **Future выполняет функцию?** Нет, он представляет итог; результат устанавливает выполняющая работу сторона.
6. **Почему async-сервер тормозит от обычного HTTP-клиента?** Блокируется поток цикла, а не только одна логическая задача.
7. **Зачем Lock при одном потоке?** Чтобы защитить инвариант через точки приостановки от вмешательства других задач.
8. **Почему после cancel задача ещё жива?** Это запрос отмены; нужно доставить исключение, выполнить очистку и дождаться завершения. Отмену также могут подавить.
9. **Почему timeout не вернул управление ровно через секунду?** Цикл мог быть занят, а отменяемая операция — выполнять cleanup или подавлять отмену.
10. **Почему запросы не стали конкурентными от двух await?** Вызовы могли идти последовательно; независимое планирование нужно организовать отдельно.
11. **Почему Semaphore не спас от роста памяти?** Он ограничил выполнение, но не число уже созданных/ожидающих задач.
12. **Почему после ошибки gather соседняя работа продолжилась?** Это его обычная политика; владение и остановка остальных задач требуют явного решения.

Если можешь объяснить каждый ответ на небольшом примере и проследить, кто сейчас исполняется, кто ждёт и кто кого пробуждает, основные механизмы поняты.
