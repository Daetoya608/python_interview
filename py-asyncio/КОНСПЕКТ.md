# asyncio: конспект к аттестации

Сжатое содержание `lvl-1.md`. Основные примеры рассчитаны на Python 3.11+. Новые возможности из исходника отмечены отдельно.

Для понимания устройства и подготовки ответов на собеседовании сначала прочитай [объекты и механизмы asyncio](МЕХАНИЗМЫ.md). Этот файл удобнее использовать как справочник API.

## 1. Модель выполнения

**Конкурентность** — несколько задач находятся в работе одновременно. **Параллелизм** — несколько задач действительно исполняются одновременно, например на разных ядрах.

`asyncio` даёт конкурентность через цикл событий (event loop). В одном потоке цикл исполняет одну задачу за раз. Пока она ждёт неблокирующую операцию, цикл может выполнять другие задачи. Подходит для большого числа сетевых запросов, соединений и других I/O-bound задач.

`async def` сам по себе не ускоряет вычисления. Долгий Python-цикл, `time.sleep()` или синхронный сетевой запрос внутри корутины занимают поток и блокируют остальные задачи.

`await` — точка, в которой задача **может** приостановиться. Если ожидаемый объект уже готов, передачи управления может не произойти. Поэтому наличие `await` не гарантирует переключение на каждом вызове.

## 2. Coroutine, Task, Future

| Объект | Что означает |
|---|---|
| Функция-корутина | Функция, объявленная через `async def`, без yield |
| Объект корутины | Результат вызова такой функции; сам по себе не запускается |
| `Task` | Оборачивает корутину и организует её выполнение в event loop |
| `Future` | Низкоуровневое представление будущего результата; связывает callbacks с `await` |
| Awaitable | Объект, который можно использовать с `await`: в частности, coroutine, Task, Future |

```python
import asyncio

async def work(delay):
    await asyncio.sleep(delay)
    return delay

async def main():
    # Последовательно: около 3 секунд.
    await work(1)
    await work(2)

    # Обе задачи созданы до ожидания: около 2 секунд.
    first = asyncio.create_task(work(1))
    second = asyncio.create_task(work(2))
    print(await first, await second)

asyncio.run(main())
```

Вызов `work(1)` только создаёт объект корутины. Чтобы выполнить его, нужны `await`, создание задачи или запуск через `asyncio.run()`.

`async def` с `yield` создаёт **асинхронный генератор**, а не корутину: его обходят через `async for`, не передают напрямую в `create_task()`.

`asyncio.run(main())` управляет жизненным циклом event loop и завершением его ресурсов. Используется как точка входа; его нельзя вызывать в потоке, где цикл уже работает.

## 3. Создание задач и управление ими

`asyncio.create_task(coro, name=...)` создаёт задачу в текущем работающем цикле; без такого цикла возникает `RuntimeError`. Обычно задача начнёт выполняться, когда цикл получит управление. `context=` позволяет задать `contextvars.Context`; по умолчанию копируется текущий контекст.

Сохраняйте сильные ссылки на отдельно созданные фоновые задачи: event loop хранит слабые ссылки. Также нужно получать их результаты или исключения, иначе ошибка может остаться только в сообщении `Task exception was never retrieved`. Для связанных задач удобнее `TaskGroup`.

| Метод `Task` | Семантика |
|---|---|
| `await task` | Дождаться результата; получить результат или исключение |
| `done()` | Завершилась успешно, с ошибкой или отменой |
| `result()` | Результат готовой задачи; ошибка задачи пробрасывается |
| `exception()` | Исключение готовой задачи или `None` при успехе |
| `cancel()` | Запросить отмену; не означает немедленную остановку |
| `cancelled()` | Задача действительно завершилась отменой |
| `get_name()` / `set_name()` | Имя для диагностики |

`result()` и `exception()` до завершения возбуждают `InvalidStateError`; для отменённой задачи — `CancelledError`. Task не предназначен для прямого использования из других потоков.

## 4. TaskGroup: связанные задачи с общим временем жизни

```python
import asyncio

async def work(value):
    await asyncio.sleep(0.1)
    return value * 2

async def main():
    async with asyncio.TaskGroup() as group:
        tasks = [group.create_task(work(i)) for i in range(3)]
    # Выход из блока дождался всех задач.
    print([task.result() for task in tasks])

asyncio.run(main())
```

- `TaskGroup` появился в Python 3.11; реализует структурную конкурентность.
- При обычном выходе ждёт завершения всех задач группы.
- Первая ошибка, отличная от `CancelledError`, запускает отмену остальных задач; группа дожидается их завершения.
- Ошибки объединяются в `ExceptionGroup` / `BaseExceptionGroup`. Для обработки подгрупп исключений используют `except*`.
- `KeyboardInterrupt` и `SystemExit` после завершения остальных задач пробрасываются отдельно.
- Новые задачи можно добавлять, пока группа активна. После завершения или начала остановки — нельзя.
- Группа управляет задачами, созданными именно через неё. Произвольный `asyncio.create_task()` внутри дочерней корутины автоматически в группу не включается.

## 5. Как выбрать способ ожидания

| API | Результат / порядок | Ошибки и таймаут |
|---|---|---|
| `TaskGroup` | Результаты забирают из задач после выхода | При ошибке отменяет соседние задачи и ждёт их |
| `gather(*aws)` | Список результатов в порядке аргументов | Первая ошибка пробрасывается; остальные задачи продолжают работу |
| `gather(..., return_exceptions=True)` | Результаты и исключения в одном списке | Нужно самостоятельно разобрать ошибки |
| `wait(tasks)` | Два множества: `done`, `pending` | По таймауту возвращает их, не отменяет задачи |
| `as_completed(aws)` | Результаты по мере готовности | По общему таймауту возбуждает `TimeoutError`; задачи не отменяет |

`gather` автоматически планирует переданные корутины. Если отменить **сам gather**, его незавершённые задачи отменяются. Отмена одной дочерней задачи не отменяет остальные. Если gather уже завершён из-за ошибки, последующий `gather.cancel()` оставшиеся задачи не остановит.

В `wait()` с Python 3.11 передают Task/Future, а не голые корутины. Условия возврата:

- `ALL_COMPLETED` — завершились все;
- `FIRST_COMPLETED` — завершилась или отменилась хотя бы одна;
- `FIRST_EXCEPTION` — возникла ошибка; если ошибок нет, ждёт всех.

`done` содержит и успешные, и упавшие, и отменённые задачи. Результаты и исключения нужно получить отдельно. Отмена самого `wait()` не отменяет переданные задачи.

Универсальная форма `as_completed`:

```python
for completed in asyncio.as_completed(tasks):
    result = await completed
```

В этой форме `completed` — служебная корутина, а не исходная Task. С Python 3.13 доступен `async for`: для исходных Task/Future он позволяет получить сами эти объекты и сопоставить результат с задачей.

## 6. Отмена и очистка ресурсов

Отмена кооперативная: `task.cancel()` организует возбуждение `asyncio.CancelledError` при возобновлении корутины. Если задача ожидает другой Future/Task, отмена обычно передаётся ему.

```python
async def worker(resource):
    try:
        await resource.process()
    except asyncio.CancelledError:
        # Здесь можно залогировать отмену.
        raise
    finally:
        await resource.close()
```

После `cancel()` обычно делают `await task`, чтобы дождаться очистки, и обрабатывают `CancelledError` в вызывающем коде.

`CancelledError` наследуется от `BaseException`, поэтому `except Exception` его не ловит. Не подавляйте отмену без причины: на ней основаны `TaskGroup` и таймауты. `cancel()` не гарантирует отмену, если корутина перехватила исключение и продолжила работу.

`cancelling()` показывает число запросов отмены за вычетом `uncancel()`. `uncancel()` уменьшает этот счётчик; это преимущественно внутренний механизм asyncio, для обычного прикладного кода он не нужен.

`asyncio.shield(task)` защищает внутреннюю задачу от отмены **ожидающего кода**. Сам ожидающий всё равно получает `CancelledError`, а task продолжает работу. Прямой `task.cancel()` shield не блокирует. Ссылку на внутреннюю задачу нужно сохранить и продумать, кто дождётся её завершения.

## 7. Таймауты

```python
async def limited(operation):
    try:
        async with asyncio.timeout(2):
            return await operation()
    except TimeoutError:
        return None
```

- `asyncio.timeout(seconds)` ограничивает блок кода. При истечении отменяет текущую задачу, а на выходе преобразует свою отмену в `TimeoutError`. Ловить его нужно **снаружи** блока.
- `timeout_at(deadline)` принимает абсолютное время по часам event loop: `loop.time() + seconds`, а не календарный timestamp.
- У объекта timeout есть `when()`, `reschedule(deadline)` и `expired()`. `None` означает отсутствие дедлайна; таймауты можно вкладывать.
- `await asyncio.wait_for(aw, timeout=2)` ограничивает ожидание одной операции; при истечении отменяет её и ждёт завершения отмены. Фактическое время может превысить две секунды из-за очистки.
- `wait_for(asyncio.shield(task), 2)` ограничивает ожидание, сохраняя работу task. Дальнейший жизненный цикл task остаётся обязанностью приложения.

Таймаут не прерывает синхронный код, который занял поток event loop и не отдаёт управление.

## 8. Блокирующий код и другие потоки

`await asyncio.to_thread(func, *args, **kwargs)` запускает синхронную функцию в рабочем потоке и переносит текущий `contextvars.Context`. Используется прежде всего для блокирующего I/O. В обычном CPython GIL ограничивает ускорение чистых Python-вычислений потоками; для CPU-bound работы подходят процессы. Расширения, отпускающие GIL, могут быть исключением.

Отмена ожидания `to_thread()` не останавливает уже работающую функцию в потоке.

Из **другого потока** корутину отправляют в нужный цикл через `asyncio.run_coroutine_threadsafe(coro, loop)`. Возвращается `concurrent.futures.Future`: у него можно вызвать `.result(timeout=...)` или `.cancel()`. Нельзя блокировать таким `.result()` поток самого event loop.

Для обычного callback из другого потока используют `loop.call_soon_threadsafe(...)`.

### Ограничение конкурентности и общее состояние

- `asyncio.Lock` защищает общее состояние между задачами одного цикла; используйте `async with lock`. Это не блокировка для потоков/процессов.
- `asyncio.Semaphore(n)` ограничивает число одновременно выполняемых операций, например запросов к API. Он ограничивает конкурентность, а не число запросов в секунду.
- `asyncio.Queue(maxsize=n)` ограничивает ожидающую очередь: `await put()` при заполнении приостанавливает producer. С фиксированным числом consumers это даёт backpressure и ограничивает накопление работы.

```python
import asyncio

async def bounded_map(operation, items, limit=10):
    if limit < 1:
        raise ValueError("limit must be positive")
    semaphore = asyncio.Semaphore(limit)

    async def run(item):
        async with semaphore:
            return await operation(item)

    async with asyncio.TaskGroup() as group:
        tasks = [group.create_task(run(item)) for item in items]
    return [task.result() for task in tasks]
```

Пример ограничивает активные операции, но создаёт Task для **каждого** элемента. Для огромного/неограниченного потока используйте bounded queue и фиксированные workers, иначе память уйдёт на ожидающие задачи. [Примитивы asyncio](https://docs.python.org/3/library/asyncio-sync.html), [очереди](https://docs.python.org/3/library/asyncio-queue.html).

## 9. Планирование и диагностика

- `await asyncio.sleep(seconds)` приостанавливает текущую задачу; `sleep(0)` отдаёт управление другим задачам. `time.sleep()` блокирует поток.
- `asyncio.current_task()` — текущая Task; `all_tasks()` — незавершённые задачи цикла; `iscoroutine(obj)` проверяет объект корутины.
- `task.get_stack()` / `print_stack()` помогают понять, где задача ждёт или упала; `get_coro()` возвращает её корутину; `get_context()` — контекст (Python 3.12+).
- `add_done_callback()` / `remove_done_callback()` — низкоуровневые callbacks завершения; обычно удобнее `await`.
- `asyncio.eager_task_factory` (3.12+) начинает корутину синхронно при создании Task и передаёт её планировщику лишь при приостановке. Это меняет порядок побочных эффектов. `create_eager_task_factory()` позволяет использовать собственный конструктор Task.
- `eager_start` у `create_task()` — возможность Python 3.14+. В исходнике также описан `TaskGroup.cancel()` **для Python 3.15**; его нельзя считать доступным в 3.11–3.14.

## 10. Самопроверка

1. Когда последовательные `await` означают последовательную работу? В `await work(1); await work(2)` вызовы корутин идут по очереди. Если обе Task созданы заранее, `await first; await second` ждёт уже конкурентно выполняемые задачи и не делает их последовательными.
2. Чем `TaskGroup` отличается от `gather` при ошибке? Группа отменяет соседей и ждёт их; обычный gather пробрасывает ошибку, оставляя соседей работать.
3. Останавливает ли `cancel()` задачу сразу? Нет: это запрос кооперативной отмены, после которого нужно дождаться завершения.
4. Чем `wait` отличается от `wait_for`? Первый возвращает множества и не отменяет pending по таймауту; второй ограничивает одну операцию и отменяет её.
5. Почему асинхронный сервер зависает от `requests.get()`? Синхронный вызов занимает поток event loop. Нужны async-клиент или вынос в поток.
6. Возможны ли гонки в одном потоке asyncio? Да, если чтение и изменение общего состояния разделены приостановкой; нужны подходящая организация состояния или `asyncio.Lock`.
