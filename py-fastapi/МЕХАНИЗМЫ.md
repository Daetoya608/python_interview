# FastAPI: путь запроса и время жизни ресурсов

Задача — понимать, что происходит между сетевым запросом и ответом, а не помнить все параметры декораторов. Справочник — [КОНСПЕКТ.md](КОНСПЕКТ.md). Примеры используют Python 3.11+, Pydantic v2 и стиль Annotated; детали новых API нужно соотносить с установленной версией FastAPI.

## 1. Сервер, ASGI и фреймворк

ASGI-сервер, например Uvicorn, работает с сетевыми соединениями и передаёт приложению события. FastAPI — приложение/фреймворк поверх ASGI, а не замена TCP-сервера. Starlette даёт маршрутизацию и веб-механизмы, Pydantic — проверку и сериализацию данных.

ASGI-приложение получает scope с контекстом запроса, receive для входных событий и send для выходных. Для HTTP события описывают тело запроса, начало ответа и части тела ответа. Это позволяет обслуживать длительные потоки без требования заранее собрать весь результат.

```text
клиент → proxy/LB → ASGI-сервер → middleware → router
→ разрешение параметров/зависимостей → обработчик
→ проверка/сериализация результата → события ответа → клиент
```

Это схема основных ролей: обработчики ошибок и cleanup оборачивают разные этапы; зависимости и их параметры разрешаются по графу, а не отдельной универсальной фазой «после всей валидации».

## 2. Почему сигнатура функции становится API

При регистрации маршрута FastAPI анализирует сигнатуру: откуда взять каждое значение, какие ограничения проверить, какие зависимости выполнить. Во время запроса он извлекает сырые данные и передаёт их на разбор.

Путь `/items/{item_id}` связывает имя с path-параметром. Обычный скаляр обычно читается из query; BaseModel — из body. Query/Body/Header/Cookie/Form явно определяют источник. Annotated сохраняет статический тип и добавляет инструкции фреймворку.

```python
from typing import Annotated
from fastapi import FastAPI, Query
from pydantic import BaseModel, Field

app = FastAPI()

class ItemIn(BaseModel):
    name: str = Field(min_length=1)

@app.post("/items/{item_id}")
async def create_item(
    item_id: int,
    item: ItemIn,
    limit: Annotated[int, Query(ge=1, le=100)] = 20,
):
    return {"id": item_id, "name": item.name, "limit": limit}
```

Строка query `limit=10` может быть преобразована в int. Несовместимое значение или нарушенное ограничение по умолчанию даёт 422, а не вызов обработчика с «почти правильным» объектом. Прямой вызов create_item как Python-функции обходит эту обработку: фреймворк участвует именно в пути запроса.

## 3. Валидация структуры и бизнес-инвариант

Pydantic подтверждает форму и ограничения модели, но не узнаёт самостоятельно, что товар принадлежит пользователю, остатка хватает или email уникален. Такие правила требуют доменной логики, доступа к данным и ограничений БД.

Обязательность и nullable различаются: `name: str | None` допускает None, но без default поле модели остаётся обязательным. Пропущенное поле и явно переданное null имеют разный смысл, особенно для PATCH.

PATCH-модель должна позволять определить, какие поля реально присланы. Exclude_unset сохраняет эту информацию; exclude_none выбросит и намеренную очистку поля. После слияния изменений иногда нужна повторная проверка полного состояния: корректные поля по отдельности могут образовать неверную комбинацию. Model_copy(update=...) сам по себе такую полную проверку не обещает.

Формат тела определяется Content-Type. JSON, urlencoded и multipart — разные способы кодирования одного тела, а не независимые тела в одном запросе. UploadFile помогает буферизовать файл, но read без ограничения всё равно может загрузить его целиком в память.

## 4. Dependency injection — разрешение графа

Depends описывает, как получить значение или выполнить обязательную проверку. Зависимость может читать параметры запроса и сама зависеть от других. Например: обработчик → текущий пользователь → токен; обработчик → сервис → Session.

FastAPI обходит зависимости, получает результаты и подставляет их в аргументы. Общий узел по умолчанию переиспользуется в пределах запроса. Это не глобальный singleton: следующий запрос получает своё разрешение графа.

```python
from typing import Annotated
from fastapi import Depends, FastAPI

app = FastAPI()

def get_settings():
    return {"currency": "RUB"}

@app.get("/settings")
def settings(value: Annotated[dict, Depends(get_settings)]):
    return value
```

Передают вызываемый объект, а не результат заранее выполненного вызова. Обычный вызов get_settings внутри обработчика не запускает анализ его Depends-параметров. Dependency override в тесте заменяет определённый узел графа, сохраняя остальную обработку.

## 5. Ресурс запроса и ресурс приложения

Зависимость с yield похожа на контекстный менеджер: получить ресурс → передать его обработчику → выполнить cleanup. Если один ресурс использует другой, их закрывают в подходящем обратном порядке.

Session часто принадлежит запросу/единице работы, Engine или HTTP-клиент с пулом — процессу приложения. Lifespan задаёт startup/shutdown процесса. При нескольких worker каждый имеет собственный lifespan, память и пул: лимит соединений нужно считать по всем worker.

В актуальном API yield-зависимостей scope определяет ранний выход после функции либо выход после отправки ответа; эта семантика менялась. Для streaming ресурс должен оставаться живым, пока генератор его использует. Параметр scope нужно проверять по версии, а не механически копировать.

Фоновой работе лучше передавать идентификаторы и создавать собственную Session. Сессия запроса может закрыться; ORM-объект может оказаться detached или содержать незагруженные поля.

Транзакцию, от которой зависит успешный ответ, завершают до отправки успеха. Если commit отложен до cleanup после ответа и упадёт, заменить уже отправленный 200 на ошибку нельзя.

## 6. Где исполняются def и async def

Async-обработчик работает в event loop. Пока он ждёт неблокирующий I/O, цикл может выполнять другие запросы. Пока он считает CPU или вызывает блокирующий клиент, занят поток цикла и задерживаются соседи.

Синхронные def-обработчики и зависимости FastAPI выполняет через пул потоков. Но синхронная helper-функция, которую напрямую вызвали из async def, автоматически туда не переносится. Граница определяется способом вызова фреймворком, а не существованием слова def где-то в проекте.

Пул потоков тоже конечен. Перенос блокировки из event loop не создаёт бесконечную пропускную способность. Долгие расчёты, ограничения БД и очереди требуют отдельных решений; дополнительные процессы worker увеличивают и память, и число подключений.

## 7. Модель ответа — внешний контракт

Response_model проверяет, преобразует и фильтрует возвращаемые данные. Это позволяет иметь отдельные модели создания, хранения и публичного ответа: пароль нужен при регистрации, хеш — при хранении, ни то ни другое не нужно клиенту в публичном объекте.

Невалидный вход — ошибка клиента. Невалидный результат обработчика — нарушение серверного контракта, обычно 500. Прямой возврат Response обходит обычную проверку тела response_model: фреймворк считает тело уже подготовленным.

OpenAPI описывает маршруты, параметры, ответы и схемы безопасности. JSON Schema описывает данные. Документированный `responses={...}` не создаёт соответствующую ветку исполнения автоматически; описание и реальный код нужно держать согласованными.

## 8. Middleware, router и обработчики ошибок

Middleware оборачивает нижележащее приложение. Порядок похож на вложенные функции: внешний проходит первым на входе и последним на выходе. Последний добавленный middleware обычно становится внешним относительно ранее добавленных.

Получение объекта Response не означает, что весь streaming-body уже передан клиенту. Измерение вокруг call_next может оценивать другой интервал, чем полное время отправки. Ошибка после начала ответа не всегда может быть представлена новым HTTP-статусом.

HTTPException возбуждают для прекращения обычного пути обработки. Обработчики переводят известные ошибки в согласованные ответы. Не стоит превращать любой Exception в «успех с пустым результатом»: это скрывает нарушение контракта.

APIRouter объединяет маршруты в приложение и его OpenAPI. Mount подключает самостоятельное ASGI-приложение с собственной границей маршрутизации/схемы. Это разные способы композиции.

## 9. Аутентификация и права — последовательность проверок

Bearer-утилита извлекает токен и описывает схему, но не доказывает его подлинность. Далее нужно проверить подпись/срок/назначение, определить пользователя и проверить права на конкретный объект.

JWT с подписью защищает от незаметного изменения, но payload обычно читаем: это не шифрование. Источник доверенного ключа и допустимый алгоритм задаёт сервер. Проверка токена не заменяет запрет пользователю читать чужой заказ.

OAuth2 — протокол делегирования доступа; OpenID Connect добавляет идентификацию. Password grant из учебных примеров не следует выбирать для нового OAuth-входа: RFC 9700 запрещает этот grant. Для пользовательских провайдеров входа обычно используют Authorization Code с PKCE и нужным OIDC-контрактом.

CORS регулирует браузерный доступ JavaScript к ответу между origin. Запрос может дойти до сервера даже при запрете чтения ответа. Поэтому CORS не является авторизацией или полноценной CSRF-защитой.

## 10. Streaming и фоновая работа

Потоковая выдача отдаёт части по готовности. JSON Lines кодирует отдельные JSON-значения по строкам; SSE — события с разделителями, id и правилами reconnect; обычный JSON-массив имеет другой формат. Клиент и proxy должны поддерживать выбранный путь.

При отключении клиента нужно завершить генератор и освободить ресурсы. Медленному клиенту нельзя бесконечно накапливать данные в памяти: нужны backpressure/лимиты. Встроенная поддержка конкретных генераторов/SSE зависит от версии, но эти ограничения остаются.

BackgroundTasks запускает работу после ответа в том же процессе. Он не даёт долговечного хранения и гарантированного повторного выполнения после сбоя worker. Для обязательной долгой работы API сохраняет задание, возвращает 202 с адресом статуса, а отдельный worker обрабатывает его с учётом повторов и идемпотентности.

## 11. Как проверить понимание

1. Проследи запрос с неверным item_id: кто разбирает строку, кто создаёт ошибку и вызывается ли обработчик?
2. Чем прямой вызов функции с Depends отличается от HTTP-вызова маршрута?
3. Когда закроется ресурс, который использует streaming-генератор? Как влияет версия/scope?
4. Почему синхронный HTTP-клиент внутри async def тормозит соседние запросы?
5. Какие данные отфильтрует response_model и когда эта защита обходится?
6. Почему успешный ответ нельзя отправлять раньше обязательного commit?
7. Что потеряется при падении worker после ответа с BackgroundTasks?
8. Что проверяет TestClient, а что останется проверить на развёрнутом сервере?
