# Packaging: от исходников к установленному пакету

Упаковка задаёт, что именно получает пользователь и как окружение собирается из зависимостей. Команды — в [КОНСПЕКТ.md](КОНСПЕКТ.md); здесь прослеживается жизненный цикл артефакта.

## 1. Модуль, import package и distribution

Модуль — единица импорта; часто это `.py`-файл, но возможны расширения и другие загрузчики. Import package организует вложенные модули: обычный пакет имеет __init__.py, namespace package может собираться из нескольких расположений без него.

Distribution — единица установки и публикации с именем, версией, метаданными и файлами. Один distribution может предоставить несколько import packages. Имя в индексе не обязано совпадать с import: Pillow предоставляет PIL.

Поэтому `pip install X` и `import X` задают вопросы разным системам. Pip ищет distribution в выбранном источнике; import ищет модуль по механизму импорта текущего интерпретатора. Ошибка импорта может означать другое имя, другое окружение или неверный состав артефакта.

## 2. Кто участвует в сборке

| Участник | Ответственность |
|---|---|
| Автор проекта | Исходники, метаданные, зависимости и настройки включения файлов |
| Build frontend | Организовать окружение и вызвать стандартные hooks backend |
| Build backend | Создать wheel/sdist по правилам проекта |
| Package index | Предоставить сведения о доступных версиях и файлах |
| Installer | Выбрать совместимые дистрибутивы и установить их |
| Publisher | Загрузить подготовленные артефакты в индекс |

Build и pip могут выступать frontend, Hatchling/Setuptools/Flit — backend, Twine — загрузчик. Один инструмент может совмещать роли, но это не делает сами роли одинаковыми.

## 3. pyproject.toml описывает несколько контрактов

```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "study-greeting"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = ["httpx>=0.27,<1"]
```

Build-system.requires нужен для **создания** артефакта; project.dependencies нужен пользователю **установленного** проекта. У чистой библиотеки backend может никогда не понадобиться в рабочем окружении, если установили готовый wheel.

Requires-python ограничивает интерпретаторы для установщика. Classifiers описывают проект, но не заменяют это ограничение. Таблицы tool содержат настройки конкретных инструментов, а не универсальную семантику Python.

Изолированная сборка создаёт отдельную среду с объявленными build-зависимостями. Это помогает заметить скрытую зависимость от компьютера автора. Однако изоляция сама по себе не гарантирует идентичные байты при двух сборках: могут меняться версии инструментов, исходные входы и временные метки.

## 4. Wheel и sdist обслуживают разные этапы

Wheel — ZIP-артефакт с подготовленными файлами и метаданными установки. Для него не нужно заново выполнять полную сборку проекта из исходников. Это не обязательно бинарник: чистая Python-библиотека тоже имеет wheel.

Sdist — исходный дистрибутив. При отсутствии подходящего wheel установщик может получить sdist, подготовить сборочную среду и собрать wheel. Поэтому установка «одного пакета» иногда внезапно требует компилятор, системные заголовки или доступ к build-зависимостям.

```text
репозиторий → sdist → изолированная сборка → wheel → установка → import
          ↘ прямая сборка wheel из рабочего дерева
```

Сборка wheel из sdist помогает проверить полноту исходного архива. Если нужный файл был только в рабочем дереве, прямая сборка могла проходить, а установка опубликованного sdist — нет.

Имя wheel содержит теги Python, ABI и платформы. `py3-none-any` подходит для соответствующего чистого Python-кода; нативному расширению часто нужны отдельные артефакты под среды. Наличие wheel с похожим именем не делает его совместимым с любой ОС и архитектурой.

## 5. Что делает установщик зависимостей

Он рассматривает требования версий, Python/platform markers, extras и доступные артефакты. Зависимости образуют граф, а не просто список строк. Два пакета могут потребовать несовместимые диапазоны третьего — тогда валидного решения нет.

Extras добавляют выбранные необязательные зависимости; они не означают автоматическую загрузку любого «необязательного» кода. Environment markers включают требования только в подходящей среде. Установщик проверяет метаданные совместимости, но не доказывает семантическую совместимость API всех версий.

Диапазон `>=0.27,<1` оставляет много решений, которые могут меняться со временем. Для приложения обычно фиксируют конкретное окружение с транзитивными версиями; для библиотеки оставляют обоснованные диапазоны и проверяют поддерживаемые сочетания.

Pyproject сам по себе не является универсальным lock-файлом. Воспроизводимость требует также версии Python, платформы, сборочных инструментов, источников артефактов и при необходимости хешей. Даже точный набор Python-пакетов не фиксирует системные библиотеки контейнера.

## 6. Окружение и путь импорта

Venv создаёт отдельный контекст установки, прежде всего свои site-packages и настройки интерпретатора. Активация меняет удобство выбора команд через PATH; важнее, какой python фактически запускается. `python -m pip` связывает установщик с выбранным интерпретатором.

Venv не является контейнером или границей безопасности и не включает отдельное ядро ОС. Системные библиотеки и внешние сервисы остаются отдельными зависимостями.

Каталог запуска может попадать в sys.path. Поэтому импорт из корня репозитория иногда находит локальный код, хотя wheel собран неверно. Src-layout уменьшает такую случайность: импортируемый пакет лежит отдельно от корня.

Editable install делает изменения исходников видимыми без обычной переустановки; детали реализует backend. Успех editable-режима не заменяет проверку обычного wheel, особенно для package data и сгенерированных файлов.

## 7. Состав артефакта — часть контракта

В репозитории могут быть тесты, документация, секреты, исходный код, данные и результаты сборки. Не всё нужно пользователю. Backend определяет, что включено в sdist и wheel; это нужно проверять отдельно для обоих форматов.

Если библиотека открывает шаблон или SQL-файл как ресурс, файл обязан попасть в distribution. Относительный путь от текущего каталога пользователя ненадёжен; пакетные ресурсы читают подходящим механизмом, например importlib.resources.

Метаданные версии и зависимости используются без чтения всего кода. Ошибка в них способна сломать установку даже правильно написанного модуля. Лицензия и README тоже являются частью публикуемого продукта, а не только оформлением GitHub.

## 8. Публикация и проверка релиза

Сборка создаёт локальный артефакт; публикация делает его доступным в индексе. TestPyPI и PyPI — отдельные среды с отдельными учётными данными и содержимым. Тестовая установка с no-deps не доказывает, что зависимости корректно разрешаются.

Полезная проверка: собрать → посмотреть содержимое → установить wheel в чистую среду → перейти вне исходников → импортировать и выполнить основной сценарий → проверить зависимые ресурсы и CLI. Затем аналогично проверить сборку из sdist.

В CI лучше продвигать проверенные артефакты, а не собирать заново между проверкой и публикацией. Секрет публикации предоставляет доверенная среда; Trusted Publishing связывает ограниченное удостоверение CI с разрешённой публикацией вместо хранения долгоживущего токена.
