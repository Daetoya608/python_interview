# Упаковка Python-проектов: конспект к аттестации

По материалам PyPA, [Packaging Python Projects](https://packaging.python.org/en/latest/tutorials/packaging-projects/). Оригинал: © PyPA и участники; перевод, сокращение и пояснения — под [CC BY-SA 3.0](https://creativecommons.org/licenses/by-sa/3.0/). Полный перевод находится в `lvl-1.md`.

## 1. Основные понятия

| Понятие | Что означает |
|---|---|
| Модуль | Импортируемая единица, например файл `example.py` |
| Import package | Пакет для `import`; обычный пакет — каталог с `__init__.py` |
| Distribution package | То, что публикуют и устанавливают через pip; может содержать несколько модулей/пакетов |
| PyPI | Индекс дистрибутивов Python |
| TestPyPI | Отдельный тестовый индекс с отдельными аккаунтами и токенами |
| Build frontend | Инструмент, который организует сборку: например, build или pip |
| Build backend | Инструмент, непосредственно создающий дистрибутив: Hatchling, Setuptools, Flit и другие |
| Twine | Инструмент загрузки готовых дистрибутивов в индекс |

**Имя для pip и имя для import не обязаны совпадать.** Например, дистрибутив Pillow предоставляет пакет PIL. В учебнике совпадающие имена выбраны для простоты. В имени дистрибутива допустим дефис, в обычной записи `import some-name` — нет.

## 2. Минимальная структура

```text
project/
├── pyproject.toml
├── README.md
├── LICENSE
├── src/
│   └── example_package_me/
│       ├── __init__.py
│       └── example.py
└── tests/
```

- `src/` отделяет распространяемый код от файлов проекта. Это помогает проверять установленный пакет, а не случайно импортировать исходники из корня репозитория.
- `__init__.py` делает каталог обычным пакетом; у namespace-пакетов его может не быть.
- README содержит подробное описание; LICENSE — условия использования; tests — тесты.
- Какие дополнительные файлы попадут в sdist и wheel, определяется настройками backend. Проверяйте содержимое архивов, особенно данные пакета.

## 3. pyproject.toml: две разные группы зависимостей

```toml
[build-system]
requires = ["hatchling >= 1.26"]
build-backend = "hatchling.build"

[project]
name = "example_package_me"
version = "0.0.1"
description = "A small example package"
readme = "README.md"
requires-python = ">=3.9"
license = "MIT"
license-files = ["LICEN[CS]E*"]
dependencies = []
```

`[build-system].requires` — **зависимости сборки**. Frontend устанавливает их в сборочное окружение и вызывает backend. Здесь требуется Hatchling; минимальная версия поддерживает используемые метаданные лицензии.

`[project].dependencies` — **зависимости установленного пакета**, например `dependencies = ["httpx>=0.27"]`. Установка Hatchling для сборки не делает его рабочей зависимостью библиотеки.

| Поле | Назначение |
|---|---|
| `name` | Имя дистрибутива; для публикации нужно свободное имя в индексе |
| `version` | Версия релиза |
| `requires-python` | Ограничение поддерживаемых версий Python для установщика |
| `readme` | Подробное описание на PyPI |
| `authors`, `maintainers` | Авторы и сопровождающие |
| `classifiers` | Описательные категории; не замена requires-python |
| `license` | SPDX-выражение, например MIT |
| `license-files` | Шаблоны файлов лицензий |
| `[project.urls]` | Ссылки на исходники, документацию, задачи |
| `[tool.<name>]` | Настройки конкретного инструмента |

Выбирают **один backend**, а не копируют все варианты `[build-system]` в один файл. `pyproject.toml` описывает проект; сам по себе он не является универсальным lock-файлом с точными версиями всего окружения.

## 4. Wheel и sdist

| Формат | Содержимое и установка |
|---|---|
| `.whl`, wheel | Готовый к установке дистрибутив; не нужно заново собирать проект из исходников |
| `.tar.gz`, sdist | Исходный дистрибутив; установщик может собрать из него wheel, для чего нужны сборочные зависимости |

Wheel не обязательно содержит машинный код: чистая Python-библиотека тоже распространяется как wheel. Пакету с нативными расширениями могут понадобиться разные wheels для платформ, архитектур и версий Python.

Для простого чистого Python-пакета учебник получает `example_package_me-0.0.1-py3-none-any.whl`. Sdist позволяет собрать пакет и там, где подходящего готового wheel нет. Pip обычно предпочитает совместимый wheel.

## 5. Последовательность команд

Ниже `python` — интерпретатор выбранного виртуального окружения. В переводе также приведены варианты `py` для Windows и `python3` для Unix/macOS. Команды выполняют в корне проекта с pyproject.toml.

```console
python -m pip install --upgrade pip build twine
python -m build
```

Результат — wheel и sdist в `dist/`. Сборка обычно использует изолированное окружение с зависимостями из build-system.requires.

Для учебной публикации после регистрации в TestPyPI и создания его API-токена:

```console
python -m twine upload --repository testpypi dist/*
```

Токен вводят по запросу, полностью, включая префикс `pypi-`. Его не записывают в исходники. Сам процесс сборки ничего в индекс не загружает.

Проверка установки **в отдельном чистом виртуальном окружении**:

```console
python -m pip install --index-url https://test.pypi.org/simple/ --no-deps example-package-me
python -c "from example_package_me.example import add_one; print(add_one(2))"
```

Ожидаемый результат — `3`, если example.py содержит функцию из учебника. Проверять лучше вне каталога с исходниками, чтобы они не подменили установленный пакет.

- `--index-url` выбирает TestPyPI вместо обычного PyPI.
- `--no-deps` отключает установку рабочих зависимостей: тестовый индекс не содержит тот же набор пакетов, что основной. Если у проекта есть зависимости, их нужно подготовить отдельно; флаг их не делает ненужными.
- TestPyPI — площадка для экспериментов, а не постоянное хранилище.

Для ручной публикации в основном индексе используется `python -m twine upload dist/*` с учётными данными **PyPI**, затем пакет устанавливают обычным pip install. В поддерживаемом CI/CD учебник рекомендует Trusted Publishing вместо долгоживущего API-токена.

## 6. Что уметь объяснить на собеседовании

1. **pip сам собирает wheel?** Он организует процесс и вызывает backend; непосредственную сборку выполняет backend.
2. **Зачем pyproject.toml?** Описать систему сборки, стандартные метаданные проекта и настройки инструментов.
3. **Почему build-system.requires и project.dependencies различаются?** Первое нужно для получения артефакта, второе — для работы установленного пакета.
4. **Зачем два архива?** Wheel удобен для готовой установки, sdist предоставляет исходники для сборки.
5. **Для wheel обязательно нужен C-код?** Нет, wheel подходит и для чистого Python.
6. **Пакет установлен через pip, но import с тем же именем не работает — почему?** Имя дистрибутива и импортируемого пакета могут отличаться; также важно использовать нужное окружение.
7. **Что не доказывает импорт из репозитория?** Что дистрибутив собран правильно: импорт мог сработать прямо из исходников.
8. **Что делает Twine?** Загружает уже собранные архивы, а не заменяет backend сборки.
9. **Зачем лицензия и README?** Лицензия задаёт условия использования, README описывает пакет и отображается на его странице.
10. **TestPyPI и PyPI — один аккаунт?** Нет, это отдельные индексы с отдельными аккаунтами и токенами.
