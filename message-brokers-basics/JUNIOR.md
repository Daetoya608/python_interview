# Брокеры сообщений — Junior

## Основные роли

**Broker** принимает и доставляет сообщения. **Producer** публикует, **queue** хранит ожидающую работу, **consumer** получает и выполняет её.

```text
API (producer) → broker / queue → worker (consumer) → результат обработки
```

Пример: API оформляет заказ, worker отправляет письмо позже. Брокер уменьшает зависимость отправителя от доступности получателя и сглаживает пики. Плата — инфраструктура, задержка и необходимость обработки сбоев/повторов. Если вход постоянно быстрее обработки, очередь растёт: она не заменяет достаточную мощность.

Consumers одной очереди обычно делят задачи между собой. Чтобы несколько независимых подписчиков получили событие, нужны отдельные подписки/очереди; два worker одной очереди не означают рассылку каждому.

## Ack и сбои

**Consumer ack** подтверждает брокеру обработку доставки. Его отправляют **после успешного результата**. Подтверждение принятия публикации брокером — другая стадия; оно не доказывает успешную работу consumer.

1. Consumer получил сообщение и записал результат.
2. Упал до ack или ack потерялся.
3. Брокер может доставить сообщение повторно: для него успешная обработка ещё не подтверждена.

Если подтверждать до выполнения, падение после ack может потерять задачу. Хранение очереди/сообщений при перезапуске зависит от настроек брокера; очередь в памяти процесса этого не гарантирует.

## Гарантии доставки

| Гарантия | Смысл в рамках механизма доставки | Цена |
|---|---|---|
| At-most-once | Без повторной доставки, но возможна потеря | Меньше повторов, задача может не обработаться |
| At-least-once | Как минимум одна доставка в рамках гарантий брокера; возможны повторы | Требуется безопасная повторная обработка |

At-least-once не означает, что любой consumer физически не может выполнить действие дважды. Нужен **идемпотентный обработчик**: повтор одного message_id/бизнес-ключа не повторяет эффект. Например, уникальный ключ операции и результат сохраняются в той же транзакции, что изменение бизнес-данных.

Простая проверка «ID уже видели?» отдельно от записи не защищает от гонки/падения между шагами. Флаг в локальном словаре теряется при перезапуске.

## DLQ и transactional outbox

**Dead-letter queue (DLQ)** — место для сообщений, которые нельзя обработать по выбранным правилам. Вместо бесконечного немедленного повтора ограничивают попытки, записывают причину и направляют проблемное сообщение на разбор. Конкретная маршрутизация зависит от брокера.

**Transactional outbox** решает разрыв «обновить БД и опубликовать событие»:

1. В одной локальной транзакции записывают бизнес-изменение и событие в outbox-таблицу.
2. Отдельный publisher читает outbox и отправляет события брокеру.
3. После сбоя публикация может повториться: consumer всё равно должен быть идемпотентным.

Outbox не делает письмо/платёж частью ACID-транзакции БД и не даёт автоматического end-to-end exactly-once. Он надёжно связывает сохранённое изменение с намерением последующей публикации.
