# SQL: сущности и механизмы выполнения

Здесь важно уметь предсказать результат и объяснить его происхождение. Синтаксис для повторения — в [КОНСПЕКТ.md](КОНСПЕКТ.md), упражнения — в [practice](practice/). Примеры ориентированы на PostgreSQL; особенности других СУБД нужно проверять отдельно.

## 1. Таблица, строка и запрос

Таблица описывает факты одного вида: например, заказы. Строка — один такой факт, столбец — его атрибут с определённым доменом значений. Первичный ключ позволяет отличать строки независимо от совпадения остальных полей.

Реляционная модель оперирует отношениями, но SQL по умолчанию допускает дубликаты в результате. Две одинаково выглядящие строки после SELECT не обязательно ошибка: проекция могла скрыть различающиеся ключи. `DISTINCT` убирает одинаковые результирующие строки, но не исправляет неверную модель соединения.

У таблицы нет гарантированного пользовательского порядка строк. Физическое расположение, порядок вставки и наличие индекса не заменяют `ORDER BY`. Для устойчивой пагинации нужен однозначный порядок, например `(created_at, id)`.

## 2. Декларативный запрос и физическое выполнение

SQL описывает, **какой результат нужен**. СУБД выбирает, как его получить:

```text
текст и параметры → разбор и разрешение имён → логическое представление
→ оптимизация и выбор плана → исполнение операторов → строки результата
```

Оптимизатор использует статистику, объём таблиц, доступные индексы и стоимость операций. Семантически одинаковый запрос на разных данных может получить разные планы. Индекс — один из вариантов доступа, а не инструкция обязательно им воспользоваться.

Полезный логический порядок одного SELECT:

```text
FROM/JOIN → WHERE → GROUP BY/агрегаты → HAVING
→ оконные вычисления → выходные выражения → DISTINCT → ORDER BY → LIMIT
```

Это модель смысла, не обязательная последовательность чтения страниц. СУБД может перенести фильтр раньше или поменять порядок внутренних соединений, если результат сохраняется. Поэтому алиас из SELECT обычно недоступен в WHERE того же уровня.

## 3. NULL и трёхзначная логика

NULL обозначает отсутствие/неизвестность значения. Сравнение `salary = NULL` не устанавливает, отсутствует ли зарплата: результат UNKNOWN. Даже `NULL = NULL` не даёт TRUE. Для проверки наличия предусмотрен `IS NULL`.

| Выражение | Результат |
|---|---|
| `TRUE AND UNKNOWN` | UNKNOWN |
| `FALSE AND UNKNOWN` | FALSE |
| `TRUE OR UNKNOWN` | TRUE |
| `NOT UNKNOWN` | UNKNOWN |

WHERE и условие совпадения JOIN принимают только TRUE. CHECK в PostgreSQL отклоняет FALSE, поэтому `CHECK (price > 0)` сам по себе допускает NULL: обязательность задаёт NOT NULL.

Ловушка `NOT IN`: если среди сравниваемых значений есть NULL и совпадения не найдено, отрицание может остаться UNKNOWN. Для задачи «нет связанного заказа» яснее `NOT EXISTS` с явным условием связи. При этом NULL в самом ключе тоже требует осмысленной бизнес-семантики.

## 4. JOIN создаёт пары строк

JOIN не «приклеивает таблицу целиком». Для каждой строки он формирует все допустимые пары со второй стороной. Если у клиента три заказа, клиент появится три раза. Если одновременно присоединить два адреса, получится до шести сочетаний заказ × адрес.

INNER сохраняет совпавшие пары. LEFT дополнительно создаёт одну строку с NULL справа для каждого левого объекта без совпадений. RIGHT симметричен LEFT; FULL сохраняет несовпадения обеих сторон; CROSS создаёт все пары.

```sql
SELECT c.id, COUNT(o.id) AS paid_orders
FROM customers AS c
LEFT JOIN orders AS o
  ON o.customer_id = c.id AND o.status = 'paid'
GROUP BY c.id;
```

Клиент без оплаченных заказов остаётся, счётчик равен нулю. Если перенести `o.status = 'paid'` в WHERE, дополненная NULL строка отфильтруется. Если заменить `COUNT(o.id)` на `COUNT(*)`, она будет посчитана как одна.

Перед JOIN полезно назвать **единицу результата**: одна строка на клиента, заказ или позицию? Если нужны только клиенты с заказами, EXISTS проверяет наличие без размножения. Если нужны суммы двух независимых коллекций, каждую сначала агрегируют до одной строки на родителя.

## 5. Агрегат сворачивает, окно дополняет

GROUP BY собирает строки по ключу группы; агрегат вычисляет одно значение на группу. После группировки отдельная исходная строка больше не является единицей результата. WHERE исключает исходные строки, HAVING исключает уже построенные группы.

COUNT(*) считает строки; COUNT(x) — строки с известным x. SUM/AVG пропускают NULL. Поэтому среднее по двум известным зарплатам и одной неизвестной — среднее двух, а не сумма, делённая на три. На пустом входе без GROUP BY COUNT возвращает 0, SUM — NULL.

Оконная функция сохраняет строки и вычисляет значение в их контексте. `PARTITION BY` выбирает раздел, оконный ORDER BY задаёт порядок расчёта, frame — подмножество строк для функций, которые его учитывают.

Например, суммы 10, 10, 20 при оконном порядке только по сумме и рамке по умолчанию дадут накопление 20, 20, 40: равные значения образуют peers. Для накопления по одной строке задают ROWS и однозначный порядок. Оконный ORDER BY не сортирует окончательный ответ автоматически.

ROW_NUMBER назначает отдельный номер каждой строке; RANK оставляет одинаковое место равным с пропусками; DENSE_RANK — без пропусков. Добавление уникального id в порядок ранжирования меняет само определение равенства.

## 6. Как реально соединяются данные

Логический вид JOIN и физический алгоритм — разные оси:

| Алгоритм | Механизм | Что определяет цену |
|---|---|---|
| Nested loop | Для каждой внешней строки ищет внутренние совпадения | Число внешних строк и стоимость каждого поиска |
| Hash join | Строит хеш-структуру по одной стороне и ищет ключи другой | Размер структуры, память, равенство ключей |
| Merge join | Продвигает два упорядоченных потока по ключу | Наличие порядка или стоимость сортировки |

Nested loop с десятью внешними строками и индексным поиском может быть отличным планом. Он же с миллионом внешних строк и повторным полным проходом станет дорогим. В EXPLAIN ANALYZE смотрят rows, loops и чтения; время родительского узла включает работу потомков.

## 7. Изменения и серверные объекты

INSERT добавляет факт, UPDATE меняет подходящие строки, DELETE удаляет их. Ограничения, индексы и триггеры обслуживаются вместе с операцией. Поэтому запись стоит больше, чем изменение одного значения в Python-словаре. Несколько связанных операторов объединяют транзакцией.

View сохраняет определение запроса: обращение к нему логически подставляет этот запрос. Materialized view хранит вычисленный результат и требует обновления. Это разные компромиссы свежести и цены чтения.

Процедуру явно вызывает клиент; функция используется в предусмотренных СУБД контекстах вычисления; триггер автоматически реагирует на событие. Перенос логики в БД может уменьшить число сетевых обменов и охватить разных писателей, но добавляет скрытые зависимости и усложняет сопровождение.

Триггер AFTER срабатывает после соответствующей операции, **внутри её транзакции**, а не после commit. Обычная запись аудита откатится вместе с изменением. Вызов внешнего HTTP API из триггера так автоматически не откатится. Простое правило уникальности надёжнее выразить UNIQUE, чем SELECT-проверкой в триггере с гонкой между писателями.

## 8. Разбор на собеседовании

1. Почему после двух LEFT JOIN сумма заказов выросла? Нарисуй пары строк и найди изменившуюся единицу результата.
2. Как оставить клиентов без заказов? Объясни создание NULL-строки и размещение условия в ON.
3. Почему AVG и SUM/COUNT(*) могут различаться? Укажи обработку NULL.
4. Почему после окна нельзя отфильтровать его алиас в WHERE этого же уровня? Сопоставь логические этапы, добавь внешний SELECT.
5. Почему один запрос ускорился после роста таблицы иначе, чем ожидалось? Сравни планы и оценки с реальными объёмами.
6. Что произойдёт с аудитом триггера после ROLLBACK? Проследи границы транзакции.
