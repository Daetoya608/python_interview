# SQL: конспект для аттестации

Уровень 1 — запросы, агрегаты, объекты БД и JOIN. Уровень 2 — преимущества/недостатки процедур и триггеров; дополнительно окна и nested loop. Подробности — в `lvl-1.md`, `lvl-2.md`, практика — в `practice/`.

## 1. SELECT, INSERT, UPDATE, DELETE

| Команда | Назначение |
|---|---|
| SELECT | Получить строки/выражения |
| INSERT | Добавить строки |
| UPDATE | Изменить подходящие строки |
| DELETE | Удалить подходящие строки, сохранив таблицу |

```sql
SELECT id, amount_cents
FROM orders
WHERE status = 'paid'
ORDER BY amount_cents DESC, id
LIMIT 10;

INSERT INTO customers (id, name, city) VALUES (4, 'Dima', 'Kazan');
UPDATE customers SET city = 'Moscow' WHERE id = 4;
DELETE FROM customers WHERE id = 4;
```

Без WHERE UPDATE/DELETE затронет все строки. Без ORDER BY порядок SELECT не гарантирован. Несколько связанных изменений объединяют транзакцией: COMMIT фиксирует, ROLLBACK отменяет. CREATE/ALTER/DROP — изменение структуры, а не обычные операции над строками.

Пользовательские значения передают параметрами драйвера, а не склеивают с SQL-строкой. В примерах значения заданы статически.

## 2. NULL и агрегаты

NULL — неизвестное/отсутствующее значение. Используйте `IS NULL` / `IS NOT NULL`, а не `= NULL`. WHERE оставляет только TRUE; UNKNOWN не проходит фильтр.

| Агрегат | Что учитывает |
|---|---|
| COUNT(*) | Все строки |
| COUNT(x) | Не-NULL значения x |
| COUNT(DISTINCT x) | Разные не-NULL значения x |
| SUM(x), AVG(x), MIN(x), MAX(x) | Не-NULL входные значения |

Без GROUP BY на пустом входе COUNT даёт 0, остальные перечисленные агрегаты — NULL. COALESCE(SUM(...), 0) подставляет 0, если это нужный смысл. AVG(x) не считает пропущенное значение нулём.

```sql
SELECT customer_id, COUNT(*) AS order_count, SUM(amount_cents) AS total_cents
FROM orders
WHERE status = 'paid' AND customer_id IS NOT NULL
GROUP BY customer_id
HAVING SUM(amount_cents) >= 20000
ORDER BY customer_id;
```

WHERE фильтрует строки **до** группировки, HAVING — группы **после** неё. Неагрегированные выбранные колонки для переносимого запроса явно включают в GROUP BY.

## 3. JOIN

| Вид | Что сохраняет |
|---|---|
| INNER | Совпавшие пары |
| LEFT | Все левые строки, при отсутствии правой — NULL |
| RIGHT | Все правые строки, при отсутствии левой — NULL |
| FULL | Совпадения и несовпавшие строки обеих сторон |
| CROSS | Все сочетания, M × N строк |

Self join — одна таблица в разных ролях с alias. EXISTS выражает проверку наличия совпадения без размножения родительских строк; NOT EXISTS — отсутствия.

Ловушки:

- Условие правой таблицы в WHERE после LEFT JOIN может удалить NULL-строки. Для сохранения родителей отбор совпадений часто нужен в ON.
- COUNT(*) после LEFT JOIN посчитает NULL-дополненную строку; для числа детей нужен COUNT(дочерний_PK).
- One-to-many закономерно повторяет родителя. Несколько независимых коллекций могут размножить строки и завысить суммы.
- SUM(DISTINCT amount) не лечит дубли JOIN: разные заказы могут иметь одинаковую сумму. Сначала агрегируйте нужную сторону или используйте подходящую семантику запроса.
- NOT IN с NULL в подзапросе может не вернуть ожидаемые строки. Для антисоединения часто яснее NOT EXISTS.

## 4. Объекты БД

| Объект | Смысл |
|---|---|
| Таблица | Хранит данные |
| PK/FK/UNIQUE/NOT NULL/CHECK | Декларативные ограничения корректности |
| Индекс | Структура доступа, ускоряющая подходящие операции за цену записи и места |
| View | Именованный запрос; обычный view не кэширует результат автоматически |
| Materialized view | Сохранённый результат, требующий обновления |
| Функция | Вычисление, обычно вызываемое в выражении/запросе |
| Процедура | Явно вызываемая серверная операция |
| Триггер | Автоматическая серверная реакция на событие |

Поддержка объектов и синтаксис зависят от СУБД. Наличие индекса не гарантирует его использование. Не каждый view обновляем; материализованный результат может устаревать.

## 5. Процедуры и триггеры — обязательно для уровня 2

**Процедуры:** сокращают обмены с БД, позволяют выполнить обработку рядом с данными, дают общий интерфейс операции для нескольких клиентов. Недостатки — зависимость от СУБД, усложнение миграций/диагностики, нагрузка на сервер и разделение логики между слоями. Сам факт хранения кода в БД не гарантирует скорость, безопасность и отсутствие гонок.

**Триггеры:** обеспечивают автоматический локальный аудит/обслуживание данных для разных писателей. Недостатки — скрытые побочные действия, цена каждой записи, цепочки/рекурсия, блокировки и сложность тестирования массовых операций.

Сначала используйте ограничение, если оно выражает правило. UNIQUE лучше триггерного SELECT «такого значения пока нет»; конкурентные проверки могут одновременно пропустить дубль.

Триггеры различают по событию, BEFORE/AFTER/INSTEAD OF и ROW/STATEMENT, если СУБД это поддерживает. В PostgreSQL триггер вызывает специальную функцию RETURNS trigger. OLD — прежняя строка, NEW — новая в подходящем row-событии. SQLite не поддерживает statement-триггеры и использует другой синтаксис тела.

**AFTER не означает после commit.** Обычная запись аудита триггером находится в той же транзакции и откатится вместе с изменением. Внешнее сетевое действие автоматически не откатится. Транзакционная согласованность требует отдельного проектирования, а не только выбора процедуры/триггера.

## 6. Оконные функции — желательно

Агрегат с GROUP BY сворачивает группу. Окно сохраняет строки и добавляет вычисление по разделу/рамке.

```sql
SELECT id, customer_id, amount_cents,
       SUM(amount_cents) OVER (PARTITION BY customer_id) AS customer_total,
       ROW_NUMBER() OVER (
           PARTITION BY customer_id ORDER BY amount_cents DESC, id
       ) AS rn
FROM orders
WHERE status = 'paid' AND customer_id IS NOT NULL
ORDER BY customer_id, id;
```

- PARTITION BY — независимые разделы.
- ORDER BY внутри OVER — порядок расчёта, не окончательная сортировка ответа.
- Frame — рамка для вычисления. При ORDER BY стандартная рамка в PostgreSQL/SQLite включает строки от начала раздела до текущей группы равных по сортировке: сумма может увеличиваться сразу на всю группу. Для построчного накопления задают `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` и определённый порядок.
- ROW_NUMBER — порядковый номер; RANK — одинаковые места с пропусками; DENSE_RANK — без пропусков. При `ORDER BY amount_cents DESC` для сумм 100, 100, 90: соответственно 1/2/3, 1/1/3, 1/1/2; порядок ROW_NUMBER внутри равных сумм не определён.
- Равенство для RANK/DENSE_RANK определяется **всем** ORDER BY окна. Добавление уникального id уберёт равные места: для рейтинга по сумме его не добавляют, а для однозначного ROW_NUMBER обычно добавляют.
- LAG/LEAD — предыдущее/следующее значение; на отсутствующей строке обычно NULL.
- ROW_NUMBER = 1 выбирает одну строку, RANK = 1 — все строки, равные по заданной сортировке на первом месте.
- Оконный результат в PostgreSQL/SQLite фильтруют внешним SELECT/CTE, а не WHERE того же уровня.

## 7. Nested loop join — желательно

**INNER/LEFT — логическая семантика; nested loop/hash/merge — физические алгоритмы.**

Nested loop берёт строку внешнего источника и ищет подходящие строки внутреннего. Полный повторный проход внутреннего набора может дать до M × N сравнений. При малом outer-наборе и подходящем внутреннем индексе index nested loop часто выгоден.

Нельзя оценивать план только по названию алгоритма. Смотрите фактические строки, loops внутреннего узла, доступ по индексу, фильтрацию и статистику. Порядок источников в плане может отличаться от текста INNER JOIN.

PostgreSQL: EXPLAIN показывает план; EXPLAIN ANALYZE **выполняет** запрос и даёт реальные измерения. Cost — не миллисекунды. SQLite использует EXPLAIN QUERY PLAN со своим форматом.
