# SQL — уровень 1: DML, агрегаты, объекты БД и JOIN

Материал под требования аттестации. Объяснения относятся к реляционным БД; SQL-примеры используют общий синтаксис, а отличия СУБД отмечены явно. Запускаемая практика — SQLite; процедуры и триггерная функция PostgreSQL — отдельный файл уровня 2.

## 1. Реляционная БД и её объекты

Реляционная БД хранит данные в таблицах и позволяет связывать их через ключи и выражения запросов. Таблица содержит строки и колонки; колонка имеет тип и ограничения, а первичный ключ идентифицирует строку.

| Объект | Для чего нужен |
|---|---|
| Таблица | Хранение строк данных |
| Ограничение | Гарантии корректности: PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL, CHECK |
| Индекс | Ускорение подходящих способов поиска/соединения; требует места и обслуживания при записи |
| Представление, VIEW | Именованный запрос, скрывающий сложность и предоставляющий удобную форму данных |
| Материализованное представление | Сохранённый результат запроса, который нужно обновлять; поддержка зависит от СУБД |
| Функция | Именованное вычисление; в зависимости от СУБД может использоваться в выражении/запросе |
| Хранимая процедура | Сохранённая серверная операция с параметрами, вызываемая явно |
| Триггер | Автоматическая реакция БД на заданное событие, например изменение строки |
| Схема | Пространство имён объектов, например public в PostgreSQL; термин зависит от СУБД |
| Последовательность / identity | Получение значений для идентификаторов; конкретный механизм зависит от СУБД |

Первичный ключ уникален и не допускает NULL; внешний ключ связывает значение с допустимой строкой другой таблицы. CHECK проверяет условие строки, но сам по себе не всегда запрещает NULL: для этого нужен NOT NULL. Ограничения в БД продолжают действовать независимо от того, какое приложение пишет данные.

Индекс не гарантирует порядок результата SELECT — для этого нужен ORDER BY. Он также не всегда ускоряет запрос: решение зависит от объёма, селективности и плана.

## 3. SELECT: прочитать данные

```sql
SELECT id, amount_cents, status
FROM orders
WHERE status = 'paid' AND amount_cents >= 10000
ORDER BY amount_cents DESC, id ASC
LIMIT 10;
```

- SELECT определяет возвращаемые выражения и колонки.
- FROM — источник строк.
- WHERE отбирает строки по условию.
- ORDER BY задаёт порядок; дополнительный уникальный ключ делает порядок при равных суммах определённым.
- LIMIT ограничивает число строк; его синтаксис и альтернативы зависят от СУБД.

Здесь результат — заказы 201, 101, 102. Без ORDER BY порядок не гарантирован. SELECT * удобен при исследовании, но в устойчивом контракте лучше явные колонки.

Основные условия: =, <>, >, >=, <, <=, AND, OR, NOT, IN (...), BETWEEN ... AND ..., LIKE. BETWEEN включает обе границы. При смешивании AND и OR используйте скобки для ясности.

В учебных классификациях SELECT иногда выделяют в DQL, а INSERT/UPDATE/DELETE называют DML. Для требования уровня нужно уметь работать со всеми четырьмя; терминология не меняет их назначения.

## 4. INSERT, UPDATE, DELETE

```sql
INSERT INTO customers (id, name, city)
VALUES (4, 'Dima', 'Kazan');

UPDATE customers
SET city = 'Moscow'
WHERE id = 4;

DELETE FROM customers
WHERE id = 4;
```

INSERT создаёт строки; перечисление колонок делает присваивание значений явным. UPDATE изменяет все строки, подходящие под WHERE. DELETE удаляет строки, но не таблицу.

**UPDATE/DELETE без WHERE затронет все строки.** Перед изменением полезно проверить соответствующий SELECT с тем же условием; при реальной конкурентной работе это не заменяет транзакцию и ограничения.

Нельзя удалить родителя, если существующие внешние ключи запрещают это действие. Возможны правила ON DELETE CASCADE/SET NULL и другие — поведение выбирают при проектировании.

Для группы изменений используют транзакцию:

```sql
BEGIN;
UPDATE orders SET status = 'paid' WHERE id = 103;
SELECT id, status FROM orders WHERE id = 103;
ROLLBACK;
```

ROLLBACK отменяет эти изменения, COMMIT фиксирует. Поддержка транзакционности отдельных DDL и поведения ошибок зависит от СУБД. Внешний вызов сети сам по себе не откатится вместе с SQL.

DDL-команды CREATE/ALTER/DROP меняют структуру, DML — данные. DELETE удаляет строки, DROP TABLE удаляет объект таблицы; TRUNCATE — отдельная массовая операция с зависящими от СУБД правилами, а не простой синоним DELETE.

Основа: [PostgreSQL Data Manipulation](https://www.postgresql.org/docs/18/dml.html).

## 5. NULL и трёхзначная логика

NULL — отсутствие/неизвестность значения, а не ноль и не пустая строка. Обычное сравнение с NULL даёт UNKNOWN; WHERE оставляет только строки, где условие TRUE.

```sql
SELECT id FROM orders WHERE customer_id IS NULL;
SELECT id FROM orders WHERE customer_id IS NOT NULL;
```

`customer_id = NULL` и `customer_id <> NULL` не заменяют эти условия. COALESCE выбирает первое не-NULL значение: `COALESCE(discount_cents, 0)`. Подставлять 0 следует только если это нужный смысл: «скидка неизвестна» и «скидка точно нулевая» могут различаться.

## 6. Основные агрегатные функции

Агрегат сворачивает набор значений в результат.

| Выражение | Назначение |
|---|---|
| `COUNT(*)` | Количество строк |
| `COUNT(column)` | Количество не-NULL значений колонки |
| `COUNT(DISTINCT column)` | Количество разных не-NULL значений |
| `SUM(column)` | Сумма не-NULL значений |
| `AVG(column)` | Среднее по не-NULL значениям |
| `MIN(column)` / `MAX(column)` | Минимальное / максимальное не-NULL значение |

```sql
SELECT COUNT(*) AS order_count,
       COUNT(discount_cents) AS known_discounts,
       SUM(amount_cents) AS total_cents,
       AVG(discount_cents) AS average_known_discount
FROM orders;
```

Результат: 5 заказов, 2 известных скидки, сумма 48000 копеек, средняя известная скидка 250. Нулевое значение скидки учитывается, NULL — нет. Для «среднего по всем заказам, считая неизвестную скидку нулевой» понадобилось бы другое выражение и другое бизнес-допущение.

```sql
SELECT MIN(amount_cents) AS minimum_cents, MAX(amount_cents) AS maximum_cents
FROM orders;
```

Минимальная сумма — 3000, максимальная — 20000. MIN/MAX возвращают значения, а не всю строку заказа; для выбора соответствующей строки нужен запрос с сортировкой/фильтрацией или другой подход.

На пустом наборе без GROUP BY COUNT возвращает 0, SUM/AVG/MIN/MAX — NULL. Поэтому часто используют COALESCE(SUM(...), 0). При GROUP BY отсутствие строк может означать отсутствие групп и строк результата вообще.

## 7. GROUP BY, WHERE и HAVING

```sql
SELECT customer_id,
       COUNT(*) AS paid_orders,
       SUM(amount_cents) AS paid_cents
FROM orders
WHERE status = 'paid' AND customer_id IS NOT NULL
GROUP BY customer_id
HAVING SUM(amount_cents) >= 20000
ORDER BY paid_cents DESC, customer_id;
```

WHERE сначала оставляет оплаченные заказы известных клиентов. GROUP BY объединяет строки по клиенту. Агрегаты вычисляются по группе, HAVING оставляет группы с суммой не меньше 20000. Anna и Boris проходят условие.

Все выбранные неагрегированные колонки в переносимом запросе явно включают в GROUP BY. СУБД могут поддерживать исключения по функциональным зависимостям или разрешать неоднозначные выражения; не стройте базовое понимание на таких послаблениях.

Полезная логическая модель SELECT: **FROM/JOIN → WHERE → GROUP BY/агрегаты → HAVING → оконные вычисления → SELECT/DISTINCT → ORDER BY → LIMIT**. Это модель семантики, а не физический порядок выполнения: оптимизатор может менять план, сохраняя результат.

Справочник: [Aggregate Functions](https://www.postgresql.org/docs/18/functions-aggregate.html).

## 8. Виды JOIN

JOIN строит строки из сочетаний двух источников по условию. Совпадение может быть не только равенством, но и другим предикатом.

| Вид | Результат |
|---|---|
| INNER JOIN | Только совпавшие пары |
| LEFT [OUTER] JOIN | Все строки слева; для отсутствующей правой части — NULL |
| RIGHT [OUTER] JOIN | Все строки справа; для отсутствующей левой части — NULL |
| FULL [OUTER] JOIN | Совпадения и несовпавшие строки обеих сторон |
| CROSS JOIN | Декартово произведение: каждая левая строка с каждой правой |

На учебных данных:

- INNER customers ↔ orders: 4 строки совпадений.
- LEFT от customers: 5 строк, включая Vera с NULL справа.
- RIGHT с orders справа: 5 строк, включая гостевой заказ 301.
- FULL: 6 строк, включая и Vera, и гостевой заказ.
- CROSS: 3 × 5 = 15 строк.

```sql
SELECT c.name, o.id AS order_id
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
ORDER BY c.id, o.id;
```

**Self join** — та же таблица в двух ролях с разными alias, а не отдельный физический алгоритм:

```sql
SELECT c.name, referrer.name AS referred_by
FROM customers AS c
LEFT JOIN customers AS referrer ON referrer.id = c.referrer_id
ORDER BY c.id;
```

Semi join возвращает строки слева при наличии совпадения, обычно выражается EXISTS. Anti join — при отсутствии, обычно NOT EXISTS. Это не обязательно отдельные ключевые слова синтаксиса вашей СУБД.

## 9. Частые ошибки JOIN

### WHERE после LEFT JOIN

```sql
-- Сохранит клиентов без оплаченных заказов.
SELECT c.name, o.id
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id AND o.status = 'paid';

-- Отбросит NULL-строки справа и не сохранит Vera.
SELECT c.name, o.id
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
WHERE o.status = 'paid';
```

ON определяет совпадения, WHERE фильтрует уже полученные строки. Эти запросы имеют разную семантику.

### COUNT после LEFT JOIN

У клиента без заказа `COUNT(*)` посчитает одну добавленную NULL-строку; `COUNT(o.id)` даст 0. Если цель — число заказов, считайте не-NULL PK заказа.

### Размножение строк

Один клиент с тремя заказами появляется в трёх строках JOIN — это нормальный результат. Если присоединить ещё одну независимую коллекцию, например три заказа и две метки клиента, можно получить шесть строк и завысить сумму заказов. Решения: агрегировать нужную сторону до соединения или выразить проверку существования через EXISTS.

SUM(DISTINCT amount) не универсальное исправление: два разных заказа по 10000 — это 20000, а SUM(DISTINCT) даст 10000.

### NOT IN и NULL

```sql
SELECT c.name
FROM customers AS c
WHERE NOT EXISTS (
    SELECT 1 FROM orders AS o WHERE o.customer_id = c.id
);
```

Это возвращает Vera. Вариант `c.id NOT IN (SELECT customer_id FROM orders)` на этих данных не вернёт никого: подзапрос содержит NULL гостевого заказа, что влияет на логическое значение NOT IN.

Основная семантика: [Table Expressions и JOIN](https://www.postgresql.org/docs/18/queries-table-expressions.html).

## 10. Представления, процедуры и триггеры

**Обычный VIEW** сохраняет описание запроса, а не автоматически кэш его результата:

```sql
CREATE VIEW paid_orders AS
SELECT id, customer_id, amount_cents
FROM orders
WHERE status = 'paid';
```

Затем можно писать SELECT ... FROM paid_orders. Представление упрощает доступ к данным и может быть частью модели доступа при правильно настроенных правах. Не любое представление обновляемо; поддержка зависит от формы запроса и СУБД. В SQLite для записи через view нужны соответствующие INSTEAD OF-триггеры. Материализованный view хранит результат и нуждается в обновлении. [PostgreSQL CREATE VIEW](https://www.postgresql.org/docs/18/sql-createview.html).

**Процедура** вызывается приложением явно, например CALL transfer_money(...). Удобна для составной серверной операции. **Функция** обычно вызывается в выражении; конкретные возможности функций/процедур зависят от СУБД.

**Триггер** автоматически запускается на настроенное событие. Типичные задачи: аудит изменений, обслуживание производных данных или нестандартного правила. BEFORE — перед изменением, AFTER — после операции над строкой/оператором, INSTEAD OF — вместо стандартного действия, обычно для view. AFTER не означает «после commit».

В PostgreSQL триггер вызывает функцию, возвращающую trigger; это не обычная процедура с CALL. В SQLite тело задаётся прямо в CREATE TRIGGER. Достоинства, риски и конкретные примеры — в уровне 2.
