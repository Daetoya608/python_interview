# SQL — уровень 2: процедуры, триггеры, окна и nested loop

**Обязательно:** понимать преимущества, недостатки и границы применения хранимых процедур и триггеров. **Желательно:** оконные функции и алгоритм nested loop join. Примеры процедур относятся к PostgreSQL, а автономная практика остальных тем выполняется на SQLite.

## 1. Процедура, функция и триггер

| Механизм | Кто запускает | Типичный контракт |
|---|---|---|
| Хранимая процедура | Явный вызов клиента, в PostgreSQL — CALL | Выполнить составную операцию с параметрами |
| Функция | Вызов в выражении/запросе или серверном коде | Вернуть значение/набор данных; дополнительные возможности зависят от СУБД |
| Триггер | БД автоматически по событию | Обработать изменение строки/оператора или другое настроенное событие |

В PostgreSQL процедура объявляется CREATE PROCEDURE и не имеет обычного RETURNS значения функции; данные можно передавать выходными параметрами. Функция объявляется CREATE FUNCTION. Триггер вызывает специальную **функцию** RETURNS trigger, а не обычную CALL-процедуру.

Возможность управлять COMMIT/ROLLBACK внутри процедур зависит от контекста вызова и СУБД. В PostgreSQL это разрешено лишь в подходящих условиях; процедура, вызванная внутри явного BEGIN, не может произвольно завершить эту внешнюю транзакцию. Пример в practice не выполняет внутренних commit.

Источники: [PostgreSQL Procedures](https://www.postgresql.org/docs/18/xproc.html), [Trigger Behavior](https://www.postgresql.org/docs/18/trigger-definition.html).

## 2. Хранимые процедуры: преимущества

- **Меньше сетевых обменов.** Составную операцию можно вызвать один раз, вместо пересылки данных клиенту для множества промежуточных действий.
- **Обработка рядом с данными.** Массовое изменение можно выразить SQL на сервере без загрузки всех строк в приложение.
- **Общий серверный интерфейс.** Несколько приложений могут вызывать одну реализацию операции.
- **Контролируемый доступ.** Можно предоставить доступ к конкретной операции вместо свободного изменения таблиц, если правильно настроить права и режим выполнения.
- **Удобная граница операции.** Серверный код может объединить проверки и изменения в существующей транзакции.

Например, перевод между счетами должен проверить сумму и счета, уменьшить один баланс, увеличить второй и сохранить согласованность. Процедура может дать этому явный именованный интерфейс.

## 3. Хранимые процедуры: недостатки и ограничения

- **Зависимость от СУБД.** PL/pgSQL, T-SQL и другие языки/модели отличаются; переносимость ниже, чем у простой прикладной логики.
- **Версионирование и развёртывание.** Код БД нужно менять миграциями и согласовывать с версиями клиентов.
- **Тестирование и диагностика.** Для значимой проверки требуется настоящая БД с нужной схемой, данными и правами; обычного Python unit-теста недостаточно.
- **Нагрузка на БД.** Ресурсы сервера ограничены. Тяжёлые вычисления и построчные циклы могут ухудшить систему, а масштабировать БД сложнее, чем stateless-приложения.
- **Скрытая связанность.** Если логика распределена между приложением, процедурами и триггерами без явных границ, становится сложнее понять полный путь операции.
- **Риски прав и динамического SQL.** Серверное размещение кода само по себе не делает его безопасным.

Процедура **не гарантирует ускорение** только потому, что хранится в БД. Сравнивают планы, число обменов, блокировки и реальную нагрузку. Одна массовая SQL-команда нередко лучше цикла с тысячей UPDATE внутри процедуры.

Не следует считать, что вызов процедуры автоматически решает все гонки. Проверка «баланса хватает» отдельно от изменения может быть небезопасна при конкурентном доступе: нужны подходящие блокировки, условные изменения и ограничения.

## 4. Триггеры: применение и цена

Триггер запускается независимо от того, записывает данные ORM, SQL-консоль или другое приложение. Это полезно для локальных правил и связанных записей, которые должны обслуживаться на стороне БД.

| Преимущество | Соответствующий риск |
|---|---|
| Автоматический аудит изменений | У простого UPDATE появляются неочевидные дополнительные записи |
| Единое поведение для всех писателей | При чтении только кода приложения часть логики не видна |
| Согласованное обновление производных данных | Увеличивается работа, время транзакции и число блокировок |
| Проверки нестандартных правил | Самописная проверка может ошибаться при конкурентных изменениях |

Возможные проблемы: цепочки триггеров, рекурсия, неожиданный порядок побочных действий, массовое изменение с тысячами row-trigger вызовов, сложная отладка и расхождение версий схемы между средами.

Сначала используйте декларативные ограничения **NOT NULL, CHECK, UNIQUE, FK**, если они выражают правило. Триггер не должен заменять UNIQUE через «SELECT, а если записи нет — разрешить»: два конкурентных процесса могут одновременно не увидеть строку.

Для триггерной логики нужны тесты массовых изменений, граничных случаев, отката и конкурентности. Триггер, реализующий межстрочное правило, не становится автоматически защищённым от гонок.

## 5. Когда срабатывает триггер

В PostgreSQL:

- **BEFORE** — до операции над строкой/оператором; row-trigger может скорректировать NEW или пропустить строку по своим правилам.
- **AFTER** — после обработки изменения, но обычно **внутри той же транзакции**. Это не событие успешного commit.
- **INSTEAD OF** — вместо стандартного изменения, например для представления.
- **FOR EACH ROW** — для каждой затронутой строки.
- **FOR EACH STATEMENT** — для оператора целиком, в том числе когда он не изменил ни одной строки.

NEW содержит новую строку для INSERT/UPDATE, OLD — прежнюю для UPDATE/DELETE в row-trigger. У statement-trigger нет одной общей NEW/OLD-строки. Дополнительные возможности, включая отложенные constraint triggers, зависят от СУБД.

SQLite поддерживает row-триггеры, но не FOR EACH STATEMENT. Синтаксис их тела отличается от PostgreSQL: здесь SQL записывается прямо в BEGIN ... END триггера. [SQLite CREATE TRIGGER](https://www.sqlite.org/lang_createtrigger.html).

### Пример аудита статуса в SQLite

После создания схемы из schema.sqlite.sql:

```sql
CREATE TRIGGER audit_order_status
AFTER UPDATE OF status ON orders
FOR EACH ROW
WHEN OLD.status <> NEW.status
BEGIN
    INSERT INTO order_status_history (order_id, old_status, new_status)
    VALUES (OLD.id, OLD.status, NEW.status);
END;
```

В учебной схеме status — NOT NULL, поэтому сравнение <> подходит. Для nullable-колонок нужен корректный NULL-aware предикат: например, IS DISTINCT FROM в PostgreSQL, а не обычное <> без дополнительных условий.

`05_triggers.sql` изменяет заказ, видит историю, затем выполняет ROLLBACK. После отката и статус, и история возвращаются в прежнее состояние.

Аудит внутри той же транзакции **не хранит откатившиеся попытки**. Отправленное из триггера внешнее письмо/HTTP-событие не откатится как SQL-строка. Для надёжной связи с внешними системами нужен отдельный продуманный механизм, например запись события в транзакционный outbox и отправка после фиксации.

## 6. Пример процедуры и триггера в PostgreSQL

`practice/postgres_procedures.sql` — самостоятельный сценарий: временные счета, процедура перевода, триггер аудита и проверка результатов. Он начинает транзакцию и заканчивает её ROLLBACK, не оставляя созданные им объекты и данные.

Основная часть перевода:

```sql
UPDATE accounts
SET balance_cents = balance_cents - p_amount
WHERE id = p_from AND balance_cents >= p_amount;
```

Внутри PL/pgSQL после изменения проверяется FOUND: ноль изменённых строк означает отсутствующий исходный счёт или нехватку денег. Затем пополняется получатель; при его отсутствии выбрасывается исключение. Ошибка не проглатывается, чтобы не зафиксировать половину перевода.

Перед изменениями обе существующие строки блокируются через SELECT ... FOR UPDATE в стабильном порядке id. Это снижает риск взаимных блокировок при встречных переводах, но не означает отсутствия всех возможных конфликтов в более сложном приложении.

Триггерная функция получает OLD/NEW и записывает аудит. После `CALL pg_temp.transfer_money(1, 2, 1500)` ожидаются остатки 8500 и 3500 копеек и две строки истории. Всё остаётся в текущей транзакции до решения вызывающего кода.

Пример запуска при наличии PostgreSQL и psql:

```console
psql -X -v ON_ERROR_STOP=1 -d "postgresql://USER@HOST/DBNAME" -f db-sql/practice/postgres_procedures.sql
```

Подставьте параметры учебной БД. Здесь PostgreSQL-сценарий приведён для изучения; в данной рабочей среде сервер и клиент PostgreSQL отсутствуют, поэтому **он не проверялся выполнением**. SQLite-runner его не исполняет.

Основы синтаксиса: [CREATE PROCEDURE](https://www.postgresql.org/docs/18/sql-createprocedure.html), [PL/pgSQL Trigger Functions](https://www.postgresql.org/docs/18/plpgsql-trigger.html).

## 7. Как выбрать место для логики

| Задача | Что рассмотреть первым |
|---|---|
| Обязательное значение / уникальность / допустимая ссылка | Ограничение БД |
| Повторяемое сложное чтение | View или обычный запрос |
| Явная составная операция над данными для нескольких клиентов | Процедура при оправданной архитектуре |
| Автоматический локальный аудит каждого изменения | Триггер |
| Работа с сетью, UI и внешними API | Прикладной слой с согласованной моделью событий |

Граница не определяется лозунгом «всё в БД» или «всё в приложении». Важно, кто записывает данные, где требуется гарантия, как менять и тестировать код, кто несёт нагрузку и как наблюдать ошибки.

## 8. Оконные функции — желательная тема

Оконная функция вычисляет значение по связанным строкам, **сохраняя строки текущей выборки**. GROUP BY обычно сворачивает строки группы в одну, а окно добавляет результат к каждой строке.

```sql
SELECT id, customer_id, amount_cents,
       SUM(amount_cents) OVER (PARTITION BY customer_id) AS customer_total
FROM orders
WHERE status = 'paid' AND customer_id IS NOT NULL
ORDER BY customer_id, id;
```

У каждого из двух оплаченных заказов Anna будет своя строка с общей суммой 20000. Окно работает уже над строками после WHERE, поэтому отменённый заказ не участвует.

Состав OVER:

- **PARTITION BY** делит выборку на независимые разделы; без него раздел — вся доступная окну выборка.
- **ORDER BY** внутри OVER задаёт порядок для оконного расчёта, а не окончательный порядок результата.
- **Frame** задаёт, какие строки раздела относительно текущей участвуют в frame-зависимом вычислении.

### Нумерация и ранги

| Функция | Смысл | Для сумм 10000, 10000, 5000 по убыванию |
|---|---|---|
| ROW_NUMBER | Уникальный порядковый номер строки | 1, 2, 3 |
| RANK | Одинаковый ранг равным значениям, затем пропуск | 1, 1, 3 |
| DENSE_RANK | Одинаковый ранг без пропусков | 1, 1, 2 |

Для ROW_NUMBER при равных суммах добавляют стабильный id в ORDER BY. Для ранжирования именно по сумме добавление уникального id **изменит понятие равенства** и уберёт связанные ранги: используйте отдельные спецификации окна по смыслу.

### Накопительная сумма и предыдущая строка

```sql
SELECT id, customer_id, amount_cents,
       SUM(amount_cents) OVER (
           PARTITION BY customer_id
           ORDER BY created_at, id
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total,
       LAG(amount_cents) OVER (
           PARTITION BY customer_id ORDER BY created_at, id
       ) AS previous_amount
FROM orders
WHERE status = 'paid' AND customer_id IS NOT NULL
ORDER BY customer_id, created_at, id;
```

LAG читает значение предыдущей строки, LEAD — следующей; на отсутствующей строке по умолчанию получается NULL. Это удобно для изменений между событиями, а не только для сумм.

ROWS задаёт рамку в терминах позиций строк. RANGE связано со значениями сортировки и группами равных строк. При ORDER BY стандартная default-рамка многих агрегатов заканчивается текущей группой равных значений; это может отличаться от ожидаемого «ровно до текущей строки». Для накопления явно задавайте рамку и стабильный порядок.

Если нужен итог всего раздела, `SUM(...) OVER (PARTITION BY ...)` без оконного ORDER BY не превращается в накопительную сумму. Для LAST_VALUE default-рамка часто даёт значение текущей строки/группы, а не последней строки всего раздела; при таком намерении нужна рамка до UNBOUNDED FOLLOWING.

### Топ-1 в каждой группе

```sql
WITH ranked AS (
    SELECT id, customer_id, amount_cents,
           ROW_NUMBER() OVER (
               PARTITION BY customer_id ORDER BY amount_cents DESC, id
           ) AS rn
    FROM orders
    WHERE status = 'paid' AND customer_id IS NOT NULL
)
SELECT id, customer_id, amount_cents
FROM ranked
WHERE rn = 1
ORDER BY customer_id;
```

Оконный результат нельзя отфильтровать в WHERE того же уровня запроса в PostgreSQL/SQLite: используйте внешний SELECT/CTE. Для «все заказы, разделившие первое место» подходит RANK = 1, а для одного выбранного заказа — ROW_NUMBER = 1 с определённым порядком.

Источники: [Window Functions Tutorial](https://www.postgresql.org/docs/18/tutorial-window.html), [Window Functions Reference](https://www.postgresql.org/docs/18/functions-window.html).

## 9. Nested loop join — желательная тема

JOIN в SQL задаёт **логический результат**, а nested loop, hash join и merge join — **физические способы его получить**. INNER/LEFT не являются альтернативами nested loop: например, INNER JOIN может быть выполнен nested loop.

Идея алгоритма:

```text
для каждой строки outer:
    найти подходящие строки inner
    выдать сочетания, удовлетворяющие условию соединения
```

Для LEFT JOIN дополнительно нужно выдать строку outer с NULL справа, если совпадений нет. Конкретная реализация может использовать индексы, материализацию и другие оптимизации.

**Простой вариант без полезного доступа:** M строк внешнего источника и полный проход N строк внутреннего для каждой — до M × N проверок.

**Index nested loop:** для каждой внешней строки выполняется короткий поиск во внутреннем индексе. Если после фильтра внешних строк мало, это может быть выгоднее построения большой хеш-таблицы или сортировки.

Хороший кандидат: один клиент по PK и его заказы по индексу customer_id. Плохой кандидат: большой внешний набор и повторяющийся полный проход большой внутренней таблицы. Однако нельзя объявить алгоритм плохим по одному имени: учитываются реальный объём, селективность, стоимость доступа и число совпадений.

Внутренний/внешний источник плана не обязательно совпадает с порядком таблиц в тексте INNER JOIN: оптимизатор может переставить их, если это сохраняет результат. Для внешних JOIN свобода перестановки ограничена семантикой.

## 10. План запроса и диагностика

PostgreSQL:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT c.name, o.id
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.id
WHERE c.id = 1;
```

Это пример для БД с аналогичными таблицами и индексами. EXPLAIN показывает план; **ANALYZE действительно выполняет запрос**, в том числе изменения, если анализируется UPDATE/DELETE. Для экспериментов используют подходящую учебную среду и осознанную транзакцию.

В плане смотрят:

- Оценённые и реальные количества строк: сильное расхождение ведёт к плохому выбору алгоритма.
- `loops` внутреннего узла: сколько раз его повторили. Реальные rows/time часто показываются в среднем на проход; большое число loops может умножить общую работу.
- Index Scan / Seq Scan и условия доступа.
- Удалённые фильтром строки и обращения к буферам.

Оценка cost — условная стоимость оптимизатора, не миллисекунды. Планы зависят от данных, статистики, настроек и версии СУБД. Наличие индекса не гарантирует его использование и не гарантирует лучший план.

В SQLite используют другой интерфейс:

```sql
EXPLAIN QUERY PLAN
SELECT c.name, o.id
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.id
WHERE c.id = 1;
```

`06_explain.sql` показывает вложенные поиски по customers PK и индексу orders.customer_id в учебной среде. SQLite реализует соединения вложенными сканированиями; формат вывода не следует принимать за стабильный контракт для приложения или за PostgreSQL-план.

Источники: [PostgreSQL EXPLAIN](https://www.postgresql.org/docs/18/using-explain.html), [SQLite EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html).
