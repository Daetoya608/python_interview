# CI/CD: граф проверок и продвижение артефакта

Цель процесса — связать конкретное изменение с проверенным артефактом и управляемым выпуском. Термины/синтаксис — [КОНСПЕКТ.md](КОНСПЕКТ.md), пример — [practice/workflow.yml](practice/workflow.yml). Пример учебный: сам по себе он не является активным workflow репозитория.

## 1. CI, delivery и deployment

Continuous Integration — частое объединение небольших изменений с автоматической проверкой совместимости. Редко запускаемый тестовый сервер не решает проблему долгоживущих расходящихся веток.

Continuous Delivery поддерживает проверенное состояние, готовое к выпуску; финальное решение о production может оставаться ручным. Continuous Deployment автоматически выпускает прошедшие условия изменения. Эти понятия различаются границей автоматизации, а не просто наличием YAML.

Pipeline не доказывает отсутствие ошибок. Он делает определённые проверки воспроизводимыми и не позволяет молча пропустить известные условия. Выбор проверок должен соответствовать рискам продукта.

## 2. Событие, workflow, job, step и runner

| Сущность | Роль |
|---|---|
| Event/trigger | Причина запуска: push, PR, tag, ручное действие |
| Workflow/pipeline | Описание автоматизированного процесса |
| Job | Набор шагов в выделенной среде исполнения |
| Step | Команда или повторно используемое действие |
| Runner | Машина/агент, реально исполняющий job |
| Artifact | Сохранённый результат для следующих стадий/пользователей |

В GitHub Actions шаги одной job обычно используют общую среду и рабочие файлы. Разные jobs обычно изолированы: нужные файлы передают артефактами, значения — outputs или другим явным механизмом. Self-hosted runner требует отдельной дисциплины очистки и изоляции.

Matrix разворачивает несколько вариантов одной job, например разные версии Python. Это проверка совместимости разных сред, а не автоматическое распараллеливание тела одного теста.

## 3. Pipeline — ориентированный граф

```text
checkout → быстрые проверки → unit tests → build
                         ↘ integration ──┘
→ проверка артефакта → staging → условия выпуска → production
```

Зависимости задают, какая работа требует успешного результата другой. Независимые проверки можно выполнять параллельно. Длинный последовательный pipeline замедляет обратную связь; чрезмерная параллельность расходует ресурсы и может перегружать общую тестовую БД.

Ошибка должна завершать соответствующий шаг ненулевым кодом и блокировать зависимое продвижение. «Тесты напечатали красный текст» не помогает, если shell скрыл exit code или шаг объявлен необязательным. Всегда выполняемые шаги подходят для cleanup и отчётов, но не должны случайно выпускать неуспешный build.

## 4. Artifact и cache имеют разные гарантии

Artifact — результат работы конкретного запуска: wheel, образ, отчёт. Cache — необязательный ускоритель повторного получения зависимостей/сборки. Отсутствие кэша должно ухудшать скорость, а не правильность.

Ключ кэша должен учитывать существенные входы: ОС, версию среды, lock-файл, иногда настройки сборки. Слишком широкий ключ создаёт несовместимое или устаревшее состояние. Кэш нельзя автоматически считать доверенным источником production-артефакта.

Принцип продвижения: один раз собрать → проверить этот результат → выпустить его же. Если после тестов заново собрать «то же самое» из плавающих зависимостей, в production может попасть другой код. Версия, commit SHA и digest помогают связать артефакт с проверками.

## 5. Воспроизводимость и среды

«У меня проходит» часто означает скрытый вход: незакоммиченный файл, глобальная библиотека, timezone, переменная окружения, другая версия Python или системного пакета. CI проявляет эти зависимости, потому что начинает с другой среды.

Для воспроизводимости описывают версии инструментов, зависимости, команды и конфигурацию. Lock-файл ограничивает Python-зависимости, но не фиксирует автоматически ОС, внешние API и время. Тестовые данные и миграции тоже должны быть управляемыми входами.

Одинаковые команды локально и в CI уменьшают расхождение. Важнее один понятный способ проверить проект, чем два независимых набора действий, которые постепенно расходятся.

## 6. Граница доверия: код PR может исполняться

Workflow запускает код, а не просто читает diff. Зависимость сборки, setup-скрипт или тест из чужого fork способны выполнить произвольную команду в пределах runner. Поэтому для PR из forks ограничивают secrets и права токенов.

Опасный сценарий — привилегированный workflow получает секреты и затем checkout/исполняет недоверенный head. Понимание события и источника кода здесь важнее названия шага. Подстановка пользовательского текста непосредственно в shell тоже превращает данные в код.

Секреты хранят в предназначенном хранилище и предоставляют только нужным стадиям. Маскирование логов не делает безопасным вывод преобразованных значений или включение токена в артефакт. Краткоживущие удостоверения/OIDC уменьшают необходимость хранить постоянный ключ там, где интеграция это поддерживает.

## 7. Deployment — переход работающей системы

Успешное копирование файлов не означает успешный выпуск. Нужно выбрать версию, обновить процессы, проверить готовность, направить трафик и убедиться, что бизнес-сценарии работают.

| Стратегия | Как происходит переход | Главное ограничение |
|---|---|---|
| Rolling | Экземпляры заменяются по частям | Старый и новый код работают одновременно |
| Blue-green | Два окружения, переключение трафика | Цена второй среды и совместимость общих данных |
| Canary | Новая версия получает часть трафика | Нужны метрики и условия остановки/расширения |

Healthcheck проверяет готовность компонента, но одной проверки порта недостаточно для успеха продукта. Нужны наблюдения ошибок, задержек и критичных результатов. Откат версии полезен, только если старая версия понимает актуальные данные и схему.

## 8. Миграции, конкуренция и откат

Если новая версия требует колонку, её добавляют до использования. Если старая ещё работает, колонку/старый формат нельзя удалять слишком рано. Expand → migrate → contract помогает обеспечить совместимость версий.

Две параллельные выкладки способны переставить версии или одновременно выполнить миграцию. Concurrency-группы, блокировки выпуска и отдельный владелец миграций задают порядок. Отмена старого запуска не должна оставлять незавершённую операцию без контроля.

Rollback кода не отменяет отправленные сообщения, внешние действия и уничтоженные данные. Иногда безопаснее roll-forward с исправлением. План восстановления проверяют заранее: где прежний артефакт, как переключить трафик и как установить, что система восстановилась.

## 9. Как обсуждать свой pipeline

Нужно уметь назвать конкретный trigger, источник кода, обязательные проверки, среду runner, создаваемый артефакт, условия публикации и процедуру отката. Если этих сведений нет в репозитории, их нельзя выдумывать из типового workflow.

Полезные измерения: время до первого полезного отказа, полная длительность, доля flaky-сбоев, очередь runner и частота неудачных выпусков. Ускорение кэшем не должно скрывать ненадёжные проверки.
