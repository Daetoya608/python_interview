# Типизация Python — уровень 1

Динамическая и статическая типизация, базовые аннотации, None и запуск mypy. Основные примеры рассчитаны на **Python 3.11+**. Различия синтаксиса версий отмечены отдельно.

## 1. Динамическая и статическая типизация

**Динамическая типизация:** у объектов есть типы во время выполнения; имя переменной может быть привязано к разным объектам. Допустимость операции в конечном счёте проверяется при её выполнении.

```python
value = 10
value = "ten"  # Интерпретатор допускает новую привязку имени.
```

**Статическая проверка типов:** инструмент анализирует программу до выполнения и ищет операции, несовместимые с объявленными или выведенными типами. Например, mypy может запретить такое переприсваивание, если вывел для value тип int.

Аннотации не превращают Python в другой язык: он продолжает выполнять динамические операции. Python поддерживает **постепенную типизацию** — типизированные и нетипизированные части можно сочетать и постепенно расширять проверку.

Главные задачи аннотаций: описывать контракт, раньше находить несовместимые вызовы и возвращаемые значения, улучшать навигацию и рефакторинг. Они не гарантируют корректность алгоритма и не заменяют тесты.

Основа подхода — [PEP 484](https://peps.python.org/pep-0484/); вводная практика — [документация mypy](https://mypy.readthedocs.io/en/stable/getting_started.html).

## 2. Аннотации сами не проверяют данные

```python
def double(value: int) -> int:
    return value * 2
```

Для mypy допустим `double(3)`, а `double("x")` — ошибка аргумента. Но при обычном выполнении Python второй вызов вернёт строку `"xx"`: функция не содержит runtime-проверки и операция умножения строки допустима.

Аннотация не выполняет автоматическое преобразование: `value: int = "123"` не вызывает int("123"). Для преобразования и проверки входа нужен явный код или соответствующая библиотека.

Даже значение правильного типа может нарушать бизнес-правило: отрицательный возраст всё ещё int. Проверка диапазонов, прав доступа и внешних данных остаётся отдельной задачей. [typing: назначение аннотаций](https://docs.python.org/3/library/typing.html).

## 3. Базовые типы и переменные

```python
age: int = 24
name: str = "Anna"
price: float = 19.5
active: bool = True
names: list[str] = ["Anna", "Boris"]
ages: dict[str, int] = {"Anna": 24, "Boris": 30}
```

Двоеточие вводит аннотацию, `=` присваивает значение. Аннотация без присваивания сама не создаёт готового значения для чтения:

```python
score: int
score = 10
```

Mypy умеет выводить тип из значения: `count = 0` обычно получает int без явного `: int`. Для пустых коллекций и сложных контрактов явная аннотация особенно полезна:

```python
results: list[int] = []
results.append(10)
```

`list` говорит о контейнере без уточнения элементов. `list[int]` задаёт, что элементы должны быть int. Аналогично dict[str, int] задаёт тип ключей и значений. В strict-режиме mypy требует параметры для многих обобщённых типов, иначе в проверку может попасть Any.

Не нужно аннотировать каждую очевидную временную переменную. Важнее правильно описать границы функций и места, где вывод типа неоднозначен. [Вывод типов mypy](https://mypy.readthedocs.io/en/stable/type_inference_and_annotations.html).

## 4. Параметры и возвращаемое значение

```python
def greet(name: str, repeats: int = 1) -> str:
    if repeats < 1:
        raise ValueError("repeats must be positive")
    return " ".join([f"Hello, {name}!"] * repeats)

def print_message(message: str) -> None:
    print(message)
```

`name: str` — тип аргумента, `-> str` — результат. Значение по умолчанию должно быть совместимо с типом параметра. `-> None` означает отсутствие полезного результата, а не запрет побочных эффектов.

Функция без явного return возвращает None. Если по одной ветке возвращается str, а по другой выполнение доходит до конца, аннотация `-> str` не соответствует всем путям: нужно обработать ветку, выбросить исключение или допустить None по контракту.

Сигнатура не описывает все ограничения: `repeats: int` не означает положительное число; это проверяет if в примере.

## 5. Optional и значение None

`Optional[T]` означает **T или None**. С Python 3.10 это можно записывать как `T | None`.

```python
from typing import Optional

old_style: Optional[str] = None
modern_style: str | None = None
```

По смыслу типы равнозначны. Optional **не означает**, что аргумент функции можно не передавать:

```python
def required_name(name: str | None) -> str:
    return "Anonymous" if name is None else name

def optional_argument(name: str | None = None) -> str:
    return "Anonymous" if name is None else name
```

Первую функцию нужно вызвать с аргументом, хотя допустим required_name(None). Вторую можно вызвать без аргумента благодаря `= None`. И наоборот, default вроде `name: str = "Guest"` делает аргумент необязательным для вызова, но не разрешает передавать None.

Типичный источник None — поиск отсутствующего элемента:

```python
def find_name(users: dict[int, str], user_id: int) -> str | None:
    return users.get(user_id)
```

## 6. Сужение типа после проверки

Перед операцией, которой нужен str, нужно исключить None:

```python
def display_name(name: str | None) -> str:
    if name is None:
        return "Anonymous"
    return name.upper()
```

После раннего return анализатор знает: на последней строке name — str. Это **type narrowing**, сужение возможных типов по потоку управления.

`if name:` исключает не только None, но и пустую строку. Если пустая строка допустима и отличается от отсутствующего значения, выбирают `is None` / `is not None`.

Не скрывайте возможный None через Any или безусловный type: ignore. Сначала решите, какое поведение требуется при отсутствии значения. `assert name is not None` тоже сужает тип, но обязательную проверку внешнего ввода надёжнее выразить явным if и осмысленной ошибкой. [Type narrowing](https://mypy.readthedocs.io/en/stable/type_narrowing.html).

## 7. Установка и запуск mypy

Из корня репозитория, PowerShell:

```powershell
cd py-typing/practice
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m mypy
.\.venv\Scripts\python.exe demo.py
```

Unix/macOS: `python3 -m venv .venv`, затем `.venv/bin/python -m pip ...`, `.venv/bin/python -m mypy` и `.venv/bin/python demo.py`.

Далее `python` означает интерпретатор этого окружения. Mypy **анализирует код, не запускает его**. `python demo.py` выполняет программу; это другая проверка.

Конфигурация практики:

```toml
[tool.mypy]
python_version = "3.11"
strict = true
show_error_codes = true
warn_unreachable = true
files = ["typed_examples.py", "demo.py"]
```

Обычный `python -m mypy` из practice проверяет два корректных файла. strict включает набор дополнительных правил; состав зависит от версии mypy. Это не запрет абсолютно всех путей появления Any и не доказательство правильности программы.

Файл `bad_examples.py` содержит **намеренные ошибки** и проверяется отдельно:

```console
python -m mypy bad_examples.py
```

Этот запуск должен завершиться с ненулевым кодом и диагностикой: строка вместо int, неверный элемент списка, обращение к None, неверный callback и другие случаи. Это ожидаемый результат упражнения. Функции с ошибками не вызываются при импорте, но запуск файла через Python не заменяет статический анализ.

Чтобы тренироваться, скопируйте файл, исправьте причины ошибок и проверьте копию явно: `python -m mypy fixed_examples.py`. Не добавляйте ignore только ради зелёного отчёта.

## 8. Как читать диагностику и внедрять типы

В сообщении обычно есть файл, строка, описание и код ошибки:

| Код mypy | Пример причины |
|---|---|
| `arg-type` | В функцию передан аргумент неподходящего типа |
| `assignment` | Присваиваемое значение не подходит аннотации |
| `return-value` | Возвращаемый тип не соответствует сигнатуре |
| `union-attr` | Операция недоступна одной из веток union, например None |
| `list-item` | Неподходящий элемент типизированного списка |

Начинайте с первого источника неправильного типа, а не с механического подавления последствий. Для исследования можно использовать reveal_type, чтобы посмотреть, какой тип анализатор вывел в конкретной точке.

Порядок внедрения в существующий код:

1. Аннотировать входы и результаты небольшого модуля.
2. Исправить несовместимые вызовы и обработать None.
3. Уточнить коллекции и внешние границы данных.
4. Добавить анализатор в обычную проверку проекта.

По умолчанию mypy не проверяет полностью тела функций без аннотированной сигнатуры. `--check-untyped-defs` расширяет проверку таких тел, но не восстанавливает точные типы параметров, если они остались Any. Strict помогает обнаружить пропущенные аннотации.

Any разрешает операции без обычной статической гарантии. Object допускает любое значение, но выполнять специфические операции с ним можно только после уточнения типа. «Заменить всё на Any» — значит потерять большую часть пользы проверки.

## 9. Версии Python и другие анализаторы

| Возможность | Версия |
|---|---|
| `list[int]`, `dict[str, int]` | С Python 3.9 |
| `int | str`, `str | None`, typing.TypeAlias | С Python 3.10 |
| `type Address = tuple[str, int]` | С Python 3.12 |

Для более старого кода встречаются List, Dict, Optional, Union из typing. В практике выбран синтаксис, работающий на Python 3.11, поэтому новое объявление type показано только в документации уровня 2.

**Pyright** — другой статический анализатор с собственными настройками и диагностикой. Он поддерживает постепенное внедрение и конфигурацию через pyrightconfig.json либо pyproject.toml. Анализаторы могут расходиться в выводе типов и поддержке новых возможностей; для проекта выбирают согласованные настройки. Здесь запускаемая проверка настроена на mypy. [Руководство Pyright](https://github.com/microsoft/pyright/blob/main/docs/getting-started.md).
