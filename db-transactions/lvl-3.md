# Транзакции — уровень 3: распределённая атомарность

По issue №6: распределённые транзакции, X/Open XA и two-phase commit.

## Проблема

Локальный COMMIT одной БД не фиксирует одновременно другую БД или сообщение в брокере. Если первая запись успешна, а вторая нет, появляется частичный результат. Сеть может оборваться и оставить исход неизвестным: отсутствие ответа не доказывает rollback.

**Распределённая транзакция** координирует несколько транзакционных ресурсов с общей целью атомарного решения. Участники должны поддерживать соответствующий протокол; произвольный HTTP endpoint не становится XA-ресурсом от внешнего BEGIN.

## Two-phase commit, 2PC

Участники — resource managers, решение ведёт coordinator/transaction manager.

1. **Prepare/vote:** координатор просит всех подготовиться. Участник сохраняет состояние, позволяющее пережить сбой, и голосует ready либо abort.
2. **Decision:** если все готовы, координатор надёжно фиксирует решение commit, затем сообщает участникам. Иначе принимает rollback. Участники завершают локальные ветки.

Решение и ход протокола должны восстанавливаться по устойчивым журналам. Повтор доставки команды решения не должен менять её смысл.

**Цена:** дополнительные обмены, синхронизация журналов и удержание ресурсов. После ready участник не может просто решить «таймаут — откатываюсь»: глобальный commit мог уже быть принят. Недоступный координатор может оставить prepared-транзакции блокирующими ресурсы до восстановления решения. 2PC решает атомарность при своих предпосылках, а не делает систему всегда доступной.

## XA

Обычно под «Open XA» имеется в виду **X/Open XA** — стандарт взаимодействия transaction manager и resource managers. XID идентифицирует глобальную транзакцию/её ветку. Интерфейс включает операции начала/завершения участия, prepare, commit, rollback и recovery.

XA — интерфейс/модель координации ресурсов, а 2PC — протокол принятия атомарного решения; это не две случайные независимые технологии. Поддержка драйвером и каждым ресурсом обязательна. Не путайте 2PC с двухфазной блокировкой 2PL: первая про commit нескольких участников, вторая — про порядок захвата/освобождения блокировок.

## Пример механизма PostgreSQL

Концептуальная ветка участника:

```sql
BEGIN;
UPDATE accounts SET balance_cents = balance_cents - 100 WHERE id = 1;
PREPARE TRANSACTION 'study-global-1-branch-a';
-- Позже координатор, уже зная общее решение:
COMMIT PREPARED 'study-global-1-branch-a';
```

Альтернативное решение — ROLLBACK PREPARED. COMMIT PREPARED/ROLLBACK PREPARED выполняют вне обычного transaction block. Эти команды не равны PREPARE SQL statement для подготовленного запроса.

PostgreSQL требует конфигурации prepared transactions; состояние видно в pg_prepared_xacts. Долго висящие prepared-транзакции удерживают ресурсы и мешают обслуживанию. В реальной системе нужен transaction manager и план recovery, а не несколько несвязанных ручных PREPARE. **Пример не запускается автономной SQLite-практикой.**

## Альтернативы: Saga и outbox

- **Saga:** последовательность локальных транзакций и компенсирующих операций. Возврат денег — новая операция, не откат времени; компенсация может тоже не выполниться и требовать повторов/разбора.
- **Transactional outbox:** изменение данных и запись события фиксируют в одной локальной БД; отдельный процесс публикует событие. Повторная публикация возможна, значит consumer должен быть идемпотентным.
- **Idempotency key/inbox:** повторный запрос/событие не применяет одно изменение многократно; это не замена всей модели согласованности.

Выбор зависит от требования атомарности, длительности операции, доступности участников и допустимой eventual consistency. Saga не даёт те же гарантии, что глобальный атомарный commit.
