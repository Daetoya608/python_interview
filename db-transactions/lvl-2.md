# Транзакции — уровень 2: изоляция

Обязательно по issue №6: знать уровни изоляции и решаемые ими проблемы. Ниже стандартная модель отделена от поведения PostgreSQL.

## Аномалии

- **Dirty read:** прочитаны чужие незакоммиченные изменения, которые ещё могут откатиться.
- **Non-repeatable read:** повторное чтение строки дало другое значение после чужого commit.
- **Phantom read:** повторный запрос по условию дал другой набор подходящих строк.
- **Lost update:** запись, вычисленная из устаревшего значения, затёрла конкурентное изменение.
- **Write skew:** транзакции проверили общий инвариант на снимках и изменили разные строки так, что вместе нарушили правило.

Пример write skew: два дежурных видят, что дежурят двое, и каждый снимает себя с дежурства в отдельной строке. Итог — никого, хотя каждая проверка по отдельности проходила.

## Уровни стандарта

| Уровень | Dirty read | Non-repeatable read | Phantom | Другие нарушения сериализуемости |
|---|---|---|---|---|
| Read Uncommitted | Возможен | Возможен | Возможен | Возможны |
| Read Committed | Запрещён | Возможен | Возможен | Возможны |
| Repeatable Read | Запрещён | Запрещён | Стандарт допускает | Возможны |
| Serializable | Запрещён | Запрещён | Запрещён | Запрещены у успешно завершённых транзакций |

Уровни задают гарантии, а не один универсальный алгоритм блокировок. MVCC позволяет читателям видеть подходящие версии, но не отменяет конфликты записи и блокировки.

## PostgreSQL: важные отличия

- Read Uncommitted ведёт себя как Read Committed.
- В Read Committed обычный SELECT получает снимок на начало **оператора**: следующий SELECT в той же транзакции может увидеть новый commit.
- Repeatable Read использует стабильный транзакционный снимок и **также исключает phantom reads**, хотя стандарт этого от уровня не требует. Но write skew/аномалии сериализации остаются возможны.
- Serializable контролирует сериализуемость; при опасном конфликте одна транзакция может завершиться serialization failure. Это нормальная часть контракта уровня, а не обещание «все всегда успешно выполнятся».

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance_cents FROM accounts WHERE id = 1;
-- Повторить SELECT после commit другого соединения.
ROLLBACK;
```

Для сравнения снимков используйте **два отдельных соединения PostgreSQL**. SQLite-пример в practice показывает atomicity/savepoint, а не воспроизводит все PostgreSQL-уровни.

## Защита операции

Плохая схема: прочитать 100, в приложении вычислить 90, позже безусловно записать 90 — конкурентное изменение могло уже произойти.

Варианты в зависимости от правила:

```sql
UPDATE accounts
SET balance_cents = balance_cents - 100
WHERE id = 1 AND balance_cents >= 100;
```

Проверить число изменённых строк. Для более сложной операции возможен SELECT ... FOR UPDATE, затем изменение в **той же транзакции**. Берите несколько блокировок в стабильном порядке. Альтернатива — optimistic locking по версии: UPDATE ... WHERE version = old_version с проверкой результата.

Не рассчитывайте, что Repeatable Read любой СУБД автоматически решит все lost update или межстрочные правила. Для инвариантов используйте подходящие ограничения, блокировки либо Serializable с повтором **всей** транзакции.

Повтор после serialization failure/deadlock должен быть ограничен, заново прочитать данные и не продублировать внешние побочные действия. Повторить только последний SQL недостаточно. Изоляция БД и идемпотентность API — разные задачи.
