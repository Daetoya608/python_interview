# Транзакции: состояние, видимость и конкурентные изменения

Цель — объяснить, какие состояния могут увидеть участники и почему. Команды — в [КОНСПЕКТ.md](КОНСПЕКТ.md), локальная модель — в [practice/demo.py](practice/demo.py). Детали MVCC и изоляции ниже относятся к PostgreSQL 18, если явно не указано другое.

## 1. Что является транзакцией

Транзакция задаёт границу совместной фиксации изменений. При переводе денег дебет одного счёта и кредит другого должны стать устойчивым результатом вместе. Промежуточное состояние внутри операции может существовать, но не должно превратиться в частично зафиксированный итог.

```text
начало → чтения и изменения → проверки → COMMIT → зафиксировано
                          ↘ ошибка/отказ → ROLLBACK
```

Соединение — канал к серверу; транзакция — единица работы внутри этого канала. Открытое соединение может последовательно обслужить много транзакций. Закрытие соединения с незавершённой транзакцией обычно приводит к её откату, но управлять результатом лучше явно.

SAVEPOINT — точка частичного отката внутри той же транзакции. RELEASE не делает изменения независимо долговечными: откат внешней транзакции отменит и их.

## 2. ACID — четыре разных вопроса

| Свойство | Какой вопрос закрывает | Чего не даёт автоматически |
|---|---|---|
| Atomicity | Можно ли зафиксировать только часть изменений? | Отката отправленного письма или внешнего платежа |
| Consistency | Сохраняются ли заданные инварианты? | Правильных бизнес-правил, которых никто не описал |
| Isolation | Какие эффекты конкуренции допускаются? | Сериализуемости на любом уровне изоляции |
| Durability | Что переживёт сбой после подтверждения commit? | Одинаковой защиты при любых настройках диска и репликации |

Consistency здесь относится к корректным состояниям и ограничениям. Она отличается от согласованности чтений реплик в распределённой системе. Даже полностью атомарный перевод может быть неверным, если дебетуется не тот счёт.

## 3. WAL и восстановление после сбоя

Изменённые страницы сначала могут существовать только в оперативной памяти. Сбрасывать все страницы на диск для каждого commit дорого. PostgreSQL использует журнал предзаписи WAL: сведения, необходимые для восстановления, должны стать устойчивыми раньше соответствующих страниц данных.

Упрощённо: изменение порождает WAL → commit подтверждается согласно настройкам надёжности → страницы могут быть записаны позже → после сбоя журнал помогает восстановить состояние. Checkpoint ограничивает объём последующей работы восстановления; он не заменяет commit.

Rollback не обязательно физически переписывает каждую страницу в прежний вид. MVCC позволяет оставить версии, которые не считаются видимыми, и позже убрать их. Не следует переносить конкретный алгоритм undo другой СУБД на PostgreSQL.

Потеря ответа на COMMIT создаёт неопределённость для клиента: сервер мог успеть зафиксировать транзакцию. Повтор внешней команды должен учитывать её идентификатор, иначе возможен двойной эффект.

## 4. MVCC: версии вместо одного изменяемого значения

**Multi-Version Concurrency Control** позволяет читателям выбирать подходящие версии строк по снимку видимости. UPDATE в PostgreSQL создаёт новую версию, а не просто заменяет единственную доступную копию. Обычный SELECT часто может читать подходящую старую версию, пока другая транзакция пишет новую.

Снимок учитывает состояние транзакций, а не является полной копией БД в памяти. «Вижу старое» не обязательно означает обращение к реплике: это может быть корректное чтение по снимку на основном сервере.

MVCC уменьшает блокирование читателей писателями, но не устраняет блокировки. Конкурентные записи одной строки, ограничения уникальности и DDL требуют согласования. VACUUM освобождает место от версий, уже не нужных активным снимкам; долгая транзакция способна мешать очистке и увеличивать разрастание таблиц.

## 5. Изоляция задаёт границу снимка и конфликты

В PostgreSQL Read Committed обычно даёт новый снимок на каждый оператор. Два SELECT в одной транзакции могут увидеть разные подтверждённые состояния. Repeatable Read использует устойчивый снимок с первого содержательного оператора, но не запрещает все опасные зависимости.

| Сценарий | Что произошло |
|---|---|
| Dirty read | Прочитано чужое незафиксированное изменение |
| Non-repeatable read | Повторное чтение строки увидело другое значение |
| Phantom | Повторная выборка по условию увидела другой набор строк |
| Lost update | Запись на основе старого чтения затёрла чужой результат |
| Write skew | Изменены разные строки, совместно нарушен общий инвариант |

PostgreSQL RU работает как RC. Его RR строже минимальных требований стандарта и не допускает phantom в обычных повторных чтениях, но допускает write skew. Название уровня без названия СУБД не описывает все гарантии.

Serializable требует результата, эквивалентного некоторому последовательному выполнению успешно завершённых транзакций. PostgreSQL выявляет опасные зависимости и может прервать участника serialization failure. Это не выполнение всех запросов в одном глобальном потоке.

## 6. Почему BEGIN не защищает остаток

На складе одна единица. Два покупателя независимо читают `stock = 1`, затем оба записывают `stock = 0` и считают покупку успешной. Каждая транзакция атомарна, однако проданы две единицы.

Один вариант — атомарно выразить проверку вместе с изменением:

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 42 AND stock > 0
RETURNING stock;
```

Успех подтверждает возвращённая строка; отсутствие строки означает, что списание не выполнено. На RC конкурентные изменения одной строки согласуются, а условие проверяется на актуальной для обновления версии. На более строгом уровне возможна ошибка сериализации и повтор транзакции.

Другие способы:

- **Пессимистический:** прочитать строку FOR UPDATE, удерживать блокировку до конца транзакции, затем проверить и изменить. Все участники должны следовать совместимому протоколу.
- **Оптимистический:** UPDATE с `WHERE version = :old_version` и увеличением версии. Ноль строк означает конфликт, требующий нового чтения/решения.
- **Декларативный:** UNIQUE/CHECK/FK там, где правило выражается ограничением. Это защищает и от альтернативных писателей.

Выбор зависит от конкуренции и границ инварианта. Блокировка одной строки не защищает автоматически условие «в таблице всегда есть хотя бы один дежурный».

## 7. Write skew, deadlock и повторы

Два врача на снимках видят, что дежурят оба. Каждый снимает себя, изменяя свою строку. Конфликта записи одной строки нет, но после двух commit не дежурит никто. Устойчивого снимка недостаточно. Нужны сериализуемость либо общий объект блокировки/протокол, охватывающий этот инвариант.

Deadlock возникает, когда A удерживает ресурс 1 и ждёт 2, а B удерживает 2 и ждёт 1. БД обнаруживает цикл и прерывает одного участника. Одинаковый порядок захвата уменьшает вероятность, но обработка ошибки всё равно нужна.

После deadlock или serialization failure повторяют **всю транзакцию с новым чтением**, ограничивая попытки и время. Повтор только последнего UPDATE может использовать уже неверные решения. Необратимые внешние действия лучше вынести за границу повторяемого участка и связать надёжным протоколом.

## 8. Граница одной БД: 2PC, XA, saga, outbox

2PC согласует общий commit нескольких участников. Сначала координатор просит prepare. Участник, ответивший ready, устойчиво сохраняет возможность завершить операцию и удерживает необходимые ресурсы. Затем координатор устойчиво фиксирует общее решение и рассылает commit либо rollback.

Если координатор пропал после prepare, участник не может просто откатиться по таймауту: другие могли уже получить commit. Отсюда блокирование и необходимость recovery. XA задаёт интерфейс transaction manager ↔ resource managers и идентификаторы веток; 2PL — отдельный механизм двухфазного удержания блокировок.

Saga состоит из локальных commit и последующих компенсаций. Возврат платежа — новое действие, а не исчезновение исходного платежа; компенсация тоже может не удаться. Промежуточные состояния должны быть допустимы для бизнеса.

Outbox сохраняет изменение и запись о будущем событии в одной локальной транзакции. Отдельный отправитель публикует событие. Сбой после публикации до отметки «отправлено» даст повтор; потребителю нужна идемпотентность. Outbox закрывает разрыв «БД обновилась, сообщение не отправилось», но не создаёт глобальную транзакцию.
