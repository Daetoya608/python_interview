# Транзакции: краткое повторение

- Транзакция объединяет операции. BEGIN начинает, COMMIT фиксирует, ROLLBACK отменяет. После commit нужен новый исправляющий шаг.
- SAVEPOINT позволяет частичный откат; RELEASE не фиксирует внешнюю транзакцию независимо.
- **ACID:** atomicity — изменения фиксируются целиком либо отменяются; consistency — сохраняются заданные ограничения/инварианты; isolation — гарантии при конкурентном выполнении; durability — зафиксированный результат переживает сбой в рамках настроенных гарантий хранения. Бизнес-инварианты нужно выразить кодом/ограничениями; внешнее письмо не откатывается с БД. Consistency здесь не означает мгновенное совпадение всех реплик.
- Dirty read — незакоммиченное; non-repeatable — изменившаяся прочитанная строка; phantom — изменившийся набор по условию; lost update — затёртое изменение; write skew — совместно нарушенный межстрочный инвариант.
- Стандарт: RC запрещает dirty reads; RR также non-repeatable; Serializable требует результата, эквивалентного некоторому последовательному выполнению.
- PostgreSQL: RU=RC, снимок RC на оператор; RR на транзакцию и без phantom, но с возможным write skew. Serializable может прерывать опасные транзакции.
- Retry после serialization failure/deadlock — ограниченный повтор всей операции с новым чтением. Для записи помогают атомарный UPDATE с условием, SELECT FOR UPDATE, версия и ограничения.
- 2PC: все prepare/vote → устойчивое общее решение → commit/rollback участников. После ready участник не волен откатиться просто по таймауту.
- XA — интерфейс TM↔RM, XID и recovery. 2PC не равно 2PL. Цена глобальной атомарности — задержки, блокировки и сложное восстановление.
- Saga компенсирует локальные операции, outbox атомарно пишет событие вместе с данными. Это не эквиваленты глобальной транзакции и не автоматическое exactly-once.

## Уровни изоляции: запомнить различия

| Уровень по стандартной модели | Какие аномалии ещё возможны |
|---|---|
| Read Uncommitted | Dirty, non-repeatable, phantom и другие нарушения сериализуемости |
| Read Committed | Non-repeatable, phantom и другие нарушения сериализуемости |
| Repeatable Read | Стандарт допускает phantom и другие нарушения сериализуемости |
| Serializable | Результат успешно завершённых транзакций эквивалентен некоторому последовательному порядку |

Поведение конкретной СУБД может быть строже стандарта: PostgreSQL RR не допускает phantom. **Write skew:** два дежурных видят друг друга на снимках и каждый снимает только себя; изменены разные строки, но инвариант «хотя бы один дежурит» нарушен. Стабильный снимок сам по себе этого не предотвращает.

От потерянного обновления часто помогает изменение в самой БД:

```sql
UPDATE accounts SET balance_cents = balance_cents - 100
WHERE id = 1 AND balance_cents >= 100;
```

Проверяют число изменённых строк. Для составного перевода дебет и кредит объединяют в одну транзакцию; одного BEGIN без корректных проверок/синхронизации недостаточно. При сериализационном конфликте повторяют **всю** транзакцию с новыми чтениями и не дублируют внешние действия.

## 2PC: что происходит после prepare

1. Координатор просит все resource managers подготовиться.
2. Готовый участник устойчиво сохраняет состояние и голосует ready; до решения он удерживает нужные ресурсы.
3. Если все готовы, координатор устойчиво фиксирует commit и рассылает его; иначе выбирает rollback.
4. После сбоя участники восстанавливают решение. Prepared-участник не может самостоятельно выбрать rollback по таймауту: commit мог уже состояться у других.

Отсюда возможность блокирования при недоступном координаторе. **X/Open XA** задаёт интерфейс transaction manager ↔ resource managers и идентификаторы веток XID. **2PL** — протокол блокировок, а не двухфазный commit. Saga выполняет новые компенсационные операции, а не превращает уже завершённые внешние действия в невыполненные.

Практика: `python db-transactions/practice/demo.py`. Изоляцию PostgreSQL исследуют двумя его соединениями; XA/2PC требуют подготовленной инфраструктуры и здесь не выполнялись.
