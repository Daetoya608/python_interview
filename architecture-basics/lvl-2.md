# Архитектура систем — уровень 2

## Монолит, модульный монолит, микросервисы

| Вариант | Граница выпуска | Сильные стороны | Цена |
|---|---|---|---|
| Монолит | Приложение выпускается как единое целое | Простые локальные вызовы, транзакции, debugging, недорогой старт | Совместный выпуск и масштабирование; без границ код превращается в тесно связанный клубок |
| Модульный монолит | Единый выпуск, внутренние модули с контрактами | Простота эксплуатации + явные границы доменов | Нужно соблюдать границы: не читать чужие таблицы/внутренности напрямую |
| Микросервисы | Сервисы можно независимо выпускать и масштабировать | Автономия команд, разные профили нагрузки, изоляция части отказов | Сеть, совместимость контрактов, наблюдаемость, эксплуатация и распределённая согласованность |

Размер файла и число Docker-контейнеров не определяют архитектуру. Монолит может работать в нескольких репликах, а десятки сервисов с общим релизом и неявными связями образуют распределённый монолит. В микросервисах владельцы данных задают контракты доступа; общая БД с произвольными cross-service запросами снижает независимость. Для межсервисного процесса часто нужны события, outbox и Saga, а не предположение об одной локальной ACID-транзакции.

Выбор: для небольшой команды и ещё меняющегося домена часто разумен модульный монолит. Микросервисы оправдываются измеримой потребностью в независимых релизах/масштабировании, устойчивыми границами и готовностью команды поддерживать распределённую систему. Это решение по ограничениям, не лестница «плохой → хороший».

## Discovery и балансировка

**Service discovery** отвечает «какие живые адреса обслуживают нужный сервис?»: DNS, реестр или платформа оркестрации. Регистрация и health checks обновляют набор экземпляров; DNS/кэши могут временно хранить устаревшие данные.

- **Client-side balancing:** клиент получает список экземпляров и выбирает адрес. Меньше промежуточных переходов, но клиенту нужны алгоритмы, обновление списка и исключение нездоровых узлов.
- **Server-side balancing:** клиент обращается к стабильному адресу балансировщика/proxy, тот выбирает backend. Проще клиент, но дополнительный переход и компонент, который тоже нужно резервировать.

Алгоритмы: round-robin, least-connections, weighted; выбор должен учитывать длительность запросов и профиль нагрузки. L4 работает с транспортными соединениями, L7 понимает прикладной протокол, например HTTP-пути. Readiness показывает готовность принимать трафик; liveness — необходимость перезапуска. Слепой restart при сбое внешней БД способен усилить аварию.

Пример server-side маршрутизации — сервисная виртуальная точка входа с backend endpoints. Конкретная реализация Kubernetes Service зависит от сетевого режима/плагина; это не обязательно отдельный центральный proxy-процесс.

## Синхронное и асинхронное взаимодействие

Синхронный запрос ожидает ответ в рамках текущего вызова. Плюсы — понятный итог и простой контроль потока; минусы — связанность по доступности и накопление задержек в цепочке. Ограничивайте connect/read timeout и общий deadline, число одновременных запросов, повторы и размер очередей.

Асинхронное взаимодействие разрывает ожидание результата: публикация сообщения или `POST /jobs` с ответом `202`, затем polling статуса/webhook. Это сглаживает нагрузку и переживает временную недоступность потребителя, но добавляет промежуточные состояния, повторы, корреляцию и eventual consistency. Нужны idempotency keys/message IDs, ограниченные retries и наблюдение за отставанием.

`async def` — способ неблокирующего выполнения кода; API при этом может оставаться синхронным по контракту: клиент всё ещё ждёт конечный ответ. Брокер тоже не гарантирует независимость, если отправитель сразу ждёт reply и не может продолжать без него.

## Stateful / stateless (желательно)

**Stateless instance** не требует локальной памяти предыдущих запросов клиента для обработки следующего; состояние заказа может храниться в общей БД. Это облегчает балансировку, замену и масштабирование экземпляров. **Stateful component** хранит значимое состояние между обращениями: БД, локальная сессия, состояние соединения. Ему нужны репликация/восстановление, корректная маршрутизация и перенос данных.

JWT не делает систему автоматически stateless: отзыв токенов, права и бизнес-состояние могут требовать обращений к хранилищу. Sticky sessions упрощают привязку клиента, но не заменяют восстановление при потере узла. У WebSocket есть состояние живого соединения даже при stateless бизнес-обработчиках.

## Безопасность системы

- Аутентификация устанавливает **кто**, авторизация проверяет **что разрешено**, включая доступ к конкретному объекту/tenant на каждой операции.
- TLS защищает транспорт; для service-to-service при необходимости используют mTLS и отдельную идентичность/политику доступа. Нахождение во внутренней сети не даёт безусловного доверия.
- Минимальные привилегии сервисов/БД, изоляция сети, secrets storage и ротация; секреты не в образах, Git и логах.
- Валидация данных, параметризованный SQL, ограничения размера/частоты/времени запросов; обновление зависимостей.
- Корреляционные IDs, метрики latency/error/saturation и распределённые traces; audit без утечки персональных данных/токенов.

API gateway может централизовать часть проверок, но объектные права и инварианты остаются ответственностью сервиса. Наблюдаемость и эксплуатационные инструкции проектируют вместе с архитектурой, а не после первого сбоя.

## Мини-кейс для аттестации

Интернет-магазин: команда из трёх разработчиков, небольшой поток заказов, домен меняется. Начните с модульного монолита: каталог/заказы/платежи с явными API; одна БД с дисциплиной владения таблицами; отправка писем через очередь. Выделяйте сервис, когда есть измеренная причина и понятная граница. При ответе назовите требования: RPS/latency, доступность, согласованность, состав команды и ограничения выпуска. Число пользователей само по себе архитектуру не выбирает.
