# Архитектура систем — Junior

## Клиент-сервер, протокол и API

**Клиент** инициирует взаимодействие, **сервер** обрабатывает запрос и отвечает. Это роли конкретного обмена: backend — сервер для браузера и клиент для БД/платёжного API. Они не обязательно находятся на разных машинах.

```text
Браузер → HTTPS → Backend → SQL через протокол БД → Database
                         → HTTPS → Внешний API
```

**Протокол** определяет правила обмена и формат сообщений. **API** задаёт доступные операции, параметры, результаты и ошибки. HTTP — протокол; GET /orders/42 и схема ответа — часть конкретного API.

## Логические слои и процессы

Presentation принимает/возвращает данные, application/domain выполняет сценарии и правила, data access работает с хранением. Это **логическое разделение обязанностей**, а не требование запустить три сервера.

Все слои могут жить в одном процессе. И наоборот, один логический компонент может иметь несколько экземпляров в отдельных процессах. Число слоёв, процессов и физических машин — разные характеристики.

## Почему сервер проверяет вход повторно

Браузерные проверки полезны для UX, но клиент контролируется пользователем: запрос можно изменить или отправить без формы. Сервер обязан проверить:

- Формат, типы, обязательные значения и ограничения размера/диапазона.
- Аутентификацию и права, включая доступ к конкретному заказу.
- Бизнес-инварианты: допустимый переход статуса, количество/сумму и другие правила.

Проверка типа не заменяет право доступа, а проверка формы — ограничение в БД. Клиент не должен самостоятельно назначать себе цену/права, которым сервер безусловно доверяет.

## Timeout не равен отмене

Клиент отправил POST создания заказа; сервер записал заказ, но ответ потерялся. Timeout означает **клиент не дождался ответа**, а не «заказ точно не создан».

Слепой повтор может создать дубль. Для операции проектируют идемпотентность: клиент передаёт стабильный ключ операции, сервер согласованно сохраняет ключ и результат. Повтор того же запроса возвращает тот же результат без нового бизнес-действия; тот же ключ с другими данными не должен молча выполнить иную операцию.

Идемпотентность — одинаковый эффект повторов, а не одинаковый HTTP-статус. Нужны корректные границы хранения/атомарности; локальная переменная одного процесса не защищает от дубля после перезапуска или на другом экземпляре.
