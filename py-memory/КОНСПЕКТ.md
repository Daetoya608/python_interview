# Память Python: конспект к аттестации

GC, подсчёт ссылок, поколения, `__del__`, heap/stack, `__slots__` и профилирование памяти. Механизмы ниже относятся прежде всего к **CPython**: язык Python не требует от всех реализаций одинакового управления памятью.

## 1. Что такое GC и зачем он нужен

**Garbage collection** — автоматическое освобождение памяти объектов, которые программа больше не может использовать. Это позволяет переиспользовать память без ручного освобождения каждого объекта.

В CPython работают два дополняющих механизма:

| Механизм | Что делает | Главное ограничение |
|---|---|---|
| Reference counting, подсчёт ссылок | Обычно освобождает объект, когда исчезла последняя сильная ссылка | Не распознаёт недостижимые циклы сам по себе |
| Cyclic GC, циклический сборщик | Находит недостижимые группы объектов, удерживающие друг друга | Требует обходов и создаёт накладные расходы |

Термин GC используют и для всей автоматической сборки, и в узком смысле — для второго механизма, которым управляет модуль `gc`.

**Недостижимый объект** — объект, до которого больше нет пути по сильным ссылкам из доступного программе состояния. GC не знает, «нужны ли» данные по бизнес-смыслу: если ненужный объект остаётся в глобальном списке или кэше, ссылка продолжает удерживать его. [Модель объектов Python](https://docs.python.org/3/reference/datamodel.html#objects-values-and-types).

## 2. Счётчик ссылок и действие del

Счётчик ссылок отражает удерживающие объект ссылки: из переменных, контейнеров, атрибутов и внутренних структур интерпретатора. Это не счётчик обращений к объекту и не количество переменных с одинаковым именем.

```python
a = []
b = a          # Второе имя указывает на тот же список, копии нет.
holder = [a]   # Контейнер тоже удерживает список.

del a          # Удалено имя a, список остаётся доступен через b и holder.
del b          # Ссылка из holder ещё существует.
holder.clear() # Удалена последняя ссылка на внутренний список.
```

При присваивании нового значения старое имя перестаёт удерживать прежний объект. При выходе из функции её локальные ссылки обычно освобождаются; объект продолжает жить, если его вернули, сохранили снаружи или удерживают другие структуры.

В обычном CPython уменьшение счётчика до нуля запускает освобождение объекта; освобождение контейнера уменьшает счётчики его элементов. Это может вызвать цепочку освобождений. Цена механизма — обновление счётчиков и память для них. Немедленное уничтожение не является общей гарантией языка; новые сборки CPython также имеют оптимизации подсчёта. [Подсчёт ссылок в CPython](https://docs.python.org/3.14/c-api/intro.html#reference-counts).

`del x` удаляет привязку имени; `del items[i]` — элемент контейнера. Это **не команда принудительно уничтожить объект** и не прямой вызов `__del__`.

`sys.getrefcount(obj)` помогает исследовать ссылки, но сам вызов обычно добавляет временную ссылку. В новых CPython есть «бессмертные» объекты со специальными счётчиками, поэтому точные числа нельзя использовать как переносимую бизнес-логику. [getrefcount](https://docs.python.org/3/library/sys.html#sys.getrefcount).

## 3. Почему нужен циклический сборщик

```python
import gc

def make_cycle():
    first = []
    second = [first]
    first.append(second)

make_cycle()
# Локальных имён уже нет, но списки всё ещё ссылаются друг на друга.
gc.collect()  # Принудительная проверка, если цикл ещё не собран автоматически.
```

Оба счётчика остаются ненулевыми из-за внутренних ссылок. При этом извне к спискам уже не обратиться.

Упрощённый алгоритм циклического GC:

1. Выбирает группу отслеживаемых объектов для проверки.
2. Использует временный учёт ссылок и вычитает ссылки между объектами внутри этой группы. Реальные счётчики на этом этапе не обнуляет.
3. Находит объекты, удерживаемые извне группы, и всё достижимое из них: они живые.
4. Оставшуюся недостижимую группу финализирует и разрывает её внутренние ссылки, позволяя освободить объекты.

Отслеживаются прежде всего объекты, способные участвовать в циклах: контейнеры и пользовательские экземпляры. Не каждый объект обязательно отслеживается: например, числа и строки не требуют проверки циклов; некоторые контейнеры тоже оптимизируются. Сам цикл не означает мусор: пока на него есть доступная внешняя ссылка, он нужен программе. [Устройство сборщика CPython](https://github.com/python/cpython/blob/main/InternalDocs/garbage_collector.md).

## 4. Поколения: как уменьшить стоимость проверок

**Гипотеза поколений:** большинство объектов живёт недолго. Поэтому молодые объекты проверяют чаще, а пережившие несколько проверок — реже.

Классическая схема CPython 3.11–3.13:

- Поколение **0**: новые отслеживаемые объекты.
- Поколение **1**: пережившие сборку поколения 0.
- Поколение **2**: пережившие следующую сборку; это старшее поколение.

Выжившие объекты переходят дальше, а из поколения 2 уже не повышаются. Сборка поколения 1 охватывает и 0; полная сборка охватывает все поколения. Возраст здесь — количество пережитых сборок, а не секунды и не значение refcount. При нулевом счётчике обычный объект освобождается независимо от поколения.

Автоматический запуск связан с количеством выделений и освобождений объектов и настроенными порогами; это не таймер «раз в N секунд» и не только реакция на заполненную RAM. [GC Python 3.13](https://docs.python.org/3.13/library/gc.html#gc.set_threshold).

**Версии имеют значение:** в ранних Python 3.14 использовались два поколения и инкрементальная обработка старых объектов; документация 3.14 отмечает восстановление поколения 1 и прежней схемы с **3.14.5**. В free-threaded сборках есть дополнительные условия запуска. На собеседовании сначала называйте версию; правило «в любом Python всегда три поколения» некорректно. [Изменения GC в Python 3.14](https://docs.python.org/3.14/library/gc.html).

Минимальный API:

| Вызов | Назначение |
|---|---|
| `gc.collect()` | Полная ручная сборка; возвращает число собранных и несобираемых объектов, а не байты |
| `gc.get_count()` | Счётчики, связанные с планированием сборок; не количество всех живых объектов |
| `gc.get_threshold()` / `set_threshold(...)` | Просмотр и настройка порогов |
| `gc.get_stats()` | Статистика сборок |
| `gc.is_tracked(obj)` | Отслеживается ли объект циклическим GC |
| `gc.disable()` / `enable()` | Отключение / включение автоматического циклического GC |

`gc.disable()` **не отключает refcount**; ручной collect остаётся доступен. Вызывать collect после каждой операции обычно не нужно: он не удалит достижимый объект и не исправит растущий кэш.

## 5. Как работает __del__

`__del__(self)` — финализатор, вызываемый при подготовке объекта к уничтожению. Его иногда называют деструктором, но время вызова ненадёжно для управления ресурсами.

```python
class Item:
    def __del__(self):
        print("Финализация")

item = Item()
alias = item
del item   # alias продолжает удерживать объект.
del alias  # В обычном CPython без других ссылок запускается финализация.
```

- Прямой `obj.__del__()` только вызывает метод: ссылки и сам объект от этого автоматически не исчезают.
- При завершении интерпретатора вызов не гарантирован; нужные глобальные объекты уже могут быть недоступны.
- Исключения из автоматически вызванного финализатора не пробрасываются обычным образом вызывающему коду; о них сообщают как о необработанных при финализации.
- Не стоит блокироваться на Lock или выполнять сложную работу: финализатор может запуститься в неудобном контексте, включая другой поток.
- Если сохранить self во внешней структуре, объект можно «воскресить». В CPython финализатор воскресшего объекта повторно не вызывается. [Семантика __del__](https://docs.python.org/3/reference/datamodel.html#object.__del__).

Утверждение «цикл с `__del__` всегда создаёт несобираемый мусор» устарело: с Python 3.4 обычные такие циклы могут безопасно финализироваться. Особые случаи C-расширений остаются. [PEP 442](https://peps.python.org/pep-0442/).

Файлы, соединения и транзакции освобождают явно: через `with`, `close()` или `try/finally`. `weakref.finalize` позволяет зарегистрировать резервную очистку без собственного __del__, но не заменяет предсказуемое закрытие ресурсов. Callback не должен сам удерживать объект, например через его bound method. [weakref.finalize](https://docs.python.org/3.14/library/weakref.html#finalizer-objects).

## 6. Heap и stack в Python

**Heap, куча** — память для Python-объектов и структур данных: списков, строк, чисел, экземпляров классов и их содержимого. Управляет ею интерпретатор. Даже объект, созданный внутри функции, не становится из-за этого объектом системного стека.

**Стек вызовов** — логическая цепочка активных вызовов. Кадр выполнения хранит локальные привязки/ссылки, состояние исполнения и промежуточные значения вычислений. Системный C-стек используется нативным кодом; это не то же самое, что все Python-кадры.

```python
def build():
    data = [1, 2, 3]
    return data

result = build()  # Список жив после окончания вызова благодаря result.
```

Список размещён в куче; data — локальная привязка к нему. Возврат не требует переносить список «со стека в кучу». У контейнера есть собственная память и ссылки на элементы; сами элементы — отдельные объекты. [Управление памятью CPython](https://docs.python.org/3/c-api/memory.html).

Фраза «все локальные переменные находятся в stack, все остальные в heap» слишком груба: размещение кадров — деталь реализации. В CPython 3.11+ обычный Python-вызов не обязательно создаёт отдельный Python frame object или углубляет C-стек. Генератор может сохранить состояние выполнения между возобновлениями. [Кадры и вызовы CPython 3.11](https://docs.python.org/3.14/whatsnew/3.11.html#cheaper-lazy-python-frames).

## 7. __slots__: назначение и применение

Обычный пользовательский экземпляр поддерживает словарь атрибутов `__dict__`. `__slots__` задаёт фиксированные места для объявленных атрибутов и обычно устраняет словарь экземпляра. Это экономит память при большом числе однотипных объектов и может ускорить доступ.

```python
class Point:
    __slots__ = ("x", "y", "__weakref__")

    def __init__(self, x, y):
        self.x = x
        self.y = y

point = Point(1, 2)
point.x = 10           # Разрешено: slots не делают объект неизменяемым.
try:
    point.color = "red"
except AttributeError:
    print("Необъявленный атрибут")
```

Ограничения:

- Slots не проверяют тип значений и не устраняют память самих объектов, на которые ссылаются поля.
- Для динамических атрибутов добавляют `"__dict__"`, теряя часть экономии; для weak references — `"__weakref__"`, если поддержка не унаследована.
- Если родитель уже имеет __dict__, slots потомка его не уберут.
- Подкласс без собственного __slots__ обычно снова получает __dict__. Для отсутствия новых полей задают `__slots__ = ()`.
- Не повторяют имена slots родителя. Несколько базовых классов с непустыми слотами могут конфликтовать по расположению полей.
- Значения по умолчанию задают в __init__, а не одноимёнными атрибутами класса: slots реализованы дескрипторами.
- Инструменты, ожидающие __dict__, могут требовать адаптации. Slots не отключают GC и не решают утечки ссылок.

Применять стоит для множества объектов с устойчивым набором полей; экономию проверяют измерением, а не универсальным обещанием процентов. [Описание __slots__](https://docs.python.org/3.14/reference/datamodel.html#slots).

## 8. Что такое профилирование памяти

**Профилировщик памяти** измеряет расход памяти и помогает связать его с участками кода. Его используют, чтобы найти рост потребления, большие временные выделения, чрезмерные копии и эффект оптимизаций.

Нужно различать:

- **Живые объекты** — что программа продолжает удерживать.
- **Пик** — максимум во время операции, даже если память затем освобождена.
- **RSS** — резидентная память всего процесса: интерпретатор, объекты, нативные буферы и прочее.

Освобождение объекта не гарантирует немедленного уменьшения RSS: аллокатор может сохранить память для повторного использования, а часть блоков удерживается из-за фрагментации. Рост памяти сам по себе ещё не доказывает утечку.

`sys.getsizeof(obj)` показывает размер самого объекта, включая непосредственно его структуры, но не сумму размеров всех объектов по его ссылкам. Поэтому один getsizeof списка не оценивает размер всего графа данных. [getsizeof](https://docs.python.org/3/library/sys.html#sys.getsizeof).

### tracemalloc: где выделена Python-память

Стандартный модуль; показывает источники выделений и разницу снимков. Включать его нужно до исследуемых выделений.

```python
import tracemalloc

tracemalloc.start(10)
before = tracemalloc.take_snapshot()

data = [bytearray(1024) for _ in range(1000)]

after = tracemalloc.take_snapshot()
for stat in after.compare_to(before, "lineno")[:5]:
    print(stat)

current, peak = tracemalloc.get_traced_memory()
print("Текущее / пик, байты:", current, peak)
tracemalloc.stop()
```

Снимки показывают остающиеся отслеживаемые блоки; временный объект, созданный и освобождённый между снимками, может не попасть в их разницу. Пик помогает обнаружить временный расход. Tracemalloc не равен измерению всего RSS и не обязательно видит буферы расширений, выделенные напрямую нативным аллокатором. Трассировка сама расходует память и время. [tracemalloc](https://docs.python.org/3/library/tracemalloc.html).

### memory_profiler: построчное потребление и график

`memory_profiler` — отдельный сторонний пакет, а не общее название всех профилировщиков. Установка: `python -m pip install memory_profiler`.

```python
from memory_profiler import profile

@profile
def allocate():
    data = [bytearray(1024) for _ in range(1000)]
    del data

if __name__ == "__main__":
    allocate()
```

Файл запускают как `python -m memory_profiler example.py`. Отчёт показывает потребление, изменение и число выполнений строк. По умолчанию измеряется память процесса через psutil; изменение RSS у строки не равно точному размеру созданного ею объекта.

`mprof run example.py` записывает потребление во времени, `mprof plot` строит график; для графика нужен matplotlib. Редкий опрос может пропустить короткий пик. В репозитории указано, что пакет больше активно не поддерживается: совместимость с окружением нужно проверять. [memory_profiler](https://github.com/pythonprofilers/memory_profiler).

Практический порядок: воспроизвести рост → прогреть приложение → сравнить одинаковые повторные операции → найти растущие выделения → проверить удерживающие ссылки → внести изменение → повторить замер. Частые причины: неограниченный кэш, глобальная коллекция, сохранённые исключения/traceback, незавершённые задачи и callbacks. Принудительная сборка не удалит объекты, которые всё ещё удерживаются.

## 9. Самопроверка

1. **Зачем два механизма?** Refcount освобождает большинство объектов; cyclic GC собирает недостижимые циклы с ненулевыми счётчиками.
2. **del удаляет объект?** Он удаляет привязку/ссылку. Другие ссылки могут сохранить объект.
3. **Каждый цикл — утечка?** Нет. Достижимый цикл живой, недостижимый обычно убирает GC.
4. **Поколение связано с refcount?** Нет. Это история пережитых сборок, а не количество ссылок.
5. **gc.disable отключает всё освобождение?** Нет, подсчёт ссылок продолжает работать.
6. **Можно закрывать транзакцию только в __del__?** Нельзя полагаться на его вызов и момент выполнения; нужен явный жизненный цикл.
7. **Локальный int живёт в системном стеке?** Он Python-объект; локальность имени не определяет размещение объекта на C-стеке.
8. **Что дают slots?** Меньше служебной памяти и фиксированный набор полей; не неизменяемость и не проверку типов.
9. **Почему после del RSS не уменьшился?** Объект может иметь другие ссылки, ждать cyclic GC или уже освободиться при сохранении памяти аллокатором.
10. **Почему getsizeof недостаточно?** Он не суммирует весь граф объектов. Для задачи выбирают измерение размера, Python-выделений или памяти процесса.
