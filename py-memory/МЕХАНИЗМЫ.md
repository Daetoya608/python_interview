# Память Python: граф объектов и жизненный цикл

Основная модель: имена удерживают объекты, объекты удерживают друг друга, интерпретатор освобождает недостижимое. API для исследования — в [КОНСПЕКТ.md](КОНСПЕКТ.md). Детали refcount, аллокатора и циклического GC ниже относятся к CPython; язык не требует одной реализации управления памятью.

## 1. Имя, ссылка и объект — разные вещи

Объект имеет идентичность, тип и состояние. Имя — привязка в пространстве имён. Присваивание связывает имя с объектом, а не копирует содержимое автоматически.

```python
a = [[1]]
b = a
c = a.copy()
b.append([2])
a[0].append(3)
assert a == [[1, 3], [2]]
assert b is a
assert c == [[1, 3]]
assert c is not a
assert c[0] is a[0]
```

Поверхностная копия создала новый внешний список, но сохранила ссылки на прежние элементы. Поэтому добавление элемента во внешний a не меняет c, а изменение общей внутренней коллекции видно обоим. Для объяснения таких случаев полезнее нарисовать стрелки, чем говорить «переменная хранит значение».

Глубокое копирование строит новый граф по правилам объектов и учитывает уже скопированные узлы, чтобы справляться с циклами. Оно не является универсальным способом клонировать соединения, файлы и внешнее состояние.

## 2. Достижимость объясняет время жизни

Объект нужен сборщику, если к нему есть путь из доступного состояния программы: активных кадров, модулей, контейнеров, внутренних корней интерпретатора. «Уже не нужен бизнесу» и «недостижим» — разные свойства.

Например, глобальный кэш удерживает все когда-либо обработанные запросы. GC не может удалить записи: программа всё ещё способна обратиться к ним. Это логическая утечка удержания, даже если все объекты корректно учитываются сборщиком.

Замыкание, bound method, callback, генератор, незавершённая Task и traceback тоже способны продлить жизнь графа. Сохранённое исключение может удерживать кадры и крупные локальные данные. Удаление одного очевидного имени не обязательно убирает все пути.

## 3. Подсчёт ссылок: быстрое локальное решение

В обычном CPython сильные ссылки учитываются счётчиками. Новая привязка/элемент контейнера увеличивает удержание, удаление — уменьшает. При исчезновении последней ссылки обычный объект может освобождаться сразу, уменьшая счётчики своих элементов и вызывая цепочку освобождений.

```python
items = []
alias = items
holder = {"data": items}
del items
del alias
assert holder["data"] == []  # Объект удерживает словарь.
holder.clear()
```

Del удаляет привязку или элемент, а не приказывает уничтожить конкретный объект. Число имён не равно числу ссылок: одна коллекция может содержать один объект много раз, а внутренние структуры тоже могут его удерживать.

Цена refcount — обновления при работе со ссылками и служебная память. У современных CPython есть бессмертные объекты и другие оптимизации, особенно в free-threaded сборках. Точные показания getrefcount и немедленная финализация не должны быть частью переносимого прикладного контракта.

## 4. Почему одного счётчика недостаточно

```python
def create_cycle():
    left = []
    right = [left]
    left.append(right)

create_cycle()
```

После возврата внешние имена исчезли, но два списка удерживают друг друга. Их счётчики не равны нулю, хотя извне группа недостижима.

Циклический GC исследует отслеживаемые объекты. Упрощённо он временно вычитает внутренние ссылки исследуемой группы, находит удерживаемые извне объекты и всё достижимое из них. Оставшаяся изолированная группа — кандидат на финализацию и разрыв ссылок. Настоящие refcount при таком анализе не обнуляют произвольно.

Цикл сам по себе не мусор: пока есть внешняя живая ссылка, граф нужен программе. Числа/строки обычно не требуют такого обхода, потому что не могут произвольно удерживать контейнерный цикл. Даже некоторые контейнеры оптимизируются и не всегда tracked.

## 5. Поколения сокращают число обходов

Большинство временных объектов быстро умирает. Поколенческий сборщик проверяет новые объекты чаще, пережившие проверки — реже. «Старый» означает переживший сборки, а не проживший определённое количество секунд.

В классической схеме CPython 3.11–3.13 три поколения 0/1/2. Сборка старшего захватывает младшие. Refcount при этом продолжает освобождать обычные объекты независимо от поколения.

Версии важны: в ранних 3.14 схема менялась; документация 3.14 отмечает возврат поколения 1 с 3.14.5. В free-threaded сборках есть дополнительные условия запуска. Поэтому для точных порогов/поколений называют версию и сборку, а не заучивают вечное число.

Отключение gc.disable убирает автоматическую циклическую сборку, но не отключает refcount. Ручной collect не освободит достижимый кэш и не вернёт обязательно всю свободную память операционной системе.

## 6. Финализация и ресурсы

__del__ — пользовательская финализация объекта. Её момент и контекст неудобны для обязательных действий: shutdown, другие потоки, уже недоступные глобальные данные, воскресший объект. Ошибка финализатора не передаётся обычным способом тому, кто сделал del.

Прямой вызов `obj.__del__()` — просто вызов метода. Объект продолжает существовать, если на него есть ссылки. Циклы с __del__ в современных Python не обязательно несобираемы: старое общее правило устарело после PEP 442.

Файл, сокет и транзакция — внешние ресурсы, их жизнь не должна зависеть от решения сборщика. Контекстный менеджер задаёт границу владения: получить → использовать → освободить в выходе, включая исключение. Это предсказуемее ожидания уничтожения объекта.

Weak reference не удерживает объект сильной ссылкой. Она полезна для наблюдателей и некоторых кэшей, но объект может исчезнуть между обращениями; полученный результат weakref сначала сохраняют и проверяют. Weakref.finalize подходит для резервной очистки, если callback сам не удерживает финализируемый объект, например через bound method.

## 7. Heap, кадры и аллокатор

Python-объекты располагаются в управляемой интерпретатором памяти. Локальная переменная списка — локальная ссылка, а не размещение всего списка на системном стеке. Возврат списка из функции продлевает его жизнь через новую внешнюю ссылку; переносить его «со стека в кучу» не требуется.

Стек вызовов — логическая цепочка кадров с локальными привязками и состоянием исполнения. Она отличается от C-стека. Реальное размещение и материализация кадров менялись; генератор сохраняет состояние даже между возобновлениями.

Аллокатор может держать освобождённые блоки для будущих объектов. Для небольших объектов обычный CPython использует специализированные структуры; другие выделения идут через иные пути, включая нативные библиотеки. Фрагментация мешает вернуть целую область ОС, даже если часть объектов уже умерла.

Поэтому падение числа живых объектов не обязано немедленно уменьшить RSS. RSS включает ещё интерпретатор, стеки, библиотеки и нативные буферы. Отдельно различают текущую живую память и пик временных выделений.

## 8. Что меняет __slots__

Slots описывают фиксированные места атрибутов и обычно позволяют обойтись без экземплярного __dict__. Это уменьшает служебную память множества однотипных объектов. Значения полей всё равно являются объектами со своей памятью.

Slots реализуются дескрипторами; они не делают поля неизменяемыми, не проверяют типы и не отключают GC. Родительский __dict__ нельзя убрать slots потомка; подкласс без slots обычно снова получает словарь. Для weak references может понадобиться __weakref__.

Пользу оценивают на всём наборе объектов, а не только getsizeof одного экземпляра: у обычного экземпляра есть отдельный словарь, у обоих вариантов — граф значений.

## 9. Как исследовать рост памяти

1. Разделить постоянный рост после одинаковых операций и разовый высокий пик.
2. Сравнить RSS и Python-выделения: tracemalloc не охватывает все произвольные нативные буферы.
3. Запустить tracemalloc до исследуемой работы, сравнить snapshots по местам выделения.
4. Для растущих типов найти цепочки удержания: кэши, подписки, задачи, traceback.
5. Изменить владение/лимиты, повторить ту же нагрузку и сравнить динамику.

Getsizeof отвечает о самом объекте, а не суммарном размере достижимого графа. Рекурсивная сумма без учёта идентичности дважды посчитает общие узлы и зациклится на циклах. Collect полезен как диагностический шаг, но не заменяет поиск удерживающей ссылки.
