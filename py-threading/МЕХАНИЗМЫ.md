# Потоки: выполнение, GIL и синхронизация

Разбор отвечает на вопросы «кто сейчас работает, кто ждёт и что защищает данные». Справочник — [КОНСПЕКТ.md](КОНСПЕКТ.md), сравнение с задачами цикла событий — [asyncio](../py-asyncio/МЕХАНИЗМЫ.md). Исполняемые примеры используют стандартную библиотеку Python 3.11+.

## 1. Процесс, поток и задача

Процесс — контейнер ресурсов ОС с собственным адресным пространством. Поток — последовательность исполнения внутри процесса: у него своё состояние процессора и стек вызовов, но Python-объекты и другие ресурсы процесса могут быть общими с соседними потоками.

ОС планирует готовые потоки и может переключать их независимо от `await`. Заблокированный на I/O поток не выполняет полезные инструкции, однако соседний поток может продвигаться. Конкурентность означает перекрытие времени работы; параллелизм — фактическое одновременное исполнение.

Объект Thread описывает управление одним запуском. Его создание ещё не создаёт работающего исполнителя; start организует новый поток, run при прямом вызове остаётся обычным вызовом. join ждёт завершения, но не запускает и не останавливает работу.

```text
создан → start → готов/выполняется ↔ ждёт I/O или синхронизацию → завершён
                                                                ↑
                                                    join ждёт этот переход
```

После join с timeout нужно проверить is_alive. Истечение ожидания не меняет состояние самого worker. Один Thread повторно не запускают; пул переиспользует потоки для разных заданий.

## 2. Что защищает GIL

В обычной сборке CPython GIL согласует исполнение Python-кода потоками одного интерпретатора: одновременно такой код исполняет один поток. Это механизм реализации интерпретатора, а не общий закон языка Python.

При блокирующем I/O интерпретатор обычно освобождает GIL. Пока один поток ждёт сеть, другой исполняет Python-код. Некоторые C-расширения тоже освобождают GIL на вычислениях и могут параллельно использовать ядра.

Чистый Python CPU-bound код в нескольких потоках обычного интерпретатора обычно не ускоряется: появляется конкуренция за GIL и накладные расходы. Для выбора решения сначала измеряют, где уходит время, затем рассматривают процессы, нативный код или другой алгоритм.

С Python 3.13 существуют отдельные free-threaded сборки. Они меняют возможность параллельного исполнения, но не превращают составные бизнес-операции в атомарные. На собеседовании стоит назвать реализацию и сборку, а не говорить «Python вообще не умеет потоки».

## 3. Гонка — нарушение инварианта между шагами

Пусть правило требует «если товара осталось достаточно, уменьшить остаток». Чтение, решение и запись образуют одну логическую операцию, но не обязательно одно неделимое действие. Между шагами может вмешаться сосед.

Детерминированная демонстрация потерянного обновления:

```python
from threading import Barrier, Thread

counter = 0
both_read = Barrier(2)

def increment():
    global counter
    old = counter
    both_read.wait()  # Оба сначала прочитали одно старое значение.
    counter = old + 1

threads = [Thread(target=increment) for _ in range(2)]
for thread in threads:
    thread.start()
for thread in threads:
    thread.join()
assert counter == 1
```

Одновременное исполнение Python-инструкций для этой ошибки не нужно. Достаточно чередования «прочитал A → прочитал B → записал A → записал B». Поведение `counter += 1` в конкретном тесте/версии не является доказательством безопасности произвольного read–modify–write.

## 4. Lock защищает область, а не переменную

Lock допускает одного участника в критическую секцию. Он не знает, какой объект мы хотим защитить. Все участники должны использовать **один общий Lock** и охватывать им всю операцию, поддерживающую инвариант.

```python
from threading import Lock

lock = Lock()
counter = 0

def increment():
    global counter
    with lock:
        counter += 1
```

Отдельный Lock на каждый вызов создаёт несколько независимых дверей. Блокировка только записи оставляет старое чтение незащищённым. `with` освобождает блокировку при обычном выходе и исключении, но не гарантирует завершение операции при аварии процесса.

RLock дополнительно хранит владельца и глубину входа: тот же поток может войти повторно, другие ждут последнего освобождения. Он помогает при вложенных вызовах, использующих одну защиту; не устраняет циклы ожиданий между разными блокировками и не делает операцию транзакцией с rollback.

## 5. Condition: данные важнее уведомления

Condition соединяет блокировку общих данных с ожиданием изменения их состояния. Потребителю нужна не абстрактная команда «проснись», а истинность предиката «очередь не пуста».

Механизм:

1. Потребитель под Lock проверяет предикат.
2. Если он ложен, wait освобождает Lock и приостанавливает поток.
3. Производитель под тем же Lock меняет данные и вызывает notify.
4. Производитель выходит из критической секции.
5. Потребитель снова получает Lock и **повторно проверяет** предикат.

Notify не передаёт владение Lock и не резервирует элемент конкретному потребителю. Пока разбуженный получал Lock, другой мог уже забрать данные. Поэтому проверка идёт в цикле или wait_for. Уведомления не являются накопительной очередью событий; если данные уже готовы, предикат позволяет не ждать вообще.

## 6. Примитивы выражают разные модели ожидания

| Примитив | Какое состояние хранит | Пример |
|---|---|---|
| Event | Установленный/сброшенный флаг | Сигнал остановки всем worker |
| Semaphore | Число свободных разрешений | Не более N одновременных запросов |
| Barrier | Приход участников на этап | Начать следующий этап после всех |
| Queue | Отдельные элементы и учёт работы | Передать каждую задачу одному потребителю |

Десять set у Event не создают десять заданий. Semaphore ограничивает активность, но не число ожидающих работ или частоту запросов в секунду. Barrier требует фиксированного состава: потеря участника должна приводить к timeout/abort, иначе остальные могут ждать бесконечно.

Bounded Queue создаёт backpressure: при заполнении producer ждёт или отказывает в новой работе. Это ограничивает память и накопление задержки. Queue.join ждёт task_done для всех поставленных элементов; Thread.join ждёт завершения потока — это разные события.

## 7. Deadlock и цена слишком широкой защиты

Если поток A держит L1 и ждёт L2, а B держит L2 и ждёт L1, возник цикл ожиданий. Другой пример — родитель делает join под Lock, который нужен ребёнку для выхода.

Основные приёмы: одинаковый порядок захвата, короткие критические секции, отсутствие сетевых ожиданий под общей блокировкой, передача сообщений владельцу данных. Timeout помогает обнаружить проблему, но после отказа захвата нужно корректно обработать незавершённую операцию.

Даже без deadlock большой Lock может сериализовать почти всю программу. Слишком мелкие Lock, наоборот, позволяют увидеть противоречивые сочетания полей. Размер защиты выбирают по инварианту, затем проверяют конкуренцию измерениями.

## 8. Остановка, ошибки и владение

Thread не имеет безопасного штатного принудительного kill: остановка посреди изменения общей структуры оставила бы повреждённое состояние. Worker периодически проверяет Event, использует ограниченные I/O-ожидания, освобождает ресурсы и завершается. Владелец подаёт сигнал и делает join.

Daemon-поток не удерживает интерпретатор от завершения. Это не гарантия надёжного фонового выполнения: обязательную запись могут оборвать. Ошибка обычного Thread завершает его и попадает в excepthook; join сам по себе её не пробрасывает. Future из ThreadPoolExecutor предоставляет отдельный канал результата и ошибки; его timeout тоже не убивает уже работающий поток.

threading.local разделяет значения по потокам. Если пул использует поток повторно для другого запроса, прежние значения могут сохраниться без очистки. Для контекста asyncio-задач применяют ContextVar: много задач может жить в одном потоке.
