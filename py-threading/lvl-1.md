## Введение

Модуль `threading` позволяет выполнять несколько [потоков](https://ru.wikipedia.org/wiki/Поток_выполнения) (более мелких единиц процесса) конкурентно в пределах одного процесса. Он позволяет создавать потоки и управлять ими, давая возможность выполнять задачи параллельно, с общим пространством памяти. Потоки особенно полезны, когда задачи ограничены вводом-выводом (I/O-bound), например работа с файлами или сетевые запросы, — когда большая часть времени уходит на ожидание внешних ресурсов.

Типичный сценарий использования `threading` — управление пулом рабочих потоков, которые могут конкурентно обрабатывать несколько задач. Вот простой пример создания и запуска потоков с помощью `Thread`:

```python
import threading
import time

def crawl(link, delay=3):
    print(f"crawl started for {link}")
    time.sleep(delay)  # Блокирующий ввод-вывод (имитация сетевого запроса)
    print(f"crawl ended for {link}")

links = [
    "https://python.org",
    "https://docs.python.org",
    "https://peps.python.org",
]

# Создаём поток для каждой ссылки
threads = []
for link in links:
    # `args` передаёт позиционные аргументы, `kwargs` — именованные
    t = threading.Thread(target=crawl, args=(link,), kwargs={"delay": 2})
    threads.append(t)

# Запускаем каждый поток
for t in threads:
    t.start()

# Ждём завершения всех потоков
for t in threads:
    t.join()
```

> *Изменено в версии 3.7:* раньше этот модуль был необязательным, теперь он доступен всегда.

> **См. также**
>
> `concurrent.futures.ThreadPoolExecutor` предлагает более высокоуровневый интерфейс для отправки задач в фоновый поток без блокировки вызывающего потока, при этом позволяя получать их результаты, когда они понадобятся.
>
> `queue` предоставляет потокобезопасный интерфейс для обмена данными между работающими потоками.
>
> `asyncio` предлагает альтернативный подход к конкурентности на уровне задач, не требующий нескольких потоков операционной системы.

> **Примечание**
>
> В серии Python 2.x этот модуль содержал имена в стиле `camelCase` для некоторых методов и функций. Начиная с Python 3.10 они устарели, но по-прежнему поддерживаются для совместимости с Python 2.5 и ниже.

> **Детали реализации CPython**
>
> В CPython из-за [глобальной блокировки интерпретатора](https://docs.python.org/3/glossary.html#term-global-interpreter-lock) (GIL) в каждый момент времени код Python может выполнять только один поток (хотя некоторые библиотеки, ориентированные на производительность, могут обходить это ограничение). Если вы хотите, чтобы приложение лучше использовало вычислительные ресурсы многоядерных машин, рекомендуется использовать `multiprocessing` или `concurrent.futures.ProcessPoolExecutor`. Тем не менее потоки остаются подходящей моделью, если нужно одновременно выполнять несколько задач, ограниченных вводом-выводом.

## GIL и вопросы производительности

В отличие от модуля `multiprocessing`, который использует отдельные процессы, чтобы обойти [глобальную блокировку интерпретатора](https://docs.python.org/3/glossary.html#term-global-interpreter-lock) (GIL), модуль `threading` работает в рамках одного процесса, то есть все потоки разделяют одно и то же пространство памяти. Однако GIL ограничивает выигрыш в производительности от потоков для задач, нагружающих процессор (CPU-bound), поскольку байт-код Python в каждый момент может выполнять только один поток. Несмотря на это, потоки остаются полезным инструментом для достижения конкурентности во многих сценариях.

Начиная с Python 3.13, [сборки со свободными потоками](https://docs.python.org/3/glossary.html#term-free-threading) (free-threaded) могут отключать GIL, обеспечивая по-настоящему параллельное выполнение потоков, но эта возможность по умолчанию недоступна (см. [PEP 703](https://peps.python.org/pep-0703/)).

## Справочник

Модуль определяет следующие функции:

### `threading.active_count()`

Возвращает количество объектов `Thread`, которые сейчас живы. Возвращаемое число равно длине списка, возвращаемого `enumerate()`.

Функция `activeCount` — устаревший псевдоним этой функции.

### `threading.current_thread()`

Возвращает текущий объект `Thread`, соответствующий потоку управления вызывающего кода. Если поток управления вызывающего кода был создан не через модуль `threading`, возвращается фиктивный (dummy) объект потока с ограниченной функциональностью.

Функция `currentThread` — устаревший псевдоним этой функции.

### `threading.excepthook(args, /)`

Обрабатывает необработанное исключение, возбуждённое в `Thread.run()`.

Аргумент *args* имеет следующие атрибуты:

* *exc_type*: тип исключения.
* *exc_value*: значение исключения, может быть `None`.
* *exc_traceback*: трассировка исключения, может быть `None`.
* *thread*: поток, возбудивший исключение, может быть `None`.

Если *exc_type* — `SystemExit`, исключение молча игнорируется. В противном случае исключение выводится в `sys.stderr`.

Если эта функция сама возбуждает исключение, для его обработки вызывается `sys.excepthook()`.

`threading.excepthook()` можно переопределить, чтобы управлять тем, как обрабатываются необработанные исключения, возбуждённые в `Thread.run()`.

Сохранение *exc_value* в пользовательском хуке может создать цикл ссылок. Его следует явно очистить, чтобы разорвать цикл, когда исключение больше не нужно.

Сохранение *thread* в пользовательском хуке может «воскресить» его, если он указывает на объект, который в данный момент финализируется. Не сохраняйте *thread* после завершения пользовательского хука, чтобы не воскрешать объекты.

> **См. также:** `sys.excepthook()` обрабатывает необработанные исключения.

> *Добавлено в версии 3.8.*

### `threading.__excepthook__`

Хранит исходное значение `threading.excepthook()`. Оно сохраняется, чтобы исходное значение можно было восстановить, если его заменили на сломанный или альтернативный объект.

> *Добавлено в версии 3.10.*

### `threading.get_ident()`

Возвращает «идентификатор потока» текущего потока. Это ненулевое целое число. Само значение не имеет прямого смысла; оно задумано как «волшебная метка», которую можно использовать, например, как индекс в словаре данных, специфичных для потока. Идентификаторы потоков могут переиспользоваться, когда один поток завершается, а другой создаётся.

> *Добавлено в версии 3.3.*

### `threading.get_native_id()`

Возвращает нативный целочисленный ID текущего потока, назначенный ядром. Это неотрицательное целое число. Его значение можно использовать для уникальной идентификации этого конкретного потока в масштабах всей системы (до завершения потока, после чего ОС может переиспользовать это значение).

> **Доступность:** Windows, FreeBSD, Linux, macOS, OpenBSD, NetBSD, AIX, DragonFlyBSD, GNU/kFreeBSD, Solaris.

> *Добавлено в версии 3.8.*
>
> *Изменено в версии 3.13:* добавлена поддержка GNU/kFreeBSD.
>
> *Изменено в версии 3.15:* добавлена поддержка Solaris.

### `threading.enumerate()`

Возвращает список всех объектов `Thread`, активных в данный момент. Список включает потоки-демоны и фиктивные объекты потоков, созданные `current_thread()`. В него не входят завершённые потоки и потоки, которые ещё не запущены. Однако главный поток всегда входит в результат, даже если он завершён.

### `threading.main_thread()`

Возвращает главный объект `Thread`. В обычных условиях главный поток — это поток, из которого был запущен интерпретатор Python.

> *Добавлено в версии 3.4.*

### `threading.settrace(func)`

Устанавливает функцию трассировки для всех потоков, запускаемых из модуля `threading`. *func* будет передана в `sys.settrace()` для каждого потока перед вызовом его метода `run()`.

### `threading.settrace_all_threads(func)`

Устанавливает функцию трассировки для всех потоков, запускаемых из модуля `threading`, и для всех потоков Python, выполняющихся в данный момент.

*func* будет передана в `sys.settrace()` для каждого потока перед вызовом его метода `run()`.

> *Добавлено в версии 3.12.*

### `threading.gettrace()`

Возвращает функцию трассировки, установленную через `settrace()`.

> *Добавлено в версии 3.10.*

### `threading.setprofile(func)`

Устанавливает функцию профилирования для всех потоков, запускаемых из модуля `threading`. *func* будет передана в `sys.setprofile()` для каждого потока перед вызовом его метода `run()`.

### `threading.setprofile_all_threads(func)`

Устанавливает функцию профилирования для всех потоков, запускаемых из модуля `threading`, и для всех потоков Python, выполняющихся в данный момент.

*func* будет передана в `sys.setprofile()` для каждого потока перед вызовом его метода `run()`.

> *Добавлено в версии 3.12.*

### `threading.getprofile()`

Возвращает функцию профилирования, установленную через `setprofile()`.

> *Добавлено в версии 3.10.*

### `threading.stack_size([size])`

Возвращает размер стека потока, используемый при создании новых потоков. Необязательный аргумент *size* задаёт размер стека для потоков, создаваемых впоследствии, и должен быть равен 0 (использовать размер по умолчанию для платформы или из конфигурации) или положительному целому числу не меньше 32 768 (32 КиБ). Если *size* не указан, используется 0. Если изменение размера стека потока не поддерживается, возбуждается `RuntimeError`. Если указан недопустимый размер стека, возбуждается `ValueError`, и размер стека не меняется. 32 КиБ — сейчас минимальный поддерживаемый размер стека, гарантирующий достаточно места в стеке для самого интерпретатора. Учтите, что на некоторых платформах могут быть особые ограничения на размер стека, например минимальный размер больше 32 КиБ или требование выделять память кратно размеру страницы памяти системы — за подробностями обращайтесь к документации платформы (часто используются страницы по 4 КиБ; при отсутствии более точной информации рекомендуется использовать размер стека, кратный 4096).

> **Доступность:** Windows, pthreads.
>
> Unix-платформы с поддержкой потоков POSIX.

Модуль также определяет следующую константу:

### `threading.TIMEOUT_MAX`

Максимальное допустимое значение параметра *timeout* блокирующих функций (`Lock.acquire()`, `RLock.acquire()`, `Condition.wait()` и т. д.). Указание таймаута больше этого значения приведёт к `OverflowError`.

> *Добавлено в версии 3.2.*

Устройство модуля в общих чертах основано на модели потоков Java. Однако если в Java блокировки и условные переменные — базовое поведение любого объекта, то в Python это отдельные объекты. Класс `Thread` в Python поддерживает часть поведения класса Thread из Java; в настоящее время нет приоритетов, нет групп потоков, и потоки нельзя уничтожать, останавливать, приостанавливать, возобновлять или прерывать. ### Данные, локальные для потока

Данные, локальные для потока (thread-local), — это данные, значения которых специфичны для каждого потока. Если у вас есть данные, которые должны быть локальными для потока, создайте объект `local` и используйте его атрибуты:

```python
>>> mydata = local()
>>> mydata.number = 42
>>> mydata.number
42
```

Можно также обращаться к словарю объекта `local`:

```python
>>> mydata.__dict__
{'number': 42}
>>> mydata.__dict__.setdefault('widgets', [])
[]
>>> mydata.widgets
[]
```

Если обратиться к данным из другого потока:

```python
>>> log = []
>>> def f():
...     items = sorted(mydata.__dict__.items())
...     log.append(items)
...     mydata.number = 11
...     log.append(mydata.number)

>>> import threading
>>> thread = threading.Thread(target=f)
>>> thread.start()
>>> thread.join()
>>> log
[[], 11]
```

мы получим другие данные. Более того, изменения, сделанные в другом потоке, не влияют на данные, видимые в этом потоке:

```python
>>> mydata.number
42
```

Разумеется, значения, полученные из объекта `local`, включая его атрибут `__dict__`, относятся к тому потоку, который был текущим в момент чтения атрибута. Поэтому, как правило, не стоит передавать эти значения между потоками, поскольку они относятся только к тому потоку, из которого получены.

Можно создавать собственные объекты `local`, наследуясь от класса `local`:

```python
>>> class MyLocal(local):
...     number = 2
...     def __init__(self, /, **kw):
...         self.__dict__.update(kw)
...     def squared(self):
...         return self.number ** 2
```

Это может пригодиться для поддержки значений по умолчанию, методов и инициализации. Обратите внимание: если определить метод `__init__()`, он будет вызываться каждый раз, когда объект `local` используется в отдельном потоке. Это необходимо, чтобы инициализировать словарь каждого потока.

Теперь, если создать объект `local`:

```python
>>> mydata = MyLocal(color='red')
```

у нас есть число по умолчанию:

```python
>>> mydata.number
2
```

начальный цвет:

```python
>>> mydata.color
'red'
>>> del mydata.color
```

И метод, работающий с данными:

```python
>>> mydata.squared()
4
```

Как и раньше, к данным можно обращаться из отдельного потока:

```python
>>> log = []
>>> thread = threading.Thread(target=f)
>>> thread.start()
>>> thread.join()
>>> log
[[('color', 'red')], 11]
```

не затрагивая данные этого потока:

```python
>>> mydata.number
2
>>> mydata.color
Traceback (most recent call last):
...
AttributeError: 'MyLocal' object has no attribute 'color'
```

Обратите внимание: подклассы могут определять `__slots__`, но они не являются локальными для потока. Они общие для всех потоков:

```python
>>> class MyLocal(local):
...     __slots__ = 'number'

>>> mydata = MyLocal()
>>> mydata.number = 42
>>> mydata.color = 'red'
```

Поэтому отдельный поток:

```python
>>> thread = threading.Thread(target=f)
>>> thread.start()
>>> thread.join()
```

влияет на то, что мы видим:

```python
>>> mydata.number
11
```

Класс, представляющий данные, локальные для потока.

### Объекты Thread

Класс `Thread` представляет действие, которое выполняется в отдельном потоке управления. Задать это действие можно двумя способами: передать вызываемый объект в конструктор или переопределить метод `run()` в подклассе. Никакие другие методы (кроме конструктора) в подклассе переопределять не следует. Другими словами, переопределяйте *только* методы `__init__()` и `run()` этого класса.

После создания объекта потока его действие нужно запустить вызовом метода `start()`. Он вызывает метод `run()` в отдельном потоке управления.

После запуска действия поток считается «живым». Он перестаёт быть живым, когда его метод `run()` завершается — либо нормально, либо из-за необработанного исключения. Метод `is_alive()` проверяет, жив ли поток.

Другие потоки могут вызывать метод `join()` потока. Это блокирует вызывающий поток до тех пор, пока не завершится поток, у которого вызван `join()`.

У потока есть имя. Его можно передать в конструктор, а читать или изменять через атрибут `name`.

Если метод `run()` возбуждает исключение, для его обработки вызывается `threading.excepthook()`. По умолчанию `threading.excepthook()` молча игнорирует `SystemExit`.

Поток можно пометить как «поток-демон» (daemon thread). Смысл этого флага в том, что вся программа на Python завершается, когда остаются только потоки-демоны. Начальное значение наследуется от создающего потока. Флаг можно задать через свойство `daemon` или аргумент конструктора *daemon*.

> **Примечание**
>
> Потоки-демоны резко останавливаются при завершении программы. Их ресурсы (открытые файлы, транзакции базы данных и т. д.) могут быть освобождены неправильно. Если вы хотите, чтобы потоки останавливались корректно, сделайте их не демонами и используйте подходящий механизм сигнализации, например `Event`.

Существует объект «главного потока»; он соответствует начальному потоку управления программы на Python. Это не поток-демон.

Возможно создание «фиктивных объектов потоков» (dummy thread objects). Это объекты потоков, соответствующие «чужим потокам» (alien threads) — потокам управления, запущенным вне модуля `threading`, например напрямую из кода на C. У фиктивных объектов потоков ограниченная функциональность; они всегда считаются живыми и демонами, и к ним нельзя применить [`join()`](#joitimeoutnone). Они никогда не удаляются, поскольку невозможно отследить завершение чужих потоков.

#### `class threading.Thread(group=None, target=None, name=None, args=(), kwargs={}, *, daemon=None, context=None)`

Этот конструктор всегда следует вызывать с именованными аргументами. Аргументы:

*group* должен быть `None`; он зарезервирован для будущего расширения, когда будет реализован класс `ThreadGroup`.

*target* — вызываемый объект, который будет вызван методом `run()`. По умолчанию `None`, то есть ничего не вызывается.

*name* — имя потока. По умолчанию создаётся уникальное имя вида «Thread-*N*», где *N* — небольшое десятичное число, или «Thread-*N* (target)», где «target» — это `target.__name__`, если указан аргумент *target*.

*args* — список или кортеж аргументов для вызова target. По умолчанию `()`.

*kwargs* — словарь именованных аргументов для вызова target. По умолчанию `{}`.

Если *daemon* не `None`, он явно задаёт, является ли поток демоном. Если `None` (по умолчанию), свойство демона наследуется от текущего потока.

*context* — значение `contextvars.Context`, используемое при запуске потока. Значение по умолчанию `None` означает, что поведение определяется флагом `sys.flags.thread_inherit_context`. Если флаг истинен, потоки будут запускаться с копией контекста того, кто вызвал `start()`. Если ложен — с пустым контекстом. Чтобы явно запустить поток с пустым контекстом, передайте новый экземпляр `contextvars.Context()`. Чтобы явно запустить поток с копией текущего контекста, передайте значение из `contextvars.copy_context()`. По умолчанию флаг истинен в сборках со свободными потоками и ложен в остальных.

Если подкласс переопределяет конструктор, он должен обязательно вызвать конструктор базового класса (`Thread.__init__()`) прежде, чем делать с потоком что-либо ещё.

> *Изменено в версии 3.3:* добавлен параметр *daemon*.
>
> *Изменено в версии 3.10:* если аргумент *name* опущен, используется имя *target*.
>
> *Изменено в версии 3.14:* добавлен параметр *context*.

##### `start()`

Запускает действие потока.

Его нужно вызывать не более одного раза для каждого объекта потока. Он организует вызов метода `run()` объекта в отдельном потоке управления.

Этот метод возбуждает `RuntimeError`, если вызвать его больше одного раза для одного и того же объекта потока.

Если это поддерживается, задаёт имя потока в операционной системе равным `threading.Thread.name`. Имя может быть обрезано в зависимости от ограничений ОС на имена потоков.

> *Изменено в версии 3.14:* задаётся имя потока в операционной системе.

##### `run()`

Метод, представляющий действие потока.

Этот метод можно переопределить в подклассе. Стандартный метод `run()` вызывает вызываемый объект, переданный в конструктор в аргументе *target* (если он есть), с позиционными и именованными аргументами, взятыми из аргументов *args* и *kwargs* соответственно.

Использование списка или кортежа в качестве аргумента *args*, передаваемого в `Thread`, даёт одинаковый результат.

Пример:

```python
>>> from threading import Thread
>>> t = Thread(target=print, args=[1])
>>> t.run()
1
>>> t = Thread(target=print, args=(1,))
>>> t.run()
1
```

##### `join(timeout=None)`

Ожидает завершения потока. Это блокирует вызывающий поток до тех пор, пока поток, у которого вызван `join()`, не завершится — нормально или из-за необработанного исключения, — либо пока не истечёт необязательный таймаут.

Если аргумент *timeout* указан и не равен `None`, это должно быть вещественное число, задающее таймаут операции в секундах (или долях секунды). Поскольку `join()` всегда возвращает `None`, чтобы понять, истёк ли таймаут, нужно после `join()` вызвать `is_alive()` — если поток всё ещё жив, вызов `join()` завершился по таймауту.

Если аргумент *timeout* не указан или равен `None`, операция будет блокироваться до завершения потока.

К потоку можно применять `join()` много раз.

`join()` возбуждает `RuntimeError` при попытке применить его к текущему потоку, поскольку это привело бы к взаимоблокировке (deadlock). Ошибкой также является вызов `join()` для потока до его запуска — такие попытки возбуждают то же исключение.

Если попытаться применить `join` к работающему потоку-демону на поздних стадиях [финализации Python](https://docs.python.org/3/glossary.html#term-interpreter-shutdown), `join()` возбуждает `PythonFinalizationError`.

> *Изменено в версии 3.14:* может возбуждать `PythonFinalizationError`.
>
> *Изменено в версии 3.15:* в качестве *timeout* принимает любое вещественное число, а не только целое или float.

##### `name`

Строка, используемая только для идентификации. Никакой семантики у неё нет. Нескольким потокам можно дать одинаковое имя. Начальное имя задаётся конструктором.

На некоторых платформах имя потока задаётся на уровне операционной системы при запуске потока, чтобы оно было видно в диспетчерах задач. Это имя может быть обрезано, чтобы уложиться в системный лимит (например, 15 байт в Linux или 63 байта в macOS).

Изменения *name* отражаются на уровне ОС только при переименовании текущего выполняющегося потока. (Изменение атрибута *name* у другого потока обновляет только объект Thread в Python.)

##### `getName()` / `setName()`

Устаревший API получения/установки для `name`; вместо этого используйте его напрямую как свойство.

> *Устарело с версии 3.10.*

##### `ident`

«Идентификатор потока» этого потока или `None`, если поток ещё не запущен. Это ненулевое целое число. См. функцию `get_ident()`. Идентификаторы потоков могут переиспользоваться, когда один поток завершается, а другой создаётся. Идентификатор доступен даже после завершения потока.

##### `native_id`

ID потока (`TID`), назначенный ОС (ядром). Это неотрицательное целое число или `None`, если поток ещё не запущен. См. функцию `get_native_id()`. Это значение можно использовать для уникальной идентификации этого конкретного потока в масштабах всей системы (до завершения потока, после чего ОС может переиспользовать это значение).

> **Примечание**
>
> Как и ID процессов, ID потоков действительны (гарантированно уникальны в системе) только с момента создания потока до его завершения.

> **Доступность:** Windows, FreeBSD, Linux, macOS, OpenBSD, NetBSD, AIX, DragonFlyBSD.

> *Добавлено в версии 3.8.*

##### `is_alive()`

Возвращает, жив ли поток.

Этот метод возвращает `True` с момента непосредственно перед запуском метода `run()` и до момента сразу после завершения метода `run()`. Функция модуля `enumerate()` возвращает список всех живых потоков.

##### `daemon`

Булево значение, указывающее, является ли этот поток демоном (`True`) или нет (`False`). Его нужно задать до вызова `start()`, иначе возбуждается `RuntimeError`. Начальное значение наследуется от создающего потока; главный поток не является демоном, поэтому у всех потоков, созданных в главном потоке, по умолчанию `daemon` = `False`.

Вся программа на Python завершается, когда не остаётся живых потоков, не являющихся демонами.

##### `isDaemon()` / `setDaemon()`

Устаревший API получения/установки для `daemon`; вместо этого используйте его напрямую как свойство.

> *Устарело с версии 3.10.*

### Объекты Lock

Примитивная блокировка (lock) — это примитив синхронизации, который в заблокированном состоянии не принадлежит какому-либо конкретному потоку. В Python сейчас это самый низкоуровневый доступный примитив синхронизации, реализованный непосредственно модулем расширения `_thread`.

Примитивная блокировка находится в одном из двух состояний: «заблокирована» или «разблокирована». Создаётся она в разблокированном состоянии. У неё два основных метода: `acquire()` и `release()`. Когда состояние «разблокирована», `acquire()` меняет его на «заблокирована» и сразу возвращает управление. Когда состояние «заблокирована», `acquire()` блокируется до тех пор, пока вызов `release()` в другом потоке не изменит его на «разблокирована», затем вызов `acquire()` снова переводит её в «заблокирована» и возвращает управление. Метод `release()` следует вызывать только в заблокированном состоянии; он меняет состояние на «разблокирована» и сразу возвращает управление. При попытке освободить разблокированную блокировку возбуждается `RuntimeError`.

Блокировки также поддерживают [протокол контекстного менеджера](#использование-блокировок-условий-и-семафоров-в-инструкции-with).

Если несколько потоков заблокированы в `acquire()` в ожидании, пока состояние станет «разблокирована», то когда вызов `release()` сбрасывает состояние в «разблокирована», продолжает работу только один поток; какой именно из ожидающих — не определено и может различаться в разных реализациях.

Все методы выполняются атомарно.

#### `class threading.Lock()`

Класс, реализующий объекты примитивной блокировки. После того как поток захватил блокировку, последующие попытки её захватить блокируются, пока она не будет освобождена; освободить её может любой поток.

> *Изменено в версии 3.13:* `Lock` теперь класс. В более ранних версиях Python `Lock` был фабричной функцией, возвращавшей экземпляр внутреннего приватного типа блокировки.

##### `acquire(blocking=True, timeout=-1)`

Захватывает блокировку, блокирующе или неблокирующе.

При вызове с аргументом *blocking*, равным `True` (по умолчанию), блокируется, пока блокировка не будет разблокирована, затем переводит её в заблокированное состояние и возвращает `True`.

При вызове с аргументом *blocking*, равным `False`, не блокируется. Если вызов с *blocking*, равным `True`, заблокировался бы, сразу возвращает `False`; иначе переводит блокировку в заблокированное состояние и возвращает `True`.

При вызове с положительным значением аргумента *timeout* блокируется не дольше числа секунд, указанного в *timeout*, и только пока блокировку нельзя захватить. Аргумент *timeout*, равный `-1`, означает неограниченное ожидание. Указывать *timeout*, когда *blocking* равен `False`, запрещено.

Возвращаемое значение — `True`, если блокировка успешно захвачена, и `False`, если нет (например, если истёк *timeout*).

> *Изменено в версии 3.2:* добавлен параметр *timeout*.
>
> *Изменено в версии 3.2:* захват блокировки теперь может прерываться сигналами в POSIX, если это поддерживает нижележащая реализация потоков.
>
> *Изменено в версии 3.14:* захват блокировки теперь может прерываться сигналами в Windows.
>
> *Изменено в версии 3.15:* в качестве *timeout* принимает любое вещественное число, а не только целое или float.

##### `release()`

Освобождает блокировку. Это можно вызывать из любого потока, а не только из того, который захватил блокировку.

Если блокировка заблокирована, сбрасывает её в разблокированное состояние и возвращает управление. Если какие-либо другие потоки заблокированы в ожидании разблокировки, позволяет продолжить работу ровно одному из них.

При вызове для разблокированной блокировки возбуждается `RuntimeError`.

Возвращаемого значения нет.

##### `locked()`

Возвращает `True`, если блокировка захвачена.

### Объекты RLock

Реентерабельная (повторно входимая) блокировка — это примитив синхронизации, который один и тот же поток может захватывать несколько раз. Внутри она использует понятия «поток-владелец» и «уровень рекурсии» в дополнение к состояниям «заблокирована/разблокирована», используемым примитивными блокировками. В заблокированном состоянии блокировкой владеет какой-то поток; в разблокированном — ни один поток ею не владеет.

Потоки вызывают метод блокировки `acquire()`, чтобы заблокировать её, и метод `release()`, чтобы разблокировать.

> **Примечание**
>
> Реентерабельные блокировки поддерживают [протокол контекстного менеджера](#использование-блокировок-условий-и-семафоров-в-инструкции-with), поэтому рекомендуется использовать `with` вместо ручного вызова `acquire()` и `release()` для захвата и освобождения блокировки для блока кода.

Пары вызовов `acquire()`/`release()` у RLock могут быть вложенными — в отличие от `acquire()`/`release()` у Lock. Только последний вызов `release()` (вызов `release()` самой внешней пары) сбрасывает блокировку в разблокированное состояние и позволяет продолжить работу другому потоку, заблокированному в `acquire()`.

`acquire()`/`release()` нужно использовать парами: на каждый acquire должен приходиться release в потоке, который захватил блокировку. Если не вызвать release столько раз, сколько раз была захвачена блокировка, это может привести к взаимоблокировке.

#### `class threading.RLock()`

Этот класс реализует объекты реентерабельной блокировки. Реентерабельную блокировку должен освобождать тот поток, который её захватил. После того как поток захватил реентерабельную блокировку, этот же поток может захватить её снова без блокировки; поток должен освободить её столько раз, сколько захватил.

Обратите внимание, что `RLock` на самом деле фабричная функция, возвращающая экземпляр самой эффективной версии конкретного класса RLock, поддерживаемой платформой.

##### `acquire(blocking=True, timeout=-1)`

Захватывает блокировку, блокирующе или неблокирующе.

> **См. также:** [Использование RLock как контекстного менеджера](#использование-блокировок-условий-и-семафоров-в-инструкции-with) — рекомендуется вместо ручных вызовов `acquire()` и `release()`, когда это возможно.

При вызове с аргументом *blocking*, равным `True` (по умолчанию):

* Если блокировкой не владеет ни один поток, захватывает блокировку и сразу возвращает управление.
* Если блокировкой владеет другой поток, блокируется, пока не удастся захватить блокировку, или до истечения *timeout*, если он задан положительным значением.
* Если блокировкой владеет этот же поток, захватывает блокировку ещё раз и сразу возвращает управление. В этом и состоит разница между `Lock` и `RLock`: `Lock` обрабатывает этот случай так же, как предыдущий, — блокируется, пока блокировку нельзя будет захватить.

При вызове с аргументом *blocking*, равным `False`:

* Если блокировкой не владеет ни один поток, захватывает блокировку и сразу возвращает управление.
* Если блокировкой владеет другой поток, сразу возвращает управление.
* Если блокировкой владеет этот же поток, захватывает блокировку ещё раз и сразу возвращает управление.

Во всех случаях, если потоку удалось захватить блокировку, возвращается `True`. Если не удалось (то есть в неблокирующем режиме или по истечении таймаута), возвращается `False`.

Если метод вызывается несколько раз, то невызов `release()` столько же раз может привести к взаимоблокировке. Подумайте об использовании `RLock` как контекстного менеджера вместо прямого вызова acquire/release.

> *Изменено в версии 3.2:* добавлен параметр *timeout*.
>
> *Изменено в версии 3.15:* в качестве *timeout* принимает любое вещественное число, а не только целое или float.

##### `release()`

Освобождает блокировку, уменьшая уровень рекурсии. Если после уменьшения он равен нулю, сбрасывает блокировку в разблокированное состояние (ни один поток ею не владеет), и если какие-либо другие потоки заблокированы в ожидании разблокировки, позволяет продолжить работу ровно одному из них. Если после уменьшения уровень рекурсии всё ещё ненулевой, блокировка остаётся заблокированной и принадлежит вызывающему потоку.

Вызывайте этот метод только когда вызывающий поток владеет блокировкой. Если вызвать этот метод, когда блокировка не захвачена, возбуждается `RuntimeError`.

Возвращаемого значения нет.

##### `locked()`

Возвращает булево значение, указывающее, заблокирован ли этот объект в данный момент.

> *Добавлено в версии 3.14.*

### Объекты Condition

Условная переменная (condition variable) всегда связана с какой-либо блокировкой; её можно передать, или она будет создана по умолчанию. Передача полезна, когда несколько условных переменных должны использовать одну и ту же блокировку. Блокировка является частью объекта условия: отслеживать её отдельно не нужно.

Условная переменная подчиняется [протоколу контекстного менеджера](#использование-блокировок-условий-и-семафоров-в-инструкции-with): инструкция `with` захватывает связанную блокировку на время выполнения вложенного блока. Методы `acquire()` и `release()` также вызывают соответствующие методы связанной блокировки.

Остальные методы нужно вызывать, удерживая связанную блокировку. Метод `wait()` освобождает блокировку, а затем блокируется, пока другой поток не разбудит его вызовом `notify()` или `notify_all()`. После пробуждения `wait()` снова захватывает блокировку и возвращает управление. Можно также указать таймаут.

Метод `notify()` будит один из потоков, ожидающих условную переменную, если такие есть. Метод `notify_all()` будит все потоки, ожидающие условную переменную.

Примечание: методы `notify()` и `notify_all()` не освобождают блокировку; это значит, что разбуженный поток или потоки вернутся из вызова `wait()` не сразу, а только когда поток, вызвавший `notify()` или `notify_all()`, наконец откажется от владения блокировкой.

Типичный стиль программирования с условными переменными использует блокировку для синхронизации доступа к некоторому общему состоянию; потоки, заинтересованные в определённом изменении состояния, многократно вызывают `wait()`, пока не увидят нужное состояние, а потоки, изменяющие состояние, вызывают `notify()` или `notify_all()`, когда изменяют его так, что оно может оказаться нужным для одного из ожидающих. Например, следующий код — общая ситуация «производитель–потребитель» с неограниченной ёмкостью буфера:

```python
# Потребить один элемент
with cv:
    while not an_item_is_available():
        cv.wait()
    get_an_available_item()

# Произвести один элемент
with cv:
    make_an_item_available()
    cv.notify()
```

Цикл `while`, проверяющий условие приложения, необходим, потому что `wait()` может вернуть управление через произвольно долгое время, и условие, вызвавшее вызов `notify()`, может уже не выполняться. Это неотъемлемое свойство многопоточного программирования. Метод `wait_for()` можно использовать, чтобы автоматизировать проверку условия и упростить вычисление таймаутов:

```python
# Потребить элемент
with cv:
    cv.wait_for(an_item_is_available)
    get_an_available_item()
```

Чтобы выбрать между `notify()` и `notify_all()`, подумайте, может ли одно изменение состояния быть интересно только одному или нескольким ожидающим потокам. Например, в типичной ситуации «производитель–потребитель» добавление одного элемента в буфер требует разбудить только один поток-потребитель.

#### `class threading.Condition(lock=None)`

Этот класс реализует объекты условных переменных. Условная переменная позволяет одному или нескольким потокам ждать, пока их не уведомит другой поток.

Если аргумент *lock* передан и не равен `None`, это должен быть объект `Lock` или `RLock`, и он используется как нижележащая блокировка. Иначе создаётся новый объект `RLock`, который и используется как нижележащая блокировка.

> *Изменено в версии 3.3:* из фабричной функции превращён в класс.

##### `acquire(*args)`

Захватывает нижележащую блокировку. Этот метод вызывает соответствующий метод нижележащей блокировки; возвращаемое значение — то, что возвращает этот метод.

##### `release()`

Освобождает нижележащую блокировку. Этот метод вызывает соответствующий метод нижележащей блокировки; возвращаемого значения нет.

##### `locked()`

Возвращает булево значение, указывающее, заблокирован ли этот объект в данный момент.

> *Добавлено в версии 3.14.*

##### `wait(timeout=None)`

Ожидает уведомления или истечения таймаута. Если на момент вызова этого метода вызывающий поток не захватил блокировку, возбуждается `RuntimeError`.

Этот метод освобождает нижележащую блокировку, а затем блокируется, пока его не разбудит вызов `notify()` или `notify_all()` для той же условной переменной в другом потоке, или пока не истечёт необязательный таймаут. После пробуждения или истечения таймаута он снова захватывает блокировку и возвращает управление.

Если аргумент *timeout* указан и не равен `None`, это должно быть вещественное число, задающее таймаут операции в секундах (или долях секунды).

Если нижележащая блокировка — `RLock`, она освобождается не с помощью своего метода `release()`, поскольку это может не разблокировать её, если она была захвачена рекурсивно несколько раз. Вместо этого используется внутренний интерфейс класса `RLock`, который действительно разблокирует её, даже если она была рекурсивно захвачена несколько раз. Затем при повторном захвате блокировки используется другой внутренний интерфейс, чтобы восстановить уровень рекурсии.

Возвращаемое значение — `True`, если только не истёк заданный *timeout*; в этом случае — `False`.

> *Изменено в версии 3.2:* раньше метод всегда возвращал `None`.

##### `wait_for(predicate, timeout=None)`

Ожидает, пока условие не станет истинным. *predicate* должен быть вызываемым объектом, результат которого интерпретируется как булево значение. Можно передать *timeout* — максимальное время ожидания.

Этот вспомогательный метод может многократно вызывать `wait()`, пока предикат не будет выполнен или пока не истечёт таймаут. Возвращаемое значение — последнее значение, возвращённое предикатом; оно будет ложным, если метод завершился по таймауту.

Если не учитывать таймаут, вызов этого метода примерно эквивалентен такому коду:

```python
while not predicate():
    cv.wait()
```

Поэтому действуют те же правила, что и для `wait()`: при вызове блокировка должна удерживаться, и при возврате она захватывается снова. Предикат вычисляется при удерживаемой блокировке.

> *Добавлено в версии 3.2.*

##### `notify(n=1)`

По умолчанию будит один поток, ожидающий это условие, если такой есть. Если на момент вызова этого метода вызывающий поток не захватил блокировку, возбуждается `RuntimeError`.

Этот метод будит не более *n* потоков, ожидающих условную переменную; если ожидающих потоков нет, он ничего не делает.

Текущая реализация будит ровно *n* потоков, если ожидают хотя бы *n* потоков. Однако полагаться на это поведение небезопасно. Будущая оптимизированная реализация может иногда будить больше *n* потоков.

Примечание: разбуженный поток на самом деле не вернётся из вызова `wait()`, пока не сможет снова захватить блокировку. Поскольку `notify()` не освобождает блокировку, это должен сделать вызвавший его код.

##### `notify_all()`

Будит все потоки, ожидающие это условие. Этот метод работает как `notify()`, но будит все ожидающие потоки, а не один. Если на момент вызова этого метода вызывающий поток не захватил блокировку, возбуждается `RuntimeError`.

Метод `notifyAll` — устаревший псевдоним этого метода.

### Объекты Semaphore

Это один из старейших примитивов синхронизации в истории информатики, изобретённый ранним нидерландским учёным-информатиком Эдсгером В. Дейкстрой (он использовал имена `P()` и `V()` вместо `acquire()` и `release()`).

Семафор управляет внутренним счётчиком, который уменьшается при каждом вызове `acquire()` и увеличивается при каждом вызове `release()`. Счётчик никогда не может стать меньше нуля; когда `acquire()` обнаруживает, что он равен нулю, он блокируется в ожидании, пока какой-нибудь другой поток не вызовет `release()`.

Семафоры также поддерживают [протокол контекстного менеджера](#использование-блокировок-условий-и-семафоров-в-инструкции-with).

#### `class threading.Semaphore(value=1)`

Этот класс реализует объекты семафоров. Семафор управляет атомарным счётчиком, равным количеству вызовов `release()` минус количество вызовов `acquire()` плюс начальное значение. Метод `acquire()` при необходимости блокируется, пока не сможет вернуть управление, не сделав счётчик отрицательным. Если *value* не передан, по умолчанию он равен 1.

Необязательный аргумент задаёт начальное значение *value* внутреннего счётчика; по умолчанию `1`. Если переданное *value* меньше 0, возбуждается `ValueError`.

> *Изменено в версии 3.3:* из фабричной функции превращён в класс.

##### `acquire(blocking=True, timeout=None)`

Захватывает семафор.

При вызове без аргументов:

* Если внутренний счётчик на входе больше нуля, уменьшает его на единицу и сразу возвращает `True`.
* Если внутренний счётчик на входе равен нулю, блокируется, пока его не разбудит вызов `release()`. После пробуждения (когда счётчик больше 0) уменьшает счётчик на 1 и возвращает `True`. Каждый вызов `release()` будит ровно один поток. Полагаться на порядок, в котором будятся потоки, не следует.

При вызове с *blocking*, равным `False`, не блокируется. Если вызов без аргументов заблокировался бы, сразу возвращает `False`; иначе делает то же, что и при вызове без аргументов, и возвращает `True`.

При вызове с *timeout*, отличным от `None`, блокируется не дольше *timeout* секунд. Если за этот интервал захват не удался, возвращает `False`. Иначе возвращает `True`.

> *Изменено в версии 3.2:* добавлен параметр *timeout*.
>
> *Изменено в версии 3.15:* в качестве *timeout* принимает любое вещественное число, а не только целое или float.

##### `release(n=1)`

Освобождает семафор, увеличивая внутренний счётчик на *n*. Если на входе он был равен нулю и другие потоки ждут, пока он снова станет больше нуля, будит *n* из этих потоков.

> *Изменено в версии 3.9:* добавлен параметр *n*, чтобы освобождать сразу несколько ожидающих потоков.

#### `class threading.BoundedSemaphore(value=1)`

Класс, реализующий объекты ограниченных семафоров. Ограниченный семафор проверяет, что его текущее значение не превышает начального. Если превышает, возбуждается `ValueError`. В большинстве случаев семафоры используются для защиты ресурсов ограниченной ёмкости. Если семафор освобождён слишком много раз, это признак ошибки. Если *value* не передан, по умолчанию он равен 1.

> *Изменено в версии 3.3:* из фабричной функции превращён в класс.

### Пример с `Semaphore`

Семафоры часто используются для защиты ресурсов ограниченной ёмкости, например сервера базы данных. В любой ситуации, когда размер ресурса фиксирован, следует использовать ограниченный семафор. Перед созданием рабочих потоков главный поток инициализирует семафор:

```python
maxconnections = 5
# ...
pool_sema = BoundedSemaphore(value=maxconnections)
```

После создания рабочие потоки вызывают методы acquire и release семафора, когда им нужно подключиться к серверу:

```python
with pool_sema:
    conn = connectdb()
    try:
        # ... используем подключение ...
    finally:
        conn.close()
```

Использование ограниченного семафора снижает вероятность того, что ошибка программирования, из-за которой семафор освобождается чаще, чем захватывается, останется незамеченной.

### Объекты Event

Это один из простейших механизмов взаимодействия между потоками: один поток сигнализирует о событии, а другие потоки его ждут.

Объект события управляет внутренним флагом, который можно установить в true методом `set()` и сбросить в false методом `clear()`. Метод `wait()` блокируется, пока флаг не станет истинным.

#### `class threading.Event()`

Класс, реализующий объекты событий. Событие управляет флагом, который можно установить в true методом `set()` и сбросить в false методом `clear()`. Метод `wait()` блокируется, пока флаг не станет истинным. Изначально флаг ложен.

> *Изменено в версии 3.3:* из фабричной функции превращён в класс.

##### `is_set()`

Возвращает `True` тогда и только тогда, когда внутренний флаг истинен.

Метод `isSet` — устаревший псевдоним этого метода.

##### `set()`

Устанавливает внутренний флаг в true. Все потоки, ожидающие, пока он станет истинным, пробуждаются. Потоки, вызывающие `wait()` после того, как флаг стал истинным, вообще не будут блокироваться.

##### `clear()`

Сбрасывает внутренний флаг в false. После этого потоки, вызывающие `wait()`, будут блокироваться, пока не будет вызван `set()`, снова устанавливающий внутренний флаг в true.

##### `wait(timeout=None)`

Блокируется, пока внутренний флаг ложен и пока не истёк таймаут, если он задан. Возвращаемое значение показывает причину, по которой этот блокирующий метод вернул управление: `True`, если флаг установлен в true, или `False`, если таймаут задан и внутренний флаг не стал истинным за указанное время ожидания.

Если аргумент timeout указан и не равен `None`, это должно быть вещественное число, задающее таймаут операции в секундах или долях секунды.

> *Изменено в версии 3.1:* раньше метод всегда возвращал `None`.

### Объекты Timer

Этот класс представляет действие, которое должно быть выполнено только по прошествии определённого времени, — таймер. `Timer` — подкласс `Thread`, и поэтому он также служит примером создания собственных потоков.

Таймеры, как и потоки, запускаются вызовом метода `Timer.start`. Таймер можно остановить (до того, как начнётся его действие) вызовом метода `cancel()`. Интервал, который таймер выждет перед выполнением действия, может не совпадать в точности с интервалом, указанным пользователем.

Например:

```python
def hello():
    print("hello, world")

t = Timer(30.0, hello)
t.start()  # через 30 секунд будет напечатано "hello, world"
```

#### `class threading.Timer(interval, function, args=None, kwargs=None)`

Создаёт таймер, который выполнит *function* с аргументами *args* и именованными аргументами *kwargs* по прошествии *interval* секунд. Если *args* равен `None` (по умолчанию), используется пустой список. Если *kwargs* равен `None` (по умолчанию), используется пустой словарь.

> *Изменено в версии 3.3:* из фабричной функции превращён в класс.

##### `cancel()`

Останавливает таймер и отменяет выполнение его действия. Это сработает, только если таймер ещё находится в стадии ожидания.

### Объекты Barrier

> *Добавлено в версии 3.2.*

Этот класс предоставляет простой примитив синхронизации для фиксированного числа потоков, которым нужно дождаться друг друга. Каждый из потоков пытается пройти барьер, вызывая метод `wait()`, и блокируется, пока все потоки не сделают свои вызовы `wait()`. В этот момент потоки освобождаются одновременно.

Барьер можно переиспользовать любое количество раз для того же числа потоков.

Например, вот простой способ синхронизировать поток клиента и поток сервера:

```python
b = Barrier(2, timeout=5)

def server():
    start_server()
    b.wait()
    while True:
        connection = accept_connection()
        process_server_connection(connection)

def client():
    b.wait()
    while True:
        connection = make_connection()
        process_client_connection(connection)
```

#### `class threading.Barrier(parties, action=None, timeout=None)`

Создаёт объект барьера для *parties* потоков. *action*, если передан, — вызываемый объект, который будет вызван одним из потоков, когда они будут освобождены. *timeout* — значение таймаута по умолчанию, если для метода `wait()` он не указан.

##### `wait(timeout=None)`

Проходит барьер. Когда все потоки — участники барьера вызвали эту функцию, все они освобождаются одновременно. Если передан *timeout*, он используется вместо любого значения, переданного в конструктор класса.

Возвращаемое значение — целое число в диапазоне от 0 до *parties* – 1, своё для каждого потока. Его можно использовать, чтобы выбрать поток для выполнения какой-либо особой служебной работы, например:

```python
i = barrier.wait()
if i == 0:
    # Напечатать это нужно только одному потоку
    print("passed the barrier")
```

Если в конструктор был передан *action*, один из потоков вызовет его перед освобождением. Если этот вызов возбудит ошибку, барьер переходит в «сломанное» состояние.

Если вызов завершается по таймауту, барьер переходит в сломанное состояние.

Этот метод может возбудить исключение `BrokenBarrierError`, если барьер сломан или сброшен, пока поток ожидает.

##### `reset()`

Возвращает барьер в исходное, пустое состояние. Все потоки, ожидающие его, получат исключение `BrokenBarrierError`.

Учтите, что использование этой функции может потребовать внешней синхронизации, если есть другие потоки, состояние которых неизвестно. Если барьер сломан, возможно, лучше просто оставить его и создать новый.

##### `abort()`

Переводит барьер в сломанное состояние. Это приводит к тому, что любые текущие или будущие вызовы `wait()` завершатся с `BrokenBarrierError`. Используйте это, например, если одному из потоков нужно прервать работу, чтобы избежать взаимоблокировки приложения.

Возможно, предпочтительнее просто создать барьер с разумным значением *timeout*, чтобы автоматически защититься от того, что один из потоков пойдёт не так.

##### `parties`

Количество потоков, необходимое для прохождения барьера.

##### `n_waiting`

Количество потоков, ожидающих у барьера в данный момент.

##### `broken`

Булево значение, равное `True`, если барьер находится в сломанном состоянии.

#### `exception threading.BrokenBarrierError`

Это исключение — подкласс `RuntimeError` — возбуждается, когда объект `Barrier` сброшен или сломан.

## Использование блокировок, условий и семафоров в инструкции `with`

Все объекты этого модуля, у которых есть методы `acquire` и `release`, можно использовать как контекстные менеджеры в инструкции `with`. Метод `acquire` вызывается при входе в блок, а `release` — при выходе из него. Поэтому следующий фрагмент:

```python
with some_lock:
    # что-то делаем...
```

эквивалентен:

```python
some_lock.acquire()
try:
    # что-то делаем...
finally:
    some_lock.release()
```

В настоящее время как контекстные менеджеры инструкции `with` можно использовать объекты `Lock`, `RLock`, `Condition`, `Semaphore` и `BoundedSemaphore`.

## Синхронизация итераторов

По умолчанию итераторы Python не поддерживают конкурентный доступ. Большинство итераторов не дают никаких гарантий при одновременном обращении из нескольких потоков. Например, итераторы-генераторы возбуждают `ValueError`, если один из их методов итератора вызывается, когда генератор уже выполняется. Инструменты этого раздела позволяют добавить надёжную поддержку конкурентности обычным итераторам и вызываемым объектам, создающим итераторы.

Обёртка `serialize_iterator` позволяет нескольким потокам совместно использовать один итератор и по очереди брать из него значения. Пока один поток выполняет `__next__()`, остальные блокируются, пока итератор не освободится. Каждое значение, выданное нижележащим итератором, достаётся ровно одному вызывающему.

Функция `concurrent_tee` позволяет нескольким потокам получать каждый полный поток значений из одного нижележащего итератора. Она создаёт независимые итераторы, которые берут значения из одного источника. Значения буферизуются, пока их не потребят все производные итераторы.

### `class threading.serialize_iterator(iterable)`

Возвращает обёртку итератора, которая сериализует конкурентные вызовы `__next__()` с помощью блокировки.

Если обёрнутый итератор также определяет `send()`, `throw()` или `close()`, эти вызовы тоже сериализуются.

Это позволяет совместно использовать один итератор, в том числе итератор-генератор, в нескольких потоках. Блокировка гарантирует, что вызовы обрабатываются по одному. Сама обёртка не дублирует и не пропускает значения. Каждый элемент нижележащего итератора отдаётся ровно одному вызывающему.

Эта обёртка не копирует и не буферизует значения. Потоки, вызывающие `next()`, пока другой поток уже продвигает итератор, будут заблокированы до завершения активного вызова.

Пример:

```python
import threading

def squares(n):
    for x in range(n):
        yield x * x

def consume(name, iterable):
    for item in iterable:
        print(name, item)

source = threading.serialize_iterator(squares(5))

t1 = threading.Thread(target=consume, args=("left", source))
t2 = threading.Thread(target=consume, args=("right", source))
t1.start()
t2.start()
t1.join()
t2.join()
```

В этом примере каждое число печатается ровно один раз, но работа делится между двумя потоками.

> *Добавлено в версии 3.15.*

### `threading.synchronized_iterator(func)`

Оборачивает вызываемый объект, создающий итераторы, так, чтобы каждый возвращаемый им итератор автоматически пропускался через `serialize_iterator`.

Это особенно полезно как [декоратор](https://docs.python.org/3/glossary.html#term-decorator) для функций-генераторов: их итераторы-генераторы можно потреблять из нескольких потоков.

Пример:

```python
import threading

@threading.synchronized_iterator
def squares(n):
    for x in range(n):
        yield x * x

def consume(name, iterable):
    for item in iterable:
        print(name, item)

source = squares(5)

t1 = threading.Thread(target=consume, args=("left", source))
t2 = threading.Thread(target=consume, args=("right", source))
t1.start()
t2.start()
t1.join()
t2.join()
```

Возвращаемая обёртка сохраняет метаданные *func*, такие как её имя и ссылку на обёрнутую функцию.

> *Добавлено в версии 3.15.*

### `threading.concurrent_tee(iterable, n=2)`

Возвращает *n* независимых итераторов из одного входного *iterable* с гарантированным поведением при конкурентном потреблении производных итераторов.

Эта функция похожа на `itertools.tee()`, но предназначена для случаев, когда исходный итератор может снабжать потребителей, работающих в разных потоках. Каждый возвращаемый итератор выдаёт все значения нижележащего итерируемого объекта в том же порядке.

Внутри значения буферизуются, пока их не потребят все производные итераторы.

Возвращаемые итераторы используют одну и ту же общую блокировку синхронизации. Каждый отдельный производный итератор предназначен для потребления одним потоком в каждый момент времени. Если один производный итератор сам должен использоваться несколькими потоками, оберните его в `serialize_iterator`.

Если *n* равно `0`, возвращается пустой кортеж. Если *n* отрицательно, возбуждается `ValueError`.

Пример:

```python
import threading

def squares(n):
    for x in range(n):
        yield x * x

def consume(name, iterable):
    for item in iterable:
        print(name, item)

source = squares(5)
left, right = threading.concurrent_tee(source)

t1 = threading.Thread(target=consume, args=("left", left))
t2 = threading.Thread(target=consume, args=("right", right))
t1.start()
t2.start()
t1.join()
t2.join()
```

В этом примере оба потока-потребителя видят полную последовательность квадратов из одного генератора.

> *Добавлено в версии 3.15.*
