# threading: конспект к аттестации

Сжатое содержание `lvl-1.md`: модель потоков, жизненный цикл, синхронизация и типичные ошибки.

## 1. Когда нужны потоки

Потоки одного процесса разделяют память и ресурсы, но имеют отдельные стеки выполнения. Планирует их операционная система; переключение не ограничено точками `await`.

Потоки полезны для I/O-bound задач с синхронными библиотеками: пока один поток ждёт сеть или диск, другие могут работать.

В обычной сборке CPython **GIL** допускает исполнение Python-байткода только одним потоком за раз в одном интерпретаторе. Поэтому чистые Python-вычисления обычно не ускоряются от добавления потоков. При I/O и в некоторых C-расширениях GIL освобождается.

С Python 3.13 существуют отдельные free-threaded сборки без обязательного GIL. Это не означает, что GIL отключён во всех установках Python. Отсутствие GIL также не отменяет необходимость синхронизации данных.

**GIL не заменяет Lock:** последовательность «проверить — изменить» не становится одной атомарной операцией. Корректность нельзя строить на случайном поведении конкретной версии интерпретатора.

## 2. Жизненный цикл Thread

```python
from threading import Thread

def worker(value):
    print(value * 2)

threads = [Thread(target=worker, args=(i,)) for i in range(3)]
for thread in threads:
    thread.start()
for thread in threads:
    thread.join()
```

- `target=worker` передаёт функцию; `target=worker()` вызовет её заранее в текущем потоке.
- `args=(value,)` — кортеж из одного элемента; `kwargs` — именованные аргументы.
- `start()` запускает `run()` в новом потоке; для одного объекта разрешён один запуск.
- Прямой `run()` — обычный вызов в текущем потоке, нового потока нет.
- `join(timeout=None)` блокирует вызывающего до завершения другого потока или таймаута. Всегда возвращает `None`.
- После `join(timeout)` вызовите `is_alive()`: `True` означает, что поток ещё работает. Истечение таймаута поток не останавливает.
- `join()` до `start()` и попытка ждать самого себя — `RuntimeError`. Повторно ждать уже запущенный поток можно.
- Если сразу после каждого `start()` делать `join()`, выполнение фактически станет последовательным.

Можно наследоваться от `Thread`, переопределяя `run()` и при необходимости `__init__()` с вызовом `super().__init__()`. Обычно передачи `target` достаточно.

`name` — диагностическое имя; `ident` — идентификатор Python, `native_id` — идентификатор ОС. Идентификаторы могут переиспользоваться после завершения потока.

## 3. Завершение и исключения

У Thread нет штатного безопасного принудительного `kill`. Используйте кооперативную остановку через `Event`, таймауты I/O и последующий `join()`.

```python
from threading import Event, Thread

stop = Event()

def worker():
    while not stop.wait(timeout=0.5):
        print("Очередная итерация")

thread = Thread(target=worker)
thread.start()
stop.set()
thread.join()
```

`stop.set()` сам по себе не прерывает зависший сетевой вызов: его ожидание тоже нужно ограничивать.

`daemon=True` означает, что этот поток не удерживает интерпретатор от завершения. Когда остаются только daemon-потоки, программа завершается; их файлы и транзакции могут остаться без корректной очистки. Демон — не способ надёжно выполнять обязательную работу в фоне. Флаг задают до `start()`; по умолчанию он наследуется от создающего потока.

Необработанная ошибка завершает соответствующий поток и передаётся в `threading.excepthook(args)`. Она не пробрасывается в вызвавший `join()` поток. По умолчанию выводится в stderr, а `SystemExit` игнорируется. Для удобного получения результатов и ошибок часто используют `ThreadPoolExecutor`: исключение будет получено через Future.

## 4. Гонки и взаимоблокировки

**Race condition** — результат зависит от порядка конкурентных действий. Например, два потока читают старое значение счётчика и записывают одинаковое новое, теряя одно увеличение.

```python
from threading import Lock

lock = Lock()
counter = 0

def increment():
    global counter
    with lock:
        counter += 1
```

Все обращения, которые должны быть согласованы, обязаны использовать **одну и ту же** блокировку. Создание нового Lock в каждом вызове ничего не защищает.

**Deadlock** — участники навсегда ждут ресурсов друг друга. Типичный случай: один захватил A и ждёт B, другой захватил B и ждёт A. Защита: одинаковый порядок захвата, короткие критические секции, отсутствие ненужных вложенных блокировок. Не ждите поток через `join()`, удерживая Lock, который ему нужен для завершения.

По возможности делите работу без общего изменяемого состояния и передавайте сообщения через `queue.Queue`.

## 5. Какой примитив выбрать

| Примитив | Назначение | Главное свойство |
|---|---|---|
| `Lock` | Взаимное исключение | Один участник в критической секции |
| `RLock` | Повторный захват владельцем | Один поток может захватить несколько раз |
| `Condition` | Дождаться состояния общих данных | Ожидание освобождает Lock и затем захватывает его снова |
| `Semaphore(N)` | Ограничить число одновременных операций | До N разрешений |
| `BoundedSemaphore(N)` | То же с проверкой лишних release | Нельзя увеличить счётчик выше исходного N |
| `Event` | Сообщить о наступлении события / остановке | Общий флаг, а не счётчик сообщений |
| `Barrier(N)` | Согласовать этап работы N участников | Все ждут прихода всех |
| `Timer` | Один отложенный вызов | Отдельный поток; время приблизительное |

## 6. Lock и RLock

`Lock.acquire()` захватывает блокировку или ждёт. `acquire(blocking=False)` возвращает `False`, если захват невозможен сразу. `acquire(timeout=...)` ограничивает ожидание. Неблокирующий режим не комбинируют с timeout.

`release()` освобождает Lock; освобождение незахваченного Lock вызывает `RuntimeError`. Обычный Lock не привязан к владельцу: технически его может освободить другой поток. Порядок пробуждения ожидающих не гарантирован.

Повторный захват обычного Lock тем же потоком блокирует его. `RLock` хранит владельца и глубину захвата; освободить его должен владелец столько же раз, сколько захватил. Другие потоки допускаются только после последнего освобождения.

Предпочитайте `with lock:` — освобождение произойдёт и при исключении. Контекстный менеджер также поддерживают RLock, Condition и семафоры.

## 7. Condition: ждать предикат, а не уведомление

Condition объединяет Lock (по умолчанию RLock) и очередь ожидающих. Состояние проверяют и изменяют под тем же Lock.

```python
from threading import Condition

condition = Condition()
items = []

def consume():
    with condition:
        condition.wait_for(lambda: bool(items))
        return items.pop()

def produce(item):
    with condition:
        items.append(item)
        condition.notify()
```

- `wait()` требует захваченного Lock; освобождает его на время ожидания и захватывает снова перед возвратом.
- После пробуждения условие могло уже измениться. Поэтому нужен `while not predicate: wait()`, а не `if`. `wait_for(predicate, timeout)` делает такую проверку сам.
- `notify(n)` будит до n ожидающих, `notify_all()` — всех. Вызывать их нужно под Lock.
- `notify()` **не освобождает** Lock: разбуженный поток продолжит работу лишь после его получения.
- Уведомления не накапливаются для будущих ожидающих; источником истины служит состояние данных.

## 8. Semaphore, Event, Barrier, Timer

**Semaphore:** `acquire()` уменьшает счётчик, при нуле ждёт; `release()` увеличивает. `with semaphore:` ограничивает число одновременных обращений, например к БД. `BoundedSemaphore` возбуждает `ValueError` при превышении исходного лимита и помогает обнаружить лишний `release()`.

**Event:** изначально флаг ложен. `set()` устанавливает его и будит всех; `clear()` сбрасывает. Пока флаг установлен, новые `wait()` проходят сразу. `wait(timeout)` возвращает `True` при установленном флаге и `False` при таймауте. `is_set()` читает флаг. Несколько `set()` не образуют несколько сообщений: для этого нужна очередь.

**Barrier:** `wait()` ждёт N участников, затем выпускает их; барьер переиспользуется. Возвращает каждому свой номер от 0 до N−1, позволяя выбрать одного для служебной работы. `action` выполняет один участник перед освобождением всех. Таймаут, ошибка action или `abort()` ломают барьер: ожидающие получают `BrokenBarrierError`. `reset()` сбрасывает барьер и тоже прерывает текущие ожидания. Диагностика: `parties`, `n_waiting`, `broken`.

**Timer(interval, function, args=..., kwargs=...):** запускается через `start()`, выполняет функцию один раз после ожидания. `cancel()` помогает только до начала функции; точный момент выполнения не гарантирован.

## 9. Локальные данные и диагностика

- `threading.local()` даёт каждому потоку собственные атрибуты одного объекта. Подходит для данных, привязанных к потоку. `__init__()` подкласса вызывается для каждого использующего его потока; `__slots__` подкласса **не** становятся локальными.
- `current_thread()`, `main_thread()`, `enumerate()`, `active_count()` — текущий, главный, список живых потоков и их число. `get_ident()` / `get_native_id()` — идентификаторы текущего потока.
- `settrace()` / `setprofile()` задают трассировку и профилирование потоков, создаваемых threading; `gettrace()` / `getprofile()` читают настройки. Варианты `*_all_threads()` охватывают уже исполняющиеся Python-потоки (3.12+).
- `stack_size()` задаёт размер стека для последующих потоков с ограничениями ОС; `TIMEOUT_MAX` — максимально допустимый timeout для блокирующих операций, превышение даёт `OverflowError`.
- `Thread(context=...)` доступен с Python 3.14 и задаёт контекст `contextvars`; при `None` наследование зависит от настроек сборки. Это отдельный механизм от `threading.local()`.

## 10. Дополнения Python 3.15 из исходника

Их нужно знать отдельно от основного API: в Python 3.11–3.14 их нет.

- `serialize_iterator(iterable)` сериализует обращения к одному итератору. Каждый элемент получает один из потребителей; копирования и буферизации нет.
- `synchronized_iterator(func)` оборачивает функцию, создающую итератор, так, чтобы каждый её результат был защищён через `serialize_iterator`.
- `concurrent_tee(iterable, n)` создаёт n независимых потоков значений: каждый потребитель видит всю последовательность. Значения буферизуются, пока их не прочтут все; медленный потребитель увеличивает расход памяти. Отдельный производный итератор рассчитан на одного потребителя одновременно.

## 11. Самопроверка

1. Почему GIL не защищает бизнес-операцию? Он не делает произвольную последовательность чтений и записей атомарной.
2. Чем `start()` отличается от `run()`? Первый создаёт поток выполнения, второй просто вызывает функцию в текущем потоке.
3. Как понять, что `join(timeout)` истёк? Проверить `is_alive()`.
4. Lock или RLock? RLock нужен, если один поток должен повторно захватывать ту же блокировку.
5. Почему Condition проверяют в цикле? Пробуждение не гарантирует, что нужное состояние сохранилось к моменту получения Lock.
6. Event или Queue? Event хранит флаг, Queue — отдельные элементы работы.
7. Как корректно остановить поток? Передать сигнал, обеспечить выход из ожиданий и дождаться через `join()`.
