# Веб-протоколы — Junior

## HTTP

HTTP — прикладной протокол запросов/ответов. HTTPS защищает транспорт TLS. Ниже текстовое представление **HTTP/1.1**; HTTP/2 и HTTP/3 передают сообщения в другом, бинарном формате.

```http
GET /items/1 HTTP/1.1
Host: api.example.test
Accept: application/json

```

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 2

{}
```

Запрос: метод + target + версия. Ответ: версия + статус. Затем headers, пустая строка и необязательное body. Границы body определяются правилами протокола, а не просто следующей пустой строкой. Имена headers регистронезависимы.

Content-Type описывает переданное тело, Accept — предпочтение клиента к представлению ответа. Authorization передаёт данные аутентификации, Location указывает адрес созданного ресурса/перенаправления.

## Статусы

| Класс | Смысл и примеры |
|---|---|
| 2xx | Успех: 200 OK, 201 Created, 202 Accepted (ещё не завершено), 204 No Content |
| 3xx | Перенаправление/условный ответ: 301/302/307/308; 304 — использовать сохранённое представление |
| 4xx | Проблема запроса/доступа: 400, 401 (нужны подходящие credentials), 403 (запрещено), 404, 409, 422, 429 |
| 5xx | Сервер/зависимость не обработали запрос: 500, 502, 503, 504 |

У 204/304 нет тела представления. 4xx не всегда ошибка человека: неверный запрос мог отправить другой сервис.

## Safe и идемпотентность

**Safe:** клиент не запрашивает изменение бизнес-состояния; служебное логирование допустимо. **Идемпотентность:** предполагаемый эффект одного и нескольких одинаковых запросов одинаков, а не обязательно одинаков статус/тело ответа.

| Метод | Назначение | Safe | Идемпотентен по семантике |
|---|---|---|---|
| GET | Получить представление | Да | Да |
| HEAD | Как GET, без тела ответа | Да | Да |
| OPTIONS | Узнать возможности | Да | Да |
| POST | Создание/обработка | Нет | Не гарантируется |
| PUT | Создать/полностью заменить по URI | Нет | Да |
| PATCH | Частичное изменение | Нет | Не гарантируется |
| DELETE | Удалить ресурс/привязку | Нет | Да |

Повтор DELETE может вернуть 404 и остаться идемпотентным. PATCH «установить 5» и «прибавить 5» имеют разные свойства. POST можно сделать идемпотентным на уровне приложения через ключ и сохранённый результат. GET не должен списывать деньги: его могут повторить без запроса пользователя.

## REST / RPC / SOAP

- **REST** — архитектурный стиль: клиент работает с ресурсами и их представлениями через единый интерфейс. Например, `/orders/42` идентифицирует заказ, GET получает его представление, DELETE удаляет привязку. Stateless означает, что запрос несёт необходимый контекст и не требует помнить историю клиентских запросов; бизнес-данные в БД при этом существуют. Остальные ограничения включают client-server, кэшируемость и слои; строгий REST использует hypermedia-ссылки для переходов. Это не просто JSON и не отдельный протокол.
- **RPC** — обращение к именованным удалённым операциям, например CreateOrder. Может работать поверх HTTP; удалённый вызов всё равно имеет задержки и сетевые отказы.
- **SOAP** — XML-протокол сообщений с Envelope/Header/Body/Fault, часто с WSDL-контрактом. Поддерживает разные стили взаимодействия, включая RPC; не равен RPC и не ограничен только HTTP.

## Желательно: OSI, SSE, WebSocket

OSI снизу вверх: **Physical → Data Link → Network → Transport → Session → Presentation → Application**. Сигнал → кадры/MAC → IP/маршрутизация → TCP/UDP → сеансы → представление → прикладной протокол. HTTP — прикладной; реальный TCP/IP-стек не раскладывает каждую технологию строго по семи отдельным слоям. HTTP/3 использует QUIC поверх UDP.

**SSE** — длительный HTTP-поток событий server → client, media type text/event-stream; браузерный EventSource поддерживает переподключение. **WebSocket** — длительное двунаправленное соединение для обмена сообщениями. SSE удобен для уведомлений/прогресса, WebSocket — для интерактивного двустороннего обмена. Ни один сам по себе не гарантирует сохранение и восстановление всех бизнес-событий.
