# Веб-протоколы — уровень 1

## Структура HTTP

HTTP — прикладной протокол обмена запросами/ответами. HTTPS — HTTP с защищённым транспортом TLS. Пример **текстового представления HTTP/1.1**; в HTTP/2 и HTTP/3 другой, бинарный формат передачи.

```http
GET /orders/42 HTTP/1.1
Host: api.example.test
Accept: application/json
Authorization: Bearer <token>

```

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 2
Cache-Control: no-store

{}
```

Запрос содержит метод, request target и версию; ответ — статусную строку. Затем идут headers, пустая строка и необязательное тело. Границы тела определяются правилами протокола, например `Content-Length` или chunked framing в HTTP/1.1; тело не заканчивается просто «следующей пустой строкой». Заголовки регистронезависимы по имени. `Content-Type` описывает переданное тело, `Accept` — какие представления клиент предпочитает получить.

Статусы: **2xx** успех (`200`, `201 Created`, `202 Accepted`, `204 No Content`); **3xx** перенаправление/условная валидация (`301`, `302`, `304`, `307`, `308`); **4xx** проблема запроса/доступа (`400`, `401`, `403`, `404`, `409`, `422`, `429`); **5xx** ошибка сервера/зависимости (`500`, `502`, `503`, `504`). `401` — нужны/неподходят credentials, `403` — доступ запрещён. `202` ещё не подтверждает завершение работы. `304` не содержит представление, клиент использует свой сохранённый вариант.

## Методы

**Safe** означает отсутствие запрошенного клиентом изменения состояния; служебное логирование допустимо. **Idempotent** означает одинаковый предполагаемый эффект одного и нескольких одинаковых запросов, а не одинаковый ответ или отсутствие вызовов.

| Метод | Назначение | Safe | Идемпотентен по семантике |
|---|---|---|---|
| GET | Получить представление | Да | Да |
| HEAD | Как GET, но без тела ответа | Да | Да |
| POST | Обработка/создание в контексте ресурса | Нет | Не гарантируется |
| PUT | Создать/полностью заменить состояние по заданному URI | Нет | Да |
| PATCH | Частичное изменение | Нет | Не гарантируется: «установить 5» и «увеличить на 5» различаются |
| DELETE | Удалить привязку ресурса к URI | Нет | Да |
| OPTIONS | Получить доступные возможности; также CORS preflight | Да | Да |

Повторный DELETE может вернуть `404`, сохранив идемпотентность. GET не должен оформлять заказ или списывать деньги: его могут повторить кэш, crawler или prefetch. POST можно сделать идемпотентным на уровне приложения через ключ и сохранённый результат; HTTP сам этого не обеспечивает.

## REST, RPC, SOAP

- **REST** — архитектурный стиль, не протокол/формат JSON. Ограничения: client-server, stateless взаимодействие, кэшируемость, uniform interface, layered system; code-on-demand опционален. Ресурсы имеют идентификаторы, представления и связи; клиент взаимодействует через единые семантические правила. В строгом REST hypermedia направляет возможные переходы. Многие JSON API называют REST, хотя реализуют лишь часть ограничений.
- **RPC** — вызов именованной удалённой операции (`CreateOrder`, `chargeCard`). Может работать поверх HTTP и использовать JSON/Protobuf. Удалённый вызов имеет сетевые отказы, даже если выглядит как локальный метод.
- **SOAP** — XML-протокол структурированных сообщений с Envelope, Header, Body, Fault; часто используется вместе с WSDL и WS-* контрактами. SOAP поддерживает RPC- и document-подходы, не равен самому RPC и не ограничен только HTTP.

REST удобен для ресурсного публичного API и стандартных HTTP-механизмов; RPC — для явных команд и сервисных контрактов; SOAP встречается в интеграциях со строгими XML-контрактами. Это выбор требований, не утверждение о безусловном превосходстве одного подхода.

## OSI (желательно)

От нижнего к верхнему: **1 Physical** (сигнал), **2 Data Link** (кадры/MAC, Ethernet), **3 Network** (IP/маршрутизация), **4 Transport** (TCP/UDP), **5 Session**, **6 Presentation**, **7 Application** (HTTP). Это концептуальная модель: реальный стек TCP/IP не укладывает каждую технологию ровно в отдельный слой. DNS — прикладной протокол, TLS обычно рассматривают между приложением и транспортом. HTTP/1.1 и HTTP/2 обычно идут через TCP, HTTP/3 — через QUIC поверх UDP с TLS.

## Как сервер сообщает об изменениях (желательно)

| Подход | Механика | Когда подходит / цена |
|---|---|---|
| Polling | Клиент регулярно запрашивает статус | Просто; пустые запросы и задержка до следующего опроса |
| Long polling | Сервер удерживает запрос до события/timeout; клиент открывает следующий | Совместим с HTTP-инфраструктурой; нужны лимиты соединений и корректные timeouts |
| SSE | Длительный HTTP-поток `text/event-stream` от сервера к браузеру | События/прогресс; встроенный EventSource умеет reconnect/Last-Event-ID, сервер должен поддержать восстановление |
| WebSocket | Долгоживущее двунаправленное соединение | Чат/интерактивность; нужны heartbeat, reconnect, auth, управление нагрузкой |

SSE однонаправлен, запросы клиента можно отправлять отдельным HTTP-вызовом. WebSocket не даёт durable queue или автоматического восстановления пропущенных сообщений; это нужно реализовать в приложении. Прокси могут буферизовать/обрывать поток, поэтому deployment-настройки тоже важны.
