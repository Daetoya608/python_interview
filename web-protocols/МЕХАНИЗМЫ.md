# Веб-протоколы: обмен сообщениями, кэш и сетевые отказы

Цель — проследить запрос и объяснить гарантии каждого уровня. Краткий справочник методов/статусов — [КОНСПЕКТ.md](КОНСПЕКТ.md), примеры модели API — [practice/demo.py](practice/demo.py).

## 1. Слои решают разные задачи

IP доставляет пакеты между узлами; TCP предоставляет упорядоченный поток байтов с механизмами надёжной передачи; TLS защищает канал и позволяет проверить идентичность сервера по сертификату. HTTP определяет смысл прикладных сообщений.

TCP не знает, что такое «заказ», и не подтверждает его commit. HTTPS не проверяет бизнес-права пользователя. Ошибка или гарантия нижнего уровня не заменяет контракт верхнего.

OSI — концептуальная семислойная модель: physical, data link, network, transport, session, presentation, application. Реальный TCP/IP стек не обязан помещать каждую технологию ровно в один из этих ящиков. DNS — прикладной протокол, а не часть IP-маршрутизации.

## 2. От URL до ответа

```text
URL/политики/кэш → разрешение имени → создание или reuse соединения
→ TLS/согласование протокола → HTTP-запрос → proxy/CDN/LB → приложение
→ ответ → правила кэша/cookie → обработка содержимого клиентом
```

DNS сопоставляет имя адресам с учётом кэшей. TLS проверяет доверенную цепочку и имя, согласует параметры защиты. Но существующий подходящий connection может позволить пропустить новое установление, а свежий кэш — вообще обращение к серверу.

При получении HTML браузер строит DOM/CSSOM, загружает ресурсы, выполняет JavaScript и выполняет layout/paint. Это отдельная работа поверх получения ответа; ответ API JSON сам по себе не проходит весь путь HTML-страницы.

## 3. Запрос, представление и ресурс

Ресурс — предмет взаимодействия, идентифицируемый URI. Представление — передаваемое описание его состояния, например JSON. Тело HTTP — байты выбранного представления, а не сам объект БД.

Запрос содержит метод, target и headers, иногда body. Ответ содержит статус, headers и допустимое для него body. Content-Type описывает формат передаваемого содержимого, Accept — предпочтение получателя. Content-Encoding описывает, например, сжатие, а не заменяет тип данных.

HTTP/1.1 имеет текстовую структуру начальной строки и заголовков; HTTP/2 и HTTP/3 кодируют обмен кадрами/потоками иначе. Семантика GET и статусов при этом сохраняется. Не следует объяснять все версии как одинаковые текстовые строки поверх TCP.

## 4. Safe и идемпотентность описывают эффект

Safe-метод не запрашивает изменение бизнес-состояния. Логирование GET возможно, но оформление заказа через GET нарушает ожидания: браузер, crawler или кэш могут повторять чтение.

Идемпотентность означает одинаковый предполагаемый эффект одного и нескольких одинаковых запросов. DELETE может сначала вернуть 204, потом 404, оставаясь идемпотентным: ресурс удалён. PUT заменяет состояние по URI и идемпотентен по своей семантике. PATCH «установить 5» и PATCH «прибавить 5» имеют разные свойства; метод сам по себе не обещает идемпотентность.

POST может получить безопасный прикладной повтор через ключ операции. Нужны область ключа, связь с payload, хранение результата и атомарное согласование с эффектом. Один HTTP-заголовок без серверного протокола не предотвращает двойное списание.

## 5. Статус — часть протокола состояния

200 сообщает успешный результат обращения, 201 — создание, 202 — принятие без обещания завершения, 204 — успех без содержимого. 401 относится к подходящим credentials, 403 — отказу по правам, 409 — конфликту состояния, 429 — ограничению частоты.

Смысл 202 требует способа узнать итог асинхронной работы. Ответ «принято» до надёжного сохранения задания может обмануть клиента после сбоя worker. Успешный HTTP-ответ одной операции также не означает успех всего многошагового бизнес-процесса.

В 204 и 304 нет тела содержимого. Клиент не должен безусловно пытаться разобрать каждый ответ как JSON. Единый формат ошибок приложения полезен, но нужно также учитывать ответы proxy и ошибки транспорта.

## 6. Кэш: хранение, свежесть и проверка версии

Кэш хранит представление вместе с метаданными. Пока ответ свежий по правилам Cache-Control и возрасту, его можно использовать без проверки origin. После устаревания валидатор позволяет спросить, изменилась ли версия, не передавая всё тело повторно.

```text
есть подходящая запись? → нет → запросить origin
           ↓ да
допустимо использовать свежую? → да → вернуть сохранённое
           ↓ нет
условный запрос с ETag → совпало → 304, использовать сохранённое тело
                     ↘ изменилось → новое представление и метаданные
```

No-cache разрешает хранение, но требует успешной валидации перед использованием. No-store запрещает соответствующее хранение, а не шифрует канал и не удаляет автоматически все прежние копии. Private запрещает shared-cache использовать ответ как общедоступный.

Vary добавляет значимые request headers к выбору варианта. Если сервер отдаёт разные языки без Vary, кэш может перепутать представления. Cookie сам по себе не создаёт универсальную политику некэшируемости; персональные данные требуют явных правил.

ETag можно использовать и для конкуренции записи. Клиент посылает If-Match с известной сильной версией; при устаревании сервер отвечает 412, а не молча затирает чужое изменение. Проверка версии и изменение должны быть согласованы атомарно на сервере.

## 7. Соединение и запрос — не одно и то же

Persistent connection переиспользуется для нескольких обменов и экономит установление. TCP keepalive проверяет жизнеспособность транспорта; HTTP keep-alive и heartbeat приложения решают другие задачи.

HTTP/2 мультиплексирует независимые HTTP streams внутри соединения. Потеря TCP-сегмента всё ещё может задерживать доставку байтов разным потокам из-за упорядоченности TCP. HTTP/3 использует QUIC поверх UDP с независимостью потоков на транспортном уровне, хотя они делят ресурсы и управление перегрузкой.

Соединение может быть оборвано proxy по idle timeout. Длительный поток должен учитывать настройки всей цепочки. Наличие открытого сокета не доказывает, что удалённый бизнес-процесс успешно работает.

## 8. Cookie, session и token

Cookie — механизм хранения небольших данных у браузера и автоматической отправки по правилам scope. Session — модель пользовательского состояния; cookie может содержать только случайный идентификатор, по которому сервер находит запись в Redis/БД.

Secure ограничивает отправку защищённым транспортом. HttpOnly закрывает чтение cookie из JavaScript, но не исключает все последствия XSS. SameSite регулирует cross-site отправку; site и origin — разные понятия. Подходящие credentials могут прикрепляться браузером без явной команды пользовательского JavaScript, поэтому важна CSRF-защита.

Bearer-токен даёт доступ предъявителю, если сервер признал его действительным. JWT обычно подписан, а не зашифрован; содержимое нельзя считать секретным. Авторизация всё равно должна проверить право на конкретный объект и действие.

## 9. CORS: разрешение браузеру читать ответ

Origin состоит из scheme, host и port. Same-origin policy ограничивает доступ браузерного кода к другим origin; CORS задаёт разрешённые исключения.

Для некоторых запросов браузер сначала делает preflight OPTIONS и проверяет допустимость метода/headers. Для других запрос может уйти сразу, а чтение ответа будет запрещено после получения. Поэтому серверное изменение может произойти даже при CORS-ошибке в консоли.

Credentialed-запрос требует согласованных настроек клиента, сервера и cookie-политики; wildcard ACAO `*` не подходит. При динамическом разрешении Origin важно корректное Vary. Curl и backend-клиенты не обязаны соблюдать браузерную политику, поэтому CORS не является защитой API от них.

## 10. REST, RPC, SOAP и gRPC

REST — архитектурный стиль с ресурсами, представлениями, единым интерфейсом, stateless-взаимодействием, кэшируемостью и слоями; строгий вариант включает hypermedia для переходов. JSON CRUD покрывает лишь часть этих идей.

RPC делает явной удалённую операцию. gRPC описывает сервисы/методы в proto, генерирует stubs, обычно использует Protobuf и HTTP/2, поддерживает unary и streaming. Генерация клиента помогает с формой контракта, но не отменяет deadline, совместимость версий и сетевую неопределённость.

SOAP задаёт XML-сообщения Envelope/Header/Body/Fault и используется с соответствующими контрактами/расширениями. Это не синоним RPC и не просто старое название JSON API. Выбор зависит от требований интеграции.

## 11. Polling, SSE и WebSocket

Polling периодически спрашивает статус; задержка зависит от интервала, а пустые запросы расходуют ресурсы. Long polling удерживает обращение до события/timeout, после чего клиент открывает следующее.

SSE передаёт поток событий сервер → браузер. EventSource поддерживает reconnect и Last-Event-ID, но сервер должен хранить/восстанавливать нужную историю. WebSocket даёт двунаправленный канал, а не долговечную очередь сообщений.

Для обоих потоковых вариантов нужны heartbeat, обнаружение разрыва, повторное подключение, права доступа и backpressure. Повторное соединение не восстанавливает автоматически потерянные бизнес-события: для этого проектируют идентификаторы и протокол продолжения.

## 12. Timeout, retry и ограничение нагрузки

Timeout означает, что клиент перестал ждать в заданных пределах, а не что сервер откатил действие. Повтор безопасен только при допустимом эффекте и ограниченном бюджете. Backoff с jitter уменьшает синхронные волны повторов; Retry-After сообщает полезную политику сервера.

Circuit breaker быстро отказывает при нездоровой зависимости и осторожно проверяет восстановление. Rate limiter ограничивает частоту, semaphore — число активных операций, bounded queue — накопленную работу. Они решают разные части перегрузки.

Fallback выбирают по допустимости для бизнеса. Лучше явный отказ оплаты, чем неправдивый успех из-за недоступности платёжного сервиса. Повторы на каждом уровне цепочки перемножаются, поэтому их владелец и общий deadline должны быть определены.
