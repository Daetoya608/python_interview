# Веб-протоколы — уровень 2

## Кэширование

Кэш сохраняет представление и может повторно использовать его согласно правилам HTTP. **Freshness** определяет, можно ли ответить без обращения к origin; **validation** проверяет, актуально ли сохранённое представление.

- `Cache-Control: max-age=60` — ответ свежий 60 секунд; `s-maxage` задаёт срок для shared caches.
- `private` запрещает shared-cache хранение, но допускает приватный кэш браузера. `public` явно разрешает shared caching с учётом остальных правил.
- `no-cache` допускает хранение, но требует успешной валидации перед повторным использованием. `no-store` запрещает хранение этого обмена соответствующими кэшами; не стирает автоматически все ранее сохранённые копии и не заменяет TLS.
- `ETag` — валидатор версии представления. Клиент посылает `If-None-Match`; при совпадении для GET/HEAD получает `304` без тела. `Last-Modified`/`If-Modified-Since` — временной валидатор с меньшей точностью.
- `Vary: Accept-Language` добавляет значение request header к выбору варианта. Без корректного Vary кэш способен перепутать представления.

```http
GET /products/7 HTTP/1.1
Host: api.example.test
If-None-Match: "v3"

HTTP/1.1 304 Not Modified
ETag: "v3"
Cache-Control: max-age=60
```

Это два сообщения (запрос/ответ), не один raw message. Для изменения можно использовать сильный ETag и `If-Match`: если версия устарела, сервер отвечает `412 Precondition Failed`, предотвращая потерянное обновление. Кэширование пользовательских данных требует явно заданной политики; cookie сам по себе не делает любой ответ некэшируемым.

## Соединения, содержимое, cookies

В HTTP/1.1 соединения по умолчанию persistent: несколько обменов могут использовать один TCP connection. `Connection: close` закрывает его после обмена. HTTP keep-alive, TCP keepalive и heartbeat приложения — разные механизмы. HTTP/2 мультиплексирует streams в соединении, HTTP/3 использует QUIC; connection-specific headers из HTTP/1.1 туда переносить нельзя.

`Content-Type: application/json` описывает media type тела, `Content-Encoding: gzip` — кодирование/сжатие. `Accept` и `Accept-Encoding` — предпочтения клиента. В JSON Unicode обычно передают UTF-8; заголовок не подтверждает, что содержимое действительно валидно — сервер его проверяет.

Сервер устанавливает cookie через `Set-Cookie`, браузер отправляет подходящие cookies в `Cookie` по правилам домена/пути/срока/SameSite. `Secure` ограничивает отправку защищённым транспортом, `HttpOnly` закрывает чтение из JavaScript, но не все последствия XSS. `SameSite` ограничивает cross-site отправку; `SameSite=None` требует `Secure`. Cross-site и cross-origin — разные понятия. Cookie обычно хранит случайный session ID, сама сессия может жить на сервере. Нужны срок действия, отзыв, ротация и защита от CSRF для запросов с автоматически прикрепляемыми credentials.

Базовые cookies описаны RFC 6265; современная семантика SameSite уточняется в [рабочем проекте 6265bis](https://httpwg.org/http-extensions/draft-ietf-httpbis-rfc6265bis.html), который ещё не следует считать опубликованным RFC.

## CORS

**Origin = scheme + host + port.** Same-origin policy ограничивает доступ браузерного кода к чужим origin; CORS позволяет серверу разрешить чтение ответа определённым origin.

Для некоторых запросов браузер сначала отправляет **preflight OPTIONS** с `Origin`, `Access-Control-Request-Method/Headers`. Сервер отвечает разрешёнными origin/методами/заголовками. Не каждый запрос вызывает preflight. Для credentialed-запроса нужны настройки клиента, конкретный `Access-Control-Allow-Origin` (не `*`) и `Access-Control-Allow-Credentials: true`; применяются также cookie-политики браузера. При динамическом ответе по Origin нужен `Vary: Origin`.

CORS проверяется браузером, а не ограничивает curl/backend-клиентов. Некоторые запрещённые для чтения cross-origin запросы всё равно доходят до сервера и могут изменить состояние. Поэтому CORS **не заменяет** аутентификацию, авторизацию и защиту от CSRF.

## Как проектировать ресурсный API

`GET /orders?status=paid&limit=20`, `GET /orders/42`, `POST /orders`, `PATCH /orders/42`, `DELETE /orders/42`. Выбирайте методы по семантике, не только имена URL. Новый ресурс: обычно `201` и `Location`; удаление без тела — `204`. Определите валидацию, единый формат ошибок, pagination/limits, контракт совместимости и объектные права доступа. Читающий GET не должен менять бизнес-состояние.

Для POST с повторами определите idempotency key: область действия (например tenant+operation), связь с payload, срок хранения и сохранённый итог. Тот же ключ с другим payload должен дать конфликт, а не молча выполнить другую команду. Запись ключа и бизнес-результата нужно согласовать транзакционно; локальный словарь не обеспечивает этого при нескольких процессах/перезапуске.

## Устойчивость вызовов

| Механизм | Что решает | Важное ограничение |
|---|---|---|
| Timeout/deadline | Ограничивает ожидание этапа/всего запроса | Не доказывает отмену удалённой операции |
| Retry | Повторяет временно неудавшийся вызов | Только безопасные по эффекту операции; лимит попыток/времени, exponential backoff + jitter, учитывать Retry-After |
| Circuit breaker | Быстро прекращает вызовы нездоровой зависимости | Closed пропускает; Open отклоняет; Half-open проверяет восстановление ограниченными пробами |
| Fallback | Даёт допустимый запасной результат | Кэшированная цена может быть допустима для витрины, «оплата успешна» вместо ошибки — нет |
| Rate limiter | Ограничивает поток по ключу/окну/токенам | Обычно `429` и по возможности Retry-After; распределённым экземплярам нужно согласованное правило |

Retry на каждом уровне умножает нагрузку: три уровня по три попытки могут вызвать до 27 обращений к нижней зависимости. Не повторяйте постоянные ошибки валидации; для `429/503` учитывайте политику сервера и бюджет запроса. Ограничение параллелизма и bounded queue защищают ресурсы даже при низком среднем RPS. Circuit breaker не заменяет timeout, а fallback должен быть заметен в метриках.

## Асинхронный бизнес-процесс

```text
POST /reports → 202 Accepted + Location: /jobs/abc
GET /jobs/abc → queued / running / succeeded / failed
GET /reports/result-id → готовый результат
```

API сначала надёжно сохраняет задачу; worker выполняет её отдельно. `202` означает принятие, не успех отчёта. Альтернатива polling — webhook с подписью, проверкой повтора и повторными доставками. Внутри можно использовать broker + consumer ack, outbox, message ID и идемпотентный worker. REST не запрещает асинхронные задачи, а `async def` сам по себе не создаёт долговечную фоновую обработку.

[practice/demo.py](practice/demo.py) моделирует `202`, повтор по ключу, конфликт payload, обработку и условный GET с `304`: `python web-protocols/practice/demo.py`. Это детерминированная модель в памяти без сети, durable queue и production-гарантий.

## gRPC (желательно)

gRPC задаёт сервис/методы в `.proto`, генерирует client/server stubs, обычно использует Protocol Buffers и HTTP/2. Есть unary, server streaming, client streaming, bidirectional streaming. Нужны deadlines, cancellation и обработка status codes. Отмена не откатывает уже выполненные действия. Плюсы — типизированные контракты, компактный обмен, streaming; цена — генерация/эволюция схем, инструменты диагностики и дополнительные ограничения браузерного доступа (часто gRPC-Web/proxy). RPC не отменяет сетевую неопределённость.

## Что происходит при переходе по HTTPS-ссылке (желательно)

1. Браузер разбирает URL, применяет политики (например HSTS), проверяет подходящие локальные кэши/service worker.
2. Если нужен адрес, DNS-разрешение использует кэши и резолвер; для локальной сети нужен link-layer доступ к next hop (ARP для IPv4/NDP для IPv6), не обязательно к самому удалённому серверу.
3. Создаётся или переиспользуется соединение: TCP + TLS для типичного HTTP/1.1/2; QUIC с TLS для HTTP/3. Проверяются сертификат/имя и согласуется протокол.
4. HTTP-запрос проходит возможные proxy/CDN/LB к серверу. Тот проверяет доступ, обрабатывает данные и возвращает ответ; возможны redirect и дополнительные запросы.
5. Браузер применяет cookie/cache/security правила, разбирает HTML, строит DOM/CSSOM, загружает ресурсы, выполняет JS, выполняет layout/paint/compositing.

Путь зависит от кэша, существующих соединений, редиректов и протокола; не каждый клик создаёт новый DNS/TCP/TLS обмен. Это укрупнённая схема, а не фиксированная последовательность для любого браузера.
