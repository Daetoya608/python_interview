# Индексы: структуры доступа и выбор плана

Главный вопрос: какую работу структура позволяет не делать и сколько стоит её поддерживать? Синтаксис — в [КОНСПЕКТ.md](КОНСПЕКТ.md). Основные примеры относятся к PostgreSQL 18; LSM рассматривается как другая организация хранения, а не встроенный тип индекса PostgreSQL.

## 1. Таблица и индекс хранят разные представления

Таблица хранит строки. Индекс содержит поисковые ключи и информацию для нахождения подходящих записей. Это дополнительная структура, согласованная с таблицей: изменение данных может потребовать изменить и её.

Без подходящего доступа СУБД читает много строк и проверяет условие. Индекс позволяет быстро сузить область поиска. Но после поиска может потребоваться сходить в таблицу за остальными полями и проверить видимость версии. «Нашёл ключ» и «получил готовую строку результата» — разные этапы.

На маленькой таблице полный проход дешёв. Если запрос возвращает большую долю большой таблицы, множество разрозненных обращений через индекс может быть дороже последовательного чтения. Поэтому Seq Scan сам по себе не признак ошибки.

## 2. B-tree: упорядоченные страницы

B-tree — сбалансированное дерево с большим числом потомков у узла. Внутренние страницы направляют поиск по диапазонам ключей, листовые содержат индексные записи. Большая ветвистость уменьшает число переходов между страницами, что важно при дисковом I/O.

Поиск `customer_id = 42` спускается к нужному диапазону, затем читает подходящие записи. Диапазон и сортировка используют порядок ключей; не требуется заново сравнивать каждую строку таблицы. После нахождения первой записи большой диапазон всё равно нужно прочитать: логарифмический спуск не делает выдачу миллиона строк бесплатной.

При вставке страница может заполниться и разделиться; при записи обслуживаются таблица, индекс, WAL и кэши. Реальный расход зависит от распределения ключей, обновлений и конкуренции. UNIQUE использует индекс для поиска конфликтов, но сама гарантия — ограничение допустимого состояния.

## 3. Составной ключ — лексикографический порядок

Индекс `(customer_id, created_at)` упорядочен сначала по клиенту, внутри него — по времени:

```text
(1, 10:00), (1, 11:00), (2, 09:00), (2, 12:00), ...
```

Равенство по клиенту выделяет непрерывный участок; диапазон времени уточняет его. Для `WHERE created_at >= ...` по всем клиентам такого одного участка нет. Планировщик всё ещё может выбрать сканирование индекса, bitmap-план или доступ со skip scan в поддерживаемых случаях: правило левого префикса объясняет порядок, а не запрещает все остальные планы.

```sql
CREATE INDEX orders_customer_time ON orders(customer_id, created_at, id)
INCLUDE (amount_cents);

SELECT created_at, id, amount_cents
FROM orders
WHERE customer_id = 42 AND created_at >= TIMESTAMP '2026-10-01'
ORDER BY created_at, id
LIMIT 20;
```

Здесь ключи помогают поиску и порядку, amount_cents — только полезная нагрузка покрытия. В обычном случае, когда используется этот порядок, LIMIT позволяет остановиться после нужного числа подходящих строк. Для другого WHERE/ORDER BY тот же индекс может оказаться неудобен.

## 4. Селективность, статистика и перекос

Важно оценивать число подходящих строк и долю таблицы. У колонки может быть много разных значений, но одно встречается в половине строк. Индекс по ней окажется полезен для редкого значения и невыгоден для самого частого.

Оптимизатор не исполняет заранее все планы. Он оценивает их по статистике: размерам, частотам, распределениям и зависимостям. Устаревшая статистика или коррелированные условия могут дать ошибочную оценку и неудачный порядок JOIN.

Сначала сравнивают estimated и actual rows. Ошибка в раннем узле способна многократно увеличить работу следующих. Обновление статистики и изменение запроса иногда полезнее ещё одного индекса.

## 5. Покрытие и MVCC

Покрывающий индекс содержит значения, необходимые запросу. Это открывает возможность index-only scan, но в PostgreSQL видимость строки зависит от MVCC. Если visibility map не подтверждает видимость страницы для всех нужных транзакций, executor обращается к heap.

Поэтому `Index Only Scan` может иметь ненулевые `Heap Fetches`. Частые обновления и состояние vacuum влияют на выгоду. Добавление всех столбцов в INCLUDE увеличивает индекс, цену записи и давление на кэш; покрытие проектируют под конкретные частые запросы.

## 6. Другие структуры решают другие задачи

| Структура | Главная идея | Где полезна / цена |
|---|---|---|
| Hash | Разместить ключ по хешу | Равенство; нет естественного диапазонного порядка |
| GIN | Обратное отображение «элемент → содержащие его строки» | Текстовые лексемы, массивы, некоторые JSONB-запросы; цена обновлений |
| GiST | Обобщённая структура поиска по поддержанным операторам | Геометрия, диапазоны и другие специализированные задачи |
| BRIN | Краткие сводки по диапазонам страниц | Очень большие физически коррелированные данные; пропускает заведомо неподходящие блоки |

Префикс строки, подстрока и поиск по словам — разные условия. Для `abc%` иногда подходит B-tree с нужной collation/operator class. `%abc%` обычно требует иного доступа, например trigram. Полнотекстовый поиск работает с лексемами и языковой обработкой, а не просто с произвольной подстрокой.

Индекс по выражению хранит результат выражения; условие запроса должно соответствовать поддержанному доступу. Частичный индекс содержит только строки своего предиката. Планировщик должен уметь доказать, что запрос этому предикату соответствует; неизвестный параметр может мешать такому доказательству.

## 7. LSM: перенести работу с записи на слияния

Типичная LSM-система пишет изменения в WAL и изменяемую структуру в памяти, затем сбрасывает отсортированные файлы. Чтение ищет актуальную версию в нескольких уровнях. Bloom-фильтры помогают исключить файлы, где ключа точно нет; положительный ответ фильтра ещё не гарантирует наличие ключа.

Compaction объединяет файлы, убирает устаревшие версии и tombstones, когда это допустимо. Это экономит чтение, но повторно переписывает данные. Возникают усиления записи, чтения и расхода места. LSM не «быстрее B-tree вообще»: важны нагрузка, задержки хвоста, политика compaction и ресурсы хранения.

## 8. Как читать план и проверять гипотезу

1. Зафиксировать смысл запроса, типичные параметры и объём данных.
2. Посмотреть план и найти узел, где растут строки, повторные запуски, сортировка или чтения.
3. Проверить расхождения оценок, а не только название scan.
4. Предложить структуру под фильтр/соединение/порядок и оценить цену записи.
5. Сравнить планы и измерения на представительных данных, проверить результат.

EXPLAIN без ANALYZE показывает оценки. ANALYZE выполняет оператор, включая изменяющий данные. `cost` — единицы модели, не миллисекунды. При loops > 1 actual rows и время показываются в среднем за запуск; суммарную работу оценивают с учётом loops. Время потомков включено во время родителя.

CREATE INDEX CONCURRENTLY не означает «бесплатно в фоне». PostgreSQL выполняет несколько этапов, учитывает конкурентные изменения и ждёт мешающие транзакции. Построение расходует I/O/CPU и может оставить invalid-индекс при ошибке. Это эксплуатационная операция с проверкой завершения.
