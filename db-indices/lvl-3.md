# Индексы — уровень 3

Обязательно: B-tree/LSM-tree, оптимизация, покрытие и селективность. Желательно: префиксный и полнотекстовый поиск.

## B-tree и LSM-tree

| | B-tree и близкие структуры | LSM-подход |
|---|---|---|
| Организация | Сбалансированное дерево страниц с упорядоченными ключами | Буфер записи в памяти и упорядоченные неизменяемые файлы/уровни |
| Запись | Изменение страниц, иногда split/rebalance | Запись в WAL/memtable, затем flush и compaction |
| Чтение | Спуск по дереву и обход нужного диапазона | Поиск по нескольким структурам, фильтры/кэш помогают |
| Издержки | Страницы, splits, случайные обращения | Compaction, write/read/space amplification |

B-tree держит небольшую высоту за счёт большого ветвления. Листья содержат ключи и данные/ссылки в зависимости от реализации. Equality и диапазоны по порядку ключей естественны для него.

LSM — не просто другое имя B-tree и не стандартный доступный индекс PostgreSQL. Это семейство подходов к хранению/индексации, например в RocksDB: запись буферизуют, затем сливают отсортированные структуры. Compaction объединяет версии и удалённые значения; высокая скорость записи оплачивается фоновой работой. Bloom filter может исключить часть заведомо бесполезных чтений, но не заменяет сами данные.

## Селективность и составные индексы

Сначала уточняйте термин: **селективность предиката** часто означает долю выбранных строк, а «высокой селективностью» разговорно называют способность отсечь почти всё. Выражайте конкретно: «нужно 10 строк из миллиона», а не спорьте о направлении слова.

```sql
CREATE INDEX idx_orders_customer_created ON orders(customer_id, created_at);
SELECT id FROM orders
WHERE customer_id = 42 AND created_at >= '2026-10-01'
ORDER BY created_at;
```

Порядок полей подбирают под равенства, диапазоны, сортировку и реальные запросы. Индекс `(a,b)` упорядочен сначала по a, затем по b внутри a. Поиск только по b может использовать его неэффективно или иным способом; не формулируйте правило «без a индекс никогда не работает»: оптимизации и skip scan зависят от СУБД/версии.

Функция над колонкой, несовместимое приведение типа, collation или выражение запроса способны лишить обычный индекс полезного доступа. Возможен индекс выражения, например на lower(email), если именно так ищут. Частичный индекс хранит подмножество строк; оптимизатор должен уметь доказать, что предикат запроса ему соответствует.

## Покрывающий индекс

Он содержит все значения, нужные запросу. PostgreSQL:

```sql
CREATE INDEX idx_orders_cover ON orders(customer_id, created_at)
INCLUDE (amount_cents);
```

Ключи поддерживают поиск/порядок, INCLUDE добавляет payload для чтения. Эти колонки не становятся дополнительными ключами сортировки. Для index-only scan нужно, чтобы метод поддерживал его и нужные колонки присутствовали; PostgreSQL также проверяет видимость по visibility map, поэтому heap fetches всё ещё возможны. Частые изменения таблицы уменьшают пользу покрытия.

## Префикс и полнотекстовый поиск

- `name LIKE 'Ann%'` — префикс; подходящий B-tree может помочь при совместимой collation/operator class. В PostgreSQL иногда нужен text_pattern_ops.
- `LIKE '%ann%'` — произвольная подстрока; обычный B-tree обычно не даёт нужного диапазона. PostgreSQL pg_trgm с GIN/GiST может помогать LIKE/ILIKE и поиску похожих строк.
- Полнотекстовый поиск работает с токенами/лексемами, нормализацией и языковой конфигурацией, а не просто с подстрокой.

PostgreSQL, для существующей таблицы articles(body):

```sql
CREATE INDEX idx_articles_fts ON articles USING GIN (to_tsvector('russian', body));
SELECT id FROM articles
WHERE to_tsvector('russian', body) @@ plainto_tsquery('russian', 'поиск документов');
```

Языковая конфигурация и выражение индекса/запроса должны соответствовать друг другу. GIN хранит инвертированный доступ «лексема → документы». Индекс нужен для скорости, но не является обязательным условием самой семантики полнотекстового запроса.
