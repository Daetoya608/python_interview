# Индексы: краткое повторение

По issue №5; подробности — в lvl-1/2/3.md.

- Индекс — структура доступа, ускоряющая подходящие equality/range/JOIN/ORDER BY. Не гарантирует использование и порядок SELECT.
- Цена: место, обслуживание INSERT/UPDATE/DELETE, I/O, WAL, кэш, построение и очистка. Маленькую таблицу/большую долю данных часто выгоднее читать последовательно.
- План — физические шаги. PostgreSQL EXPLAIN показывает оценки, ANALYZE выполняет запрос. Проверяйте actual/estimated rows, loops, фильтры, чтения и сортировки. Cost — не время.
- CREATE INDEX CONCURRENTLY позволяет писать в таблицу при построении, но ждёт завершения, расходует ресурсы, может ждать транзакций и оставлять invalid index. Не работает внутри обычного BEGIN.
- B-tree: упорядоченное сбалансированное дерево страниц. LSM: memtable/WAL, sorted files и compaction; это компромиссы усиления чтения/записи/места, а не «всегда быстрее».
- Селективность обсуждайте числом строк/долей результата. Кардинальность, перекос распределения и статистика влияют на оценки.
- Составной `(a,b)` упорядочен сначала по a. Выбирайте поля под равенства, диапазоны и сортировку; не заменяйте план догмой о левом префиксе.
- Покрытие хранит нужные запросу значения. PostgreSQL INCLUDE — payload; index-only scan может всё равно проверять heap из-за MVCC-видимости.
- Prefix `abc%`, substring `%abc%` и full-text — разные задачи: B-tree при подходящих условиях, trigram-индексы и инвертированный FTS соответственно.

Пример под конкретный запрос (PostgreSQL):

```sql
CREATE INDEX idx_orders_customer_created ON orders(customer_id, created_at)
INCLUDE (amount_cents);
SELECT created_at, amount_cents FROM orders
WHERE customer_id = 42 AND created_at >= '2026-10-01'
ORDER BY created_at;
```

Равенство по customer_id выбирает участок индекса, диапазон/сортировка используют created_at; amount_cents хранится для покрытия, но не служит ключом поиска. Пользу подтверждают планом, а не наличием CREATE INDEX.

В PostgreSQL `actual rows` и времена узла с несколькими `loops` показываются в среднем на один запуск. Для суммарного объёма учитывают loops; времена родителя включают работу потомков, поэтому складывать все времена дерева нельзя. Большое расхождение estimated/actual — повод проверить статистику, распределение и условия запроса. [Чтение EXPLAIN](https://www.postgresql.org/docs/18/using-explain.html).

Практика: `python db-indices/practice/demo.py`. SQLite-пример запускается локально; PostgreSQL CONCURRENTLY/INCLUDE/GIN в этой среде не выполнялись.
