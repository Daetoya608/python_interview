# Индексы — уровень 2

Обязательно: цена индексов и анализ плана. Желательно: создание индекса без длительной остановки записи.

## Цена индексов

| Издержка | Почему возникает |
|---|---|
| Место | Структура хранится отдельно от основных данных |
| INSERT/DELETE | Нужно добавить/удалить записи индексов |
| UPDATE | Изменение индексируемых значений требует обслуживания; детали зависят от движка |
| I/O, WAL и кэш | Дополнительные страницы, журналирование и конкуренция за память |
| Обслуживание | Построение, проверки, очистка, возможное разрастание |

Избыточные и почти дублирующиеся индексы могут замедлить запись без заметной пользы чтению. Но удалять их только по одной метрике нельзя: индекс может обеспечивать ограничение, обслуживать редкий важный запрос или задачу обслуживания.

## План запроса

План — дерево физических операций, выбранных оптимизатором: сканирование, соединение, сортировка, агрегирование. Он показывает **как**, а SQL — **что** нужно получить.

PostgreSQL:

```sql
EXPLAIN SELECT id FROM orders WHERE customer_id = 42;
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM orders WHERE customer_id = 42;
```

EXPLAIN показывает оценки. ANALYZE действительно исполняет запрос и добавляет фактические измерения, даже если анализируется изменение данных. Cost — условная стоимость, а не миллисекунды.

Порядок чтения плана:

1. Где расходуются время и чтения? Смотреть всё дерево, не только верхний узел.
2. Насколько estimated rows отличаются от actual rows? Ошибочные оценки могут дать плохой JOIN/доступ.
3. Сколько loops у внутреннего узла? Повторяющаяся недорогая операция суммарно может быть дорогой.
4. Какие условия вошли в Index Cond, а какие применяются как Filter после чтения?
5. Есть ли лишние сортировки, большой промежуточный результат, временные файлы?

Seq Scan не означает ошибку; Index Scan не означает оптимальность. Проверяют реальные данные и распределение, актуальность статистики, а также влияние LIMIT и параметров запроса. EXPLAIN ANALYZE добавляет собственные накладные расходы; одного прогона недостаточно для точного бенчмарка.

SQLite: `EXPLAIN QUERY PLAN ...`; формат и названия его узлов отличаются от PostgreSQL.

## «Асинхронно создать индекс»: что имеется в виду

В PostgreSQL для уменьшения блокирования обычной записи применяют:

```sql
CREATE INDEX CONCURRENTLY idx_orders_customer ON orders(customer_id);
```

CONCURRENTLY — **конкурентное/online-построение**, а не обещание немедленно вернуть управление клиенту. Сам вызов обычно ждёт окончания; при необходимости запуском управляет отдельная задача/соединение.

- Обычный CREATE INDEX блокирует конкурентные записи на время построения; CONCURRENTLY позволяет им продолжаться, но выполняет больше работы и может ждать транзакции.
- Нельзя выполнять CREATE INDEX CONCURRENTLY внутри обычного transaction block.
- Нагрузка на CPU/I/O остаётся; это не полностью бесплатная и не абсолютно неблокирующая операция.
- При сбое может остаться invalid index: нужно проверить состояние и выбрать удаление/перестроение.
- Поддержка и ограничения для partitioned tables и параллельных построений зависят от версии. Не переносите PostgreSQL-синтаксис в SQLite/MySQL.
