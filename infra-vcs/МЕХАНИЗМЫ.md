# Git: снимки, граф истории и перемещение ссылок

Понимание модели позволяет предсказывать последствия команд. Их краткий справочник — в [КОНСПЕКТ.md](КОНСПЕКТ.md), безопасный учебный репозиторий создаёт [practice/demo.py](practice/demo.py). Описывается Git; PR/MR и fork — дополнения платформ хостинга.

## 1. Что Git сохраняет

Git хранит объекты по идентификаторам содержимого. Blob представляет содержимое файла, tree связывает имена с файлами/поддеревьями, commit ссылается на корневой tree, родителей и метаданные.

Коммит логически описывает **снимок проекта**, а не только текстовый патч. Diff вычисляется сравнением снимков. Неизменившиеся объекты переиспользуются; внутреннее сжатие/упаковка не меняет модель.

Идентификатор commit зависит не только от кода, но и от родителей и метаданных. Поэтому одинаковые файлы могут находиться в разных коммитах. Amend и rebase создают новые объекты; старый commit не редактируется на месте.

## 2. Три состояния, которые нужно различать

| Область | Что представляет | Относительно чего показывают изменения |
|---|---|---|
| Working tree | Текущие файлы для редактирования | git diff сравнивает с index |
| Index/staging area | Подготовленный снимок следующего commit | diff --cached сравнивает с HEAD |
| HEAD | Текущий commit/обычно текущая ветка | Основа локальной работы |

Add сохраняет текущую версию пути в index. Если затем снова изменить файл, часть изменений уже подготовлена, часть ещё нет. Commit берёт index, а не автоматически всё содержимое каталога.

Это позволяет выделять логические изменения, но требует проверки staged diff. Удалённый из working tree файл не исчезнет из следующего снимка, пока удаление не отражено в index.

Tracked означает, что Git уже учитывает путь. Untracked — новый путь вне index. Gitignore фильтрует неучтённые файлы и не удаляет ранее отслеживаемые секреты из истории.

## 3. Ветка — подвижная ссылка

Ветка хранит указание на commit. Новый commit текущей ветки сдвигает её вперёд. Создание ветки не копирует все файлы и не создаёт отдельную историю до появления новых коммитов.

HEAD обычно символически указывает на ветку. В detached HEAD он указывает прямо на commit. Работать так можно, но для сохранения удобной достижимости новых коммитов полезно создать именованную ветку.

```text
A → B → C          main
     ↘ D → E       feature
```

Здесь B — общий предок. Удаление feature убирает ссылку, а не немедленно физически уничтожает все её объекты. Если коммиты перестанут быть достижимыми из ссылок/reflog и пройдут сроки хранения, сборка мусора сможет их удалить.

## 4. Local, remote и fork

Remote — имя адреса другого репозитория. Origin — соглашение, а не специальный главный сервер Git. Remote-tracking ссылка `origin/main` отражает последнее полученное состояние main удалённого репозитория; это не постоянно обновляемая сетью переменная.

Fetch получает объекты и обновляет соответствующие tracking-ссылки, обычно не меняя текущие рабочие файлы. Merge/rebase выполняют интеграцию. Pull соединяет получение и выбранный способ интеграции, поэтому его поведение зависит от стратегии/настроек.

Push предлагает серверу обновить ссылку и передаёт недостающие объекты. Сам commit остаётся локальным до передачи. Обычный push может отклонить движение, которое выбросило бы известную серверу историю.

Fork — отдельный репозиторий на платформе, связанный с исходным. Ветка — ссылка внутри репозитория. PR/MR просит платформу сравнить head с base, провести review и затем интегрировать изменения. Создание PR само по себе не выполняет merge.

## 5. Merge и rebase решают интеграцию по-разному

Fast-forward возможен, когда текущий commit — предок входящего: достаточно сдвинуть ссылку. Если истории разошлись, обычный merge сопоставляет общий предок и две стороны; итоговый merge commit хранит обоих родителей.

Rebase берёт изменения выбранных коммитов и воспроизводит их поверх новой базы. Получаются новые commit с другими родителями и идентификаторами. Даже если итоговые файлы совпадают, история уже другая.

Cherry-pick воспроизводит изменение отдельного commit на текущей основе, не превращая исходную ветку в предка автоматически. Это удобно для выборочного переноса, но может дублировать смысл и осложнить дальнейшую интеграцию.

## 6. Конфликт — необходимость выбрать итоговый смысл

Трёхстороннее слияние сравнивает базу, нашу и входящую версии. Если нельзя безопасно совместить изменения, Git оставляет конфликт и хранит необходимые варианты в index. Маркеры в файле — лишь представление части ситуации: бывают конфликты удаления/изменения, переименования и бинарных файлов.

Разрешить конфликт означает подготовить правильный итог, добавить его в index и продолжить операцию. Простое удаление маркеров или механический выбор ours/theirs не доказывает корректность. В rebase термины сторон могут восприниматься непривычно, поэтому надёжнее смотреть конкретные версии.

Текстово бесконфликтное слияние тоже может сломать поведение: одна ветка переименовала функцию, другая добавила её новый вызов в другом файле. Проверки нужны и без сообщения CONFLICT.

## 7. Отмена: новая история или движение ссылки

Revert добавляет новый commit, обращающий изменение прежнего. Он сохраняет факт исходного действия в общей истории. Reset передвигает текущую ветку и, в зависимости от режима, меняет index и working tree.

| Операция | Ссылка ветки | Index | Working tree |
|---|---|---|---|
| reset --soft | Передвигается | Сохраняется | Сохраняется |
| reset --mixed | Передвигается | Под целевой commit | Сохраняется |
| reset --hard | Передвигается | Под целевой commit | Перезаписывается под целевой commit |
| revert | Новый обратный commit | Готовит его изменение | Применяет обратное изменение |

Restore восстанавливает выбранные пути и тоже может отбросить правки. Clean удаляет untracked-пути, которых история вообще могла не хранить. Reflog не восстановит всё, что никогда не попало в Git-объекты.

Amend/rebase уже опубликованных commit требуют координации: чужие ветки могут опираться на старые идентификаторы. Force-with-lease проверяет ожидаемую удалённую ссылку, но не заменяет договорённость о допустимости переписывания.

## 8. Stash, worktree и восстановление

Stash сохраняет временное состояние в Git-объектах; включение untracked/ignored зависит от флагов. Apply восстанавливает без удаления записи, pop удаляет её после успешного применения. Перенос на изменившуюся базу способен вызвать конфликт.

Worktree даёт несколько рабочих каталогов с отдельными index/HEAD при общей базе объектов и ссылках репозитория. Это удобно для независимых задач, но общие ссылки всё ещё общие; одна ветка обычно не должна быть одновременно checkout в двух местах.

Reflog записывает локальные перемещения ссылок и помогает найти commit после ошибочного reset. Это локальный журнал с ограниченным сроком жизни, а не резервная копия всех файлов и не история всех действий коллег.

## 9. Командный процесс следует модели

Gitflow вводит долгоживущие ветки разработки/релиза; GitHub flow строит короткие ветки и review в основную; trunk-based требует очень частой интеграции небольших изменений. Выбор зависит от выпусков и совместимости, а не только названия платформы.

Небольшой логический commit легче проверить, перенести и отменить. Hook даёт ранний локальный сигнал, но его можно обойти; обязательные правила проверяют независимо в CI. Реальный процесс команды нужно знать отдельно от учебного примера.

2. Почему fetch не обновил рабочие файлы? Что такое origin/main?
3. Почему rebase изменил идентификатор commit с тем же кодом?
4. Чем revert отличается от reset в общей истории?
5. Что именно создают fork, branch и PR? Где находятся предлагаемые изменения?
