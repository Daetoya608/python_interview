# Проектирование БД — Junior

## DDL

DDL задаёт структуру БД; DML меняет строки.

| Команда | Назначение |
|---|---|
| CREATE | Создать таблицу/индекс/другой объект |
| ALTER | Изменить структуру существующего объекта |
| DROP | Удалить объект, для таблицы — вместе с данными |
| TRUNCATE | Удалить все строки, сохранив таблицу; отдельные правила блокировок/FK/триггеров зависят от СУБД |

TRUNCATE не синоним DELETE; в SQLite его нет. Транзакционность DDL и доступные ALTER проверяют для конкретной СУБД.

## Ограничения

| Ограничение | Гарантия |
|---|---|
| PRIMARY KEY | Уникальная идентичность строки без NULL; может состоять из нескольких колонок |
| UNIQUE | Уникальность значения/комбинации; особенности NULL зависят от СУБД |
| NOT NULL | Запрет NULL |
| CHECK | Допустимость по условию, например quantity > 0 |
| FOREIGN KEY | Допустимые ссылки на ключи другой/той же таблицы |

CHECK не заменяет NOT NULL: неизвестный результат условия из-за NULL может не считаться нарушением. Ограничения БД действуют для всех приложений, которые пишут в неё.

```sql
CREATE TABLE customers (
    id INTEGER PRIMARY KEY,
    email VARCHAR(200) NOT NULL UNIQUE
);
CREATE TABLE orders (
    id INTEGER PRIMARY KEY,
    customer_id INTEGER NOT NULL REFERENCES customers(id) ON DELETE NO ACTION,
    amount_cents INTEGER NOT NULL CHECK (amount_cents >= 0)
);
ALTER TABLE customers ADD COLUMN name VARCHAR(80);
```

FK обеспечивает **ссылочную целостность**: заказ не может ссылаться на несуществующего клиента. Nullable FK допускает отсутствие ссылки. Индекс на дочерней колонке может требоваться отдельно: например, PostgreSQL не создаёт его автоматически только из-за FOREIGN KEY.

## Удаление родителя

| Правило | Что произойдёт с существующей зависимой строкой |
|---|---|
| NO ACTION | Удаление не должно оставить нарушенную ссылку; момент проверки зависит от ограничений/СУБД |
| CASCADE | Зависимая строка удалится автоматически |
| SET NULL | Ссылка станет NULL; колонка должна это допускать |

NO ACTION и RESTRICT не всегда полностью взаимозаменяемы по моменту проверки. Выбор следует смыслу данных: историю заказов не стоит удалять с клиентом автоматически только ради удобства.

В SQLite FK включают `PRAGMA foreign_keys=ON` для каждого соединения до начала транзакции. Наличие описания FK в SQL без включённой проверки там не гарантирует целостность.
