# Проектирование БД — уровень 3

Обязательно по issue №7: денормализация и materialized view.

## Зачем денормализовывать

Денормализация — намеренное хранение производных/повторяющихся данных ради конкретных операций. Например, total_cents заказа, число комментариев или отчёт по продажам вместо пересчёта большого JOIN на каждый запрос.

Причина должна быть измеримой: дорогие агрегации, большой read/write ratio, известный предел допустимой задержки данных. Сначала проверьте запрос, индексы и модель: копирование не лечит любую проблему.

| Выигрыш | Цена |
|---|---|
| Более дешёвое чтение | Обслуживание при записи/обновлении |
| Меньше JOIN | Дополнительное место |
| Готовая форма для отчёта | Возможная устарелость |
| Изоляция тяжёлой агрегации | Процессы пересчёта, recovery и наблюдение за lag |

Для каждого дублированного факта определите:

1. Где источник истины?
2. Как обновляется производное значение: транзакционно, триггером, CDC/событием или по расписанию?
3. Какова допустимая устарелость и как она видна пользователю?
4. Как обработать повтор/потерю/неправильный порядок события?
5. Как полностью пересобрать и проверить проекцию?

Триггер даёт локальную транзакционную связь, но увеличивает цену записи. Асинхронная проекция масштабирует обработку, но требует идемпотентности и модели eventual consistency. Изменяемый кэш с TTL не становится источником истины автоматически.

## View и materialized view

Обычный view хранит определение запроса. Materialized view хранит **результат** и определение для его пересчёта. Чтение может быть быстрым, но данные соответствуют последнему обновлению.

PostgreSQL, при наличии схемы уровня 2:

```sql
CREATE MATERIALIZED VIEW customer_totals AS
SELECT o.customer_id,
       SUM(i.quantity * i.unit_price_cents) AS total_cents
FROM orders AS o
JOIN order_items AS i ON i.order_id = o.id
GROUP BY o.customer_id;

CREATE UNIQUE INDEX customer_totals_pk ON customer_totals(customer_id);
REFRESH MATERIALIZED VIEW CONCURRENTLY customer_totals;
```

Это общий оборот строк заказов, не обязательно оплаченная выручка: фильтр статуса должен следовать требованию отчёта.

- В PostgreSQL materialized view не обновляется автоматически при каждом изменении исходных таблиц.
- Обычный REFRESH может блокировать чтение результата на время обновления. CONCURRENTLY позволяет читать старое содержимое во время обновления, но имеет дополнительные затраты и требования.
- Для CONCURRENTLY нужен подходящий UNIQUE-индекс на обычных колонках, покрывающий все строки, и уже заполненное представление. Частичный/expression-индекс не удовлетворяет этому условию.
- WITH NO DATA создаёт незаполненный объект: сначала нужен обычный первоначальный refresh.
- Индексы materialized view ускоряют его чтение отдельно от индексов источников.
- Полный пересчёт большого отчёта может быть дорогим; incremental maintenance зависит от СУБД/расширений и не обещается обычным REFRESH PostgreSQL.

SQLite не имеет встроенного CREATE MATERIALIZED VIEW: отдельная таблица с ручным пересчётом может показать идею, но не является той же возможностью СУБД.

Самопроверка: что станет устаревшим? Как пересобрать данные после сбоя? Кто владеет истинным значением? Что нужно для concurrent refresh? Когда исторический снимок — отдельный факт, а не просто денормализация?
