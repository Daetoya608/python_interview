# Проектирование БД: краткое повторение

- CREATE/ALTER/DROP управляют структурой. Конкретные ALTER и транзакционность DDL проверяют для целевой СУБД.
- PK идентифицирует строку; FK обеспечивает ссылочную целостность; UNIQUE запрещает дубли по правилам СУБД; NOT NULL запрещает NULL; CHECK проверяет условие. CHECK сам по себе не всегда исключает NULL. Индекс FK на дочерней стороне может требоваться отдельно.
- One-to-many: FK у ребёнка. One-to-one: FK + UNIQUE, обычно NOT NULL; это не гарантирует ребёнка у каждого родителя. Many-to-many: таблица двух FK, ключ пары и при необходимости атрибуты связи.
- ON DELETE CASCADE/SET NULL/RESTRICT выбирают по жизненному циклу данных, а не ради удобства удаления.
- Доменная модель начинается со сценариев, идентичности, состояний и инвариантов. ERD показывает сущности/кардинальности, ограничения реализуют гарантии.
- Нормализация уменьшает аномалии вставки, изменения и удаления. 1NF — нет повторяющихся групп; 2NF — нет частичной зависимости неключевых данных от составного кандидатного ключа; 3NF — устраняются нежелательные транзитивные зависимости. Строгая проверка требует функциональных зависимостей и всех кандидатных ключей.
- Текущий email клиента — в customers. Цена на момент покупки — самостоятельный исторический факт позиции; её нельзя заменять текущей ценой товара.
- Денормализация покупает чтение ценой записи, места и согласованности. Нужны источник истины, допустимый lag, обновление, обработка повторов и полный rebuild.
- View хранит запрос; materialized view — результат последнего refresh. В PostgreSQL автоматического обновления нет; CONCURRENTLY требует заполненного объекта и подходящего UNIQUE-индекса.

Практика: `python db-design/practice/demo.py`; ERD — в lvl-2.md. PostgreSQL materialized-view примеры описаны, но не выполнялись без сервера.
