# Принципы проектирования — уровень 1

## ООП

**Класс** описывает поведение и состояние, **объект** — конкретный экземпляр. **Инкапсуляция** удерживает инварианты за понятным интерфейсом; это не только скрытие полей. В Python `_name` — соглашение, `__name` вызывает name mangling, но не обеспечивает защиту доступа. **Абстракция** выделяет существенный контракт. **Наследование** выражает отношение подтипа. **Полиморфизм** позволяет работать с разными реализациями через общий контракт; Python поддерживает duck typing, базовый класс не всегда обязателен.

Композиция: объект владеет частью и организует её жизненный цикл. Агрегация: использует независимо существующий объект. В Python это прежде всего смысл модели, а не особый синтаксис. Передача `OrderService(repository, notifier)` обычно гибче наследования от `DatabaseAndEmailService`: зависимости можно менять отдельно и подменять в тестах. Наследование уместно при настоящем отношении «является» и соблюдении контракта базового типа.

## SOLID в одном примере

| Принцип | Смысл | Практическое применение |
|---|---|---|
| S — Single Responsibility | Одна связная ответственность, одна ось причин изменения | Расчёт заказа отделён от SQL и отправки письма |
| O — Open/Closed | Предусмотренное расширение без изменения стабильного ядра | Новый способ оплаты реализует контракт, не добавляет ветку в каждый сервис |
| L — Liskov Substitution | Подтип сохраняет обещания базового контракта | Хранилище не должно внезапно возвращать иной смысл результата или усиливать предусловия |
| I — Interface Segregation | Клиент зависит только от нужных ему операций | Для чтения достаточно `get`, не требуется реализовать CRUD и отчёты |
| D — Dependency Inversion | Политики зависят от абстракций, детали реализуют их | Сервис использует порт Repository, SQL-адаптер подключается снаружи |

DIP — направление зависимостей; dependency injection — техника передачи зависимостей. DI-контейнер не обязателен, обычного конструктора часто достаточно. SOLID — ориентиры управления изменениями, а не требование создать интерфейс и класс для каждой функции.

## Частые паттерны

| Паттерн | Когда нужен | Цена/опасность |
|---|---|---|
| Singleton | Один контролируемый экземпляр в заданной области | Скрытое глобальное состояние, трудные тесты; Python module не делает экземпляр общим для всех процессов |
| Proxy | Посредник с тем же интерфейсом для доступа, удалённого вызова, ленивого создания | Скрытая задержка/ошибки; сетевой вызов не становится локальным по надёжности |
| Builder | Пошаговое создание сложного объекта с проверкой перед `build` | Избыточен для простого конструктора с keyword arguments/dataclass |
| Factory | Выбор/создание реализации за отдельной функцией или объектом | Не нужен, если достаточно прямого вызова конструктора |
| Decorator | Обёртка добавляет поведение, сохраняя контракт | Порядок обёрток влияет на результат; это паттерн, а `@decorator` — синтаксис Python для преобразования объекта |

Пример фабрики: `make_notifier(config)` возвращает email- или console-реализацию. Пример декоратора: `LoggingNotifier(real_notifier)` записывает попытку и вызывает `send`. Proxy чаще контролирует доступ к объекту, decorator наращивает его поведение; механически оба могут делегировать вызов.

## Простота и антипаттерны

- **KISS:** выбирайте простое решение, которое удовлетворяет текущим ограничениям; «короче» не всегда «понятнее».
- **DRY:** у каждого знания/правила должен быть один авторитетный источник. Похожие строки кода с разным смыслом не обязательно нужно объединять.
- **YAGNI:** не реализуйте возможности без подтверждённой потребности. Это не повод игнорировать известные требования безопасности и нагрузки.
- **God object:** один объект знает всё — HTTP, SQL, оплату, отчёты. Высокая связанность мешает менять и тестировать части. Разделяют по связным обязанностям, а не механически по числу строк.
- **Magic numbers:** непонятные `if retries > 7` заменяют осмысленной константой/конфигурацией `MAX_RETRIES`; очевидные `0` и `1` не всегда требуют имени.
- **«Процедурный стиль» сам по себе не антипаттерн.** Плохое решение — разнесённые по обработчикам дублирующиеся бизнес-правила и доступ к чужому внутреннему состоянию. Небольшие чистые функции часто лучше искусственной иерархии классов.

## Парадигмы (желательно)

Императивная программа описывает шаги **как** получить результат; декларативная — **что** требуется (например SQL). Процедурная организует шаги в процедуры, ООП — вокруг объектов и контрактов. Функциональная делает акцент на функциях, композиции и уменьшении изменяемого состояния. Реактивная описывает обработку потоков изменений/событий, часто с управлением скоростью потока. Реактивность не равна любому `async def`. Python допускает смешение подходов под задачу.
