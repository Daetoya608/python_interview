# Проектирование: инварианты, контракты и направление зависимостей

Принципы полезны, когда позволяют объяснить цену изменения кода. Краткие определения — [КОНСПЕКТ.md](КОНСПЕКТ.md), учебные примеры — [practice/demo.py](practice/demo.py). Здесь паттерны рассматриваются как решения конкретных проблем, а не обязательный список классов.

## 1. Объект соединяет состояние и правила его изменения

Смысл инкапсуляции — не просто поставить подчёркивание перед полем. Объект должен контролировать переходы, сохраняющие инвариант. Например, денежный счёт не должен позволять произвольно разойтись balance и историей операций.

Абстракция выделяет важные для клиента операции и скрывает несущественные детали. Полиморфизм позволяет разным реализациям выполнять один контракт. Python поддерживает это через обычные методы, duck typing, Protocol и другие средства; обязательная иерархия наследования не нужна.

В Python `_name` — соглашение, `__name` включает name mangling, но ни то ни другое не является непроницаемой границей безопасности. Защита модели строится прежде всего на ясном публичном интерфейсе и дисциплине доступа.

## 2. Контракт включает больше сигнатуры

Контракт задаёт допустимые входы, результат, ошибки и наблюдаемые эффекты. Два метода с одинаковыми параметрами несовместимы, если один обещает не менять данные, а другой их удаляет.

Подтип должен сохранять ожидания клиента: не требовать более сильных предусловий и не ослаблять обещанный результат. Класс «только чтение», который наследует writable storage и бросает ошибку на любой save, может нарушать такой контракт, даже если наследование технически работает.

Композиция передаёт часть работы вложенному объекту без заявления «я являюсь этим типом». Она удобна для замены поведения и уменьшения связанности. Наследование оправдано, когда отношение подтипа действительно сохраняется, а не только экономит несколько строк.

## 3. Cohesion и coupling определяют масштаб изменения

Высокая cohesion означает, что содержимое модуля относится к одной связной задаче. Низкая coupling — что изменение детали одного модуля не заставляет переписывать много других.

Класс, который рассчитывает цену, пишет SQL, отправляет письмо и форматирует HTML, меняется по разным причинам. Это god object независимо от числа строк. Разделение по ответственности позволяет локализовать изменения и отдельно проверять правила.

Но дробление на десятки классов без самостоятельных контрактов тоже увеличивает связанность понимания: читателю приходится переходить по цепочке ради одного простого действия. Граница полезна, если она скрывает сложность или защищает самостоятельное решение.

## 4. SOLID как проверка изменений

| Принцип | Вопрос к дизайну | Возможное исправление |
|---|---|---|
| SRP | Какие независимые причины меняют этот модуль? | Разделить расчёт, хранение и доставку |
| OCP | Можно ли добавить ожидаемый вариант без правки стабильного ядра? | Вынести изменяемую стратегию |
| LSP | Сохраняются ли обещания при подстановке реализации? | Уточнить контракт или отказаться от неверного подтипа |
| ISP | Зависит ли клиент от ненужных ему операций? | Выделить небольшой интерфейс роли |
| DIP | Знают ли бизнес-правила конкретную инфраструктуру? | Направить зависимости к контракту политики |

OCP не требует никогда не менять старый код. Он помогает изолировать действительно ожидаемую ось изменения. Универсальный plugin framework ради двух стабильных веток может противоречить простоте.

ISP не требует отдельный интерфейс на каждый метод. Важно, чтобы потребитель не зависел от несвязанных возможностей. DIP не равен обязательному контейнеру: зависимости можно передать обычным аргументом.

## 5. DI и DIP на одном примере

```python
from dataclasses import dataclass
from typing import Protocol

class Notifier(Protocol):
    def send(self, text: str) -> None: ...

@dataclass
class Checkout:
    notifier: Notifier

    def complete(self, order_id: int) -> None:
        self.notifier.send(f"order {order_id} completed")

class RecordingNotifier:
    def __init__(self):
        self.messages = []

    def send(self, text: str) -> None:
        self.messages.append(text)

notifier = RecordingNotifier()
Checkout(notifier).complete(42)
assert notifier.messages == ["order 42 completed"]
```

DI здесь — передача notifier извне. DIP — то, что Checkout выражает нужный ему контракт и не импортирует конкретный SMTP-клиент. Внешняя точка сборки выбирает реализацию и связывает объекты.

Пример показывает зависимости, а не надёжное оформление заказа: в реальной системе сохранение и уведомление нужно согласовать через транзакцию/outbox. Чистая структура классов сама не решает сетевые сбои.

## 6. Как работают распространённые паттерны

Factory локализует выбор/создание конкретного объекта. Builder собирает сложный объект шагами и может отделять промежуточную конфигурацию от готового состояния. Decorator оборачивает тот же интерфейс дополнительным поведением, например метриками. Proxy контролирует доступ к другому объекту: ленивость, права, удалённый вызов.

Обёртки внешне похожи, но отличаются намерением. Retry-decorator должен учитывать идемпотентность оборачиваемой операции; одного красивого интерфейса недостаточно для корректного повторения платежа.

Singleton означает единственный экземпляр **в выбранной области**. Глобальный объект Python обычно единственен в процессе, а не во всём кластере. Он скрывает зависимость и разделяет изменяемое состояние между тестами. Явно переданный ресурс с процессным временем жизни часто понятнее.

Dynamic binding выбирает реализацию метода во время выполнения по объекту. Аннотация типа не выполняет этот выбор. AOP выделяет сквозное поведение; в Python middleware и декораторы могут реализовывать часть такой идеи, но порядок обёрток влияет на семантику.

## 7. DRY, KISS и YAGNI регулируют сложность

DRY касается повторения **знания**: одно бизнес-правило не должно независимо расходиться в нескольких местах. Похожие строки для разных правил не обязательно нуждаются в общей абстракции. Объединение их по внешнему сходству может связать независимые изменения.

KISS требует понятного решения заданной задачи. Это не запрет на сложный алгоритм, если без него нельзя выполнить требования. YAGNI удерживает от реализации гипотетического будущего; оно не отменяет подготовку к уже известным ограничениям.

BDUF — большое предварительное проектирование. Полезно заранее исследовать дорогие необратимые решения, модель данных и риски. Попытка детально угадать все будущие функции приводит к лишней структуре. Ранние небольшие эксперименты помогают проверить предположения дешевле.

Magic number скрывает причину значения. Именованная константа помогает, если сообщает смысл/единицы. Но переименование `42` в `VALUE_42` ничего не объясняет. Аналогично абстракция должна передавать решение, а не просто прятать код.

## 8. Слои, Clean и Hexagonal

Layered разделяет роли: транспорт, сценарии приложения, предметные правила, хранение. Проблема возникает, если бизнес-код начинает зависеть от HTTPRequest, конкретного ORM-запроса и внешнего SDK одновременно.

Clean направляет исходные зависимости к более устойчивым бизнес-политикам. Hexagonal описывает порты, через которые ядро взаимодействует с внешним миром, и адаптеры, реализующие эти порты. HTTP и тестовый вызов могут быть входными адаптерами, PostgreSQL и fake repository — выходными.

```text
HTTP adapter → application use case → domain
                         ↓ port
                  storage adapter
```

Во время выполнения сценарий может вызвать адаптер, но на уровне импортов контракт принадлежит ядру/его границе. Это и есть инверсия зависимости. Слои не требуют микросервисов и не оправдывают дублирование каждого поля через десять бессодержательных объектов.

## 9. DDD: общий смысл и границы согласованности

Ubiquitous language согласует термины кода и предметной области. Bounded context ограничивает модель, внутри которой термин имеет определённый смысл: «клиент» в биллинге и доставке может иметь разные атрибуты и правила.

Entity узнаётся по идентичности во времени. Value object определяется значением, часто неизменяем и проверяет инварианты при создании. Aggregate объединяет объекты вокруг корня, который контролирует согласованные изменения. Граница aggregate выбирается по инвариантам, а не по желанию загрузить весь связанный граф.

DDD не требует микросервисов. Несколько контекстов могут жить в модульном монолите; один сервис может содержать плохо определённую модель. Repository даёт предметный интерфейс доступа, unit of work задаёт границу сохранения изменений.

## 10. Другие способы организации модели и UI

Active Record соединяет объект данных с операциями собственного хранения. Data Mapper отделяет отображение в БД от предметного объекта. Первый проще в небольших CRUD-сценариях, второй удобнее для независимой сложной модели; название ORM не освобождает от анализа фактических зависимостей.

MVC разделяет обработку ввода, модель и представление. MVVM добавляет ViewModel с состоянием/командами представления и часто binding. Это модели организации интерфейса, а не замена транзакциям или универсальная архитектура всего backend.

Процедурный и функциональный код может хорошо выражать задачу без классов. Принципы оценивают по понятности контрактов, локальности изменений и проверяемости, а не числу использованных паттернов.
