# Принципы проектирования — уровень 2

## Применение SOLID без лишних абстракций

**SRP:** у отчёта могут быть независимые причины изменения — формула расчёта, формат PDF, схема БД. Отделите расчёт от представления и хранения. Один метод не означает одну ответственность, а несколько методов могут поддерживать один инвариант.

**OCP:** если ожидаются новые способы доставки, выделите контракт `calculate(order)`. Новая реализация добавляется без изменения расчёта итоговой суммы. Полной закрытости к изменениям не бывает: абстракция защищает выбранную ось вариативности. Строить систему плагинов ради двух стабильных `if` может быть дороже их поддержки.

**LSP:** предусловия подтипа не должны быть сильнее, постусловия — слабее; сохраняются инварианты и допустимое наблюдаемое поведение. Если `withdraw` обещает работать для любого достаточного баланса, подтип не может неожиданно запретить снятие по вторникам. Пример «квадрат наследуется от изменяемого прямоугольника» нарушается, если независимое изменение ширины вдруг меняет высоту. Исправление — другой контракт/неизменяемые значения/композиция. Исключение, разрешённое общим контрактом, само по себе LSP не нарушает.

**ISP:** разделите читателя каталога и администратора каталога, если их клиенты имеют разные потребности. **DIP:** прикладной сервис определяет необходимый контракт хранилища, инфраструктура предоставляет реализацию; точка сборки приложения связывает их. Интерфейс ради единственного тривиального вызова без изменчивости может не окупиться.

## Coupling, cohesion и правила простоты

**Coupling (связанность)** — насколько изменение одного модуля требует изменения другого. **Cohesion (связность внутри модуля)** — насколько его части служат одной цели. Нужна высокая cohesion внутри границ и низкая ненужная coupling между ними. Абсолютно независимых модулей нет: задача — явные, небольшие контракты. Сотни getter/setter через границы не дают слабой связанности только потому, что поля private.

DRY борется с повторением знания, **DIE (Duplication Is Evil)** — распространённая формулировка той же проблемы, а не универсальный запрет двух похожих блоков. Преждевременное объединение разных правил создаёт случайную связанность. KISS снижает сложность; YAGNI ограничивает спекулятивные функции. **BDUF (Big Design Up Front)** — подробное проектирование заранее; помогает при дорогих необратимых решениях, но детальное предсказание всех будущих требований быстро устаревает. Полезный компромисс: заранее определить риски, границы и важные контракты, детали уточнять итеративно.

## Организация приложения

| Подход | Главное правило | Подходит / ограничения |
|---|---|---|
| Layered | Разделение представления, прикладной логики, доступа к данным | Понятно для CRUD; сквозные изменения могут затрагивать все слои, домен легко связать с ORM |
| Clean Architecture | Зависимости исходного кода направлены к политикам/use cases, внешние детали подключаются через контракты | Удобно тестировать правила отдельно; добавляет границы и преобразования |
| Hexagonal / Ports & Adapters | Приложение общается с внешним миром через порты, HTTP/SQL/CLI — адаптеры | Несколько способов ввода/хранения без переписывания ядра; простому скрипту полный набор портов не нужен |

Во время выполнения домен может вызвать метод SQL-адаптера, но тип/контракт этого метода определяется внутренним слоем. Направление runtime-вызова и направление зависимости исходников — не одно и то же. Эти подходы пересекаются: это не три взаимоисключающих набора каталогов.

```text
HTTP/CLI adapter → use case → domain
                       ↓
                Repository port ← SQL adapter
```

В [практике](practice/demo.py) `OrderService` зависит от Protocol, а не от базы или транспорта. В реальном проекте интерфейс размещают на стороне потребителя, адаптеры — снаружи. Возвращать ORM-объекты с активной сессией наружу может протащить инфраструктурную зависимость и скрытые запросы.

## DDD (желательно)

Domain-Driven Design — проектирование через модель предметной области и общий язык с экспертами. **Bounded context** задаёт границу смысла модели: «клиент» у биллинга и поддержки может означать разные вещи. **Entity** имеет устойчивую идентичность; **value object** определяется значением (например Money с валютой); **aggregate** защищает связанные инварианты через aggregate root. Repository представляет доступ к агрегатам, domain service выражает правило, не принадлежащее одному объекту. Не каждая таблица — агрегат и не каждый bounded context — отдельный микросервис. Для простого CRUD полная DDD-модель может не окупиться.

## Смежные термины

- **Active Record:** объект совмещает данные/поведение и операции сохранения (`user.save()`). Прост в CRUD, но связывает модель с БД. **Data Mapper:** отдельный mapper переносит данные между объектами и БД; доменная модель может не знать о сохранении. SQLAlchemy ORM реализует Data Mapper и Unit of Work; Django ORM ближе к Active Record.
- **MVC:** Model — данные/правила, View — представление, Controller обрабатывает ввод и координирует. В веб-фреймворках имена ролей могут отличаться. **MVVM:** ViewModel предоставляет состояние/команды представления, часто с data binding; удобен для интерактивных UI, но не заменяет доменную модель.
- **Статическое связывание:** цель/реализация определяется до runtime (например некоторые компилируемые вызовы). **Динамическое:** выбор зависит от runtime-объекта; типичный вызов метода Python использует динамическое разрешение. Это не то же, что статическая/динамическая типизация и не `@staticmethod`.
- **AOP:** сквозные аспекты (логирование, метрики, tracing, транзакции) отделены от бизнес-кода. Декораторы, middleware и interceptors могут реализовывать подобное разделение. Скрытая магия и неверный порядок обёрток усложняют отладку; бизнес-решения не следует прятать в неочевидный аспект.

Самопроверка: придумайте реальное нарушение LSP, объясните место SQL-адаптера в Clean Architecture и случай, когда две похожие функции лучше оставить раздельными.
