# Принципы проектирования — Junior

## ООП

- **Инкапсуляция:** объект удерживает инварианты за своим интерфейсом. Счёт не разрешает отрицательное списание через метод withdraw; это не только сокрытие полей.
- **Абстракция:** выделяется нужный контракт, детали скрываются. Клиенту notifier нужен send, а не знание SMTP.
- **Наследование:** создаётся подтип с поведением базового типа. Подходит для отношения «является», а не только ради копирования кода.
- **Полиморфизм:** разные реализации выполняют общий контракт. EmailNotifier и ConsoleNotifier имеют send; Python допускает duck typing без общего базового класса.

`_name` в Python — соглашение о внутренней детали; не механизм запрета доступа.

**Композиция** — объект использует другой объект как часть: OrderService получает notifier и вызывает его. Можно заменить отправку письма без новой иерархии сервисов. Наследование уместно, когда подтип действительно сохраняет контракт родителя.

## SOLID на примере заказа

| Принцип | Что означает | Практический пример |
|---|---|---|
| S — Single Responsibility | Одна связная ответственность/ось причин изменения | Расчёт суммы отделён от SQL и форматирования письма |
| O — Open/Closed | Предусмотренное расширение без правок стабильного ядра | Новый способ доставки реализует calculate, не добавляет if во все сервисы |
| L — Liskov Substitution | Подтип сохраняет обещания общего контракта | Реализация хранилища не меняет смысл get и не требует неожиданно дополнительных условий |
| I — Interface Segregation | Клиент зависит лишь от нужных операций | Для чтения достаточно get, не требуется весь административный API |
| D — Dependency Inversion | Политики опираются на абстракции; детали подключаются снаружи | Сервис использует контракт notifier, конкретный EmailNotifier передают конструктору |

Нарушение L: базовый withdraw разрешает снять сумму при достаточном балансе, а потомок неожиданно запрещает любое снятие. Формальная совместимость методов не сохраняет поведение. Лучше изменить модель/контракт, чем маскировать несовместимость исключением.

Передача зависимости через конструктор — dependency injection; принцип DIP — про направление зависимостей. SOLID не требует интерфейса и класса для каждой короткой функции.

## KISS / DRY / YAGNI

- **KISS:** простое понятное решение под текущие ограничения; меньше строк не всегда понятнее.
- **DRY:** у одного бизнес-правила один авторитетный источник. Похожие строки с разным смыслом не обязательно объединять.
- **YAGNI:** не реализовывать возможности без подтверждённой потребности. Например, не строить сложную систему плагинов для одного стабильного варианта.

Принципы применяются к реальным причинам изменения, а не ради количества абстракций.

## Базовые паттерны

| Паттерн | Идея | Пример / ограничение |
|---|---|---|
| Singleton | Контролируемый единственный экземпляр в заданной области | Общее состояние усложняет тесты; один экземпляр процесса не становится общим для всех процессов |
| Proxy | Посредник с тем же интерфейсом, управляющий доступом | Ленивое создание/проверка прав перед реальным вызовом; удалённый proxy не отменяет сетевых ошибок |
| Builder | Пошаговое создание сложного объекта | Собрать конфигурацию и проверить её в build; для простого объекта достаточно конструктора |
| Factory | Вынести выбор/создание реализации | make_notifier(config) возвращает нужный notifier |
| Decorator | Обернуть объект и добавить поведение, сохранив контракт | LoggingNotifier(real) логирует и делегирует send; порядок обёрток важен |

Proxy чаще контролирует доступ, Decorator добавляет поведение. Python-синтаксис @decorator — применение преобразования к функции/классу; не каждая такая функция представляет именно объектный паттерн Decorator.
