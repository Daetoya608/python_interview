# multiprocessing и выбор конкурентности: конспект к аттестации

Объединяет `lvl-1.md` и `lvl-1-guide.md`: выбор инструмента, процессы, обмен данными, синхронизация, пулы и ошибки.

## 1. Конкурентность, параллелизм и выбор инструмента

**Конкурентность** — перекрытие работы нескольких задач во времени. **Параллелизм** — их одновременное исполнение, например на разных ядрах.

**I/O-bound**: время уходит на ожидание сети, диска, БД. **CPU-bound**: время уходит на вычисления. Сначала измеряют, где узкое место: конкурентность не исправляет плохой алгоритм и может добавить расходов.

| Инструмент | Модель | Память | Когда применять |
|---|---|---|---|
| `threading` / `ThreadPoolExecutor` | Потоки ОС, переключает ОС | Общая | Блокирующие I/O-библиотеки |
| `asyncio` | Задачи event loop, кооперативное переключение | Общая в процессе | Много I/O с асинхронными библиотеками |
| `multiprocessing` / `ProcessPoolExecutor` | Отдельные процессы ОС | Обычно раздельная | Достаточно тяжёлые CPU-bound вычисления |

В обычном CPython GIL ограничивает одновременное исполнение Python-байткода потоками одного интерпретатора. При I/O и в некоторых C-расширениях GIL освобождается. Существуют отдельные free-threaded сборки, но это не свойство любой установки Python.

У процессов отдельные интерпретаторы и память: GIL одного процесса не мешает другому. Цена — запуск процессов, дополнительная память, сериализация и пересылка данных. Небольшие задачи могут стать медленнее.

Если 20 независимых запросов ждут по 0,5 с, последовательный запуск займёт примерно 10 с; 10 рабочих потоков — около 1 с; 20 одновременно ожидающих async-задач — около 0,5 с при отсутствии других ограничений. Это иллюстрация перекрытия ожиданий, а не гарантия производительности сети.

Количество процессов для вычислений обычно соотносят с доступными ядрами и памятью. Число I/O-потоков может быть больше числа ядер. Конкурентность ограничивают, чтобы не исчерпать соединения и ресурсы.

## 2. Process: запуск и жизненный цикл

```python
import multiprocessing as mp

def worker(queue, value):
    queue.put(value * value)

if __name__ == "__main__":
    ctx = mp.get_context("spawn")
    queue = ctx.Queue()
    process = ctx.Process(target=worker, args=(queue, 7))
    process.start()
    print(queue.get(timeout=5))
    process.join(timeout=5)
    if process.is_alive():
        raise RuntimeError("Рабочий процесс не завершился")
    print(process.exitcode)
    process.close()
    queue.close()
    queue.join_thread()
```

Пример запускают из `.py`-файла. В интерактивной среде дочерний процесс может не найти импортируемую функцию.

- `Process(target=func, args=..., kwargs=..., name=..., daemon=...)` описывает работу.
- `start()` запускает её в новом процессе; повторный запуск того же объекта запрещён.
- `run()` напрямую — обычный вызов в текущем процессе.
- `join(timeout)` ждёт завершения и возвращает `None`; затем проверяют `is_alive()` или `exitcode`. Таймаут не завершает процесс.
- `pid` — PID, `name` — диагностическое имя, `sentinel` — дескриптор готовности к завершению, пригодный для ожидания.
- `exitcode=None` — ещё нет результата завершения; `0` — успех; `1` — обычно необработанная ошибка; в POSIX `-N` означает завершение сигналом N.
- `close()` освобождает ресурсы объекта завершённого процесса; для работающего процесса это ошибка.
- Исключение дочернего Process автоматически не пробрасывается в родителя: нужен канал результата, проверка exitcode или пул.

Процесс с `daemon=True` не может создавать дочерние процессы и принудительно завершается при выходе родителя. Это не системный daemon-сервис.

## 3. Методы запуска и безопасный импорт

| Метод | Что происходит | Ограничения |
|---|---|---|
| `spawn` | Новый интерпретатор импортирует главный модуль | Медленнее; функции и аргументы должны быть пригодны для передачи/импорта |
| `fork` | Ответвляется снимок родительского процесса | POSIX; наследование состояния опасно при наличии потоков |
| `forkserver` | Выделенный сервер порождает процессы через fork | Поддерживаемые POSIX-системы; меньше проблем с потоками родителя |

В Windows и macOS по умолчанию используется spawn. В исходнике отмечен переход поддерживаемых POSIX-платформ на forkserver с Python 3.14; fork с 3.14 больше не является значением по умолчанию ни на одной платформе. Старые версии Python могут иметь другие значения.

`if __name__ == "__main__":` защищает создание процессов, пулов и менеджеров от повторного выполнения при импорте модуля дочерним интерпретатором. Без защиты возможны рекурсивный запуск и `RuntimeError`.

Для spawn/forkserver:

- Функции рабочего процесса определяют на верхнем уровне импортируемого модуля; обычные lambda и вложенные функции не подходят для стандартной pickle-передачи.
- Аргументы и результаты должны сериализоваться. Не передавайте живые соединения БД и произвольные открытые ресурсы; создавайте их внутри worker или `initializer`.
- Изменения глобальных переменных родителя не являются способом обмена состоянием с дочерним процессом.
- При fork начальное состояние наследуется, но последующие обычные изменения памяти тоже не становятся общими.

`get_context("spawn")` позволяет локально выбрать метод и создавать согласованные `ctx.Process`, `ctx.Queue`, `ctx.Lock`, `ctx.Pool`. Объекты разных контекстов могут быть несовместимы. Библиотеке лучше принимать контекст от пользователя, чем менять глобальные настройки.

`set_start_method()` обычно вызывают один раз в защищённой точке входа до создания ресурсов. `get_start_method()` читает метод; `get_all_start_methods()` показывает доступные.

`freeze_support()` нужен для некоторых упакованных исполняемых программ. `set_executable()` задаёт интерпретатор дочерних процессов; `set_forkserver_preload()` — предварительные импорты fork-сервера до его запуска.

## 4. Обмен данными: Queue и Pipe

| API | Использование |
|---|---|
| `Queue` | Несколько производителей и потребителей; передача сообщений |
| `SimpleQueue` | Более простой канал очереди с меньшим API |
| `JoinableQueue` | Очередь с учётом незавершённой работы |
| `Pipe(duplex=True)` | Пара связанных Connection для двух сторон |

`Queue.put(obj)` сериализует объект, `get()` возвращает восстановленный объект. Это копия данных, а не ссылка на общую память. У обычной Queue есть фоновый feeder-thread, пересылающий сериализованные данные в канал.

Важные свойства очереди:

- `get(timeout=...)` при отсутствии данных возбуждает `queue.Empty`, `put(timeout=...)` при переполнении — `queue.Full`.
- `empty()`, `full()`, `qsize()` ненадёжны для принятия конкурентных решений. Не делайте «если не empty, то get»; вызывайте get с нужным режимом и обрабатывайте исключение.
- Порядок сообщений одного производителя сохраняется; между разными производителями общий порядок не гарантируется.
- Избегайте изменения отправляемого изменяемого объекта сразу после `put()`: его фактическая сериализация может выполняться фоновым потоком.
- `close()` запрещает дальнейшую работу с очередью в данном процессе; `join_thread()` после close ждёт сброса буфера.
- `cancel_join_thread()` позволяет не ждать сброса, но может потерять сообщения.

**Ловушка deadlock:** дочерний процесс положил большой результат в очередь и ждёт сброса буфера, а родитель вызвал `process.join()` до чтения. Родитель ждёт завершения, ребёнок ждёт освобождения канала. Сначала прочитайте данные, затем делайте join.

У `JoinableQueue` на каждый извлечённый элемент вызывают `task_done()`, обычно в `finally`; `queue.join()` ждёт выполнения всех поставленных работ. Это другой смысл join, чем `process.join()`. У обычной multiprocessing.Queue этих методов нет. Для завершения потребителей удобно отправлять sentinel-сообщение каждому из них.

`Pipe()` возвращает `(conn1, conn2)`. `send(obj)` / `recv()` передают pickle-объекты; `send_bytes()` / `recv_bytes()` — байты. `poll(timeout)` проверяет готовность чтения, `close()` закрывает конец. При `duplex=False` первый конец только читает, второй только пишет.

Разные концы можно использовать конкурентно. Конкурентная запись или чтение **одного конца** без синхронизации может повредить сообщения. Неиспользуемые копии концов нужно закрывать, иначе обнаружение конца потока может задержаться. `recv()` при закрытии другой стороны и отсутствии данных возбуждает `EOFError`.

## 5. Общая память и синхронизация

Обычный `dict` или список не становится общим от передачи в Process. Для общего состояния есть следующие механизмы.

**Value / Array:** числовое значение или массив ctypes в общей памяти; `'i'` — знаковое целое, `'d'` — double. По умолчанию оборачиваются синхронизацией доступа.

Но составная операция всё равно требует общего Lock:

```python
def increment(counter):
    with counter.get_lock():
        counter.value += 1
```

Отдельная защита чтения и записи не делает весь read–modify–write атомарным.

`sharedctypes` позволяет размещать структуры ctypes в общей памяти. `RawValue` / `RawArray` не имеют автоматической синхронизации. Указатель на обычную память одного процесса не становится корректным указателем другого процесса.

Примитивы multiprocessing аналогичны threading:

- `Lock` — взаимное исключение;
- `RLock` — повторный захват владельцем;
- `Semaphore` / `BoundedSemaphore` — ограничение одновременного доступа;
- `Condition` — ожидание состояния под Lock;
- `Event` — флаг/сигнал;
- `Barrier` — встреча фиксированного числа участников.

Используйте `with`. API похож, но детали различаются: например, у multiprocessing.Lock аргумент называется `block`, отрицательный timeout трактуется как нулевой, а освобождение незахваченного Lock даёт `ValueError`. У RLock освобождение не владельцем даёт `AssertionError`. В macOS часть возможностей семафоров ограничена реализацией ОС.

## 6. Manager и прокси

`Manager()` запускает серверный процесс, который хранит Python-объекты, а клиентам выдаёт прокси: `manager.dict()`, `list()`, `Namespace()`, очереди и примитивы синхронизации. Менеджер гибче общей памяти и может работать по сети, но каждый вызов прокси несёт расходы межпроцессного взаимодействия.

```python
import multiprocessing as mp

if __name__ == "__main__":
    with mp.Manager() as manager:
        shared = manager.dict()
        shared["state"] = "ready"
        print(shared["state"])
```

Ловушки:

- `proxy["counter"] += 1` — несколько удалённых операций, не одна атомарная транзакция; нужна блокировка.
- Если в proxy хранится обычный вложенный dict, его изменение на клиенте может остаться локальным. Нужно присвоить изменённый dict обратно или использовать вложенный manager.dict.
- Один proxy при использовании несколькими потоками защищают блокировкой.
- Proxy — удалённый интерфейс, поэтому сравнение с обычной коллекцией не всегда имеет семантику сравнения содержимого. При необходимости получите копию данных.
- У Namespace атрибуты с `_` относятся к самому прокси, а не удалённому объекту.

`BaseManager.register()` позволяет зарегистрировать свои типы и доступные методы; `start()` запускает сервер, `get_server().serve_forever()` обслуживает его явно, `connect()` подключает клиента, `shutdown()` завершает собственный сервер. Контекстный менеджер помогает освободить ресурсы.

## 7. Pool: переиспользование рабочих процессов

```python
import multiprocessing as mp

def square(value):
    return value * value

if __name__ == "__main__":
    with mp.get_context("spawn").Pool(processes=4) as pool:
        print(pool.map(square, range(10)))
```

| Метод | Поведение |
|---|---|
| `apply(func, args)` | Одна задача; вызывающий ждёт результат |
| `apply_async(...)` | Одна задача; сразу возвращает `AsyncResult` |
| `map(func, iterable)` | Параллельная обработка; возвращает весь список в исходном порядке |
| `map_async(...)` | Аналог map с `AsyncResult` |
| `imap(...)` | Итератор результатов в исходном порядке |
| `imap_unordered(...)` | Итератор по готовности, порядок не сохраняется |
| `starmap(func, tuples)` | Распаковывает каждый набор аргументов: `func(*args)` |
| `starmap_async(...)` | Асинхронная постановка starmap |

«Async» здесь означает неблокирующую постановку работы, а не asyncio-корутину. `AsyncResult.get(timeout)` ждёт результат, пробрасывает исключение worker или `multiprocessing.TimeoutError`. Таймаут get работу не отменяет. `ready()` проверяет готовность, `successful()` — успех уже готовой работы, `wait()` только ждёт.

Настройки пула:

- `processes` — число worker;
- `initializer` / `initargs` — инициализация каждого worker, например создание его подключения;
- `maxtasksperchild` — замена worker после заданного числа задач для освобождения накопленных ресурсов;
- `chunksize` — размер пачек при map: больше пачки — меньше накладных расходов, но хуже балансировка неравномерных задач;
- `callback` / `error_callback` — обработка результата/ошибки; callbacks должны быть короткими, чтобы не задерживать обработку результатов.

Методы пула вызывает создавший его процесс. Большой `map` может потреблять много памяти; для постепенного потребления используют imap.

Завершение: `close()` запрещает новые задачи, `join()` ждёт workers после close/terminate, `terminate()` останавливает без завершения всей работы. Выход из `with Pool(...)` вызывает terminate; если задачи поставлены через apply_async, дождитесь результатов **внутри** блока, иначе незавершённая работа будет прервана.

`ProcessPoolExecutor` предлагает похожую модель через `submit()`, Future и `map()`. `multiprocessing.dummy.Pool` / `ThreadPool` используют потоки: похожий API не означает обход GIL.

## 8. Корректное завершение и служебные средства

Сначала передайте worker сигнал завершения через Event или очередь, затем получите результаты и дождитесь процессов. Не рассчитывайте на сборщик мусора для закрытия пула.

`terminate()` не выполняет `finally` и exit handlers; может оставить захваченные Lock и повреждённые очереди. Потомки автоматически не завершаются. `kill()` использует более жёсткий механизм ОС. `interrupt()` — отдельная возможность Python 3.14 для SIGINT в POSIX; поведение на Windows не определено этим API.

В POSIX явно присоединяйте завершённые процессы через join, чтобы освобождать системные ресурсы. Resource tracker при spawn/forkserver отслеживает именованные ресурсы, но не заменяет аккуратное управление ими.

`active_children()` возвращает живых детей; `current_process()` и `parent_process()` — текущий и родительский Process; `cpu_count()` — число CPU системы, которое может отличаться от доступного процессу лимита.

`multiprocessing.connection.wait(objects, timeout)` ждёт готовности Connection и process sentinel. `Listener` / `Client` дают соединения через сокеты или именованные каналы. `authkey` обеспечивает HMAC-аутентификацию сторон, но не шифрование транспорта. `recv()` выполняет unpickle: недоверенные данные принимать нельзя.

`get_logger()` / `log_to_stderr()` включают служебное логирование multiprocessing. Обычные файловые обработчики logging не обеспечивают общей межпроцессной блокировки; сообщения могут перемешиваться.

## 9. Смешанные сценарии и версии

В async-приложении блокирующий I/O можно вызвать через `await asyncio.to_thread(func)`. Тяжёлые вычисления — через `await loop.run_in_executor(process_pool, func, arg)`. Скачать и обработать файлы: I/O через async/потоки, CPU-обработку через процессы. Не создавайте отдельный большой пул на каждую мелкую операцию.

Гонки возможны и между потоками, и в общей памяти процессов, и между asyncio-задачами при приостановках между чтением и записью. Лучший первый шаг — уменьшить общее изменяемое состояние.

В исходнике есть отдельные возможности **Python 3.15–3.16**, включая `set_forkserver_preload(on_error=...)`, `Pool.imap(..., buffersize=...)` и fallback метода запуска при недоступном временном каталоге. Они не являются базовым API Python 3.11–3.14.

## 10. Самопроверка

1. Почему процессы ускоряют CPU-bound Python-код? У каждого свой интерпретатор и собственная область действия GIL.
2. Почему нельзя просто передать обычный dict и ждать общих изменений? Процессы имеют раздельную память; передача обычно создаёт восстановленную копию.
3. Зачем main guard? Чтобы безопасно импортировать главный модуль в дочернем интерпретаторе без повторного запуска процессов.
4. Почему Queue + join иногда зависают? Родитель ждёт процесс, который ждёт опустошения канала; сначала нужно получать данные.
5. Почему Value не делает `+=` атомарным? Операция состоит из чтения и записи; нужна блокировка на всю последовательность.
6. Manager или Value/Array? Manager удобнее для сложных объектов, общая память дешевле для подходящих числовых структур.
7. Почему больше процессов не всегда быстрее? Запуск, IPC, память и переключение могут стоить дороже самих вычислений.
8. Как получить ошибку worker? В Pool — через AsyncResult.get, в executor — Future.result; у обычного Process нужен свой протокол и проверка exitcode.
