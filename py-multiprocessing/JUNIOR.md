# multiprocessing — Junior

## Зачем нужны процессы

Процессы выполняются в отдельных интерпретаторах с обычно раздельной памятью. GIL одного процесса не мешает другому, поэтому CPU-bound Python-работа может идти параллельно на ядрах. Потоки разделяют память и дешевле обмениваются данными, но обычный CPython ограничивает их параллелизм Python-байткода GIL.

Преимущества процессов: параллельные вычисления и изоляция обычного состояния. Цена: запуск, память, сериализация и IPC — межпроцессный обмен. Для маленьких задач накладные расходы могут превысить выигрыш. Процесс сам по себе не является полной защитной песочницей: доступ к файлам и внешним ресурсам определяется отдельно.

## Process и Queue

Пример запускают из `.py`-файла, не из интерактивной строки:

```python
import multiprocessing as mp

def worker(queue, number):
    queue.put(number * number)

if __name__ == "__main__":
    ctx = mp.get_context("spawn")
    queue = ctx.Queue()
    process = ctx.Process(target=worker, args=(queue, 7))
    process.start()
    try:
        result = queue.get(timeout=5)
        assert result == 49
    finally:
        process.join(timeout=5)
        if process.is_alive():
            process.terminate()
            process.join()
        process.close()
        queue.close()
        queue.join_thread()
```

**Main guard** защищает запуск от повторного исполнения при импорте главного модуля дочерним интерпретатором. При spawn worker должен быть импортируемой функцией верхнего уровня, передаваемые данные — пригодными для сериализации. Новый процесс не получает работающую общую копию родительского dict.

Явный spawn делает метод запуска понятным независимо от платформенных defaults. Для Junior важно понимать его безопасный импорт, а не заучивать все внутренности запуска.

| Действие | Смысл |
|---|---|
| start | Запустить новый процесс; прямой run выполняет функцию в текущем |
| join | Дождаться завершения, возвращает None |
| join(timeout) + is_alive | Проверить, успел ли завершиться; timeout сам не останавливает |
| exitcode | None до завершения; 0 — успех, ненулевой — ошибка/сигнал |
| terminate | Принудительно остановить; затем нужно дождаться через join |

Исключение обычного Process не пробрасывается в родителя автоматически: нужны exitcode и собственный протокол сообщения об ошибке. При аварии worker родитель не должен бесконечно ждать результат.

## Как передаются данные

Queue сериализует сообщение и восстанавливает его на другой стороне. Это не общая ссылка на исходный Python-объект; последующие изменения родительского списка не обновят его копию у ребёнка. `empty()`/`qsize()` ненадёжны для конкурентного решения: вызывают get с timeout и обрабатывают отсутствие данных.

Сначала получают большой результат из Queue, затем ждут process.join: иначе ребёнок может ждать сброса буфера очереди, пока родитель ждёт завершения ребёнка.

**terminate — крайняя мера:** finally и обычная очистка не гарантируются, очереди/блокировки могут остаться повреждёнными. Штатно лучше передать сигнал завершения через очередь и дождаться выхода. Не передавай готовую Session/соединение БД как обычные данные: ресурс создают внутри worker.
