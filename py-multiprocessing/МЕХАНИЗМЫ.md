# multiprocessing: процессы, передача данных и стоимость параллелизма

Здесь разбирается путь задания от родителя к worker и обратно. Перечень методов — в [КОНСПЕКТ.md](КОНСПЕКТ.md); потоки — в [соседней теме](../py-threading/МЕХАНИЗМЫ.md). Пример запускают как отдельный `.py`-файл на Python 3.11+.

## 1. Что даёт отдельный процесс

У процесса своё виртуальное адресное пространство и экземпляр интерпретатора. Два процесса могут одновременно исполнять Python-код на разных ядрах: GIL обычного CPython ограничивает один интерпретатор, а не все процессы машины.

Изоляция означает и отсутствие автоматической общей памяти. Изменение обычного списка у ребёнка не меняет список родителя. Даже если значения и адреса сразу после fork выглядят одинаково, это не один общий изменяемый Python-объект.

Процессы полезны для достаточно тяжёлых независимых вычислений. Цена включает запуск, память интерпретаторов, передачу данных, сбор результатов и переключения ОС. Для короткой функции эти расходы могут превысить выигрыш.

## 2. Как появляется дочерний интерпретатор

| Способ | Модель появления | Следствие |
|---|---|---|
| spawn | Новый интерпретатор импортирует нужные модули | Нужен безопасный импорт и передаваемые аргументы |
| fork | ОС создаёт дочернее состояние на основе родителя | Наследуются в том числе потенциально опасные ресурсы/блокировки |
| forkserver | Запрос отдельному серверу, который делает fork | Не копируется произвольное текущее состояние многопоточного родителя |

Fork обычно использует copy-on-write: страницы физически разделяются, пока запись не потребует копии. Это оптимизация ОС, а не механизм обмена изменениями. Операции интерпретатора могут загрязнять страницы и уменьшать экономию памяти.

При fork многопоточного процесса у ребёнка остаётся только вызывающий поток, но могут остаться блокировки, захваченные исчезнувшими потоками. Поэтому «быстро скопировать всё» не равно безопасно продолжить работу с любыми библиотеками, пулами и соединениями.

В Python 3.14 fork больше не является default; на поддерживаемых POSIX используется forkserver, Windows/macOS используют spawn. В старых версиях значения отличаются. Явный `get_context` делает учебный пример предсказуемым; библиотеке лучше принимать контекст, чем менять глобальную настройку.

## 3. Зачем main guard и импортируемая функция

```python
import multiprocessing as mp

def square(value):
    return value * value

if __name__ == "__main__":
    ctx = mp.get_context("spawn")
    with ctx.Pool(2) as pool:
        result = pool.map(square, [2, 3, 4])
    assert result == [4, 9, 16]
```

При spawn ребёнок импортирует главный модуль. Функция square становится доступна, но защищённый блок не запускает ещё один пул. Без guard импорт повторно начал бы создание процессов.

Стандартный pickle обычно описывает функцию через модуль и имя, а не переносит её код вместе со всем окружением. Поэтому функция верхнего уровня импортируемого модуля подходит, а локальная closure или lambda обычно нет. Интерактивный `__main__` также может быть недоступен ребёнку как импортируемый файл.

## 4. Путь задачи через пул

```text
родитель: функция + аргументы → сериализация → канал заданий
→ worker: восстановление → вызов → результат/ошибка
→ сериализация → канал ответов → родитель получает итог
```

Pool переиспользует созданные процессы. Это уменьшает цену запуска, но задания и результаты всё равно передаются. Даже при fork аргументы отдельных заданий пула проходят IPC.

Map возвращает результаты во входном порядке; медленный ранний элемент способен задержать выдачу упорядоченного потока. Unordered-выдача отдаёт готовые результаты раньше, но требует самостоятельно сохранять связь с исходными данными.

Chunksize объединяет элементы в пачки: крупные уменьшают число пересылок, но ухудшают баланс при разной длительности задач. Число процессов ограничивают не только ядрами, но и памятью, квотами контейнера и внутренними потоками нативных библиотек. Иначе легко получить чрезмерное число исполнителей.

`apply_async` возвращает AsyncResult, а ProcessPoolExecutor — Future. Это объекты ожидания, не корутины asyncio. Ошибка worker становится доступна при получении результата. Timeout ожидания не означает остановку уже начатого вычисления.

## 5. Queue и Pipe передают сообщения

Queue обычно сериализует объект и передаёт данные через системный канал. Получатель восстанавливает новый объект. Отправка списка не позволяет удалённо менять исходный список.

У multiprocessing.Queue есть буфер и feeder-thread, поэтому put не обязательно означает, что байты уже прочитаны получателем или даже окончательно сериализованы. Не стоит менять переданный изменяемый объект сразу после put. Для согласования используют протокол сообщений.

Empty/qsize не подходят для решения «можно ли сейчас get»: другой потребитель может опередить между проверкой и чтением. Делают get с нужным режимом/timeout и обрабатывают отсутствие сообщения.

Pipe предоставляет связанные концы. Неиспользуемые копии концов закрывают, иначе EOF может не наступить, пока где-то ещё жив писатель. Одновременный доступ нескольких участников к одному концу требует согласования.

**Классический deadlock:** ребёнок отправляет большой результат и ждёт сброса буфера; родитель сначала ждёт join ребёнка и не читает канал. Канал заполнен, оба ждут. Родителю нужно получать результаты до окончательного ожидания завершения отправителя.

## 6. Shared memory и Manager — разные модели

| Механизм | Где данные | Что пересекает границу процессов |
|---|---|---|
| Queue/Pipe | У каждого своя восстановленная копия | Сериализованное сообщение |
| Value/Array/SharedMemory | Общий участок памяти | Доступ к согласованному представлению байтов |
| Manager proxy | Объект у отдельного сервера | Удалённый вызов и его ответ |

Общая память полезна для больших массивов: можно передать имя сегмента и форму вместо многократного копирования массива. Но нужно отдельно определить тип, размер, владение, синхронизацию и момент освобождения. Обычный адрес Python-объекта одного процесса не является переносимой ссылкой другого.

Value с автоматической блокировкой защищает отдельные обращения, но `value += 1` включает чтение и запись. Всю операцию защищают одним get_lock. Shared memory устраняет часть копий, но не гонки.

Manager хранит объект на сервере и выдаёт proxy. `proxy[key] += 1` выполняет несколько удалённых шагов и тоже может потерять обновление. Изменение обычного вложенного dict может остаться в локальной копии: нужен обратный set или вложенный proxy. Удобство Manager покупается задержками IPC.

## 7. Жизненный цикл и сбои

Созданный Process запускают один раз, ждут join и проверяют exitcode. Необработанное исключение не прилетает родителю через обычный join. Для понятного результата нужен собственный протокол или пул.

Корректная остановка: перестать выдавать новую работу → передать сигнал/сентинел → получить необходимые результаты → дождаться worker → закрыть каналы и освобождаемые ресурсы. У JoinableQueue завершение каждой работы отмечают task_done; её join ждёт работ, а не выхода процессов.

Terminate может оборвать процесс посреди записи в очередь или с захваченным Lock. Python finally при этом не гарантирован. Потомки также не обязательно завершатся автоматически. Принудительное завершение требует плана восстановления согласованности, а не только удаления PID.

Daemon-процесс multiprocessing ограничен в создании потомков и может быть оборван при выходе родителя. Это не замена надёжному системному сервису.

## 8. Почему ускорение ограничено

Для одной задачи полезно сравнить время вычисления с временем передачи туда/обратно. Глобально часть работы остаётся последовательной: подготовка, сбор результатов, запись в один ресурс. По закону Амдала даже бесконечное число worker не ускорит эту часть.

Если десять процессов считают быстро, но все последовательно пишут в один файл под Lock, узкое место переехало в запись. Если каждый получает гигабайт копируемых данных, узким местом может стать память/IPC. Измеряют весь путь, пиковую память и распределение длительностей, а не только тело функции.
